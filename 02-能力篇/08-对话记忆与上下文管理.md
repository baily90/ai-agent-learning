# 第8章：对话记忆与上下文管理 — 让 AI 记住你说过的话

## 引言

你有没有遇到过这种情况：和 AI 聊了半天，突然它来一句"抱歉，你能再说一下你的名字吗？"——你明明五分钟前刚说过。

或者更微妙的情况：你在第一轮对话里说"我喜欢简洁的代码风格"，到第五轮你让它写代码时，它又开始写一堆啰嗦的注释和冗长的变量名。

这不是 AI "不听话"，是它根本**没有记忆**。

对，你没看错。那个能和你流畅对话、好像"记得"之前说过什么的 AI——它其实什么都不记得。它之所以看起来有记忆，完全是因为**你把之前的对话历史又重新发了一遍**。

这就像打电话时每说一句都会自动挂断。你想继续对话，就得从头把前面说的全部重复一遍："你好，我叫小王，我之前说过我在北京，然后你建议我去故宫，然后我说太远了……好，现在我要问的是……"

荒谬吗？但这就是 LLM 的真实工作方式。这一章，我们来解决这个问题——让 AI 拥有**记忆**。

---

## 8.1 LLM 的"失忆"本质：每次调用都是一张白纸

**一句话直觉**：LLM 不是"忘记"了上一轮对话，它从来就没"记住"过。

### 无状态的真相

LLM 的 API 调用是**完全无状态的**。每次你发送一个请求，对模型来说都是它"人生中的第一次对话"。它不知道你是谁，不知道之前聊过什么，不知道这是第一轮还是第一百轮。

```typescript
import { deepseek } from '@ai-sdk/deepseek';

// 第一轮对话
const response1 = await generateText({
  model: deepseek('deepseek-chat'),
  prompt: '我叫小王，我在北京工作',
});
// AI: "你好小王！北京是个好地方..."

// 第二轮对话 — AI 完全不知道你是谁
const response2 = await generateText({
  model: deepseek('deepseek-chat'),
  prompt: '我叫什么名字？',
});
// AI: "抱歉，我不知道你的名字，你能告诉我吗？"
```

两次 `generateText` 调用之间**没有任何关联**。第二次调用时，模型的"大脑"是全新的、空白的。它不是"忘了"你叫小王——它从未在第二次调用中获得过这个信息。

### 前端类比：HTTP 的无状态性

这个概念，每个前端开发者都深刻理解过——**HTTP 协议是无状态的**。

```
HTTP 请求 1: GET /dashboard
→ 服务器: "你是谁？我不认识你。请登录。"

HTTP 请求 2: GET /dashboard
→ 服务器: "你是谁？我不认识你。请登录。"
（虽然 30 秒前你刚登录过）
```

HTTP 服务器不会"记住"你上一个请求是什么。每个请求都是独立的。那我们是怎么实现"登录状态"的？**Cookie + Session**。

```
HTTP 请求 + Cookie: GET /dashboard  Cookie: session_id=abc123
→ 服务器查 Session: "abc123 对应用户小王"
→ 服务器: "欢迎回来，小王！这是你的 Dashboard。"
```

LLM 的记忆问题和 HTTP 的无状态问题，**解决思路完全一样**：

| HTTP | LLM |
|------|-----|
| 每个请求是独立的 | 每次 API 调用是独立的 |
| Cookie 携带身份标识 | messages 数组携带对话历史 |
| Session 存储用户状态 | 数据库存储长期记忆 |
| 服务器重建用户上下文 | 模型基于 messages 重建对话上下文 |

理解了这个类比，你就理解了整个记忆体系的设计逻辑。

### 那对话怎么才能连起来？

答案很简单——**把历史消息塞回去**：

```typescript
import { deepseek } from '@ai-sdk/deepseek';

// 正确的多轮对话方式
const messages = [
  { role: 'user', content: '我叫小王，我在北京工作' },
  { role: 'assistant', content: '你好小王！北京是个好地方...' },
  { role: 'user', content: '我叫什么名字？' },  // 新消息
];

const response = await generateText({
  model: deepseek('deepseek-chat'),
  messages,  // 包含完整的对话历史
});
// AI: "你叫小王，你在北京工作。"
```

模型"看到"了完整的对话历史，所以它"知道"你叫小王。但这不是因为它"记得"——而是因为你**每次都把全部历史重新发了一遍**。

这引出了一个关键问题：上下文窗口是有限的，你不能无限地塞消息进去。

## 8.2 短期记忆：对话历史管理

**一句话直觉**：短期记忆就是 messages 数组——简单粗暴，但上下文窗口是硬性天花板。

### 最基础的记忆实现

```typescript
import { generateText, type ModelMessage } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';

// 用一个数组维护对话历史
const conversationHistory: ModelMessage[] = [];

async function chat(userMessage: string): Promise<string> {
  // 1. 把用户消息加入历史
  conversationHistory.push({
    role: 'user',
    content: userMessage,
  });

  // 2. 把完整历史发给模型
  const result = await generateText({
    model: deepseek('deepseek-chat'),
    instructions: '你是一个友好的助手。',
    messages: conversationHistory,
  });

  // 3. 把 AI 回复也加入历史
  conversationHistory.push({
    role: 'assistant',
    content: result.text,
  });

  return result.text;
}

// 使用
await chat('我叫小王');        // "你好小王！"
await chat('我在北京工作');     // "北京是个好城市！你从事什么工作？"
await chat('我叫什么？');       // "你叫小王，在北京工作。"
```

这就是最简单的"记忆"——一个数组。每次对话时，把完整数组发给模型。模型从数组中读取上下文，就好像它"记得"之前的对话。

### 使用 Vercel AI SDK 的 useChat（前端自动管理）

在前端使用 `useChat` 时，Vercel AI SDK 自动管理了消息历史：

```typescript
'use client';
import { useState, type FormEvent } from 'react';
import { useChat } from '@ai-sdk/react';
import { DefaultChatTransport, type UIMessage } from 'ai';

function messageText(message: UIMessage): string {
  return message.parts
    .map((part) => (part.type === 'text' ? part.text : ''))
    .join('');
}

export default function ChatPage() {
  const [input, setInput] = useState('');
  const { messages, sendMessage, status } = useChat({
    transport: new DefaultChatTransport({ api: '/api/chat' }),
  });
  const isLoading = status === 'submitted' || status === 'streaming';

  const handleSubmit = (event: FormEvent<HTMLFormElement>) => {
    event.preventDefault();
    const text = input.trim();
    if (!text || isLoading) return;
    sendMessage({ text });
    setInput('');

  // messages 自动包含完整的对话历史
  // 每次发送消息时，SDK 自动把 messages 发给后端
  
  return (
    <div>
      {messages.map(m => (
        <div key={m.id}>
          <strong>{m.role}:</strong> {messageText(m)}
        </div>
      ))}
      <form onSubmit={handleSubmit}>
        <input value={input} onChange={(e) => setInput(e.target.value)} />
        <button type="submit">发送</button>
      </form>
    </div>
  );
}
```

### 问题来了：上下文窗口的限制

一切看起来很美好，直到你的对话变得很长。

假设你和 AI 聊了 200 轮。每轮平均 200 token（用户消息 + AI 回复）。那么 messages 数组里就有大约 40,000 token。如果你用的模型上下文窗口是 128K，看起来还行。但：

1. **成本问题**：每次请求都发送 40K token，即使用户只是问一句"你好"。Token 是按量计费的！
2. **速度问题**：输入 token 越多，响应的首个 token 延迟（TTFT）越大
3. **注意力衰减**：模型对长上下文中间部分的关注度会下降（后面详讲）
4. **硬性上限**：再长的上下文窗口也有极限，总有塞满的一天

所以，我们需要**上下文管理策略**。

---

## 8.3 上下文窗口管理策略

**一句话直觉**：上下文窗口就像浏览器的内存——你需要策略来管理哪些数据留在内存中、哪些移到磁盘。

### 策略 1：滑动窗口 — 只保留最近 N 条消息

最简单直接的策略。就像日志轮转（logrotate）——只保留最近的内容，旧的自动丢弃。

```typescript
import { deepseek } from '@ai-sdk/deepseek';

function slidingWindowMessages(
  messages: ModelMessage[],
  maxMessages: number = 20
): ModelMessage[] {
  if (messages.length <= maxMessages) {
    return messages;
  }
  // 保留最近 N 条消息
  return messages.slice(-maxMessages);
}

// 使用
async function chat(userMessage: string) {
  conversationHistory.push({ role: 'user', content: userMessage });

  const result = await generateText({
    model: deepseek('deepseek-chat'),
    instructions: '你是一个友好的助手。',
    messages: slidingWindowMessages(conversationHistory, 20),  // 只传最近 20 条
  });

  conversationHistory.push({ role: 'assistant', content: result.text });
  return result.text;
}
```

**优点**：实现简单，能有效控制 token 使用。

**缺点**：丢掉了早期对话。如果用户在第 3 轮说了自己的名字，到第 25 轮时（假设窗口大小 20），这个信息就丢了。

**前端类比**：浏览器的 `localStorage` 容量限制。当存储空间不够时，最简单的策略就是 LRU（最近最少使用）——删除最旧的缓存。

### 策略 2：Token 计数截断

比消息计数更精确。因为不同消息的 token 长度差异很大——一条短消息可能只有 10 token，一段代码可能有 2000 token。

```typescript
import { encode } from 'gpt-tokenizer';  // 或使用 tiktoken

function truncateByTokens(
  messages: ModelMessage[],
  maxOutputTokens: number = 4000,
  reservedForResponse: number = 1000
): ModelMessage[] {
  const budget = maxOutputTokens - reservedForResponse;
  let totalTokens = 0;
  const result: ModelMessage[] = [];

  // 从最新消息开始往回数
  for (let i = messages.length - 1; i >= 0; i--) {
    const msgContent = typeof messages[i].content === 'string' 
      ? messages[i].content as string 
      : JSON.stringify(messages[i].content);
    const msgTokens = encode(msgContent).length;

    if (totalTokens + msgTokens > budget) {
      break;  // 超出预算，停止
    }

    totalTokens += msgTokens;
    result.unshift(messages[i]);
  }

  return result;
}
```

**优点**：更精确地控制 token 使用，避免一条长消息占掉大量预算。

**缺点**：需要额外的 token 计数库；仍然会丢失早期信息。

**注意**：`reservedForResponse` 很重要——你需要为模型的回复预留空间。如果把上下文窗口塞满了，模型就没有空间生成回复。

### 策略 3：摘要压缩 — AI 压缩 AI

这是最优雅也最强大的策略。当对话太长时，用 AI 把旧的对话压缩成一段摘要，然后用摘要替代原始对话。

```typescript
import { deepseek } from '@ai-sdk/deepseek';

async function compressHistory(
  messages: ModelMessage[],
  maxMessages: number = 20
): Promise<{ instructions: string; messages: ModelMessage[] }> {
  if (messages.length <= maxMessages) {
    return { instructions: '', messages };
  }

  // 把旧消息拿出来做摘要
  const oldMessages = messages.slice(0, messages.length - maxMessages);
  const recentMessages = messages.slice(-maxMessages);

  // 用 AI 压缩旧消息
  const summaryResult = await generateText({
    model: deepseek('deepseek-chat'),  // 用便宜模型做摘要
    instructions: `你是一个对话摘要助手。请将以下对话历史压缩为一段简洁的摘要，
保留所有重要信息，包括：
- 用户的身份信息（名字、位置、职业等）
- 用户表达的偏好和需求
- 做出的决定和达成的共识
- 关键的事实和数据
删除寒暄、重复和无关信息。用第三人称描述。`,
    prompt: oldMessages.map(m => `${m.role}: ${m.content}`).join('\n'),
  });

  // 把摘要拼进 instructions，而不是作为 system 消息放进 messages
  // 注：AI SDK 7 中 messages 里不允许 role: 'system'，system 内容必须走 instructions
  return {
    instructions: `[之前的对话摘要] ${summaryResult.text}`,
    messages: recentMessages,
  };
}
```

**前端类比**：这就是 Git 的 `squash` 操作。把 20 个小 commit 压缩成一个大 commit。信息不会完全丢失（摘要保留了关键内容），但细节被简化了。

```
Git squash:
  commit: "fix typo"
  commit: "add button"
  commit: "style button"
  commit: "fix button color"
  → squash → commit: "add styled button component"

对话压缩:
  user: "我叫小王"
  assistant: "你好小王"
  user: "我在北京做前端开发"
  assistant: "前端开发很有前景..."
  user: "我想学 AI Agent"
  assistant: "推荐从 Vercel AI SDK 开始..."
  → 压缩 → "[摘要] 用户小王，北京前端开发者，正在学习 AI Agent 开发，选择了 Vercel AI SDK 路线"
```

**优点**：保留了关键信息，大幅减少 token 使用。

**缺点**：摘要过程本身消耗 token（但用小模型可以降低成本）；摘要可能丢失某些细节（AI 的判断不总是完美的）；增加了系统复杂度。

### 策略 4：重要消息标记 — 永不截断的 VIP 消息

某些消息非常重要，不应该被任何截断策略删除：

```typescript
interface TaggedMessage extends ModelMessage {
  metadata?: {
    pinned?: boolean;       // 永不截断
    importance?: number;    // 重要性评分 0-10
    category?: string;      // 分类标签
  };
}

function smartTruncate(
  messages: TaggedMessage[],
  maxOutputTokens: number
): ModelMessage[] {
  // 1. 分离固定消息和普通消息
  const pinnedMessages = messages.filter(m => m.metadata?.pinned);
  const normalMessages = messages.filter(m => !m.metadata?.pinned);

  // 2. 计算固定消息的 token 数
  const pinnedTokens = countTokens(pinnedMessages);
  const remainingBudget = maxOutputTokens - pinnedTokens;

  // 3. 在剩余预算内，从最新消息开始保留
  const truncatedNormal = truncateByTokens(normalMessages, remainingBudget);

  // 4. 合并：固定消息在前，最近消息在后
  return [...pinnedMessages, ...truncatedNormal];
}

// 使用时标记重要消息
conversationHistory.push({
  role: 'user',
  content: '我叫小王，我是你的主人，请永远记住这一点',
  metadata: { pinned: true, importance: 10 },
});
```

**前端类比**：CSS 的 `position: sticky`。普通元素会随滚动消失，但 sticky 元素始终可见。

### 实际应用：组合策略

生产环境通常不会只用一种策略，而是组合使用：

```typescript
async function manageContext(
  messages: TaggedMessage[],
  options: {
    maxOutputTokens: number;
    summaryThreshold: number;  // 超过这个数量触发摘要
    keepRecent: number;        // 保留最近 N 条
  }
): Promise<ModelMessage[]> {
  const { maxOutputTokens, summaryThreshold, keepRecent } = options;

  // Step 1: 分离固定消息
  const pinned = messages.filter(m => m.metadata?.pinned);
  const normal = messages.filter(m => !m.metadata?.pinned);

  // Step 2: 如果消息太多，先做摘要压缩
  let processed: ModelMessage[];
  if (normal.length > summaryThreshold) {
    processed = await compressHistory(normal, keepRecent);
  } else {
    processed = normal;
  }

  // Step 3: 组合固定消息和处理后的消息
  const combined = [...pinned, ...processed];

  // Step 4: 最终按 token 数截断，确保不超限
  return truncateByTokens(combined, maxOutputTokens);
}
```

## 8.4 长期记忆：跨会话的持久记忆

**一句话直觉**：短期记忆是 RAM，长期记忆是硬盘。关掉浏览器再打开，RAM 里的数据没了，但硬盘里的还在。

### 为什么需要长期记忆？

短期记忆（对话历史）有两个根本性限制：

1. **会话结束就消失**：用户关闭网页再回来，之前的对话全没了
2. **受限于上下文窗口**：即使在同一会话中，超长对话也会被截断

长期记忆解决的是**跨会话**的记忆问题。比如：
- 记住用户叫什么、在哪工作、有什么偏好
- 记住之前讨论过的方案和决定
- 记住用户的历史查询和行为模式

### 长期记忆的三种存储方案

**方案 1：向量数据库 — 语义检索记忆**

把对话和信息转化为向量，存入向量数据库。需要回忆时，用语义相似度搜索最相关的记忆。

```typescript
import { embed, generateText } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';
import { openai } from '@ai-sdk/openai'; // 仅用于 Embedding：DeepSeek 没有 Embedding 模型

// 存储记忆
async function storeMemory(content: string, metadata: Record<string, any>) {
  // 1. 将文本转化为向量
  const { embedding } = await embed({
    model: openai.embedding('text-embedding-3-small'),
    value: content,
  });

  // 2. 存入向量数据库
  await vectorDb.insert({
    vector: embedding,
    metadata: {
      content,
      timestamp: new Date().toISOString(),
      ...metadata,
    },
  });
}

// 检索记忆
async function recallMemory(query: string, topK: number = 5) {
  const { embedding } = await embed({
    model: openai.embedding('text-embedding-3-small'),
    value: query,
  });

  const results = await vectorDb.search({
    vector: embedding,
    topK,
  });

  return results.map(r => r.metadata.content);
}

// 在对话中使用
async function chatWithMemory(userMessage: string) {
  // 1. 检索相关记忆
  const memories = await recallMemory(userMessage);

  // 2. 把记忆注入 system prompt
  const result = await generateText({
    model: deepseek('deepseek-chat'),
    instructions: `你是用户的私人助手。
    
以下是你对用户的了解（来自之前的交互）：
${memories.map(m => `- ${m}`).join('\n')}

请基于这些信息为用户提供个性化的帮助。`,
    messages: conversationHistory,
  });

  // 3. 从对话中提取新的记忆并存储
  await extractAndStoreMemories(userMessage, result.text);

  return result.text;
}
```

**前端类比**：这就像浏览器的全文搜索功能。你不需要记住某篇文章在哪一页，只要搜索关键词就能找到。向量数据库更进一步——它不是关键词匹配，而是语义匹配。搜"有没有带宠物的规定"也能匹配到"宠物入住政策"。

**方案 2：关系数据库 — 结构化记忆**

把记忆结构化存储在传统数据库中。适合用户画像、偏好设置这类结构化数据。

```typescript
}

// 在对话中使用
async function chatWithProfile(userId: string, userMessage: string) {
  const profile = await db.userProfiles.findUnique({ where: { userId } });
  
  const result = await generateText({
    model: deepseek('deepseek-chat'),

用户信息：
```

**方案 3：Key-Value 存储 — 快速访问记忆**

最简单的方案，适合存储少量高频访问的信息。

```typescript
// 使用 Redis 或简单的内存 Map
const memoryStore = new Map<string, string>();

// 存储
function remember(key: string, value: string) {
  memoryStore.set(key, value);
}

// 读取
function recall(key: string): string | undefined {
  return memoryStore.get(key);
}

// AI 通过工具来操作记忆
const rememberTool = tool({
  description: '将重要信息保存到长期记忆中。当用户告诉你需要记住的信息时使用。',
  inputSchema: z.object({
    key: z.string().describe('记忆的键名，如 "user_name", "favorite_color"'),
    value: z.string().describe('要记住的信息'),
  }),
  execute: async ({ key, value }) => {
    remember(key, value);
    return { success: true, message: `已记住: ${key} = ${value}` };
  },
});

const recallTool = tool({
  description: '从长期记忆中检索之前保存的信息。',
  inputSchema: z.object({
    key: z.string().describe('要检索的记忆键名'),
  }),
  execute: async ({ key }) => {
    const value = recall(key);
    return value
      ? { success: true, value }
      : { success: false, message: `没有找到关于 "${key}" 的记忆` };
  },
});
```

这种方案的优势在于：**AI 自己决定什么时候存、什么时候取**。通过 Tool Use（第 7 章学到的），AI 可以在对话中主动管理自己的记忆。

## 8.5 记忆的层级架构：像 CPU 缓存一样思考

**一句话直觉**：不同的记忆有不同的速度、容量和用途，就像 CPU 的 L1/L2/L3 缓存。

### 四级记忆层级

这是理解 AI 记忆系统最重要的心智模型：

```
┌────────────────────────────────────────────┐
│  L1: 当前对话上下文（Context Window）         │
│  ├── 速度: 最快（直接在 prompt 中）            │
│  ├── 容量: 最小（4K - 200K tokens）           │
│  ├── 持久性: 无（API 调用结束就消失）           │
│  └── 类比: CPU L1 Cache / React state        │
├────────────────────────────────────────────┤
│  L2: 会话摘要                                │
│  ├── 速度: 快（检索摘要，注入 prompt）          │
│  ├── 容量: 中等（压缩后的历史）                 │
│  ├── 持久性: 会话级（会话结束可能丢失）          │
│  └── 类比: CPU L2 Cache / sessionStorage     │
├────────────────────────────────────────────┤
│  L3: 向量数据库长期记忆                        │
│  ├── 速度: 较慢（需要 embedding + 搜索）        │
│  ├── 容量: 大（百万级文档）                     │
│  ├── 持久性: 永久                              │
│  └── 类比: CPU L3 Cache / localStorage        │
├────────────────────────────────────────────┤
│  L4: 关系数据库全量数据                        │
│  ├── 速度: 最慢（需要查询 + 处理）              │
│  ├── 容量: 无限                               │
│  ├── 持久性: 永久                              │
│  └── 类比: 主内存 + 磁盘 / 服务器数据库         │
└────────────────────────────────────────────┘
```

### 数据在层级间的流动

就像 CPU 缓存一样，数据在不同层级之间流动：

```typescript
import { deepseek } from '@ai-sdk/deepseek';

async function chatWithLayeredMemory(
  userId: string,
  userMessage: string,
  conversationHistory: ModelMessage[]
) {
  // L4 → L3: 应用启动时，从数据库加载用户数据到向量库
  // （通常是后台任务，不在对话流程中）

  // L3 → L1: 从向量库检索相关记忆，注入当前上下文
  const relevantMemories = await recallMemory(userMessage);

  // L2 → L1: 获取会话摘要
  const sessionSummary = await getSessionSummary(userId);

  // L4 → L1: 获取用户基本信息
  const userProfile = await getUserProfile(userId);

  // 组装完整的上下文（L1）
  const result = await generateText({
    model: deepseek('deepseek-chat'),
    instructions: `你是用户的私人助手。

[用户画像]
${JSON.stringify(userProfile)}

[之前的对话摘要]
${sessionSummary}

[相关记忆]
${relevantMemories.map(m => `- ${m}`).join('\n')}`,
    messages: conversationHistory,  // 当前对话的最近消息
  });

  // L1 → L3/L4: 从当前对话中提取有价值的信息，存储到长期记忆
  await extractAndStoreMemories(userMessage, result.text, userId);

  return result.text;
}
```

**前端类比**：这就像一个完善的缓存策略：

```
浏览器渲染页面需要数据:
1. 先看 React state (L1) — 最快，有就直接用
2. 没有？看 sessionStorage (L2) — 稍慢，但本次会话内有效
3. 还没有？看 localStorage (L3) — 稍慢，但持久化了
4. 都没有？请求服务器 (L4) — 最慢，但一定有
5. 拿到数据后，逐级缓存回去
```

AI 的记忆管理遵循完全相同的模式。这也意味着你需要考虑**缓存一致性问题**——如果用户在另一个会话中更新了偏好，当前会话的 L1 缓存怎么更新？我们在灵魂拷问中会讨论这个问题。

## 8.6 上下文窗口的"注意力衰减"问题

**一句话直觉**：模型对上下文开头和结尾的内容记得最清楚，中间的容易"看漏"。

### Lost in the Middle 现象

这是一个被研究论文证实的现象（"Lost in the Middle: How Language Models Use Long Contexts", 2023）。当上下文很长时，模型对不同位置信息的"注意力"分布不均：

```
注意力强度:
高 ████████                                      ████████
中   ██████                                    ██████
低     ████████████████████████████████████████
      ↑ 开头                中间                结尾 ↑
      (system prompt)   (中间的消息)        (最近的消息)
```

开头（通常是 system prompt）和结尾（最近的消息）被关注得最多，中间的消息容易被"忽略"。

### 这意味着什么？

1. **System prompt 放在开头是对的**——它会得到最高的注意力
2. **最新的对话内容也很重要**——模型对最近几轮的关注度很高
3. **中间的历史消息最容易被忽略**——如果重要信息在第 15 轮对话中提到，到了第 50 轮可能被"忘记"

### 应对策略

**策略 1：重要信息放在两端**

```typescript
function arrangeMessages(
  systemPrompt: string,
  memories: string[],
  conversationHistory: ModelMessage[]
): { instructions: string; messages: ModelMessage[] } {
  // 把重要的记忆信息放在 system prompt 中（开头）
  const enhancedSystem = `${systemPrompt}

[重要信息 — 请始终牢记]
${memories.join('\n')}`;

  // 最近的消息自然在末尾
  return {
    instructions: enhancedSystem,
    messages: conversationHistory,
  };
}
```

**策略 2：关键信息折叠进 system prompt**

在长对话中，把关键信息持续地放在 system prompt 里，让模型始终"记得"。注意：AI SDK 7 不允许在 messages 里插入 `role: 'system'` 消息，所以旧版本"周期性地在对话中插入 system 提醒"的写法已经失效，只能把提醒内容合并进 instructions：

```typescript
function buildSystemWithReminders(
  systemPrompt: string,
  keyFacts: string[],
): string {
  if (keyFacts.length === 0) return systemPrompt;

  // 把关键信息追加到 system prompt 末尾
  // 注：AI SDK 7 中 messages 里不允许 role: 'system'，system 内容只能走 instructions
  return `${systemPrompt}

[请始终牢记的关键信息]
${keyFacts.map(f => `- ${f}`).join('\n')}`;
}
```

**策略 3：摘要 + 最近消息**

最实用的策略——保留完整的最近消息（注意力高的区域），把早期消息压缩为摘要（放在注意力高的开头位置）：

```
[system prompt + 历史摘要]  ← 注意力高的开头
[最近 10-20 条完整消息]      ← 注意力高的结尾
```

这样，早期的关键信息通过摘要被保留在注意力高的区域，最近的上下文保持完整。

## 8.7 Token 计算实战

**一句话直觉**：在发送消息前，你需要知道会消耗多少 token，就像前端要计算请求的 payload 大小。

### 为什么需要在发送前估算 token 数？

1. **避免超出限制**：超出上下文窗口会导致 API 报错
2. **成本预估**：提前知道这次请求会花多少钱
3. **策略触发**：当 token 快满时，自动触发压缩或截断

### 实际的 token 计算

```typescript
// 方案 1：使用 tiktoken（OpenAI 官方分词器；DeepSeek 未公开分词器，这里只能做近似估算）
import { encoding_for_model } from 'tiktoken';

function countTokensExact(text: string, model: string = 'gpt-4o'): number {
  const enc = encoding_for_model(model as any);
  const tokens = enc.encode(text);
  enc.free();  // 释放 WASM 内存
  return tokens.length;
}

// 方案 2：简单估算（不需要额外依赖）
function countTokensEstimate(text: string): number {
  // 经验规则：
  // 英文约 1 token ≈ 4 个字符 或 0.75 个单词
  // 中文约 1 个汉字 ≈ 1-2 个 token
  const chineseChars = (text.match(/[一-鿿]/g) || []).length;
  const otherChars = text.length - chineseChars;
  return Math.ceil(chineseChars * 1.5 + otherChars / 4);
}

// 计算 messages 数组的总 token 数
function countMessagesTokens(messages: ModelMessage[]): number {
  let total = 0;
  for (const msg of messages) {
    const content = typeof msg.content === 'string' 
      ? msg.content 
      : JSON.stringify(msg.content);
    total += countTokensEstimate(content);
    total += 4;  // 每条消息有格式开销（role 标记等）
  }
  total += 2;  // 对话整体的格式开销
  return total;
}
```

### 集成到上下文管理中

```typescript
import { deepseek } from '@ai-sdk/deepseek';

class ContextManager {
  private maxContextTokens: number;
  private reserveForResponse: number;
  private summaryThreshold: number;

  constructor(options: {
    maxContextTokens?: number;
    reserveForResponse?: number;
    summaryThreshold?: number;
  } = {}) {
    this.maxContextTokens = options.maxContextTokens ?? 8000;
    this.reserveForResponse = options.reserveForResponse ?? 2000;
    this.summaryThreshold = options.summaryThreshold ?? 30;
  }

  async prepareMessages(
    systemPrompt: string,
    messages: ModelMessage[],
    additionalContext?: string
  ): Promise<{ instructions: string; messages: ModelMessage[] }> {
    const systemTokens = countTokensEstimate(systemPrompt);
    const contextTokens = additionalContext
      ? countTokensEstimate(additionalContext)
      : 0;
    const budget = this.maxContextTokens - this.reserveForResponse 
                   - systemTokens - contextTokens;

    // 如果消息太多，先压缩
    let processedMessages = messages;
    if (messages.length > this.summaryThreshold) {
      processedMessages = await compressHistory(messages, 20);
    }

    // 按 token 预算截断
    const finalMessages = truncateByTokens(processedMessages, budget);

    // 组装 system prompt
    const fullSystem = additionalContext
      ? `${systemPrompt}\n\n[额外上下文]\n${additionalContext}`
      : systemPrompt;

    return { instructions: fullSystem, messages: finalMessages };
  }
}

// 使用
const contextManager = new ContextManager({
  maxContextTokens: 8000,   // 控制成本，只用 8K
  reserveForResponse: 2000, // 预留 2K 给模型回复
  summaryThreshold: 30,     // 超过 30 条消息触发压缩
});

async function chat(userMessage: string) {
  conversationHistory.push({ role: 'user', content: userMessage });

  const { instructions, messages } = await contextManager.prepareMessages(
    '你是一个友好的助手。',
    conversationHistory,
  );

  const result = await generateText({
    model: deepseek('deepseek-chat'),
    instructions,
    messages,
  });

  conversationHistory.push({ role: 'assistant', content: result.text });
  return result.text;
}
```

## 概念辨析

### 上下文窗口 vs 记忆

| 维度 | 上下文窗口 | 记忆 |
|------|-----------|------|
| 本质 | 模型一次能处理的 token 上限 | 应用层的持久化存储 |
| 管理者 | 模型架构决定（不可更改） | 开发者设计和管理 |
| 生命周期 | 单次 API 调用 | 可跨会话、跨应用 |
| 类比 | 工作台大小（固定的） | 书柜和仓库（可扩展的） |

上下文窗口是**硬件限制**，记忆是**软件方案**。记忆系统的目标就是：在有限的上下文窗口内，放入最有价值的信息。

### 短期记忆 vs 长期记忆

| 维度 | 短期记忆 | 长期记忆 |
|------|---------|---------|
| 存储位置 | messages 数组（内存） | 数据库 |
| 生命周期 | 当前会话 | 跨会话持久化 |
| 访问速度 | 即时（直接在 prompt 中） | 需要检索 |
| 容量 | 受限于上下文窗口 | 理论上无限 |
| 信息粒度 | 原始对话（完整） | 经过提炼的信息 |
| 前端类比 | React state / useState | 数据库 / localStorage |

### 摘要 vs RAG

| 维度 | 摘要压缩 | RAG（第 9 章详讲） |
|------|---------|-------------------|
| 目的 | 压缩对话历史 | 检索外部知识 |
| 数据来源 | 当前对话 | 外部文档库 |
| 触发时机 | 对话过长时自动触发 | 每次查询时主动检索 |
| 信息方向 | 内部 → 压缩 → 内部 | 外部 → 检索 → 内部 |

## 灵魂拷问

> **Q1: 为什么 LLM 没有原生记忆？这是设计缺陷还是架构特性？**

> A: 这是**架构特性**，不是缺陷。LLM（Transformer 架构）本质上是一个函数：输入一串 token，输出下一个 token 的概率分布。这个函数是**纯函数**——相同的输入永远产生相同的输出（忽略采样随机性），没有副作用，也没有内部状态。
>
> 这和 React 的纯组件理念一致：`UI = f(state)`。组件本身不持有状态，状态由外部管理。LLM 也是如此：`output = f(input_tokens)`。
>
> 为什么这样设计？几个原因：
> 1. **可扩展性**：无状态意味着可以轻松分布式部署，任何服务器都能处理任何请求
> 2. **可预测性**：没有隐藏状态，调试和测试更简单
> 3. **安全性**：用户 A 的信息不会意外泄露给用户 B（因为没有共享状态）
>
> 代价是需要应用层实现记忆——但这也带来了灵活性，你可以根据业务需求设计最适合的记忆策略。

> **Q2: 滑动窗口丢弃了早期消息，如果用户突然问"我们最开始聊了什么"怎么办？**

> A: 这是滑动窗口策略的致命弱点。早期消息被丢弃后，AI 确实无法回答这个问题。
>
> 解决方案：
> 1. **摘要 + 滑动窗口**：丢弃原始消息前，先压缩为摘要保留。用户问"最开始聊了什么"时，AI 可以基于摘要大致回答
> 2. **全量存储 + 按需检索**：所有消息都存入数据库，正常对话用滑动窗口。当用户明确问到早期对话时，通过工具从数据库检索
> 3. **用户提示**：在 UI 上展示完整的对话历史，用户可以翻看。AI 负责最近的上下文，UI 负责完整的历史展示
>
> 最佳实践是方案 1 和方案 2 的组合——摘要保证了基本的连续性，数据库保证了完整性。

> **Q3: 摘要压缩会丢失信息，怎么决定哪些信息可以丢？AI 做摘要可靠吗？**

> A: 这确实是摘要策略的核心挑战。
>
> **什么信息应该保留**：
> - 用户的身份信息（名字、角色、偏好）
> - 做出的决定和达成的共识
> - 关键的业务数据和数字
> - 未完成的任务和后续计划
>
> **什么信息可以丢弃**：
> - 寒暄和社交性对话
> - 已解决的问题的详细讨论过程
> - 重复的信息
> - 探索性的讨论（最终没有采纳的方案）
>
> **AI 做摘要可靠吗？** 大部分情况下是可靠的，但不是 100%。AI 可能：
> - 遗漏你认为重要但看起来"不起眼"的细节
> - 错误地理解某些信息的重要性
> - 在摘要中引入轻微的偏差
>
> 缓解策略：在摘要的 prompt 中明确指定保留的信息类别；对摘要质量做定期评估；关键信息用"固定消息"策略单独保存，不依赖摘要。

> **Q4: 128K 上下文是不是意味着不用管记忆问题了？为什么不是？**

> A: 绝对不是，这是一个常见的误解。128K token 大约是一本 200 页的书，看起来很多。但有几个关键问题：
>
> 1. **成本**：即使模型支持 128K，每次请求发送 128K 输入 token 的费用是巨大的。如果用户只是问一句"你好"，你也要为这 128K 买单
> 2. **速度**：输入 token 越长，首 token 延迟（TTFT）越大。128K 输入可能需要等几秒才能开始回复
> 3. **Lost in the Middle**：128K 上下文中间的信息被忽略的概率更高
> 4. **不等于无限**：一个活跃用户一天可能产生数十万 token 的对话。128K 也只能撑一天
>
> 大上下文窗口应该被看作**给更好的记忆策略留出空间**，而不是**取代记忆策略**。你应该用 128K 来装更丰富的上下文（system prompt + 记忆 + 完整的最近对话 + 检索到的知识），而不是粗暴地塞入所有原始对话。

> **Q5: "Lost in the Middle" 现象的本质原因是什么？怎么缓解？**

> A: 本质原因在于 Transformer 架构的**注意力机制（Attention）**。
>
> 理论上，Self-Attention 可以关注输入中的任意位置。但在实际训练后，模型形成了一种"偏好"：对开头和结尾的 token 赋予更高的注意力权重。这可能和训练数据的分布有关——重要信息通常出现在文档的开头（标题、摘要）和用户最新的消息中。
>
> 缓解方法：
> 1. **重要信息放两端**：system prompt（开头）和最新消息（结尾）
> 2. **信息冗余**：关键信息在多个位置重复出现
> 3. **主动提取**：不要指望模型从长上下文中"找到"信息，而是用工具主动检索，将最相关的信息放在显眼位置
> 4. **缩短上下文**：与其塞满 128K，不如精心管理，只放 10-20K 高质量内容

> **Q6: 如何在不同记忆层级之间做数据同步？（类比缓存一致性问题）**

> A: 这是一个经典的分布式系统问题，和前端的缓存一致性完全同构。
>
> **问题场景**：用户在会话 A 中说"我搬到上海了"，这个信息更新了 L3（向量数据库）和 L4（关系数据库）。但如果用户同时开着会话 B，B 的 L1（当前上下文）还是旧的"北京"。
>
> **解决方案**：
>
> 1. **Write-Through**（同步写穿）：每次更新都同时写入所有层级。最一致，但最慢。
>
> 2. **Write-Back + TTL**（延迟写回 + 过期时间）：先更新 L1 和 L2，异步更新 L3 和 L4。设置 TTL（过期时间），定期从 L4 重新加载。类比：React Query 的 staleTime 和 refetchInterval。
>
> 3. **Event-Driven**（事件驱动）：用户画像更新时发出事件，所有活跃会话监听事件并刷新 L1 缓存。类比：WebSocket 推送 + React 的 useSyncExternalStore。
>
> 实际项目中，大多数场景用方案 2 就够了——用户偏好更新不是高频操作，几分钟的延迟是可接受的。

## 最佳实践

### DO

- **DO** 从第一天就设计记忆策略，不要等对话变长了才补——这就像不要等数据库满了才想分库分表
- **DO** 对 system prompt 和关键上下文信息使用"固定"策略，确保它们不会被截断
- **DO** 在发送请求前估算 token 数，留出回复空间（至少预留 1000-2000 token）
- **DO** 组合使用多种策略（摘要 + 滑动窗口 + 固定消息），而不是只用一种
- **DO** 用小模型（如 gpt-5-mini）做摘要压缩，降低成本
- **DO** 将用户的关键信息（身份、偏好）结构化存储，而不是只依赖对话历史
- **DO** 在 UI 上展示完整对话历史，即使 AI 只"记得"最近的部分
- **DO** 测试长对话场景（50+ 轮），验证记忆策略的效果

### DON'T

- **DON'T** 把所有历史消息无脑塞进 messages 数组——迟早会超出上下文限制，而且浪费钱
- **DON'T** 完全依赖大上下文窗口（128K）来替代记忆管理——成本和延迟都不允许
- **DON'T** 在每次请求中都做摘要压缩——应该设定阈值，只在消息数量或 token 超过阈值时触发
- **DON'T** 忽视 "Lost in the Middle" 问题——不要假设模型能平等关注上下文中的所有内容
- **DON'T** 把敏感信息存入长期记忆时不做脱敏处理——密码、token、身份证号等不应直接存储
- **DON'T** 在摘要中包含"用户说了什么"的逐字引用——摘要应该是提炼的信息，不是缩写的对话
- **DON'T** 假设所有模型的 tokenizer 都一样——不同模型的分词方式不同，token 计数会有差异

```typescript
// memory-system.ts — 分层记忆管理
import 'dotenv/config';
import { generateText, type ModelMessage } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';

// ===== Token 估算 =====
function estimateTokens(text: string): number {
  const chineseChars = (text.match(/[一-鿿]/g) || []).length;
  const otherChars = text.length - chineseChars;
  return Math.ceil(chineseChars * 1.5 + otherChars / 4);
}

function estimateMessagesTokens(messages: ModelMessage[]): number {
  return messages.reduce((total, msg) => {
    const content = typeof msg.content === 'string'
      ? msg.content
      : JSON.stringify(msg.content);
    return total + estimateTokens(content) + 4;  // 4 tokens for message format
  }, 2);  // 2 tokens for conversation overhead
}

// ===== 摘要压缩 =====
async function summarizeMessages(messages: ModelMessage[]): Promise<string> {
  const conversation = messages
    .map(m => `${m.role}: ${typeof m.content === 'string' ? m.content : JSON.stringify(m.content)}`)
    .join('\n');

  const result = await generateText({
    model: deepseek('deepseek-chat'),
    instructions: `你是一个对话摘要助手。将以下对话压缩为简洁的摘要。
要求：
1. 保留用户的身份信息、偏好、关键需求
2. 保留做出的决定和达成的共识
3. 保留未完成的任务
4. 删除寒暄、重复和不重要的内容
5. 用第三人称，200字以内`,
    prompt: conversation,
  });

  return result.text;
}

// ===== 上下文管理器 =====
class ConversationMemory {
  private fullHistory: ModelMessage[] = [];  // 完整历史（永久保存）
  private summary: string = '';              // 压缩摘要
  private pinnedFacts: string[] = [];        // 固定不丢弃的事实

  private config = {
    maxContextTokens: 6000,     // 最大上下文 token 数
    reserveForResponse: 1500,   // 为回复预留的 token
    recentMessageCount: 15,     // 保留最近 N 条完整消息
    summaryTrigger: 25,         // 超过这个数触发摘要
  };

  constructor(config?: Partial<typeof ConversationMemory.prototype.config>) {
    if (config) Object.assign(this.config, config);
  }

  // 添加一条消息
  addMessage(message: ModelMessage) {
    this.fullHistory.push(message);
  }

  // 添加固定事实（不会被压缩丢弃）
  addPinnedFact(fact: string) {
    if (!this.pinnedFacts.includes(fact)) {
      this.pinnedFacts.push(fact);
    }
  }

  // 获取准备好的上下文
  async getContext(systemPrompt: string): Promise<{
    instructions: string;
    messages: ModelMessage[];
    stats: { totalMessages: number; sentMessages: number; estimatedTokens: number };
  }> {
    const totalMessages = this.fullHistory.length;

    // Step 1: 判断是否需要摘要压缩
    if (this.fullHistory.length > this.config.summaryTrigger) {
      const oldMessages = this.fullHistory.slice(
        0, 
        this.fullHistory.length - this.config.recentMessageCount
      );
      this.summary = await summarizeMessages(oldMessages);
    }

    // Step 2: 获取最近的消息
    const recentMessages = this.fullHistory.slice(-this.config.recentMessageCount);

    // Step 3: 构建 system prompt
    const parts = [systemPrompt];

    if (this.pinnedFacts.length > 0) {
      parts.push(`\n[用户关键信息 — 请始终牢记]\n${this.pinnedFacts.map(f => `- ${f}`).join('\n')}`);
    }

    if (this.summary) {
      parts.push(`\n[之前的对话摘要]\n${this.summary}`);
    }

    const fullSystem = parts.join('\n');

    // Step 4: Token 检查和最终截断
    const systemTokens = estimateTokens(fullSystem);
    const budget = this.config.maxContextTokens - this.config.reserveForResponse - systemTokens;

    let finalMessages = recentMessages;
    let currentTokens = estimateMessagesTokens(finalMessages);

    // 如果还超预算，从最旧的消息开始删除
    while (currentTokens > budget && finalMessages.length > 2) {
      finalMessages = finalMessages.slice(1);
      currentTokens = estimateMessagesTokens(finalMessages);
    }

    const estimatedTokens = systemTokens + currentTokens;

    return {
      instructions: fullSystem,
      messages: finalMessages,
      stats: {
        totalMessages,
        sentMessages: finalMessages.length,
        estimatedTokens,
      },
    };
  }

  // 从对话中自动提取关键信息
  async extractKeyFacts(userMessage: string, assistantResponse: string) {
    const result = await generateText({
      model: deepseek('deepseek-chat'),
      instructions: `分析以下对话片段，提取用户的关键个人信息。
只提取明确说出的信息，不要猜测。
每条信息一行，用简洁的"标签: 内容"格式。
如果没有关键信息，返回"无"。
示例：
姓名: 小王
位置: 北京
职业: 前端开发`,
      prompt: `用户: ${userMessage}\n助手: ${assistantResponse}`,
    });

    if (result.text !== '无') {
      const facts = result.text.split('\n').filter(Boolean);
      facts.forEach(fact => this.addPinnedFact(fact));
    }
  }

  // 获取完整历史（用于 UI 展示或持久化存储）
  getFullHistory(): ModelMessage[] {
    return [...this.fullHistory];
  }

  // 获取统计信息
  getStats() {
    return {
      totalMessages: this.fullHistory.length,
      summaryLength: this.summary.length,
      pinnedFacts: this.pinnedFacts.length,
      estimatedTotalTokens: estimateMessagesTokens(this.fullHistory),
    };
  }
}

// ===== 带记忆的 Agent =====
async function createMemoryAgent() {
  const memory = new ConversationMemory({
    maxContextTokens: 6000,
    recentMessageCount: 15,
    summaryTrigger: 25,
  });

  const systemPrompt = `你是用户的私人智能助手。
你有记忆能力，能记住用户之前告诉你的信息。
请基于已知的用户信息提供个性化的回答。
如果不确定某个信息，可以直接问用户。`;

  async function chat(userMessage: string): Promise<string> {
    // 1. 添加用户消息
    memory.addMessage({ role: 'user', content: userMessage });

    // 2. 获取优化后的上下文
    const { instructions, messages, stats } = await memory.getContext(systemPrompt);
    console.log(`[记忆] 总消息: ${stats.totalMessages}, 发送: ${stats.sentMessages}, Token 估算: ${stats.estimatedTokens}`);

    // 3. 生成回复
    const result = await generateText({
      model: deepseek('deepseek-chat'),
      instructions,
      messages,
    });

    // 4. 保存回复
    memory.addMessage({ role: 'assistant', content: result.text });

    // 5. 提取关键信息（异步，不阻塞回复）
    memory.extractKeyFacts(userMessage, result.text).catch(console.error);

    return result.text;
  }

  return { chat, memory };
}

// ===== 测试 =====
async function main() {
  const { chat, memory } = await createMemoryAgent();

  // 模拟多轮对话
  await chat('你好，我叫小王');
  await chat('我在北京做前端开发，用 React');
  await chat('我想学 AI Agent 开发');
  await chat('我比较喜欢简洁的代码风格');

  // 验证记忆
  const response = await chat('你还记得我的信息吗？');
  console.log('\n助手:', response);

  // 查看记忆统计
  console.log('\n记忆状态:', memory.getStats());
}

main();
```

```typescript
  messages: ModelMessage[];

  pinnedFacts: string[];

// 简单实现：用文件存储（生产环境换成数据库）
import fs from 'fs/promises';
import path from 'path';

const STORE_DIR = path.join(process.cwd(), '.chat-sessions');

export async function saveSession(session: ChatSession): Promise<void> {
  await fs.mkdir(STORE_DIR, { recursive: true });
  await fs.writeFile(
    path.join(STORE_DIR, `${session.id}.json`),
    JSON.stringify(session, null, 2)
  );
}

export async function loadSession(sessionId: string): Promise<ChatSession | null> {
  try {
    const data = await fs.readFile(
      path.join(STORE_DIR, `${sessionId}.json`),
      'utf-8'
    );
    return JSON.parse(data);
  } catch {
    return null;
  }
}

export async function listSessions(): Promise<string[]> {
  try {
    const files = await fs.readdir(STORE_DIR);
    return files
      .filter(f => f.endsWith('.json'))
      .map(f => f.replace('.json', ''));
  } catch {
    return [];
  }
}
```

```typescript
  // 加载会话的持久化信息

  const pinnedFacts = session?.pinnedFacts ?? [];

    systemParts.push(`\n[之前对话摘要]\n${session.summary}`);
  }

  const modelMessages = await convertToModelMessages(messages);

  const result = streamText({
    model: deepseek('deepseek-chat'),
    instructions: systemParts.join('\n'),
    messages: modelMessages,
    // 流式结束后异步保存会话（不阻塞响应）
    onFinish({ text }) {
      saveSession({
        id: sessionId,
        messages: [
          ...modelMessages,
          { role: 'assistant', content: text },
        ],
        summary: session?.summary ?? '',
        pinnedFacts,
        createdAt: session?.createdAt ?? new Date().toISOString(),
        updatedAt: new Date().toISOString(),
      }).catch(console.error);
    },
  });

  return createUIMessageStreamResponse({
    stream: toUIMessageStream({ stream: result.stream }),
  });
}
```

## 实操练习

### 目标

为你的 AI 工作助手添加完整的对话记忆能力，支持长对话不丢失上下文，并实现跨会话的持久化记忆。

### 步骤

1. **实现基础对话历史管理**
   - 用 messages 数组维护对话历史
   - 实现滑动窗口截断（保留最近 20 条）
   - 添加 token 估算函数

2. **实现摘要压缩**
   - 当消息数超过阈值时，自动用 AI 压缩旧消息
   - 摘要作为 system prompt 的一部分
   - 测试压缩前后的 token 使用量变化

3. **实现 "固定事实" 机制**
   - 从对话中自动提取用户关键信息
   - 将关键信息作为 "pinned facts" 固定在 system prompt 中
   - 验证：即使对话很长，AI 仍然记得用户的名字和偏好

4. **实现会话持久化**
   - 将对话历史保存到文件（或数据库）
   - 支持关闭后重新打开，继续之前的对话
   - 支持多个会话（每个会话独立的历史）

5. **长对话压力测试**
   - 模拟 50 轮对话，验证记忆策略是否正常工作
   - 检查 token 使用量是否被有效控制
   - 验证关键信息在长对话中是否保持可用

### 验收标准

- 对话历史能正确管理，不会超出上下文窗口
- 摘要压缩能保留关键信息，丢弃不重要的内容
- 用户的关键信息（名字、偏好）在长对话中持续可用
- 关闭应用后重新打开，能继续之前的对话
- 能清楚解释 token 估算和各种截断策略的原理

### 挑战加分项

1. 实现基于向量数据库的语义记忆检索（使用 Chroma 或 Pinecone）
2. 实现记忆的"遗忘曲线"——越久不被提及的记忆，检索优先级越低
3. 让 AI 通过 Tool Use（第 7 章）主动管理自己的记忆——提供 `remember` 和 `recall` 工具
4. 实现 "Lost in the Middle" 的可视化——标记出当前上下文中各位置信息的理论注意力分布

## 本章小结

这一章，我们系统地解决了 LLM 的"失忆症"问题。回顾关键要点：

1. **LLM 天生无记忆**：每次 API 调用都是全新的，完全无状态。这和 HTTP 的无状态性是同一个问题，解决思路也一样——把"状态"从外部注入。

2. **短期记忆就是 messages 数组**：把历史消息塞回去，模型就能"记住"之前的对话。但上下文窗口有限，不能无限塞。

3. **四种上下文管理策略**：
   - 滑动窗口：简单粗暴，丢掉旧消息
   - Token 计数截断：更精确地控制上下文大小
   - 摘要压缩：用 AI 压缩历史，保留关键信息
   - 重要消息标记：VIP 消息永不截断

4. **记忆的层级架构**：L1（当前上下文）→ L2（会话摘要）→ L3（向量数据库）→ L4（关系数据库）。就像 CPU 缓存层级，越远越慢但容量越大。

5. **Lost in the Middle**：长上下文中间的信息容易被忽略。重要信息放两端（system prompt 和最新消息），或者主动检索而非被动期待模型发现。

6. **Token 管理是成本控制的关键**：在发送前估算 token，设置合理的预算，为回复预留空间。

下一章，我们将学习另一种"给 AI 装眼睛"的技术——**RAG（检索增强生成）**。如果说记忆让 AI 记住了"我们聊过什么"，那 RAG 让 AI 能查阅"你的知识库里有什么"。两者结合，AI Agent 就真正拥有了感知世界的能力。
