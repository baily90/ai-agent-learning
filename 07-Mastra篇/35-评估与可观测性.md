# 第35章：评估与可观测性 — 给 agent 装上质量仪表盘

## 引言

第 21 章你手写过评测脚本（准备测试集、逐条跑、打分、算通过率），第 22、29 章你又接 Langfuse 做追踪。那段经历让你明白：**AI 应用没有「跑通了」这回事，只有「能持续观测和度量」才算靠谱**。

Mastra 把评测（Evals）和可观测（Observability）都做成了内置能力。这一章我们看看，你之前手动搭的那套「质量护栏」在 Mastra 里是什么体验。

---

## 35.1 心智转变：从「事后测试」到「持续打分」

### 一句话直觉

传统测试是「通过/失败」二选一；AI 的输出是**不确定的**，同一条输入每次可能不一样。所以 Mastra 用 **Scorer（打分器）** 来量化质量——返回 0~1 的分数，而不是布尔值。

### 前端类比

- 单元测试（断言通过/失败）≈ 传统软件测试
- Mastra Scorer ≈ **代码覆盖率 / Lighthouse 评分**——不是「过没过」，而是「质量打几分」

你第 21 章手写的评测脚本，本质就是在做 Scorer 的活；Mastra 把它抽象成了标准组件。

## 35.2 评估：Scorer

### 装包

```bash
npm install @mastra/evals
```

### 给 agent 挂内置打分器

```typescript
import { Agent } from '@mastra/core/agent';
import { createAnswerRelevancyScorer, createToxicityScorer } from '@mastra/evals/scorers/prebuilt';

const supportAgent = new Agent({
  name: 'support',
  model: 'deepseek/deepseek-chat',
  instructions: '你是客服。',
  scorers: {
    relevancy: {
      scorer: createAnswerRelevancyScorer({ model: 'deepseek/deepseek-chat' }),  // 答案相关性
      sampling: { type: 'ratio', rate: 0.5 },   // 抽样 50% 打分
    },
    safety: {
      scorer: createToxicityScorer({ model: 'deepseek/deepseek-chat' }),        // 毒性检测
      sampling: { type: 'ratio', rate: 1 },     // 全量打分
    },
  },
});
```

关键点：

- **scorer 用模型打分**（model-graded），所以也要配 model
- **sampling 抽样**：不是每条都打分（省钱），可以按比例抽样

### Scorer 的类型（呼应第 21 章）

| 类型 | 测什么 | 你的旧对应 |
|---|---|---|
| 文本质量（relevancy/toxicity） | 答案相关性、安全性 | 手写的「答案是否切题」脚本 |
| 分类准确率 | 分类对不对 | 手写的分类测试集 |
| 提示词效果 | 不同 prompt 的优劣 | 手动 A/B 对比 |

### 给 workflow 的单个 step 打分

```typescript
const contentStep = createStep({
  id: 'content-step',
  inputSchema: z.object({ topic: z.string() }),
  outputSchema: z.object({ content: z.string() }),
  scorers: {
    quality: {
      scorer: createAnswerRelevancyScorer({ model: 'deepseek/deepseek-chat' }),
      sampling: { type: 'ratio', rate: 1 },
    },
  },
  execute: async ({ inputData }) => {
    return { content: '...' };
  },
});
```

这样你能定位到「是哪个 step 出了问题」，而不是只看最终答案——**这就是第 21 章「逐环节评测」的成品版**。

### Datasets + Experiments：正式评测循环

单个 scorer 只能测一条输出。要系统改进 agent，需要三件套：

- **Dataset**：版本化的测试用例集
- **Experiment**：拿 agent/workflow 跑一遍 dataset，逐条打分，保留结果
- **对比**：改完 prompt/参数后重跑，看分数涨没涨

这就是一个完整的 **eval loop**（评测循环）——改 → 测 → 对比 → 再改。和你在第 21 章手写的那套流程一模一样，只是标准化了。

## 35.3 可观测性：Tracing

### 心智转变

第 22 章你接 Langfuse 做追踪，要自己埋点、自己传 span。Mastra 的 tracing 是**自动的**——每个 agent 调用、工具调用、workflow step、模型调用，都自动变成 span，聚合成 trace。

### 一个 trace 长什么样

```
请求进来
└── trace
    ├── span: agent 调用
    │   ├── span: 模型调用（token 用量、耗时）
    │   └── span: 工具调用 getOrder
    ├── span: workflow step: extract-intent
    └── span: workflow step: refund-approval（status: suspended）
```

每个 span 记录：

- **outcome**：执行结果（`success` / `error` / `suspend` / `interrupted` 等）
- **stopReason**：为什么停（正常结束 / 超长 / 要调工具）
- **耗时、token 用量**（成本核算靠它）

### 在哪看

```bash
npx mastra dev
```

Studio 里点开一次运行，就能看到完整 trace——**不需要你额外埋点，也不需要接 Langfuse**（第 29 章 Langfuse 那套可以省了，或作为外部导出可选）。

### 导出到第三方

如果你公司已有 Langfuse 等体系，Mastra 支持把 trace 导出去对接，不用重造。

## 概念辨析：Evals vs Observability vs 传统测试

| 维度 | 传统测试 | Mastra Evals | Mastra Observability |
|---|---|---|---|
| 回答的问题 | 「对不对」 | 「质量打几分」 | 「运行时发生了什么」 |
| 输出 | 通过/失败 | 0~1 分数 | trace（spans） |
| 时机 | 开发期 | 开发期 + 运行时（live） | 运行时（自动） |
| 对应旧知识 | 单元测试 | 第 21 章评测脚本 | 第 22/29 章 Langfuse |

一句话：**Evals 是「测质量」，Observability 是「看过程」**，两者合起来才是完整的质量体系。

## 灵魂拷问

**Q1：为什么 AI 的评测不能用「通过/失败」，而要用 0~1 的分数？**

因为 AI 输出是概率性的、非确定的——同一个 prompt，两次回答可能都不错，只是措辞不同。布尔值会把这些「都算对」的情况粗暴二值化。分数能表达「这次 0.9 分、那次 0.7 分」的**质量梯度**，让你能追踪「改了什么之后质量是升了还是降了」。

**Q2：sampling（抽样打分）为什么要存在？直接全量打分不行吗？**

因为 scorer 本身也要调模型，**打分是有成本的**（额外的 token 和延迟）。全量打分 = 每个输出都额外跑一次模型。抽样是「用 50% 的成本覆盖 95% 的质量信号」的工程权衡——这和第 23 章「成本控制」是同一个思路。

**Q3：Mastra 内置 tracing 了，我第 29 章学的 Langfuse 是不是白学了？**

不白学。**概念全通用**：span、trace、token 用量、延迟、采样——Mastra 的 tracing 概念和 Langfuse/OpenTelemetry 完全对齐。你学的是「可观测性的思维模型」，Mastra 只是换了个实现。而且公司如果已有 Langfuse，Mastra 还能导出对接。

## 最佳实践

**✅ DO：**

- 核心 agent 至少挂一个「相关性」+ 一个「安全性」scorer。
- 用 sampling 抽样控制成本，别默认全量。
- 建立 dataset + experiment，每次改 prompt 都重跑对比分数。
- 开发期常看 Studio 的 trace，定位慢 step 和贵 step。

**❌ DON'T：**

- 别只测最终输出——给关键 step 也挂 scorer，才能定位问题。
- 别把 scorer 分数当「唯一真理」——model-graded 也有偏差，要结合人工抽检。
- 别忽视 trace 里的 token 用量——它既是质量线索，也是成本账单。

## 代码实战：挂上评测的工单客服

```typescript
import { Agent } from '@mastra/core/agent';
import { createAnswerRelevancyScorer, createToxicityScorer } from '@mastra/evals/scorers/prebuilt';

const supportAgent = new Agent({
  name: 'support',
  model: 'deepseek/deepseek-chat',
  instructions: '你是电商售后客服，语气友好，如实回答。',
  tools: { getOrder },
  scorers: {
    relevancy: {
      scorer: createAnswerRelevancyScorer({ model: 'deepseek/deepseek-chat' }),
      sampling: { type: 'ratio', rate: 0.5 },
    },
    safety: {
      scorer: createToxicityScorer({ model: 'deepseek/deepseek-chat' }),
      sampling: { type: 'ratio', rate: 1 },
    },
  },
});
```

跑一次对话，在 Studio 里你同时能看到：

1. **trace**：agent → getOrder 工具 → 模型回复，每步耗时和 token
2. **scores**：这次回答的相关性、毒性分数

## 实操练习（工单客服 Agent · 第 5 步）

**练习 1**：给客服 agent 挂 `createAnswerRelevancyScorer` + `createToxicityScorer`。

**验收标准**：Studio 里能看到每次运行的相关性和毒性分数。

**练习 2**：建一个 5 条测试用例的 dataset，跑一次 experiment。

**验收标准**：能看到每条用例的分数和平均分。

**练习 3（进阶）**：改一下 agent 的 instructions，重跑 experiment，对比分数变化。

**验收标准**：能说出「这次改动让相关性分数涨/跌了 X」。

## 本章小结

- Mastra 用 **Scorer** 量化 AI 输出质量（0~1 分数），替代传统布尔测试。
- 内置 scorer（relevancy/toxicity 等）开箱即用，可挂到 agent 或单个 step。
- **sampling 抽样**控制评测成本；**dataset + experiment** 构成完整评测循环。
- Observability 的 tracing **自动记录** agent/工具/workflow/model 每一步，Studio 可视化。
- Evals 测质量、Observability 看过程，两者互补——你第 21/22/29 章学的概念全部通用。
