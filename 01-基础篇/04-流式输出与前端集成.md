# 第4章：流式输出与前端集成 — 让 AI 像人一样说话

## 引言

你一定有过这样的体验：在 ChatGPT 里提问，文字一个一个蹦出来，像有人在实时打字。但你用 API 自己写的时候，发送请求后要干等好几秒，然后"啪"——整段文字一次性出现。

这两种体验的差距，就像 2024 年的网站和 2004 年的网站。2004 年你点一个链接，白屏等 3 秒，然后页面一次性渲染出来；2024 年你看到骨架屏、渐进加载、流畅的过渡动画。技术本质没变——都是服务端返回数据、浏览器渲染——但用户感知完全不同。

流式输出就是 AI 领域的"渐进式渲染"。它不能让 AI 思考得更快，但能让用户**感觉**它很快。在用户体验层面，感觉就是事实。

作为前端开发者，这一章你会觉得非常亲切。流式输出的很多技术概念——SSE、ReadableStream、AbortController——你可能已经在日常工作中用过。我们要做的就是把这些熟悉的武器用在 AI 场景中。

## 4.1 为什么需要流式输出：感知性能的艺术

### 一句话直觉解释

流式输出不减少总时间，但通过"边生成边显示"大幅缩短首次内容可见时间（TTFB），让等待变得可以忍受。

### 前端类比

前端开发者对这个概念再熟悉不过了——它就是**渐进式加载**的 AI 版本。

| 传统 API（非流式） | 流式 API |
|---|---|
| 骨架屏等 5 秒 → 内容一次性出现 | 内容逐字出现，5 秒后全部完成 |
| `<Suspense fallback={<Loading />}>` | `<StreamingText>` |
| 加载完成前用户无法获得任何信息 | 第一个字出现后用户就开始获取信息 |
| 类比：整页 SSR | 类比：Streaming SSR |

React 18 引入了 Streaming SSR，让页面可以分块发送到浏览器。AI 的流式输出是完全相同的思路——数据分块传输，前端分块渲染。

### 详细原理讲解

先理解 LLM 的生成过程。如第1章所讲，LLM 是**逐 Token 生成**的——它不是"想好整段话再说出来"，而是"说一个字，想一下，再说一个字"。这个过程本身就是流式的。

非流式 API 的工作方式是：模型在后台一个一个地生成 Token，但 API 服务器把它们全部攒起来，等到最后一个 Token 生成完毕，才把整段文本打包返回给你。

这就很浪费了。模型在第 100 毫秒就生成了第一个 Token，但你在第 5000 毫秒模型全部生成完之后才收到。中间那 4900 毫秒，模型已经产出了大量有用的内容，你却看不到。

流式 API 则是：模型每生成一个（或几个）Token，立刻通过网络推送给你。前端收到一个 Token 就渲染一个 Token。

用数字来感受一下：

```
假设一次请求，模型生成 500 个 Token，耗时 5 秒

非流式：
- 0s ~ 5s：用户看到 Loading
- 5s：突然看到完整的 500 Token 文本
- 首字时间（TTFB）：5s

流式：
- 0.1s：用户看到第 1 个 Token
- 0.1s ~ 5s：文字持续流入，用户边看边读
- 5s：全部内容显示完毕
- 首字时间（TTFB）：0.1s
```

总时间都是 5 秒，但用户体验天差地别。心理学研究表明：**有持续反馈的等待比无反馈的等待感知时间短 30-50%**。这就是为什么你等电梯时看楼层数字跳动不觉得久，但电梯没有显示屏时等同样的时间会觉得特别慢。

### 深层追问

**流式输出还有什么更深层的价值？**

除了感知性能，流式输出还有一个工程上的重要价值：**提前终止**。

想象用户问了一个问题，AI 开始回答。用户看了前两句就发现 AI 理解错了，于是点了"停止生成"。在非流式模式下，即使用户不想要结果了，服务端已经把所有 Token 都生成完了——白白浪费了算力和 Token 费用。在流式模式下，用户一旦取消，服务端就能停止生成，**真正节省了成本**。

在 Agent 场景中，这尤其重要——一个 Agent 可能需要调用多次 LLM，如果中间某一步的输出让你发现方向不对，流式模式允许你"看一眼就掉头"，而不是"等它说完才知道走错了"。

## 4.2 SSE（Server-Sent Events）原理：单向的实时推送

### 一句话直觉解释

SSE 是 HTTP 的"单向广播"模式——服务端不断地向客户端推送数据，客户端只需要听，不需要回话。

### 前端类比

想想你订阅的 RSS。你订阅了一个博客，博客每发一篇新文章就推送给你，但你不需要每次都回复博主。SSE 就是这样——服务端单方面推数据给浏览器。

和它对比的是 WebSocket，WebSocket 更像微信聊天——双方都可以随时发消息，是全双工通信。

### 详细原理讲解

SSE 是 HTML5 标准的一部分，它基于 HTTP 协议，通过设置特殊的响应头来维持一个长连接。

**SSE 的技术细节**

```
// 请求
GET /api/stream HTTP/1.1
Accept: text/event-stream

// 响应头
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

// 响应体（持续推送）
data: {"token": "你"}

data: {"token": "好"}

data: {"token": "，"}

data: {"token": "有什么"}

data: {"token": "可以帮"}

data: {"token": "你的？"}

data: [DONE]
```

几个关键点：

1. **Content-Type** 必须是 `text/event-stream`，浏览器才会启用 SSE 模式
2. 每个事件以 `data: ` 前缀开始，以空行 `\n\n` 结尾
3. 连接持续保持，直到服务端发送完毕或客户端断开
4. 如果连接中断，浏览器会自动重连（内置的重连机制）

**SSE vs WebSocket：深度对比**

| 维度 | SSE | WebSocket |
|------|-----|-----------|
| 通信方向 | 单向（服务端→客户端） | 双向 |
| 协议 | 基于 HTTP | 独立的 ws:// 协议 |
| 自动重连 | 内置支持 | 需要手动实现 |
| 数据格式 | 纯文本（通常是 JSON） | 文本或二进制 |
| 浏览器支持 | 除 IE 外全部支持 | 全部现代浏览器 |
| 通过代理/CDN | 容易（标准 HTTP） | 较难（需要特殊配置） |
| 连接限制 | HTTP/1.1 下每个域名 6 个 | 无此限制 |
| 适用场景 | 服务端推送（通知、流式输出） | 双向实时通信（聊天、协作编辑） |

**为什么 AI 场景更适合 SSE？**

核心原因：AI 对话是**请求-响应模式**的升级版——用户发一条消息，AI 返回一段流式响应。在 AI 生成回复的过程中，用户不需要向服务端发送任何数据（用户只是在"听"AI 说话）。这恰好是 SSE 的完美场景——单向推送。

用 WebSocket 也能做，但它是"杀鸡用牛刀"：
- WebSocket 需要维护有状态的长连接，对 Serverless 环境不友好（每个函数执行完就销毁）
- WebSocket 需要额外的心跳检测和重连逻辑
- WebSocket 穿越代理和负载均衡器时需要额外配置

而 SSE 基于标准 HTTP，天然兼容 CDN、代理、负载均衡器和 Serverless 平台。在 Vercel、Cloudflare Workers 等 Serverless 环境中，SSE 开箱即用，WebSocket 则需要特殊支持。

**什么时候该用 WebSocket？**

当你需要在 AI 生成过程中双向交互时。例如：
- 用户在 AI 回复过程中发送追加指令（"换个方向"）
- 多人协作的 AI 会话（多个用户实时看到彼此的操作）
- 需要推送非文本数据（图片、音频流）

但这些是少数场景。对于 80% 以上的 AI 应用，SSE 就够了。

### 深层追问

**HTTP/2 对 SSE 有什么影响？**

在 HTTP/1.1 下，SSE 有一个明显的限制：每个域名最多 6 个并发连接。如果你同时开 7 个 AI 对话标签页，第 7 个会被阻塞。

HTTP/2 通过多路复用（Multiplexing）解决了这个问题——所有 SSE 流可以在一个 TCP 连接上并行传输。所以在现代部署环境下，这个限制已经基本不存在了。

## 4.3 streamText API 详解：Vercel AI SDK 的流式引擎

### 一句话直觉解释

`streamText` 是 Vercel AI SDK 的核心 API——它调用 LLM 并返回一个流式响应，你可以逐 Token 消费，也可以直接转成 HTTP 响应。

### 前端类比

如果把 LLM API 调用比作数据请求：
- `generateText` 就像 `await fetch()` —— 等到所有数据都到了才返回
- `streamText` 就像 `fetch()` 返回的 `response.body`（ReadableStream）—— 数据到一部分你就能处理一部分

### 详细原理讲解

**generateText vs streamText**

```typescript
import { generateText, streamText } from "ai";
import { deepseek } from "@ai-sdk/deepseek";

// generateText：等待完整响应
const { text } = await generateText({
  model: deepseek("deepseek-chat"),
  prompt: "解释什么是闭包",
});
console.log(text); // 一次性输出完整文本

// streamText：流式响应
const result = streamText({
  model: deepseek("deepseek-chat"),
  prompt: "解释什么是闭包",
});

// 注意：streamText 是同步调用，不需要 await
// 它立即返回一个 result 对象，真正的异步操作在消费 stream 时发生
```

这是一个很重要的细节：**`streamText` 本身不是 async 函数**。它立即返回一个包含多种消费方式的结果对象。真正的 API 调用在你开始消费流的时候才发生。

**streamText 返回值解析**

`streamText` 返回的 result 对象包含以下重要属性：

```typescript
const result = streamText({
  model: deepseek("deepseek-chat"),
  instructions: "你是一个前端专家",
  messages: [{ role: "user", content: "React 和 Vue 的核心区别？" }],
  maxOutputTokens: 1000,

  // 生命周期回调
  onChunk({ chunk }) {
    // 每个 chunk 到达时触发
    // chunk 可能是 text-delta、tool-call 等类型
  },
  onEnd({ text, usage, finishReason }) {
    // 全部生成完毕时触发
    // text: 完整的生成文本
    // usage: { inputTokens, outputTokens, totalTokens }
    // finishReason: 'stop' | 'length' | 'tool-calls' | ...
    console.log(`消耗 Token: ${usage.totalTokens}`);
  },
});

// 消费方式 1：转成 HTTP 响应（最常用，用于 API Route）
return createUIMessageStreamResponse({
    stream: toUIMessageStream({ stream: result.stream }),
  });

// 消费方式 2：转成文本流（用于自定义处理）
for await (const textPart of result.textStream) {
  process.stdout.write(textPart);
}

// 消费方式 3：获取完整文本（等同于 generateText 的效果）
const fullText = await result.text;

// 消费方式 4：获取 Token 使用量
const usage = await result.usage;
```

**关键概念：UI Message Stream 协议**

`createUIMessageStreamResponse()` 不是简单地把文本流转成 HTTP 响应。Vercel AI SDK 定义了一套 **UI Message Stream 协议**，传输的不仅仅是文本，还包含结构化的元信息：

```
// 实际传输的格式（简化示意）
0: "你"           // 文本 token
0: "好"           // 文本 token
0: "，"           // 文本 token
0: "有什么"        // 文本 token
e: {"finishReason": "stop", "usage": {"inputTokens": 20, "outputTokens": 15}}
d: {"finishReason": "stop", "usage": {"inputTokens": 20, "outputTokens": 15}}
```

每行的前缀数字/字母表示数据类型：`0` 是文本 chunk，`e` 是 token 使用量等元信息，`d` 是流结束标记。前端的 `useChat` hook 知道如何解析这个协议，自动将文本片段拼接成完整消息，并提取 metadata。

这就是为什么你需要在前后端都使用 Vercel AI SDK——它们通过这个协议"握手"，前端才能正确解析后端推送的流式数据。如果你用其他方式发送流式数据，前端的 hook 可能无法正确解析。

### 深层追问

**ReadableStream 和 AsyncIterator 有什么关系？**

这是一个好的技术追问。在 `streamText` 的返回值中，你可以用 `for await...of` 来消费 `textStream`，这说明它实现了 AsyncIterator 协议。而 `createUIMessageStreamResponse()` 内部是用 ReadableStream 来构建 HTTP 响应的。

两者的关系：
- **ReadableStream** 是 Web Streams API 的一部分，是浏览器和 Node.js 都支持的底层流接口。它代表一个可读的数据源。
- **AsyncIterator** 是 JavaScript 的异步迭代协议，让你可以用 `for await...of` 语法消费异步数据。

ReadableStream 可以转换成 AsyncIterator（通过 `stream[Symbol.asyncIterator]()`），反过来也可以。Vercel AI SDK 同时提供了两种消费方式，让你根据场景选择最方便的方式。

在 API Route 中，用 ReadableStream（通过 `createUIMessageStreamResponse()`）是最方便的；在非 HTTP 场景（如 CLI 工具、测试脚本），用 AsyncIterator 更直观。

## 4.4 React 中的流式渲染：useChat hook 详解

### 一句话直觉解释

`useChat` 是一个 React Hook，帮你管理 AI 对话的全部状态——消息列表、加载状态、输入框、发送和停止。就像 `useState` + `useEffect` + `fetch` 的 AI 专用封装。

### 前端类比

用过 SWR 或 React Query 吗？`useChat` 就是 AI 对话版的 `useSWR`：

```
useSWR         → 管理数据请求的状态（data, error, isLoading）
useChat        → 管理 AI 对话的状态（messages, error, isLoading, input）
```

它帮你处理了：
- 消息列表的状态管理
- 流式数据的接收和拼接
- 加载状态的切换
- 输入框的双向绑定
- 请求的发送和取消

### 详细原理讲解

**基础用法**

```tsx
"use client";

import { useChat } from "@ai-sdk/react";

export default function ChatPage() {
  const {
    messages,    // 消息列表 Message[]
    input,       // 输入框的值
    setInput,    // 设置输入框的值
    handleInputChange,  // 绑定到 input 的 onChange
    handleSubmit,       // 绑定到 form 的 onSubmit
    isLoading,   // 是否正在生成
    stop,        // 停止生成
    error,       // 错误信息
    reload,      // 重新生成最后一条回复
    append,      // 手动追加一条消息并触发生成
  } = useChat({
    api: "/api/chat",           // 后端 API 路由
    initialMessages: [],         // 初始消息列表
    onFinish(message) {          // 一条消息完全生成后的回调
      console.log("生成完毕:", message);
    },
    onError(error) {             // 错误回调
      console.error("出错了:", error);
    },
  });

  return (
    <div className="flex flex-col h-screen max-w-2xl mx-auto">
      {/* 消息列表 */}
      <div className="flex-1 overflow-y-auto p-4 space-y-4">
        {messages.map((message) => (
          <div
            key={message.id}
            className={`flex ${
              message.role === "user" ? "justify-end" : "justify-start"
            }`}
          >
            <div
              className={`max-w-[80%] rounded-lg px-4 py-2 ${
                message.role === "user"
                  ? "bg-blue-500 text-white"
                  : "bg-gray-100 text-gray-900"
              }`}
            >
              {message.content}
            </div>
          </div>
        ))}
      </div>

      {/* 输入区域 */}
      <form onSubmit={handleSubmit} className="border-t p-4 flex gap-2">
        <input
          value={input}
          onChange={handleInputChange}
          placeholder="输入你的问题..."
          className="flex-1 border rounded-lg px-4 py-2"
          disabled={isLoading}
        />
        {isLoading ? (
          <button
            type="button"
            onClick={stop}
            className="px-4 py-2 bg-red-500 text-white rounded-lg"
          >
            停止
          </button>
        ) : (
          <button
            type="submit"
            className="px-4 py-2 bg-blue-500 text-white rounded-lg"
          >
            发送
          </button>
        )}
      </form>
    </div>
  );
}
```

**useChat 的内部工作流程**

当用户点击"发送"后，`useChat` 内部做了这些事情：

```
1. 将用户消息追加到 messages 数组（乐观更新）
2. 设置 isLoading = true
3. 向 /api/chat 发送 POST 请求，body 包含 messages
4. 开始读取 SSE 流
5. 每收到一个 text chunk：
   - 追加到最后一条 assistant 消息的 content 中
   - 触发 React 重渲染
6. 流结束后：
   - 设置 isLoading = false
   - 调用 onFinish 回调
```

注意第5步——**每个 chunk 都触发一次重渲染**。这就是为什么你能看到文字逐渐出现的效果。但这也引出了一个性能问题：如果 Token 生成速度很快（比如每秒 50 个 Token），就意味着每秒 50 次重渲染。对于简单的文本显示这不是问题，但如果你在做 Markdown 实时渲染（每次重渲染都要重新解析 Markdown），性能就可能成为瓶颈。这个问题我们在后面的性能优化部分讨论。

**Message 类型的结构**

```typescript
interface Message {
  id: string;           // 唯一标识
  role: "user" | "assistant" | "system";
  content: string;      // 文本内容
  createdAt?: Date;     // 创建时间
}
```

`useChat` 会自动为每条消息生成唯一的 `id`，用于 React 的 `key`。你不需要手动管理消息的增删改——hook 帮你搞定了。

### 深层追问

**useChat 和自己用 fetch + useState 有什么区别？**

你当然可以自己实现，核心逻辑并不复杂。但 `useChat` 帮你处理了大量细节：

1. **UI Message Stream 协议解析**：你需要手动解析 Vercel AI SDK 的流式数据格式
2. **消息 ID 生成和管理**：需要保证唯一性和顺序性
3. **中断和重发**：AbortController 的管理、reload 逻辑
4. **并发控制**：用户快速连续发送消息时的竞态处理
5. **错误恢复**：网络中断后的重试逻辑

自己实现一个简陋版本很快，但实现一个生产级版本需要处理大量边界情况。这和你用 `useSWR` 而不是自己封装 `fetch` 是一个道理——核心逻辑简单，但边界情况处理很复杂。

## 4.5 打字机效果实现：不只是逐字显示

### 一句话直觉解释

打字机效果是流式输出最直观的表现形式。但一个好的打字机效果要解决 Markdown 实时渲染、代码块高亮和光标动画等问题。

### 前端类比

这就像实现一个实时编辑器的协作功能——你需要处理"部分内容"的渲染问题。想想 Google Docs 的实时协作：你看到另一个人在打字，文字一个一个出现，同时格式、高亮实时更新。AI 的打字机效果面临完全相同的挑战。

### 详细原理讲解

**基础打字机效果——光标闪烁**

最简单的打字机效果就是在文字末尾加一个闪烁的光标。

```tsx
// components/TypingIndicator.tsx
"use client";

interface TypingIndicatorProps {
  content: string;
  isStreaming: boolean;
}

export function TypingIndicator({
  content,
  isStreaming,
}: TypingIndicatorProps) {
  return (
    <div className="relative">
      <span className="whitespace-pre-wrap">{content}</span>
      {isStreaming && (
        <span className="inline-block w-2 h-5 bg-gray-800 ml-0.5 animate-pulse" />
      )}
    </div>
  );
}
```

**进阶：Markdown 实时渲染**

AI 的输出通常包含 Markdown 格式——标题、列表、代码块、粗体等。问题是：流式输出的过程中，你拿到的是**不完整的 Markdown**。

比如 AI 正在输出这段内容：

```
## React Hooks 的优势

1. **更简洁**：不需要 `this` 绑定
2. **更灵活**：自定义 Hook 可以复用逻
```

在第三行输出到一半时，你的 Markdown 解析器看到了一个没有关闭的 `**`（粗体标记）和一个没有结束的列表项。如果直接丢给 Markdown 渲染器，可能会产生错误的格式。

解决方案有两种思路：

**思路1：用容错性好的 Markdown 渲染器**

```tsx
// 推荐：react-markdown，对不完整 Markdown 有较好的容错性
import ReactMarkdown from "react-markdown";
import remarkGfm from "remark-gfm";

function MessageContent({
  content,
  isStreaming,
}: {
  content: string;
  isStreaming: boolean;
}) {
  return (
    <div className="prose prose-sm max-w-none">
      <ReactMarkdown remarkPlugins={[remarkGfm]}>{content}</ReactMarkdown>
      {isStreaming && (
        <span className="inline-block w-2 h-5 bg-gray-800 ml-0.5 animate-pulse" />
      )}
    </div>
  );
}
```

**思路2：节流渲染，减少解析频率**

如果 Markdown 解析是性能瓶颈，可以加节流——不是每个 Token 都重新解析，而是积累一批再解析。

```tsx
import { useState, useRef, useEffect } from "react";
import ReactMarkdown from "react-markdown";

function ThrottledMarkdown({ content }: { content: string }) {
  const [displayContent, setDisplayContent] = useState(content);
  const rafRef = useRef<number>();

  useEffect(() => {
    // 使用 requestAnimationFrame 节流
    // 确保每帧最多渲染一次，大约 16ms/次
    if (rafRef.current) {
      cancelAnimationFrame(rafRef.current);
    }
    rafRef.current = requestAnimationFrame(() => {
      setDisplayContent(content);
    });

    return () => {
      if (rafRef.current) {
        cancelAnimationFrame(rafRef.current);
      }
    };
  }, [content]);

  return <ReactMarkdown>{displayContent}</ReactMarkdown>;
}
```

**代码块高亮的挑战**

AI 输出代码块时，你会面临这样的情况：

```
阶段1：收到  ```typ                     → 还不知道是什么语言
阶段2：收到  ```typescript\n             → 知道了是 TypeScript
阶段3：收到  ```typescript\nconst x     → 开始有代码内容
阶段4：收到  ```typescript\nconst x = 1;\n```  → 代码块完成
```

在阶段 1-3 之间，代码块是不完整的。你需要决定：是等代码块完成再高亮，还是实时高亮不完整的代码？

实践中推荐的方案是：**实时渲染不完整代码块，但高亮延迟到代码块闭合后再做**。原因是：语法高亮器（如 Prism、Shiki）处理不完整代码时可能产生错误的高亮，反而影响阅读。

```tsx
import { Prism as SyntaxHighlighter } from "react-syntax-highlighter";
import { oneLight } from "react-syntax-highlighter/dist/esm/styles/prism";

interface CodeBlockProps {
  language: string;
  children: string;
  isComplete: boolean; // 代码块是否已闭合
}

function CodeBlock({ language, children, isComplete }: CodeBlockProps) {
  if (!isComplete) {
    // 代码块未完成时，用等宽字体纯文本显示
    return (
      <pre className="bg-gray-50 p-4 rounded-lg overflow-x-auto">
        <code className="font-mono text-sm">{children}</code>
      </pre>
    );
  }

  // 代码块完成后，用语法高亮
  return (
    <SyntaxHighlighter language={language} style={oneLight}>
      {children}
    </SyntaxHighlighter>
  );
}
```

## 4.6 流式输出的边界情况

### 网络中断恢复

流式传输过程中网络中断了怎么办？SSE 有内置的自动重连机制，但对于 AI 对话来说，自动重连后需要的不是"从头开始"，而是"从断点续传"。

遗憾的是，大多数 LLM API 不支持真正的断点续传。所以实践中的处理方式是：

```typescript
// 方案：检测中断，提供重试选项
function useStreamWithRetry() {
  const { messages, error, reload, isLoading } = useChat({
    api: "/api/chat",
    onError(err) {
      // 区分错误类型
      if (err.message.includes("network")) {
        // 网络错误：可以重试
        console.log("网络中断，可以点击重试");
      } else if (err.message.includes("rate_limit")) {
        // 限流：需要等待
        console.log("请求过于频繁，请稍后再试");
      }
    },
  });

  return { messages, error, reload, isLoading };
}
```

### 用户中途取消：AbortController

用户可能在 AI 回复到一半时想要取消。`useChat` 内置了 `stop` 方法，但理解底层原理很重要。

```typescript
// useChat 底层的取消逻辑（简化版）
function fetchStream(url: string, body: object) {
  const abortController = new AbortController();

  const response = fetch(url, {
    method: "POST",
    body: JSON.stringify(body),
    signal: abortController.signal, // 关键：传入 AbortSignal
  });

  return {
    response,
    cancel: () => abortController.abort(), // 调用 abort() 取消请求
  };
}
```

`AbortController` 对前端开发者来说应该不陌生——它就是 `fetch` API 的标准取消机制。当调用 `abort()` 时：

1. 浏览器断开与服务端的 HTTP 连接
2. `fetch` 的 Promise 被 reject，错误类型为 `AbortError`
3. 服务端收到连接断开的信号，可以停止生成

```tsx
// 在组件中使用 stop
function ChatInterface() {
  const { messages, handleSubmit, isLoading, stop } = useChat();

  return (
    <div>
      {/* 消息列表 */}
      {messages.map((msg) => (
        <div key={msg.id}>{msg.content}</div>
      ))}

      {/* 停止按钮 */}
      {isLoading && (
        <button
          onClick={stop}
          className="flex items-center gap-2 text-red-500 hover:text-red-700"
        >
          <StopIcon className="w-4 h-4" />
          停止生成
        </button>
      )}
    </div>
  );
}
```

### 多条消息并发

用户快速连续发送多条消息时会发生什么？

```
用户 0.0s：发送消息 A
AI 0.1s：开始回复消息 A（流式）
用户 0.5s：发送消息 B（此时消息 A 还在生成中）
```

`useChat` 的默认行为是：**取消正在进行的生成，开始处理新消息**。这通常是合理的——用户发了新消息说明上一条的回复不再需要了。

但如果你的场景需要不同的行为（比如让 AI 按顺序回答所有问题），你需要自定义逻辑：

```typescript
// 方案：消息队列，按顺序处理
import { useChat } from "@ai-sdk/react";
import { useRef, useCallback } from "react";

function useSequentialChat() {
  const { messages, append, isLoading } = useChat();
  const queueRef = useRef<string[]>([]);
  const processingRef = useRef(false);

  const processQueue = useCallback(async () => {
    if (processingRef.current || queueRef.current.length === 0) return;

    processingRef.current = true;
    const nextMessage = queueRef.current.shift()!;

    await append({ role: "user", content: nextMessage });
    // append 会在流式响应完成后 resolve

    processingRef.current = false;
    processQueue(); // 处理下一条
  }, [append]);

  const sendMessage = useCallback(
    (content: string) => {
      queueRef.current.push(content);
      processQueue();
    },
    [processQueue]
  );

  return { messages, sendMessage, isLoading };
}
```

### Token 流和完整消息的关系

一个常见的困惑：流式传输过程中，`messages` 数组是怎么更新的？

`useChat` 的策略是**乐观更新 + 流式追加**：

```
1. 用户发送消息
   messages: [{ role: "user", content: "你好" }]

2. 收到第一个 Token
   messages: [
     { role: "user", content: "你好" },
     { role: "assistant", content: "你" }  // 新创建一条 assistant 消息
   ]

3. 持续收到 Token
   messages: [
     { role: "user", content: "你好" },
     { role: "assistant", content: "你好，有什么可以帮" }  // content 持续增长
   ]

4. 流结束
   messages: [
     { role: "user", content: "你好" },
     { role: "assistant", content: "你好，有什么可以帮你的？" }  // 最终的完整内容
   ]
```

注意：在整个过程中，`messages` 数组的长度在步骤2之后就固定了。后续只是最后一条 assistant 消息的 `content` 在增长。这对 React 渲染很友好——只有最后一个消息组件需要重渲染，其他消息组件通过 `React.memo` 或 `key` 稳定性可以跳过渲染。

## 4.8 性能优化：当消息越来越多

### 防抖渲染

正如前面提到的，流式输出意味着高频的状态更新。当消息内容很长、包含复杂 Markdown 时，每次更新都重新解析和渲染 Markdown 可能导致 UI 卡顿。

```tsx
// 方案：用 useDeferredValue 降低 Markdown 渲染优先级
import { useDeferredValue } from "react";
import ReactMarkdown from "react-markdown";

function DeferredMarkdown({ content }: { content: string }) {
  // useDeferredValue 让 React 在有更高优先级更新时
  // 跳过这个值的渲染，避免阻塞用户交互
  const deferredContent = useDeferredValue(content);

  return <ReactMarkdown>{deferredContent}</ReactMarkdown>;
}
```

`useDeferredValue` 是 React 18 引入的并发特性，完美适配流式渲染场景——它告诉 React："这个值的更新不紧急，如果有更重要的事（比如用户正在打字），可以晚一点渲染"。

### 虚拟滚动

当对话历史累积到几十条甚至上百条消息时，全部渲染在 DOM 中会导致严重的性能问题。解决方案是虚拟滚动（Virtual Scrolling），只渲染可视区域内的消息。

```tsx
// 使用 @tanstack/react-virtual 实现消息列表虚拟滚动
import { useVirtualizer } from "@tanstack/react-virtual";
import { useRef } from "react";
import type { Message } from "ai";

function VirtualMessageList({ messages }: { messages: Message[] }) {
  const parentRef = useRef<HTMLDivElement>(null);

  const virtualizer = useVirtualizer({
    count: messages.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 100, // 预估每条消息高度 100px
    overscan: 5, // 上下各多渲染 5 条，减少白屏
  });

  return (
    <div ref={parentRef} className="h-full overflow-y-auto">
      <div
        style={{
          height: `${virtualizer.getTotalSize()}px`,
          width: "100%",
          position: "relative",
        }}
      >
        {virtualizer.getVirtualItems().map((virtualItem) => {
          const message = messages[virtualItem.index];
          return (
            <div
              key={virtualItem.key}
              data-index={virtualItem.index}
              ref={virtualizer.measureElement}
              style={{
                position: "absolute",
                top: 0,
                left: 0,
                width: "100%",
                transform: `translateY(${virtualItem.start}px)`,
              }}
            >
              <MessageBubble message={message} />
            </div>
          );
        })}
      </div>
    </div>
  );
}
```

### 自动滚动到底部

用户在看 AI 的流式回复时，页面需要自动滚动到底部。但如果用户手动往上翻看历史消息，又不应该强制滚动打断他。

```tsx
import { useRef, useEffect, useState, useCallback } from "react";

function useAutoScroll(dependency: unknown) {
  const containerRef = useRef<HTMLDivElement>(null);
  const [isUserScrolledUp, setIsUserScrolledUp] = useState(false);

  // 检测用户是否手动上翻
  const handleScroll = useCallback(() => {
    const container = containerRef.current;
    if (!container) return;

    const { scrollTop, scrollHeight, clientHeight } = container;
    // 如果距离底部超过 100px，认为用户在查看历史
    const isNearBottom = scrollHeight - scrollTop - clientHeight < 100;
    setIsUserScrolledUp(!isNearBottom);
  }, []);

  // 当内容更新时，如果用户没有上翻，自动滚动到底部
  useEffect(() => {
    if (!isUserScrolledUp && containerRef.current) {
      containerRef.current.scrollTo({
        top: containerRef.current.scrollHeight,
        behavior: "smooth",
      });
    }
  }, [dependency, isUserScrolledUp]);

  return { containerRef, handleScroll, isUserScrolledUp };
}

// 使用
function ChatMessages({ messages }: { messages: Message[] }) {
  const { containerRef, handleScroll, isUserScrolledUp } = useAutoScroll(
    messages[messages.length - 1]?.content
  );

  return (
    <div className="relative">
      <div
        ref={containerRef}
        onScroll={handleScroll}
        className="h-[600px] overflow-y-auto"
      >
        {messages.map((msg) => (
          <MessageBubble key={msg.id} message={msg} />
        ))}
      </div>

      {/* 当用户上翻时，显示"回到最新"按钮 */}
      {isUserScrolledUp && (
        <button
          onClick={() => {
            containerRef.current?.scrollTo({
              top: containerRef.current.scrollHeight,
              behavior: "smooth",
            });
          }}
          className="absolute bottom-4 right-4 bg-blue-500 text-white rounded-full px-3 py-1 shadow-lg"
        >
          ↓ 回到最新
        </button>
      )}
    </div>
  );
}
```

## 概念辨析

### SSE vs WebSocket vs Long Polling

| 维度 | SSE | WebSocket | Long Polling |
|------|-----|-----------|-------------|
| 通信模型 | 单向推送 | 全双工 | 模拟推送 |
| 连接方式 | HTTP 长连接 | 独立的 WebSocket 连接 | 反复建立 HTTP 连接 |
| 效率 | 高 | 最高 | 低（频繁建连） |
| 兼容性 | 好（标准 HTTP） | 好（需要特殊支持） | 最好（纯 HTTP） |
| Serverless 兼容 | 好 | 差 | 好 |
| AI 场景适配度 | 最佳 | 过度设计 | 不合适（延迟高） |

### generateText vs streamText

| 维度 | generateText | streamText |
|------|-------------|-----------|
| 返回方式 | 等待完成后一次性返回 | 立即返回流对象 |
| 调用语法 | `await generateText(...)` | `streamText(...)`（同步） |
| 适用场景 | 后台处理、不需要实时展示 | 用户界面、需要实时反馈 |
| TTFB | 等于总生成时间 | 约 100ms |
| 中途取消 | 不支持 | 支持（AbortController） |
| 用户体验 | Loading → 完整结果 | 逐字出现 |

什么时候用 `generateText`？
- 后台批量处理（用户不需要看到过程）
- 需要对完整输出做后处理才能展示（如 JSON 解析）
- Prompt Chaining 的中间步骤

什么时候用 `streamText`？
- 用户界面的实时交互
- 长回复（超过 2-3 秒的生成任务）
- 需要支持用户中途取消

### useChat vs useCompletion

Vercel AI SDK 提供了两个主要的 React Hook：

| 维度 | useChat | useCompletion |
|------|---------|--------------|
| 用途 | 多轮对话 | 单次文本生成 |
| 状态管理 | 管理完整的消息列表 | 管理单个输出文本 |
| 适用场景 | 聊天界面 | 文本补全、翻译、摘要 |
| 输入方式 | 消息列表（messages） | 单个提示词（prompt） |

## 灵魂拷问

> **Q: SSE 和 WebSocket 都能做实时通信，为什么 AI 场景 SSE 更合适？什么情况下该用 WebSocket？**

> A: 核心原因是**通信模型的匹配度**。
>
> AI 对话的典型模式是"一来一回"——用户发一条消息，AI 返回一段流式响应。在 AI 生成回复的过程中，用户不需要向服务端发送任何数据。这恰好是 SSE 的设计场景：单向推送。
>
> 用 WebSocket 能实现吗？当然能。但你引入了不必要的复杂性：
> 1. WebSocket 需要握手升级协议，增加了连接建立时间
> 2. 需要自己管理心跳、重连、状态恢复
> 3. 在 Serverless 环境中（Vercel、Cloudflare Workers），WebSocket 要么不支持要么需要额外配置
> 4. CDN 和反向代理对 HTTP 更友好
>
> 什么时候该用 WebSocket？
> - AI 生成过程中需要双向交互（如用户发送"换个方向"的实时指令）
> - 多人协作的 AI 会话（类似 Google Docs 的实时协作）
> - 需要推送非文本数据（如实时语音流）
> - 单个页面需要大量独立的实时通道（HTTP/1.1 下 SSE 有 6 个连接的限制）

> **Q: streamText 返回的 stream 是什么类型？ReadableStream 和 AsyncIterator 有什么区别？**

> A: `streamText` 返回的 result 对象提供了多种消费方式：
>
> - `result.textStream`：实现了 AsyncIterable 协议，可以用 `for await...of` 消费
> - `result.createUIMessageStreamResponse()` 内部构建了一个 ReadableStream 作为 HTTP Response 的 body
>
> 两者的本质区别在于**消费模型**：
> - **ReadableStream** 是"拉模型"（Pull）—— 消费者主动调用 `read()` 来获取数据。它是 Web Streams API 的一部分，可以通过管道（pipe）连接多个处理步骤。
> - **AsyncIterator** 是"拉模型"的语法糖 —— `for await...of` 每次循环自动调用 `next()` 获取下一个值。代码更简洁易读。
>
> 在实际使用中：
> - 构建 HTTP 响应 → ReadableStream（`createUIMessageStreamResponse()`）
> - 在 Node.js 中处理流 → AsyncIterator（`for await...of`）
> - 前端消费 → 不需要直接接触这些底层 API，`useChat` 已经封装好了

> **Q: 流式渲染时 Markdown 解析的挑战是什么？为什么不能等全部输出完再解析？**

> A: 核心挑战是**不完整语法的处理**。
>
> Markdown 中有大量"成对出现"的标记：`**粗体**`、`` `代码` ``、`[链接](url)`、```` ```代码块``` ````。流式输出过程中，你经常遇到这些标记只出现了开头但还没有闭合的情况。
>
> 不同的 Markdown 解析器对此的处理不同。有的会报错，有的会忽略未闭合的标记，有的会做"最大努力"渲染。这是选择 Markdown 库时的重要考量。
>
> 为什么不能等全部输出完再解析？因为那就失去了流式输出的意义。用户看到的不是逐字出现的格式化文本，而是一大段原始 Markdown 源码突然变成格式化内容——这种"闪烁"体验比逐字出现更差。
>
> 实践建议：使用 `react-markdown`，它对不完整 Markdown 的容错性较好。对于代码块，在未闭合时用纯文本样式显示，闭合后再用语法高亮渲染。

> **Q: 如果用户快速连续发送多条消息，前端应该如何处理？**

> A: 这取决于你的产品设计。有三种主流策略：
>
> **策略1：中断旧的，处理新的（默认行为）**
> `useChat` 的默认行为。当用户发送新消息时，取消正在进行的流式响应。这在大多数场景下是合理的——用户发新消息通常意味着对之前的回复不满意或有新需求。
>
> **策略2：排队处理**
> 把新消息放入队列，等当前回复完成后依次处理。适用于"批量提问"的场景，比如用户一次性输入多个独立的问题。需要自行实现队列逻辑。
>
> **策略3：禁止并发**
> 在 AI 回复过程中禁用输入框，不允许用户发送新消息。简单粗暴但有效，避免了所有并发问题。很多产品（包括 ChatGPT）的早期版本就是这么做的。
>
> 选择哪种策略取决于你的产品场景。如果是通用对话助手，策略1通常最好；如果是批量处理工具，策略2更合适；如果是简单的问答场景，策略3够用了。

> **Q: 流式输出能减少 TTFB 但不能减少总时间，为什么用户体验却更好？这给我们什么启示？**

> A: 这揭示了一个深刻的产品原则：**用户体验的核心不是客观性能，而是主观感知**。
>
> 心理学中有两个相关概念：
> 1. **进度反馈效应**：有进度指示的等待比无进度指示的等待感知时间短 30-50%
> 2. **首次有意义内容时间**：用户看到第一个有意义的内容后，焦虑感大幅降低
>
> 流式输出同时利用了这两个效应——它既提供了持续的进度反馈（文字在不断出现），又将首次有意义内容时间从"总生成时间"缩短到了"第一个 Token 的生成时间"。
>
> 对前端开发者的启示：
> - 骨架屏（Skeleton Screen）之所以有效，同理——它不加速数据加载，但改善了感知
> - 列表的渐进加载（先显示前几项）优于等全部数据到齐再渲染
> - 图片的渐进式加载（先显示模糊缩略图再加载高清图）
> - 动画和过渡效果不只是"好看"，它们在管理用户的时间感知
>
> 回到 AI 领域：即使未来 AI 的生成速度快到 1 秒内就能输出完整回复，流式输出可能仍然有价值——因为"逐字出现"的视觉效果暗示了"AI 在认真思考"，给用户一种被重视的感觉。这就是为什么很多 AI 产品即使收到了完整响应，也会用打字机效果"慢慢"显示。

## 最佳实践

### DO

- **DO** 在用户界面上始终使用流式输出
  - 原因：任何超过 1 秒的等待都应该有实时反馈

- **DO** 提供"停止生成"按钮
  - 原因：给用户掌控感，同时在用户取消时节省 API 成本

- **DO** 处理自动滚动的边界情况
  - 原因：用户上翻查看历史时不应被强制滚动到底部

- **DO** 对 Markdown 渲染做性能优化
  - 原因：高频状态更新 + 复杂 Markdown 解析 = 潜在的性能瓶颈

- **DO** 在后端 API Route 中做输入校验和错误处理
  - 原因：永远不要信任前端传来的数据

- **DO** 记录每次请求的 Token 使用量
  - 原因：成本监控和异常检测的基础

### DON'T

- **DON'T** 在后台批处理中使用 streamText
  - 原因：没有用户在等，流式输出增加了不必要的复杂性

- **DON'T** 每个 Token 都做一次完整的 Markdown 解析
  - 原因：性能灾难。用 `requestAnimationFrame` 或 `useDeferredValue` 节流

- **DON'T** 忽略网络错误处理
  - 原因：流式连接比普通 HTTP 请求更容易受网络波动影响

- **DON'T** 把 API Key 放在前端代码中直接调用 LLM API
  - 原因：API Key 会暴露。始终通过后端 API Route 中转

- **DON'T** 在流式响应中返回敏感信息
  - 原因：流式数据一旦发出就无法撤回，不像普通 API 可以在发送前完整审查

#### 完整的 API Route

```typescript
// app/api/chat/route.ts
import { streamText, toUIMessageStream, createUIMessageStreamResponse } from "ai";
import { deepseek } from "@ai-sdk/deepseek";
import { WORK_ASSISTANT_PROMPT } from "@/prompts/work-assistant";
import { z } from "zod";

// 请求体校验
const ChatRequestSchema = z.object({
  messages: z
    .array(
      z.object({
        role: z.enum(["user", "assistant"]),
        content: z.string().min(1).max(10000),
      })
    )
    .min(1)
    .max(50),
});

export async function POST(req: Request) {
  try {
    const body = await req.json();

    const parseResult = ChatRequestSchema.safeParse(body);
    if (!parseResult.success) {
      return new Response(
        JSON.stringify({
          error: "请求格式错误",
          details: parseResult.error.flatten(),
        }),
        { status: 400, headers: { "Content-Type": "application/json" } }
      );
    }

    const { messages } = parseResult.data;

    const result = streamText({
      model: deepseek("deepseek-chat"),
      instructions: WORK_ASSISTANT_PROMPT.system,
      messages,
      maxOutputTokens: 2000,
      abortSignal: req.signal, // 传递请求的 abort signal，客户端断开时自动停止生成
      onEnd({ text, usage, finishReason }) {
        // 生产环境中，这里可以：
        // 1. 记录对话日志
        // 2. 统计 Token 使用量
        // 3. 监控异常（如 finishReason !== 'stop'）
        console.log(
          `[Chat API] finished - reason: ${finishReason}, tokens: ${usage.totalTokens}`
        );
      },
    });

    return createUIMessageStreamResponse({
      stream: toUIMessageStream({ stream: result.stream }),
    });
  } catch (error) {
    console.error("[Chat API] Error:", error);
    return new Response(
      JSON.stringify({ error: "服务暂时不可用，请稍后重试" }),
      { status: 500, headers: { "Content-Type": "application/json" } }
    );
  }
}
```

#### AbortController 手动管理流式请求

```typescript
// utils/manual-stream.ts

/**
 * 如果你不使用 useChat，而是需要手动管理流式请求
 * 下面是一个完整的底层实现参考
 */
export async function fetchStreamManually(
  messages: Array<{ role: string; content: string }>,
  onToken: (token: string) => void,
  onDone: () => void,
  onError: (error: Error) => void
): Promise<AbortController> {
  const abortController = new AbortController();

  try {
    const response = await fetch("/api/chat", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ messages }),
      signal: abortController.signal,
    });

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}: ${response.statusText}`);
    }

    if (!response.body) {
      throw new Error("Response body is null");
    }

    const reader = response.body.getReader();
    const decoder = new TextDecoder();

    while (true) {
      const { done, value } = await reader.read();

      if (done) {
        onDone();
        break;
      }

      // 将 Uint8Array 解码为文本
      const chunk = decoder.decode(value, { stream: true });

      // 解析 UI Message Stream 协议
      // 每行格式：{type}:{data}\n
      const lines = chunk.split("\n").filter((line) => line.trim());

      for (const line of lines) {
        // "0:" 前缀表示文本 token
        if (line.startsWith("0:")) {
          const token = JSON.parse(line.slice(2));
          onToken(token);
        }
        // "d:" 前缀表示流结束
        if (line.startsWith("d:")) {
          onDone();
          return abortController;
        }
      }
    }
  } catch (error) {
    if (error instanceof Error && error.name === "AbortError") {
      // 用户主动取消，不算错误
      console.log("Request cancelled by user");
    } else {
      onError(error instanceof Error ? error : new Error(String(error)));
    }
  }

  return abortController;
}

## 本章小结

这一章我们完成了从"API 调用"到"流式聊天界面"的跨越：

1. **流式输出是 AI 应用的标配**，它不减少总时间但大幅改善感知性能。首字时间（TTFB）从秒级降到百毫秒级，用户体验天差地别。

2. **SSE 是 AI 场景的最佳选择**，基于标准 HTTP、单向推送、兼容 Serverless，比 WebSocket 简单且够用。除非需要双向实时交互，否则不要引入 WebSocket 的额外复杂性。

3. **streamText 是流式核心**，它同步返回一个结果对象，提供多种消费方式——`createUIMessageStreamResponse()` 用于 API Route，`textStream` 用于自定义消费，`text` 用于等待完整结果。

4. **useChat 封装了对话的全部状态管理**，包括消息列表、输入框、加载状态、取消和重试。它和后端通过 UI Message Stream 协议通信，开箱即用。

5. **打字机效果不只是"逐字显示"**，还需要处理 Markdown 实时渲染、代码块高亮和光标动画。性能优化的关键是避免每个 Token 都触发完整的 Markdown 解析。

6. **边界情况是区分 demo 和产品的关键**——网络中断恢复、用户取消、并发消息处理、自动滚动逻辑，这些细节决定了用户体验的上限。

7. **后端 API Route 不只是"转发"**，它承担了输入校验、错误处理、成本监控等职责。永远不要在前端直接调用 LLM API。

到这里，我们的"AI 智能工作助手"已经有了产品级 Prompt 和流畅的流式聊天界面。下一章，我们将进入结构化输出的世界——让 AI 不只是"说话"，还能输出结构化的数据，和你的代码无缝对接。
