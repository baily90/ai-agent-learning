# 第6章：模型选择与多模型策略 -- 不是最贵的就最好

## 引言

你写 React 应用时，不会所有请求都打到数据库吧？静态资源走 CDN，热数据走 Redis 缓存，只有真正需要的请求才到数据库。你会根据请求的特点选择不同的"后端" -- 这不是偷懒，这是架构设计。

AI 模型选择也是同样的道理。

市场上有几十种大语言模型，从 OpenAI 的 GPT-5 到 Anthropic 的 Claude，从 DeepSeek 到开源的 Llama、Qwen、Mistral。它们的价格差距可以达到 100 倍 -- 最贵的和最便宜的之间，就像五星级酒店和青年旅社。

问题是：你的 Agent 里每一次 AI 调用都需要住五星级酒店吗？

一个"帮用户把英文翻译成中文"的请求，和一个"帮用户分析 100 页财务报告并给出投资建议"的请求，需要的"智力水平"天差地别。用同一个最贵的模型处理所有请求，就像用 PostgreSQL 来缓存 session -- 能用，但浪费。

本章要回答三个关键问题：
1. 面对这么多模型，怎么选？
2. 一个模型够不够？什么时候需要多个模型？
3. 怎么在质量和成本之间找到最优解？

如果你觉得"先不管成本，开发阶段用最好的模型" -- 这其实是对的。但你迟早要面对成本问题，而本章会让你在那一天到来时，心里有底。

## 6.1 模型市场概览

### 一句话直觉

大语言模型的市场就像前端框架的生态 -- 没有"最好的"，只有"最适合的"。

### 前端类比

选模型就像选前端技术栈：

| 选前端框架 | 选 AI 模型 |
|-----------|-----------|
| React -- 生态最大，适合大型项目 | GPT-5 -- 综合能力最强，适合复杂任务 |
| Vue -- 上手简单，性价比高 | Claude Sonnet -- 平衡性好，长文本强 |
| Svelte -- 轻量极速，特定场景最优 | GPT-5-mini -- 便宜快速，简单任务首选 |
| Preact -- React 的轻量替代 | DeepSeek V4 -- 性价比极高的替代方案 |

没有人说"所有项目都应该用 React"，同样，没有人该说"所有 AI 任务都应该用 GPT-5"。

### 主流模型详解

#### OpenAI 系列

**GPT-5**
- 定位：旗舰全能模型
- 擅长：复杂推理、代码生成、多语言、工具调用
- 短板：价格较高、偶尔过于"话痨"
- 价格区间：输入 $2.5/百万 token，输出 $10/百万 token（价格随时间调整，以官网为准）
- 适合场景：复杂 Agent 任务、需要高准确率的生产环境

**GPT-5-mini**
- 定位：小而快的经济型模型
- 擅长：简单分类、提取、翻译、格式转换
- 短板：复杂推理能力有限、容易在长任务中"迷路"
- 价格区间：输入 $0.15/百万 token，输出 $0.6/百万 token
- 适合场景：高频简单任务、成本敏感场景

**o1 / o3 系列**
- 定位：深度推理模型（"慢思考"模型）
- 擅长：数学推理、复杂逻辑、科学问题
- 短板：速度慢、价格贵、简单任务反而表现不如 GPT-5
- 适合场景：需要多步推理的复杂问题

#### Anthropic 系列

**Claude Sonnet**
- 定位：综合平衡型模型
- 擅长：长文本理解（200K context）、代码生成、指令遵循
- 短板：工具调用的稳定性在持续改进中
- 适合场景：长文档分析、代码辅助、需要忠实遵循指令的任务

**Claude Haiku**
- 定位：极速经济型模型
- 擅长：速度快、分类/提取任务性价比极高
- 短板：复杂推理能力有限
- 适合场景：实时响应场景、简单的信息处理

**Claude Opus**
- 定位：最强推理型模型
- 擅长：最复杂的推理和分析任务、nuanced 理解
- 短板：价格最高、速度最慢
- 适合场景：需要顶级推理能力的关键任务

#### DeepSeek 系列

**DeepSeek V4**
- 定位：高性价比全能模型
- 擅长：中文理解、代码生成、数学推理
- 短板：多语言能力（非中英文）、某些边缘场景的稳定性
- 价格区间：极具竞争力，通常只有 GPT-5 的几分之一
- 适合场景：中文场景的首选、成本敏感但需要高质量的场景

**DeepSeek V4 Pro**
- 定位：开源推理模型
- 擅长：数学、逻辑推理、代码
- 短板：速度较慢（推理链长）、生成内容偶尔不稳定
- 适合场景：需要深度推理且预算有限

#### 开源模型

**Llama 系列（Meta）**
- 定位：最主流的开源基础模型
- 特点：生态最大、微调资源最多、可自部署
- 版本：从 8B 到 405B 多种规格

**Qwen 系列（阿里）**
- 定位：中文能力出色的开源模型
- 特点：中文场景下表现优异、多种规格可选

**Mistral 系列**
- 定位：欧洲开源模型，注重效率
- 特点：小模型性能好、推理速度快

### 关键认知

**没有"最好的模型"，只有"最适合场景的模型"。** 这不是外交辞令，而是技术事实。每个模型的训练数据、训练方法、优化目标不同，导致它们在不同任务上的表现有显著差异。

GPT-5 可能在英文创意写作上最强，但在中文技术文档理解上不如 DeepSeek V4。Claude Sonnet 可能在 200K 长文本上表现卓越，但在简单的 yes/no 分类上不如 GPT-5-mini 快速高效。

## 6.2 如何评估模型

### 一句话直觉

不要只看排行榜，要看你自己的使用场景。

### 前端类比

你选前端框架时会看 Star 数和 npm 下载量吗？会看。但你不会只看这些。你还会考虑：团队熟悉度、项目规模、生态成熟度、长期维护性。AI 模型评估也一样 -- benchmark 只是参考，不是答案。

### 评估维度矩阵

| 维度 | 含义 | 重要场景 |
|------|------|---------|
| **推理能力** | 多步逻辑推理的准确性 | Agent 规划、复杂分析 |
| **指令遵循** | 按你的要求精确执行的能力 | 结构化输出、工具调用 |
| **工具调用** | Function Calling 的稳定性 | Agent 开发的核心能力 |
| **代码生成** | 生成正确代码的能力 | 开发辅助场景 |
| **多语言** | 非英语场景的表现 | 中文场景尤其重要 |
| **上下文长度** | 能处理的文本量上限 | 长文档、对话历史 |
| **速度** | 首 token 延迟 + 生成速度 | 用户面对的实时场景 |
| **价格** | 输入/输出的 token 价格 | 高频调用场景 |

### 为什么 Benchmark 不够

AI 领域有很多 benchmark：MMLU、HumanEval、GSM8K、GPQA 等。它们测试模型在标准化题目上的表现。但这些分数和你的实际场景之间，有一个巨大的鸿沟。

**前端类比**：这就像 Lighthouse 分数。一个 100 分的网站不一定用户体验好 -- 它可能加载快但交互卡顿，可能性能好但设计丑。Lighthouse 测的是它能测的维度，不是你业务真正关心的维度。

模型 benchmark 也是如此。一个 MMLU 分数 90+ 的模型，在你的"客服工单分类"任务上可能不如分数 85 的模型，因为：

1. **Benchmark 的题目分布和你的任务不同**。MMLU 考的是通识知识，你需要的是领域能力。
2. **Benchmark 不测工程化能力**。指令遵循、输出格式稳定性、错误恢复 -- 这些 Agent 开发的关键能力，标准 benchmark 基本不测。
3. **Benchmark 存在数据污染风险**。模型可能在训练时"看过"测试题，导致分数虚高。

### 正确的评估方法

```
1. 收集 20-50 个你真实场景的测试用例
2. 用相同的 prompt 分别调用候选模型
3. 人工评估输出质量（或用 AI 辅助评估）
4. 综合考虑质量、速度、价格
5. 选定后持续监控线上效果
```

这就是为什么第20章会专门讲"评估与测试" -- 因为模型评估不是选型时做一次就完了，而是需要持续做的事情。

## 6.3 成本计算 -- 你以为每月几美元，实际可能几百美元

### 一句话直觉

AI 的计费按 token 算，输入和输出分开计价，而且输出比输入贵很多。

### 前端类比

想想你们公司的云服务账单。刚开始用的时候 CEO 说"一个月也就几百块"，上线后发现是几万 -- 因为没人算过高并发下的实际用量。AI 成本也会有同样的"惊喜"。

### 计费模型详解

几乎所有商业 AI 模型都按 token 计费，分为两种：

- **输入 token（Input/Prompt tokens）**：你发给模型的内容 -- system prompt + 用户消息 + 上下文
- **输出 token（Output/Completion tokens）**：模型生成的内容 -- AI 的回复

**关键认知：输出 token 通常比输入 token 贵 2-4 倍。**

为什么？因为输入 token 的处理可以高度并行化（所有 token 一次性进入模型），而输出 token 必须逐个生成（每个 token 都依赖前一个 token），计算资源消耗更大。

### 真实场景成本估算

让我们算一个真实的例子。假设你开发了一个 AI 客服助手：

**场景参数**：
- 日均用户消息：10,000 条
- 每条消息的平均输入：500 tokens（system prompt 200 + 对话历史 200 + 用户消息 100）
- 每条消息的平均输出：300 tokens
- 使用模型：GPT-5

**月度成本计算**：

```
月消息量 = 10,000 × 30 = 300,000 条

输入 token 总量 = 300,000 × 500 = 1.5 亿 tokens
输出 token 总量 = 300,000 × 300 = 9,000 万 tokens

输入成本 = 150M × $2.5/1M = $375
输出成本 = 90M × $10/1M = $900

月总成本 = $375 + $900 = $1,275/月（约 ￥9,000）
```

**如果换成 GPT-5-mini**：

```
输入成本 = 150M × $0.15/1M = $22.5
输出成本 = 90M × $0.6/1M = $54

月总成本 = $22.5 + $54 = $76.5/月（约 ￥550）
```

**成本差距：16 倍。**

而如果你的 Agent 更复杂 -- 比如每次对话要做工具调用（额外的 token）、维护长对话历史（输入 token 快速膨胀）、做多轮推理（多次 API 调用） -- 实际成本可能远超上面的估算。

### 成本膨胀的陷阱

有几个容易忽视的成本膨胀因素：

**1. System Prompt 的"隐形税"**

每次 API 调用都会发送 system prompt。如果你的 system prompt 有 1000 tokens，每天 1 万次调用，一个月就是 3 亿个"白白"重复发送的 token。

```
System prompt 月成本 = 300M × $2.5/1M = $750
仅 system prompt 就要 $750/月！
```

这就是为什么后面章节会讲 prompt 缓存（Prompt Caching） -- 它能大幅降低重复 system prompt 的成本。

**2. 对话历史的累积效应**

多轮对话中，每次请求都要带上之前的对话历史。第1轮发 500 tokens，第2轮发 1000 tokens，第3轮发 1500 tokens... 到第10轮可能就是 5000 tokens。

```
10轮对话的总输入 = 500 + 1000 + 1500 + ... + 5000 = 27,500 tokens
而不是 500 × 10 = 5,000 tokens
```

这是一个等差数列求和，实际消耗是线性计算的 5.5 倍。这就是为什么第8章会讲上下文管理和对话压缩。

**3. 工具调用的额外开销**

Agent 做工具调用时，工具的定义（function schema）会占用输入 token，工具的返回结果也会增加输入 token。一次工具调用循环可能产生 2-3 次 API 调用。

### Token 估算快速参考

| 内容类型 | 大约 token 数 |
|---------|-------------|
| 1 个英文单词 | ~1.3 tokens |
| 1 个中文字 | ~1.5-2 tokens |
| 1 行代码 | ~10-15 tokens |
| 一段 100 字的中文 | ~150-200 tokens |
| 一页 A4 文档 | ~500-800 tokens |
| 一个典型的 system prompt | ~200-500 tokens |

## 6.4 小模型 vs 大模型的选择

### 一句话直觉

不是所有请求都需要最强的大脑 -- 算加减法不需要数学教授。

### 前端类比

```
CDN 缓存      ←  静态资源（99%的请求）    ←  小模型处理简单任务
Redis 缓存    ←  热数据查询              ←  中等模型处理一般任务  
数据库查询    ←  复杂业务逻辑            ←  大模型处理复杂任务
跨服务调用    ←  最复杂的聚合查询         ←  推理模型处理最难的任务
```

你的架构里，只有需要的请求才会打到数据库。同样，只有需要的 AI 调用才应该用最贵的模型。

### 什么任务用小模型就够

**分类任务**：判断用户消息的意图（问候/咨询/投诉/其他）

```typescript
import { openai } from '@ai-sdk/openai';

// 意图分类 -- GPT-5-mini 绰绰有余
const { output } = await generateText({
  model: openai('gpt-5-mini'), // 便宜够用
  output: Output.object({
    schema: z.object({
      intent: z.enum(['greeting', 'inquiry', 'complaint', 'feedback', 'other']),
      confidence: z.number().min(0).max(1),
    }),
  }),
  prompt: `分类用户意图：${userMessage}`,
});
```

**信息提取**：从文本中提取结构化信息（姓名、日期、地址等）

**格式转换**：把一种格式的数据转换成另一种格式

**简单翻译**：日常用语的翻译

**文本摘要**：短文本的简单摘要

### 什么任务必须上大模型

**复杂推理**：需要多步逻辑推理的任务（"分析这份财报，判断这家公司未来的发展趋势"）

**长文档理解**：需要理解和综合数万字文档内容的任务

**高精度工具调用**：Agent 的工具调用决策 -- 选错工具的代价很高

**创意生成**：需要高质量创意写作的任务

**模糊指令理解**：用户的指令不明确时，需要模型自己理解意图

### 判断标准

一个简单的经验法则：

```
如果一个普通大学生能在 30 秒内完成 → 小模型
如果一个普通大学生需要仔细思考 → 中等模型
如果需要领域专家才能做好 → 大模型
如果需要专家深思熟虑很长时间 → 推理模型
```

当然这只是经验法则。最终还是要用你的实际数据做测试。

## 6.5 多模型策略

### 一句话直觉

一个 Agent 不必绑定一个模型 -- 就像你的应用不必只用一种数据库。

### 前端类比

现代 Web 应用的数据层通常是多存储的：

```
Redis    -- 缓存、Session、排行榜
PostgreSQL -- 关系型业务数据
MongoDB    -- 文档型数据、日志
Elasticsearch -- 全文搜索
S3         -- 文件存储
```

每种存储解决不同的问题。AI Agent 也可以这样：

```
GPT-5-mini  -- 意图分类、简单提取
Claude Sonnet -- 长文档分析、代码生成
GPT-5       -- 复杂推理、关键决策
DeepSeek V4  -- 中文场景、性价比需求
```

下面介绍三种经典的多模型策略。

### 策略一：Router Pattern（路由模式）

**核心思想**：根据任务的特征，路由到最合适的模型。就像 Nginx 根据 URL 路径把请求路由到不同的后端服务。

```typescript
import { generateText, Output } from 'ai';
import { openai } from '@ai-sdk/openai';
import { anthropic } from '@ai-sdk/anthropic';
import { z } from 'zod';

// 第一步：用小模型做任务分类（成本极低）
async function classifyTask(userMessage: string) {
  const { output } = await generateText({
    model: openai('gpt-5-mini'), // 用最便宜的模型做分类
    output: Output.object({
      schema: z.object({
        complexity: z.enum(['simple', 'moderate', 'complex']),
        taskType: z.enum(['chat', 'analysis', 'coding', 'translation', 'creative']),
        estimatedTokens: z.number().describe('预估需要的输出 token 数'),
      }),
    }),
    prompt: `分析以下用户消息的任务复杂度和类型：\n${userMessage}`,
  });
  return output;
}

// 第二步：根据分类结果选择模型
function selectModel(classification: {
  complexity: string;
  taskType: string;
}) {
  const { complexity, taskType } = classification;

  // 简单任务 → 小模型
  if (complexity === 'simple') {
    return openai('gpt-5-mini');
  }

  // 编程任务 → Claude Sonnet（代码能力强）
  if (taskType === 'coding') {
    return anthropic('claude-sonnet-5');
  }

  // 长文档分析 → Claude Sonnet（长上下文好）
  if (taskType === 'analysis') {
    return anthropic('claude-sonnet-5');
  }

  // 复杂推理 → GPT-5
  if (complexity === 'complex') {
    return openai('gpt-5');
  }

  // 默认 → 中等选择
  return openai('gpt-5-mini');
}

// 完整的路由逻辑
async function routedGenerate(userMessage: string, systemPrompt: string) {
  const classification = await classifyTask(userMessage);
  const model = selectModel(classification);
  
  console.log(`任务分类: ${classification.complexity}/${classification.taskType}`);
  console.log(`选择模型: ${model.modelId}`);

  const { text } = await generateText({
    model,
    instructions: systemPrompt,
    prompt: userMessage,
  });

  return { text, model: model.modelId, classification };
}
```

**注意**：路由本身的 AI 调用也有成本和延迟。所以路由模型一定要用最便宜最快的（如 GPT-5-mini）。如果路由调用的成本和延迟超过了直接用大模型的节省，那路由就没意义了。

**经验法则**：如果你的任务中超过 50% 可以用小模型处理，Router Pattern 就值得做。

### 策略二：Fallback Pattern（降级模式）

**核心思想**：先用首选模型，如果失败了就降级到备用模型。就像你的前端应用有 fallback 机制 -- CDN 挂了走源站，主 API 挂了走备用 API。

```typescript
import { generateText } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';
import { openai } from '@ai-sdk/openai';
import { anthropic } from '@ai-sdk/anthropic';

interface ModelConfig {
  model: ReturnType<typeof openai>; // 简化类型
  name: string;
  timeout: number;
}

const modelChain: ModelConfig[] = [
  { model: openai('gpt-5'), name: 'GPT-5', timeout: 30000 },
  { model: anthropic('claude-sonnet-5'), name: 'Claude Sonnet', timeout: 30000 },
  { model: deepseek('deepseek-chat'), name: 'DeepSeek V4', timeout: 45000 },
];

async function generateWithFallback(
  prompt: string,
  systemPrompt?: string,
): Promise<{ text: string; model: string; attempts: number }> {
  let lastError: Error | null = null;

  for (let i = 0; i < modelChain.length; i++) {
    const { model, name, timeout } = modelChain[i];
    
    try {
      console.log(`尝试模型: ${name} (第${i + 1}次)`);
      
      const { text } = await generateText({
        model,
        instructions: systemPrompt,
        prompt,
        // 超时控制可以在调用层面做
        abortSignal: AbortSignal.timeout(timeout),
      });

      return { text, model: name, attempts: i + 1 };
    } catch (error) {
      lastError = error as Error;
      console.warn(`${name} 失败: ${lastError.message}`);
      
      // 如果是最后一个模型，不要继续了
      if (i === modelChain.length - 1) {
        throw new Error(
          `所有模型均失败。最后的错误: ${lastError.message}`
        );
      }
      
      // 等一小段时间再重试，避免连续打爆
      await new Promise(resolve => setTimeout(resolve, 1000));
    }
  }

  throw lastError; // 不应该到达这里，但 TypeScript 要求
}
```

**适用场景**：
- 对可用性要求极高的生产系统（SLA 99.9%+）
- 第三方 API 偶尔不稳定的情况
- 不同地区用户访问不同模型的延迟差异大

**注意事项**：
- 备用模型的能力可能不如主模型，要确保在降级时输出质量仍可接受
- 要记录降级事件，方便监控和分析
- 不同模型的 prompt 格式和行为可能有差异，确保你的 prompt 在所有候选模型上都能正常工作

### 策略三：Cascade Pattern（级联模式）

**核心思想**：先用小模型尝试，如果小模型"不确定"，再升级到大模型。就像医院的分诊 -- 普通感冒社区医院看就行，疑难杂症才需要转到三甲医院。

```typescript
import { generateText, Output } from 'ai';
import { openai } from '@ai-sdk/openai';
import { z } from 'zod';

// 统一的输出 schema，加上置信度字段
const AnalysisSchema = z.object({
  answer: z.string().describe('分析结果'),
  confidence: z.number().min(0).max(1).describe('对结果的置信度，0-1'),
  reasoning: z.string().describe('推理过程'),
});

async function cascadeAnalysis(prompt: string) {
  // 第一级：用小模型快速尝试
  const firstTry = await generateText({
    model: openai('gpt-5-mini'),
    output: Output.object({ schema: AnalysisSchema }),
    instructions: '请分析问题并给出你的置信度。如果你不确定，诚实地给出低置信度。',
    prompt,
  });

  console.log(`小模型置信度: ${firstTry.output.confidence}`);

  // 如果小模型有信心（置信度 > 0.8），直接返回
  if (firstTry.output.confidence > 0.8) {
    return {
      ...firstTry.output,
      modelUsed: 'gpt-5-mini',
      escalated: false,
    };
  }

  // 置信度不够，升级到大模型
  console.log('置信度不足，升级到 GPT-5...');
  
  const secondTry = await generateText({
    model: openai('gpt-5'),
    output: Output.object({ schema: AnalysisSchema }),
    instructions: `请仔细分析这个问题。
之前一个初步分析的结果是："${firstTry.output.answer}"（置信度：${firstTry.output.confidence}）。
请给出你的独立分析。`,
    prompt,
  });

  return {
    ...secondTry.output,
    modelUsed: 'gpt-5',
    escalated: true,
    initialAnalysis: firstTry.output,
  };
}
```

**这个模式的精妙之处在于：大部分请求（可能 60-80%）会在第一级就结束**，只有真正需要的请求才会消耗大模型的资源。

**前端类比**：这就像你做的渐进式图片加载 -- 先加载低分辨率的缩略图（快、便宜），如果用户要看大图再加载高分辨率的（慢、贵）。大部分用户可能根本不会点开大图。

**注意事项**：
- 置信度的阈值需要根据实际数据调优。设太高了所有请求都会升级，等于没用；设太低了可能漏掉需要大模型处理的请求
- AI 对自己的置信度评估不一定准确。有些模型会"过度自信"（明明不确定但给出高置信度），需要你做校准
- 可以参考第一级模型的回答来辅助第二级模型 -- 这叫"热启动"，通常能提升第二级的质量

### 三种策略对比

| 维度 | Router | Fallback | Cascade |
|------|--------|----------|---------|
| 核心目标 | 成本优化 | 可用性保证 | 质量+成本平衡 |
| 额外延迟 | 路由调用的延迟 | 失败后的重试延迟 | 升级时的二次调用 |
| 复杂度 | 中等 | 低 | 中等 |
| 最大收益场景 | 任务类型多样 | API 稳定性差 | 简单任务占比高 |

**实际生产中，这三种策略可以组合使用。** 比如：先用 Router 分流，Router 内部每条路径用 Fallback 保证可用性，在最热的路径上用 Cascade 优化成本。

## 6.6 Vercel AI SDK 中的多模型实现

### 一句话直觉

Vercel AI SDK 的 Provider 抽象让你切换模型就像切换 npm 包一样简单。

### Provider 机制

Vercel AI SDK 通过 Provider 模式抽象了不同模型提供商的差异。你用统一的 API 调用，底层走哪个提供商取决于你传入的 model 对象。

```typescript
import { generateText } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';
import { openai } from '@ai-sdk/openai';
import { anthropic } from '@ai-sdk/anthropic';

// 三个不同的 Provider，但使用完全相同的 API
async function compareModels(prompt: string) {
  const models = [
    { provider: openai('gpt-5'), name: 'GPT-5' },
    { provider: anthropic('claude-sonnet-5'), name: 'Claude Sonnet' },
    { provider: deepseek('deepseek-chat'), name: 'DeepSeek V4' },
  ];

  for (const { provider, name } of models) {
    const start = Date.now();
    const { text, usage } = await generateText({
      model: provider,  // 只有这一行不同
      prompt,
    });
    const elapsed = Date.now() - start;

    console.log(`[${name}] ${elapsed}ms | tokens: ${usage.totalTokens}`);
    console.log(text.slice(0, 200));
    console.log('---');
  }
}
```

**前端类比**：这就像前端的数据库 ORM（比如 Prisma）-- 你写一样的查询代码，底层可以是 PostgreSQL、MySQL 或 SQLite。Provider 就是 AI 世界的"数据库驱动"。

### 动态模型选择

```typescript

import { openai } from '@ai-sdk/openai';
import { anthropic } from '@ai-sdk/anthropic';

// 模型注册表
const MODEL_REGISTRY = {
  'fast-cheap': openai('gpt-5-mini'),
  'balanced': openai('gpt-5'),
  'long-context': anthropic('claude-sonnet-5'),
  'reasoning': anthropic('claude-opus-5'),
};

type ModelTier = keyof typeof MODEL_REGISTRY;

function getModel(tier: ModelTier) {
  return MODEL_REGISTRY[tier];
}

// 使用时

```

### 环境变量驱动的模型切换

在实际项目中，你可能希望通过环境变量来控制模型选择，不需要改代码就能切换：

```typescript
// config/models.ts
import { openai } from '@ai-sdk/openai';
import { anthropic } from '@ai-sdk/anthropic';
import { deepseek } from '@ai-sdk/deepseek';

// 环境变量里存字符串（"provider/modelId"，或 DeepSeek 的裸模型 ID），
// 这里把它解析成 v7 的 model 对象，再传给 generateText({ model })。
function createModelFromEnv(envKey: string, defaultModel: string) {
  const value = process.env[envKey] || defaultModel;
  const [provider, modelId] = value.split('/');

  switch (provider) {
    case 'openai':
      return openai(modelId);
    case 'anthropic':
      return anthropic(modelId);
    case 'deepseek':
      return deepseek(modelId);
    default:
      // 没有 provider 前缀时，默认按 DeepSeek 处理（如 deepseek-chat / deepseek-reasoner）
      return deepseek(value);
  }
}

export const models = {
  primary: createModelFromEnv('AI_PRIMARY_MODEL', 'openai/gpt-5'),
  fast: createModelFromEnv('AI_FAST_MODEL', 'deepseek-chat'),
  reasoning: createModelFromEnv('AI_REASONING_MODEL', 'deepseek-reasoner'),
};
```

```bash
# .env -- 开发环境
AI_PRIMARY_MODEL=deepseek-chat
AI_FAST_MODEL=deepseek-chat

# .env.production -- 生产环境
AI_PRIMARY_MODEL=openai/gpt-5
AI_FAST_MODEL=openai/gpt-5-mini
```

**前端类比**：这跟你用环境变量切换 API 地址一样 -- 开发环境打 localhost，生产环境打真实服务。

## 6.7 开源 vs 闭源模型

### 一句话直觉

闭源模型是"点外卖" -- 省事但贵且受制于人；开源模型是"自己做饭" -- 灵活但需要投入精力和设备。

### 详细对比

| 维度 | 闭源模型（GPT-5/Claude） | 开源模型（Llama/Qwen/Mistral） |
|------|------------------------|--------------------------|
| **上手难度** | 极低 -- 注册账号拿 API Key 就能用 | 需要部署基础设施（GPU 服务器） |
| **性能天花板** | 通常更高（训练资源更多） | 在追赶，某些场景已接近 |
| **成本结构** | 按量付费，用多少花多少 | 前期投入大（GPU），后续边际成本低 |
| **数据隐私** | 数据发送到第三方服务器 | 数据完全在自己的服务器上 |
| **定制性** | 有限（Fine-tuning 选项有限） | 完全可控（微调、量化、修改） |
| **可用性保证** | 依赖提供商（可能限流、涨价、停服） | 完全自控 |
| **更新迭代** | 提供商控制节奏 | 社区驱动，可自行选择版本 |

### 什么时候选哪个？

**选闭源 API 的场景**：
- 快速验证阶段 -- 你不确定 AI 功能是否可行，需要最快速度验证
- 团队没有 ML 基础设施经验 -- 部署和运维模型是一个完整的技术栈
- 调用量不大（每月百万 token 级别以下）-- 按量付费更划算
- 需要顶级能力 -- 目前闭源模型在最高难度任务上仍有优势

**选开源自部署的场景**：
- 数据隐私是硬性要求 -- 比如医疗、金融、政府等行业
- 调用量极大 -- 每月数十亿 token，自部署的边际成本远低于 API 调用
- 需要深度定制 -- 在你的专业领域数据上微调模型
- 不能依赖第三方 -- 业务不能因为 API 停服而停止

**混合方案（最常见）**：
- 开发阶段用闭源 API，快速迭代
- 生产环境的非敏感任务用闭源 API
- 敏感数据处理用开源自部署
- 核心业务逻辑用闭源 API 做主路径，开源模型做 fallback

## 6.8 模型更新和版本管理

### 一句话直觉

模型也会"升级"和"退役" -- 而升级不总是好事。

### 前端类比

这个问题和 npm 依赖管理简直一模一样：

```javascript
// package.json -- 你一定见过这种"惊喜"
{
  "dependencies": {
    "some-library": "^2.0.0"  // 你以为是 2.0.0，实际装了 2.3.0，然后某个功能就坏了
  }
}

// 解决方案
{
  "dependencies": {
    "some-library": "2.0.0"   // 锁定版本，或者用 package-lock.json
  }
}
```

AI 模型也有同样的问题。当 OpenAI 把 `gpt-5` 的底层版本从 `2026-06-01` 升级到 `2026-09-15` 时，你的 Agent 的行为可能会发生变化 -- 可能更好，也可能更差，但一定是"变了"。

### 版本管理策略

**策略一：锁定具体版本**

```typescript
import { openai } from '@ai-sdk/openai';

// 不要这样 -- 模型版本可能随时变化
const model = openai('gpt-5');

// 要这样 -- 锁定到具体的版本日期（如果提供商支持的话）
const model = openai('gpt-5-2026-09-15');
```

并非所有提供商都支持版本锁定，但 OpenAI 提供了带日期的模型 ID。使用带日期的版本号，就像在 package.json 中锁定依赖版本一样。

**策略二：用配置管理模型版本**

```typescript
// config/ai-models.ts
export const AI_MODELS = {
  // 用语义化的名字，映射到具体的模型版本
  primary: 'gpt-5-2026-09-15',
  fast: 'gpt-5-mini-2026-08-01',
  reasoning: 'gpt-5-2026-10-01',
  
  // 每次更新模型版本时，在这里记录
  // 2026-10-10: primary 从 gpt-5-2026-06-01 升级到 gpt-5-2026-09-15
  // 原因：新版本在结构化输出上更稳定
  // 回滚方案：改回 gpt-5-2026-06-01
} as const;
```

**策略三：灰度升级**

当你需要升级模型版本时，不要一刀切，可以先对一部分流量使用新版本：

```typescript
import { openai } from '@ai-sdk/openai';

function selectModelVersion(userId: string) {
  // 10% 的用户用新版本
  const hash = simpleHash(userId);
  if (hash % 100 < 10) {
    return openai('gpt-5-2026-09-15'); // 新版本
  }
  return openai('gpt-5-2026-06-01'); // 稳定版本
}
```

**前端类比**：这就是 A/B 测试 + Feature Flag -- 和你在前端做新功能灰度发布一样的套路。先给一小部分用户用，确认没问题再全量。

### 模型退役的应对

模型提供商会定期退役旧模型。比如 OpenAI 的 `gpt-4-0314` 已经被退役。你的代码如果硬编码了这个模型名，上线后就会直接报错。

**应对策略**：
1. 关注提供商的更新公告和退役时间表
2. 代码中的模型名通过配置管理，不要硬编码
3. 有 Fallback 机制，一个模型出问题能自动切换
4. 建立模型变更的测试流程 -- 每次换模型都要跑评估测试

## 概念辨析

### 模型能力 vs 模型大小

- 模型大小（参数量）只是影响能力的因素之一
- 小模型经过好的训练和优化，可能在特定任务上超过大模型
- 不要用"参数量"来判断模型好坏，用实际任务表现来判断

### 输入 Token vs 输出 Token 的成本差异

- 输入 Token 处理可以高度并行化，成本低
- 输出 Token 必须逐个生成，计算量大，成本高
- 因此优化 Agent 成本时，减少不必要的输出比减少输入更有效

### Context Window（上下文窗口）vs 有效利用长度

- 模型号称支持 128K 或 200K 的上下文窗口
- 但"支持"不等于"用满了效果还一样好"
- 大多数模型在接近上下文窗口上限时，对中间部分信息的理解会下降（"Lost in the Middle"现象）
- 实际使用建议控制在上下文窗口的 50-70% 以内

### API 调用 vs 自部署

- API 调用：简单、按量付费、受限于提供商
- 自部署：复杂、前期投入大、完全自控
- 两者不是非此即彼，混合使用是最常见的方案

## 灵魂拷问

> **Q1：DeepSeek V4 和 GPT-5 各自的优势和劣势是什么？为什么不存在"最好的模型"？**

A：这个问题的本质是理解模型之间的差异化。

**DeepSeek V4 的优势**：
- 价格极具竞争力（通常只有 GPT-5 的几分之一）
- 中文理解和生成能力出色
- 代码和数学推理能力强
- 开放权重，可自行部署

**DeepSeek V4 的劣势**：
- 非中英文语种的能力相对弱
- 工具调用（Function Calling）的稳定性还在迭代中
- 生态和文档相对 OpenAI 不够丰富

**GPT-5 的优势**：
- 综合能力最均衡
- 多语言能力最强
- 工具调用最稳定
- 文档和社区生态最完善
- 多模态能力（图片、语音）最成熟

**GPT-5 的劣势**：
- 价格高
- 在某些中文场景下不如专门优化过的模型
- 有时输出过于冗长

**为什么不存在"最好的模型"**：因为"好"是相对于具体任务而言的。模型的训练数据分布、优化目标、架构设计决定了它在不同任务上的表现。就像没有一种编程语言是"最好的" -- Python 做 ML 最好，JavaScript 做前端最好，Rust 做系统编程最好。

---

> **Q2：你的 Agent 每月调用 100 万次，选模型时怎么算成本？输入和输出哪个更贵？为什么？**

A：我们来做一个真实的成本计算。

假设每次调用平均 800 输入 token + 400 输出 token：

**GPT-5**：
```
输入: 1,000,000 × 800 = 8 亿 tokens → 800M × $2.5/1M = $2,000
输出: 1,000,000 × 400 = 4 亿 tokens → 400M × $10/1M = $4,000
月总计: $6,000（约 ￥42,000）
```

**GPT-5-mini**：
```
输入: 800M × $0.15/1M = $120
输出: 400M × $0.6/1M = $240
月总计: $360（约 ￥2,500）
```

**输出比输入贵的原因**：

这涉及 Transformer 架构的计算特性。处理输入时，所有 token 可以并行处理（一次前向传播），所以虽然 token 数量多，但摊到每个 token 上的计算成本不高。而输出时，每个 token 的生成都依赖于前面所有已生成的 token（自回归生成），必须逐个执行，无法并行。这导致输出的计算资源消耗远高于输入。

类比 -- 阅读一本书（输入）你可以快速扫读，但写一本书（输出）你必须一个字一个字写。

---

> **Q3：为什么说"先用最好的模型开发，再降级优化"是好策略？**

A：这个策略的智慧在于它解耦了两个问题：功能验证和成本优化。

**先用最好的模型开发**：
1. 排除模型能力不足的干扰 -- 如果 GPT-5 都做不好的任务，换 mini 只会更差
2. 建立质量基线 -- 你知道"最好能做到什么程度"
3. 快速验证产品逻辑 -- 不用纠结于模型选择，专注于业务逻辑
4. prompt engineering 更容易 -- 强模型对 prompt 的容错性更高

**再降级优化**：
1. 有了质量基线后，逐步尝试更便宜的模型
2. 对每个任务分别测试 -- 有些任务降级后质量不变，有些会明显下降
3. 找到每个任务的"性价比最优模型"

**前端类比**：这就像性能优化的铁律 -- "先让它工作，再让它快"（Make it work, then make it fast）。如果你一开始就为了省钱用最便宜的模型，结果 Agent 根本不能用，你分不清是模型的问题还是你的 prompt/架构的问题。

**反面教训**：我见过团队一开始就用最便宜的模型开发，花了两周调 prompt，效果始终不好。最后换了 GPT-5，发现 prompt 本身就有逻辑问题 -- 只是被强模型的容错性掩盖了。如果一开始就用好模型，可能第一天就发现了问题。

---

> **Q4：模型的 Benchmark 分数高就一定适合你的场景吗？**

A：绝对不是。Benchmark 和你的业务场景之间有几个关键的"认知鸿沟"。

**1. 分布不匹配**

MMLU 测试的是通识知识（历史、科学、法律等），而你可能需要的是"能准确提取中文电商评论中的情感倾向"。这两个任务的能力要求几乎没有交集。

**2. 格式不匹配**

Benchmark 通常是选择题或简短回答，而你的 Agent 需要的是长篇分析、工具调用、多轮对话。一个在选择题上表现很好的模型，不一定能稳定地做 Function Calling。

**3. 污染风险**

部分模型可能在训练数据中见过 benchmark 的题目，导致分数虚高。这在开源模型中尤其需要警惕。

**4. 任务特异性**

你的业务数据有自己的特点 -- 行业术语、表达习惯、隐含知识。没有任何 benchmark 能覆盖这些。

**正确的做法**：把 benchmark 当作初筛工具（淘汰明显不行的），但最终决策一定要基于你自己业务数据的测试结果。

---

> **Q5：开源模型自部署 vs 调用闭源 API，什么时候该选哪个？**

A：最核心的判断因素是三个：**数据敏感度、调用量级、团队能力**。

**数据敏感度**：如果你处理的数据涉及用户隐私（医疗记录、金融信息、个人身份信息），法规可能要求数据不能发送到第三方服务器。这时自部署是强制要求，不是可选项。

**调用量级**：有一个"成本交叉点"。API 按量付费，自部署有固定的 GPU 成本。假设一台 A100 服务器月租 $5,000，能承受每月约 5000 万 token 的推理量。如果你的调用量超过这个数字，自部署的单位成本就低于 API 调用了。

粗略计算：
```
API 成本: 50M tokens × $2.5/1M (GPT-5) = $125（输入部分）
自部署: 一台 A100 的月租 ≈ $5,000

交叉点大约在每月 20 亿+ token（GPT-5 级别的模型）
```

但这个计算要考虑很多因素：自部署的运维人力、可用性保证、模型更新升级等隐性成本。

**团队能力**：自部署需要 ML 运维能力 -- GPU 管理、模型量化、推理优化、服务化部署。如果你的团队是前端团队，这些能力需要时间建设。

**我的建议**：大部分团队应该先用 API，等到以下任何一个条件满足时再考虑自部署：
1. 数据隐私有法规要求
2. 月 token 消耗超过数十亿
3. 团队已经有 ML 基础设施经验

---

> **Q6：如果 OpenAI 明天涨价 10 倍，你的 Agent 怎么办？多模型策略如何对冲这个风险？**

A：这不是假设 -- 这是真实的商业风险。AI 模型的定价权完全在提供商手中，你的业务不应该被单一提供商绑架。

**多模型策略的对冲价值**：

1. **代码层面的抽象**：使用 Vercel AI SDK 的 Provider 抽象，切换模型只需改一行配置。如果你直接调用 OpenAI 的原生 API，切换成本就大得多了。

2. **Fallback 保底**：即使不做成本优化，也应该有备选模型。这样任何一家涨价或停服，你都有退路。

3. **多提供商分散风险**：核心业务不依赖单一提供商。比如用 OpenAI 做主力，用 Claude 做备用，用 DeepSeek 做成本敏感的任务。

4. **提前评估替代模型**：定期用你的评估测试集测试新出的模型。这样当你需要切换时，已经有数据支撑决策。

**具体应对方案**：

```typescript
import { openai } from '@ai-sdk/openai';
import { anthropic } from '@ai-sdk/anthropic';
import { deepseek } from '@ai-sdk/deepseek';

// 通过配置快速切换
const MODEL_CONFIG = {
  // 正常情况
  default: {
    primary: openai('gpt-5'),
    fast: openai('gpt-5-mini'),
  },
  // 应急方案 -- OpenAI 涨价/不可用时
  emergency: {
    primary: anthropic('claude-sonnet-5'),
    fast: deepseek('deepseek-chat'),
  },
};

// 通过环境变量或远程配置切换
const activeConfig = process.env.AI_MODE === 'emergency'
  ? MODEL_CONFIG.emergency
  : MODEL_CONFIG.default;
```

**前端类比**：这跟你做 CDN 多活一样 -- 不会只用一个 CDN 提供商，至少有一个备用。不是因为你预期 CDN 会挂，而是因为"万一挂了"的后果你承受不起。

> **Q7：先选模型还是先写 Prompt？模型和 Prompt 之间是什么关系？**

A：这是一个鸡生蛋的问题，但有一个实用的答案。

**先用最强的模型把 Prompt 写好，再降级模型优化成本。**

原因在于：强模型对 Prompt 的容错性高。如果你在弱模型上写 Prompt，你不知道效果不好是因为 Prompt 的问题还是模型的问题。用强模型相当于消除了一个变量。

一旦 Prompt 在强模型上效果好了，再换到弱模型上测试。如果效果明显变差，有两条路：
1. 优化 Prompt 以适配弱模型（加更多 Few-shot 示例、更详细的指令）
2. 接受这个任务必须用强模型

**模型和 Prompt 的关系**是互补的：
- 强模型 + 简单 Prompt = 通常效果不错
- 弱模型 + 精心调优的 Prompt = 可能效果也不错
- 强模型 + 精心调优的 Prompt = 最佳效果
- 弱模型 + 简单 Prompt = 效果最差

你的优化策略应该是：先达到第三种状态（验证功能可行性），再尝试降级到第二种状态（优化成本）。

## 最佳实践

### DO

- **DO 用 Vercel AI SDK 的 Provider 抽象层**。直接调用提供商原生 API 会增加切换成本。统一的抽象让你能随时换模型。

- **DO 从一开始就做成本监控**。记录每次 API 调用的 token 消耗和成本。等到月底看账单才发现成本超标就太晚了。

- **DO 对不同的任务使用不同的模型**。意图分类用 mini，复杂推理用旗舰级模型，长文档用 Claude。一个 Agent 用多个模型是正常的。

- **DO 定期评估新模型**。AI 模型迭代很快，三个月前的最佳选择现在可能已经不是了。

- **DO 先用最好的模型开发**。等功能验证通过后再做成本优化。别一开始就为了省钱选弱模型，会浪费更多的时间在调试上。

- **DO 有至少一个备用模型**。不管是为了应对涨价、停服还是性能下降，备用方案是必须的。

### DON'T

- **DON'T 只看 Benchmark 分数选模型**。Benchmark 是参考，不是答案。用你自己的业务数据做评估。

- **DON'T 忽视输出 Token 的成本**。输出 Token 通常比输入贵 2-4 倍。让 AI 少说废话，能省不少钱。

- **DON'T 过早做模型优化**。在功能还没验证可行的阶段，不要花时间在"选最便宜的模型"上。先让它 work。

- **DON'T 假设模型永远不变**。模型会升级、会退役、会涨价。你的架构要能应对这些变化。

- **DON'T 把所有鸡蛋放在一个篮子里**。100% 依赖单一模型提供商是一种技术债。

- **DON'T 忽视延迟**。用户体验中，速度也是"质量"的一部分。一个回答完美但等 10 秒的 Agent，不如一个回答略逊但 2 秒就响应的 Agent。

### 实战1：智能模型路由器

为"AI 智能工作助手"实现一个完整的模型路由系统：

```typescript
// lib/model-router.ts
import { generateText, Output } from 'ai';
import { openai } from '@ai-sdk/openai';
import { anthropic } from '@ai-sdk/anthropic';
import { z } from 'zod';

// ---- 模型注册表 ----
const MODELS = {
  // 极速经济型：简单分类、提取
  mini: openai('gpt-5-mini'),
  // 平衡型：一般对话、常规分析
  standard: openai('gpt-5'),
  // 长文本专家：长文档、代码
  longContext: anthropic('claude-sonnet-5'),
  // 深度推理：复杂逻辑
  reasoning: anthropic('claude-opus-5'),
};

type ModelTier = keyof typeof MODELS;

// ---- 任务分析 Schema ----
const TaskAnalysisSchema = z.object({
  complexity: z.enum(['trivial', 'simple', 'moderate', 'complex']).describe(
    'trivial=一句话能答的、simple=简单任务、moderate=需要思考、complex=需要深度推理'
  ),
  taskType: z.enum([
    'greeting',       // 打招呼
    'factual_qa',     // 事实性问答
    'classification', // 分类
    'extraction',     // 信息提取
    'analysis',       // 分析
    'reasoning',      // 推理
    'creative',       // 创意写作
    'coding',         // 代码相关
    'translation',    // 翻译
  ]).describe('任务类型'),
  requiresLongContext: z.boolean().describe('是否需要处理超长文本（>2000字）'),
  estimatedOutputLength: z.enum(['short', 'medium', 'long']).describe(
    'short=一句话、medium=一段话、long=多段'
  ),
});

type TaskAnalysis = z.infer<typeof TaskAnalysisSchema>;

// ---- 路由逻辑 ----
function routeToModel(analysis: TaskAnalysis): ModelTier {
  const { complexity, taskType, requiresLongContext } = analysis;

  // 规则1：长文本场景优先用长上下文模型
  if (requiresLongContext) return 'longContext';

  // 规则2：极简任务用 mini
  if (complexity === 'trivial') return 'mini';

  // 规则3：复杂推理用推理模型
  if (complexity === 'complex' && (taskType === 'reasoning' || taskType === 'analysis')) {
    return 'reasoning';
  }

  // 规则4：简单任务用 mini
  if (complexity === 'simple' && ['greeting', 'factual_qa', 'classification', 'extraction', 'translation'].includes(taskType)) {
    return 'mini';
  }

  // 规则5：编码任务用长上下文模型（Claude 代码能力强）
  if (taskType === 'coding') return 'longContext';

  // 默认：standard
  return 'standard';
}

// ---- 完整的路由函数 ----
export async function smartRoute(userMessage: string): Promise<{
  model: (typeof MODELS)[ModelTier];
  modelTier: ModelTier;
  analysis: TaskAnalysis;
}> {
  // 用最便宜的模型做路由分析
  const { output: analysis } = await generateText({
    model: MODELS.mini,
    output: Output.object({ schema: TaskAnalysisSchema }),
    prompt: `分析以下用户消息的任务特征：\n\n${userMessage}`,
  });

  const modelTier = routeToModel(analysis);
  
  return {
    model: MODELS[modelTier],
    modelTier,
    analysis,
  };
}

// ---- 成本追踪 ----
interface CostRecord {
  timestamp: Date;
  modelTier: ModelTier;
  inputTokens: number;
  outputTokens: number;
  estimatedCost: number;
}

// 每百万 token 的价格（美元），简化版
const PRICING: Record<ModelTier, { input: number; output: number }> = {
  mini: { input: 0.15, output: 0.6 },
  standard: { input: 1.25, output: 10 },
  longContext: { input: 3, output: 15 },
  reasoning: { input: 1.1, output: 4.4 },
};

export function calculateCost(
  modelTier: ModelTier,
  inputTokens: number,
  outputTokens: number
): number {
  const pricing = PRICING[modelTier];
  return (inputTokens * pricing.input + outputTokens * pricing.output) / 1_000_000;
}

// ---- 使用示例 ----
async function handleUserMessage(message: string) {
  const { model, modelTier, analysis } = await smartRoute(message);
  
  console.log(`[路由] 复杂度=${analysis.complexity}, 类型=${analysis.taskType} → ${modelTier}`);

  const startTime = Date.now();
  const { text, usage } = await import('ai').then(ai => 
    ai.generateText({
      model,
      prompt: message,
    })
  );
  const elapsed = Date.now() - startTime;

  const cost = calculateCost(modelTier, usage.inputTokens, usage.outputTokens);
  
  console.log(`[性能] ${elapsed}ms | tokens: ${usage.totalTokens} | 成本: $${cost.toFixed(6)}`);

  return { text, modelTier, analysis, cost, elapsed };
}
```

### 实战2：带 Fallback 的多模型客户端

```typescript
// lib/resilient-ai.ts
import { generateText, Output } from 'ai';
import { openai } from '@ai-sdk/openai';
import { anthropic } from '@ai-sdk/anthropic';

interface ModelOption {
  model: LanguageModel;
  name: string;
  priority: number; // 优先级，数字越小优先级越高
}

interface ResilientAIConfig {
  models: ModelOption[];
  maxRetries: number;
  retryDelay: number; // 重试间隔，毫秒
  timeout: number;    // 单次调用超时，毫秒
}

export function createResilientAI(config: ResilientAIConfig) {
  const sortedModels = [...config.models].sort((a, b) => a.priority - b.priority);

  // 健康状态追踪
  const healthStatus = new Map<string, {
    failCount: number;
    lastFailTime: number;
    isCircuitOpen: boolean; // 熔断器
  }>();

  function getHealth(modelName: string) {
    if (!healthStatus.has(modelName)) {
      healthStatus.set(modelName, {
        failCount: 0,
        lastFailTime: 0,
        isCircuitOpen: false,
      });
    }
    return healthStatus.get(modelName)!;
  }

  function recordSuccess(modelName: string) {
    const health = getHealth(modelName);
    health.failCount = 0;
    health.isCircuitOpen = false;
  }

  function recordFailure(modelName: string) {
    const health = getHealth(modelName);
    health.failCount++;
    health.lastFailTime = Date.now();
    
    // 连续失败 3 次，打开熔断器
    if (health.failCount >= 3) {
      health.isCircuitOpen = true;
      console.warn(`[熔断] ${modelName} 已熔断，30秒后重试`);
    }
  }

  function isAvailable(modelName: string): boolean {
    const health = getHealth(modelName);
    if (!health.isCircuitOpen) return true;
    
    // 熔断 30 秒后允许一次探测
    if (Date.now() - health.lastFailTime > 30000) {
      health.isCircuitOpen = false;
      health.failCount = 0;
      return true;
    }
    return false;
  }

  return {
    async generateText(options: Omit<Parameters<typeof generateText>[0], 'model'>) {
      const availableModels = sortedModels.filter(m => isAvailable(m.name));
      
      if (availableModels.length === 0) {
        throw new Error('所有模型均不可用（熔断中）');
      }

      let lastError: Error | null = null;

      for (const { model, name } of availableModels) {
        try {
          const result = await generateText({
            ...options,
            model,
            abortSignal: AbortSignal.timeout(config.timeout),
          });
          
          recordSuccess(name);
          return { ...result, modelUsed: name };
        } catch (error) {
          lastError = error as Error;
          recordFailure(name);
          console.warn(`[Fallback] ${name} 失败: ${lastError.message}`);
          
          await new Promise(r => setTimeout(r, config.retryDelay));
        }
      }

      throw new Error(`所有模型均失败: ${lastError?.message}`);
    },

    // 健康状态查看
    getHealthReport() {
      const report: Record<string, any> = {};
      for (const { name } of sortedModels) {
        const health = getHealth(name);
        report[name] = {
          status: health.isCircuitOpen ? 'circuit_open' : 'healthy',
          failCount: health.failCount,
          lastFailTime: health.lastFailTime
            ? new Date(health.lastFailTime).toISOString()
            : 'never',
        };
      }
      return report;
    },
  };
}

// ---- 使用 ----
const ai = createResilientAI({
  models: [
    { model: openai('gpt-5'), name: 'GPT-5', priority: 1 },
    { model: anthropic('claude-sonnet-5'), name: 'Claude Sonnet', priority: 2 },
    { model: openai('gpt-5-mini'), name: 'GPT-5-mini', priority: 3 },
  ],
  maxRetries: 3,
  retryDelay: 1000,
  timeout: 30000,
});

// 使用方式和普通的 generateText 一样
const { text, modelUsed } = await ai.generateText({
  prompt: '解释一下什么是 React Server Components',
});

console.log(`使用模型: ${modelUsed}`);
console.log(text);

// 查看健康状态
console.log(ai.getHealthReport());
```

### 实战3：成本报告看板

```typescript
// lib/cost-tracker.ts

interface UsageRecord {
  timestamp: Date;
  model: string;
  inputTokens: number;
  outputTokens: number;
  cost: number;
  taskType: string;
  latencyMs: number;
}

class CostTracker {
  private records: UsageRecord[] = [];

  record(usage: UsageRecord) {
    this.records.push(usage);
  }

  // 按模型汇总
  getSummaryByModel(): Record<string, {
    calls: number;
    totalInputTokens: number;
    totalOutputTokens: number;
    totalCost: number;
    avgLatencyMs: number;
  }> {
    const summary: Record<string, any> = {};
    
    for (const record of this.records) {
      if (!summary[record.model]) {
        summary[record.model] = {
          calls: 0,
          totalInputTokens: 0,
          totalOutputTokens: 0,
          totalCost: 0,
          totalLatency: 0,
        };
      }
      const s = summary[record.model];
      s.calls++;
      s.totalInputTokens += record.inputTokens;
      s.totalOutputTokens += record.outputTokens;
      s.totalCost += record.cost;
      s.totalLatency += record.latencyMs;
    }

    // 计算平均延迟
    for (const model of Object.keys(summary)) {
      summary[model].avgLatencyMs = Math.round(
        summary[model].totalLatency / summary[model].calls
      );
      delete summary[model].totalLatency;
    }

    return summary;
  }

  // 成本趋势（按天）
  getDailyTrend(): Record<string, number> {
    const trend: Record<string, number> = {};
    
    for (const record of this.records) {
      const day = record.timestamp.toISOString().split('T')[0];
      trend[day] = (trend[day] || 0) + record.cost;
    }

    return trend;
  }

  // 生成可读的报告
  generateReport(): string {
    const summary = this.getSummaryByModel();
    const totalCost = Object.values(summary).reduce((sum, s) => sum + s.totalCost, 0);
    const totalCalls = Object.values(summary).reduce((sum, s) => sum + s.calls, 0);

    let report = `=== AI 成本报告 ===\n`;
    report += `总调用次数: ${totalCalls}\n`;
    report += `总成本: $${totalCost.toFixed(4)}\n`;
    report += `\n--- 按模型分布 ---\n`;

    for (const [model, stats] of Object.entries(summary)) {
      const costPercentage = ((stats.totalCost / totalCost) * 100).toFixed(1);
      report += `\n${model}:\n`;
      report += `  调用次数: ${stats.calls} (${((stats.calls / totalCalls) * 100).toFixed(1)}%)\n`;
      report += `  总成本: $${stats.totalCost.toFixed(4)} (${costPercentage}%)\n`;
      report += `  平均延迟: ${stats.avgLatencyMs}ms\n`;
      report += `  平均每次成本: $${(stats.totalCost / stats.calls).toFixed(6)}\n`;
    }

    // 优化建议
    report += `\n--- 优化建议 ---\n`;
    for (const [model, stats] of Object.entries(summary)) {
      if (model.includes('gpt-5') && !model.includes('mini') && stats.calls > 100) {
        report += `* ${model} 调用 ${stats.calls} 次，考虑将简单任务降级到 mini 版本\n`;
      }
    }

    return report;
  }
}

export const costTracker = new CostTracker();

// 使用示例 -- 在每次 AI 调用后记录
import { generateText } from 'ai';

async function trackedGenerate(options: Parameters<typeof generateText>[0] & { taskType?: string }) {
  const startTime = Date.now();
  const result = await generateText(options);
  const elapsed = Date.now() - startTime;

  const modelId = typeof options.model === 'object' && 'modelId' in options.model
    ? (options.model as any).modelId
    : 'unknown';

  costTracker.record({
    timestamp: new Date(),
    model: modelId,
    inputTokens: result.usage.inputTokens,
    outputTokens: result.usage.outputTokens,
    cost: calculateCost(modelId, result.usage.inputTokens, result.usage.outputTokens),
    taskType: options.taskType || 'unknown',
    latencyMs: elapsed,
  });

  return result;
}

function calculateCost(model: string, inputTokens: number, outputTokens: number): number {
  const pricing: Record<string, { input: number; output: number }> = {
    'gpt-5': { input: 1.25, output: 10 },
    'gpt-5-mini': { input: 0.15, output: 0.6 },
    'claude-sonnet-5': { input: 3, output: 15 },
  };
  
  const p = pricing[model] || { input: 1, output: 3 };
  return (inputTokens * p.input + outputTokens * p.output) / 1_000_000;
}
```

## 实操练习

### 目标

为"AI 智能工作助手"添加智能模型切换能力。简单问题用小模型快速响应，复杂问题自动升级到大模型。

### 步骤

**Step 1：实现模型路由器**

创建一个 `ModelRouter` 类，能根据用户消息的特征自动选择模型。路由本身要用最便宜的模型。

**Step 2：实现 Fallback 机制**

当主选模型不可用时，自动降级到备用模型。实现简单的熔断器逻辑。

**Step 3：添加成本追踪**

记录每次调用的模型、token 消耗和成本。能生成简单的成本报告。

**Step 4：配置化管理**

模型选择通过环境变量或配置文件控制，支持不改代码切换模型。

**Step 5：集成到助手**

把模型路由集成到之前的聊天助手中，让用户感知不到模型切换，但能在后台看到路由决策和成本数据。

### 验收标准

- [ ] 简单问题（打招呼、简单翻译）自动路由到小模型
- [ ] 复杂问题（分析、推理）自动路由到大模型
- [ ] 主模型不可用时能自动 Fallback
- [ ] 能输出成本报告（每个模型的调用次数和成本）
- [ ] 模型切换对用户透明（用户不需要手动选模型）

### 挑战加分项

- [ ] 实现 Cascade Pattern：先用小模型回答，如果置信度低则自动升级
- [ ] 实现灰度发布：通过用户 ID 控制一部分用户使用新模型版本
- [ ] 成本预警：当日成本超过阈值时发出告警
- [ ] A/B 测试框架：同一个问题随机用不同模型回答，记录用户满意度
- [ ] 可视化看板：用 React 组件展示模型路由分布和成本趋势图

## 本章小结

本章回答了"面对几十种 AI 模型，怎么选、怎么用"这个关键问题。

**核心要点**：

1. **没有"最好的模型"**。每个模型有自己的优势场景。选型的标准不是 benchmark 分数最高，而是在你的实际任务上表现最好。

2. **成本是真实的工程约束**。输出 token 比输入贵 2-4 倍，对话历史会导致成本累积膨胀。从第一天就要建立成本意识。

3. **多模型是架构，不是锦上添花**。Router（成本优化）、Fallback（可用性保障）、Cascade（质量+成本平衡）三种模式解决不同的问题，实际中可以组合使用。

4. **先用最好的模型开发，再降级优化**。这是最高效的开发策略。解耦功能验证和成本优化。

5. **不要被单一提供商绑架**。用 SDK 抽象层、配置化模型管理、Fallback 机制来保持灵活性。AI 模型市场变化极快，你的架构要能适应。

6. **模型版本管理和前端依赖管理异曲同工**。锁定版本、灰度升级、退役应对 -- 套路是一样的。

**一句话总结**：选模型就像选技术栈 -- 不选最贵的，选最合适的。而"最合适"不是拍脑袋决定的，是用数据测出来的。

下一章，我们进入 Agent 开发最激动人心的部分 -- **Function Calling**。AI 不再只是"说"，而是可以"做"了。它可以调用你定义的函数，查天气、查数据库、发邮件。这是 Agent 从"聊天机器人"进化为"智能助手"的关键一步。
