# 第1章：AI 与大语言模型基础

## 引言

想象一下这个场景：你团队新来了一个实习生，这个实习生非常特别——他读过几乎整个互联网上的文字内容，从 Stack Overflow 的每一个回答、到 GitHub 上的海量代码、到维基百科的每一篇文章、到无数本书籍和论文。他的知识储备堪称恐怖。

但你很快发现这个实习生有些奇怪的毛病：

- 你问他"今天天气怎么样"，他可能一本正经地给你编一个天气预报
- 你让他算 17 x 24，他偶尔会算错
- 他的知识停留在某个时间点，之后的事一概不知
- 如果你的问题不够明确，他会按自己的"理解"自由发挥，有时候发挥得让你哭笑不得
- 但如果你把需求说清楚了，他的产出质量往往能超出你的预期

这个"超级实习生"就是大语言模型（Large Language Model, LLM）。

作为前端开发者，你可能已经用过 ChatGPT 或者 Claude 来帮你写代码、查 bug。但要在工作中真正落地 AI Agent 功能，光会"对话"远远不够——你需要理解它的底层逻辑，知道它为什么能做到某些事，又为什么会在某些地方翻车。

这一章，我们不讲数学公式，不搞学术黑话，而是用你作为前端开发者最熟悉的概念，帮你建立起对 LLM 的系统认知。这些认知会直接影响你后面写 Agent 代码时的每一个设计决策。

## 1.1 什么是大语言模型（LLM）

### 直觉理解

大语言模型，用一句话说：**它是一个"下一个词预测器"，但因为这件事做到了极致，所以涌现出了看起来像"智能"的能力。**

别小看"预测下一个词"这件事。当你输入"中国的首都是"，它预测下一个词是"北京"——这需要的不只是记忆，还需要理解"首都"这个概念、"中国"和"北京"之间的关系。当预测能力强大到一定程度，模型就能写文章、写代码、做翻译、做推理。

### 前端类比

你可以把 LLM 类比为一个**极其强大的自动补全引擎**。

你用 VS Code 写代码时，按下 Tab 键，IDE 会帮你补全代码。这个补全是基于语法规则和上下文分析的。而 LLM 做的事情本质上一样——只不过它的"上下文"是你给它的所有输入文字，它的"语法规则"是从海量文本中学到的语言规律，它补全的不是一个变量名，而是整段整段的文字。

再往深里想：React 中的 `useMemo` 会基于依赖数组缓存计算结果。LLM 也类似——它基于你给它的输入（依赖），通过内部的"计算"（参数运算），生成输出（返回值）。但不同的是，LLM 的"计算"是统计学意义上的，不是确定性的逻辑运算。这一点极其重要，后面我们会反复提到。

### 深入原理

LLM 的核心架构叫 **Transformer**（2017 年 Google 提出的论文 "Attention Is All You Need"）。你不需要理解 Transformer 的数学细节，但需要理解几个关键直觉：

**1. 自注意力机制（Self-Attention）**

这是 Transformer 最核心的创新。简单说，当模型处理一个句子时，每个词都会"看看"句子里其他所有词，判断哪些词对理解自己最重要。

举个例子："小明把苹果给了小红，因为**她**饿了。"

当模型处理"她"这个字时，自注意力机制会让它"注意"到"小红"这个词——因为在这个语境下，"她"指代的是"小红"。这种注意力权重是通过训练自动学会的。

用前端的话说，自注意力像是一个**动态的事件委托系统**。普通事件只监听一个目标，而自注意力让每个元素都能"感知"页面上其他所有元素的状态，并根据重要程度加权处理。

**2. 预训练 + 微调的两阶段模式**

LLM 的训练分两大阶段：

- **预训练（Pre-training）**：在海量文本上做"下一个词预测"任务。这个阶段让模型学会了语言本身的规律——语法、语义、常识、推理模式。这个阶段消耗的算力是天文数字，普通公司根本做不起。
- **微调（Fine-tuning）/ 对齐（Alignment）**：在预训练的基础上，用人类标注的高质量数据教模型"怎么做一个有用的助手"。比如 RLHF（基于人类反馈的强化学习）就是让人类评价模型的回答好不好，模型根据这些反馈调整自己。

这很像前端的**框架 vs 业务代码**的关系。React 框架本身（预训练）提供了通用的 UI 渲染能力，而你写的业务组件（微调）让它变成了具体的产品。

**3. 涌现能力（Emergent Abilities）**

这是 LLM 最让人兴奋也最让人困惑的特性。当模型参数量达到某个临界点，会突然出现训练过程中没有明确教过的能力。比如没有人教 GPT-3 做算术，但当它够大的时候，它自己"学会"了简单的数学运算。

这就像你往一个容器里不断加水，在某个临界点水会突然溢出。这些涌现能力无法被精确预测，也是为什么 AI 领域的进展经常让人感到惊讶。

### 深层追问

**为什么"下一个词预测"这么简单的任务能产生"智能"？**

我认为这里有一个深刻的洞见：**当你要在任意语境下准确预测下一个词时，你必须理解世界是怎么运作的。**

要预测"如果你把一个玻璃杯从桌子上推下去，它会___"后面的词，模型必须"理解"重力、玻璃的脆弱性、"推"这个动作的物理含义。虽然模型并不真的"理解"物理，但它的内部表征方式足够强大，能够在统计意义上捕捉到这些关系。

这个问题目前学术界还有激烈争论——LLM 到底是真的"理解"了，还是只是"看起来像理解"？实践中的态度是：**别纠结哲学问题，关注它能不能可靠地完成你需要的任务。**

## 1.2 Token：AI 世界的基本单位

### 直觉理解

**Token 是 LLM 处理文字的最小单位，它不是字符，也不是单词，而是介于两者之间的"语言碎片"。**

你给 LLM 的每一段文字，都会先被一个叫 **Tokenizer（分词器）** 的程序切成一个个 token。模型处理的是 token 序列，而不是字符序列。

### 前端类比

这个类比特别贴切：**Token 之于自然语言，就像虚拟 DOM 节点之于真实 DOM。**

在 React 中，你写的 JSX 不会直接操作浏览器的 DOM。React 会先把你的 JSX 转成虚拟 DOM 树（一种中间表示），然后通过 diff 算法高效地更新真实 DOM。

类似地，LLM 不直接处理你写的原始文字。Tokenizer 会先把文字转成 token 序列（一种中间表示），模型在 token 空间里做计算，最后再把 token 序列转回文字。

就像你不理解虚拟 DOM 就很难优化 React 性能一样，不理解 token 就很难理解 LLM 的成本和限制。

### 深入原理

**BPE（Byte Pair Encoding）算法**

主流 LLM 使用的分词算法叫 BPE（字节对编码），它的原理其实很直觉：

1. 从最小单位开始——每个字节就是一个 token
2. 统计训练文本中，哪两个相邻的 token 最常一起出现
3. 把这对 token 合并成一个新 token
4. 重复步骤 2-3，直到 token 词汇表达到预设大小（通常 32K-100K 个）

比如，英语中 "th" 出现的频率极高，所以 "t" 和 "h" 很早就会被合并成 "th" 这个 token。接着 "th" 和 "e" 可能合并成 "the"。最终，像 "the"、"ing"、"tion" 这样的常见片段都会变成单个 token。

**中英文 Token 效率的巨大差异**

这里有一个对前端开发者来说非常实际的问题：**同样的语义内容，中文消耗的 token 数量通常是英文的 1.5-2 倍。**

为什么？因为主流 LLM 的 tokenizer 是在以英文为主的语料上训练的。英文中的常见词（the、is、have）通常是 1 个 token，而中文的每个汉字通常需要 1-2 个 token，有些生僻字甚至需要 3 个 token。

举个实际的例子：

```
英文: "Hello, how are you?" → 大约 6 个 token
中文: "你好，你最近怎么样？" → 大约 9-11 个 token
```

两句话表达的意思一样，但中文版本消耗的 token 几乎翻倍。这直接影响两件事：

1. **成本**：API 调用按 token 计费，中文场景的成本天然更高
2. **上下文利用率**：同样的上下文窗口，中文能装下的信息量更少

实践中的建议是：system prompt 尽量用英文写（反正用户看不到），可以节省不少 token。当然，如果你的模型对中文 prompt 的响应质量明显更好，那就别省这个钱。

**Token 与计费的关系**

几乎所有 LLM API 都按 token 数量计费，通常分为：
- **输入 token（Prompt tokens）**：你发给模型的内容，包括 system prompt、历史对话、当前用户输入
- **输出 token（Completion tokens）**：模型生成的回复

一个关键事实：**输出 token 的价格通常是输入 token 的 2-5 倍。** 为什么？因为生成每个输出 token 需要的计算量远大于处理每个输入 token。输入 token 可以并行处理，而输出 token 必须一个接一个地生成（自回归特性）。

用前端的话说，这就像 SSR（服务端渲染）比 SSG（静态生成）贵，因为 SSR 需要实时计算，而 SSG 的计算是提前完成的。

### 实际应用场景

在你后面开发 AI Agent 时，token 的理解会直接影响这些决策：

- **控制成本**：一个客服 Agent 如果每次都把完整的对话历史发给模型，token 消耗会呈指数增长。你需要设计"记忆管理"策略。
- **Prompt 优化**：精炼你的 system prompt，去掉废话，用英文写不面向用户的指令。
- **选择模型**：有些模型按 token 计费更便宜，但响应质量可能下降。你需要在成本和质量之间找到平衡点。

## 1.3 模型参数量：7B / 13B / 70B / 671B 到底意味着什么

### 直觉理解

**参数量就是模型的"大脑容量"——参数越多，模型能存储的知识和模式就越多，但运行起来也越慢、越贵。**

当你看到 "LLaMA-70B" 这样的名字，70B 的意思是这个模型有 700 亿个参数。每个参数都是一个浮点数，你可以粗略理解为模型从训练数据中提炼出来的 700 亿个"经验值"。

### 前端类比

**参数量之于模型，就像 bundle size 之于前端应用。**

你打包一个 React 项目，bundle 可能是 200KB（小型应用）、2MB（中型应用）、20MB（大型 SPA）。bundle 越大，通常意味着功能越多、依赖越全——但也意味着加载更慢、内存占用更大。

而且你一定知道，bundle 大不一定代表应用好。一个 200KB 的精心优化过的应用可能比一个 20MB 的臃肿应用体验更好。LLM 也是同样的道理：**参数量大不代表效果好。**

### 深入原理

**参数量的数量级对比**

| 参数量级 | 代表模型 | 典型用途 | 硬件需求 |
|---------|---------|---------|---------|
| 1-4B | Qwen3-1.7B, Gemma-3 | 简单任务、端侧部署 | 手机/笔记本 |
| 7-8B | Llama-3.1-8B, Qwen3-8B | 通用对话、代码辅助 | 单张消费级 GPU |
| 14-32B | Llama-4-Scout-17B, Qwen3-32B | 复杂推理、专业任务 | 单张高端 GPU |
| 70-72B | Llama-3.3-70B, Qwen3-72B | 接近商用大模型能力 | 多张 GPU |
| 200B+（含 MoE 旗舰） | GPT-6, Claude 4/5, DeepSeek-V4, Gemini 3 | 最强综合能力 | 集群级算力 |

**为什么 bigger 不一定 better？**

这里有几个关键因素：

1. **训练数据质量 > 参数量**：一个在高质量数据上训练的 7B 模型，在特定任务上可能吊打在低质量数据上训练的 70B 模型。这就像一个写了 5 年 React 的工程师和一个写了 10 年 jQuery 的工程师——经验多不代表技术好，要看学的是什么。

2. **训练充分度**：根据 Chinchilla 论文的发现，模型需要和参数量匹配的训练数据。一个 70B 模型如果训练数据不够多，效果可能还不如充分训练的 7B 模型。这就像你给一个巨大的 React 组件树只传了一半 props——组件能力是有了，但数据不足导致渲染不出该有的内容。

3. **推理成本**：参数量翻倍，推理成本大致也翻倍（甚至更多）。在实际业务中，如果一个 7B 模型就能搞定的任务你用 70B 模型去跑，那就是纯粹在烧钱。

4. **量化与蒸馏技术**：通过模型压缩技术（比如把 FP16 参数量化到 INT4），可以让大模型在更小的硬件上运行，只有微小的精度损失。这就像前端的 Tree Shaking——不改变功能，但减小体积。

**实践中的选择策略**

我的建议是：**从最便宜的模型开始，只在效果不达标时才升级。** 这就像前端性能优化的原则——先让它能跑，再看需不需要优化。

很多团队犯的错误是一上来就用 GPT-4 级别的模型做所有事情，然后发现成本 hold 不住。实际上，80% 的场景用中等参数量的模型就够了。

## 1.4 推理（Inference）vs 训练（Training）

### 直觉理解

**训练是"教"模型学东西，推理是"用"模型做事情。作为应用开发者，你只做推理——就像你只用 npm 包而不去开发它一样。**

### 前端类比

这个类比非常精确：

- **训练 = 开发 npm 包**：React 团队花了数年时间、大量工程师和计算资源来开发 React 框架。这个过程极其昂贵、耗时，需要深厚的专业知识。
- **推理 = 使用 npm 包**：你 `npm install react` 然后 `import React from 'react'`，就可以用了。你不需要理解 React 的 Fiber 架构实现细节，就能构建复杂的 UI。

同样，OpenAI / Anthropic / DeepSeek 花了数千万甚至数亿美元训练模型，而你只需要一个 API Key 就能调用这些模型的推理能力。

### 深入原理

**训练（Training）**
- 时间：数周到数月
- 成本：数百万到数千万美元（GPT-4 的训练成本估计超过 1 亿美元，最新一代前沿模型的成本还要高出一个数量级）
- 硬件：数千张顶级 GPU 集群
- 产出：模型权重文件（本质上就是一大堆数字）
- 频率：做一次就够（除非要更新模型）

**推理（Inference）**
- 时间：毫秒到秒级
- 成本：每次请求几分钱到几毛钱
- 硬件：API 调用的话，提供商负责硬件
- 产出：模型的回复文本
- 频率：每次用户交互都是一次推理

**这意味着什么？**

1. **低门槛入场**：你不需要懂深度学习、不需要 GPU、不需要 Python，就能用 LLM 构建产品。一个 API Key + TypeScript 就够了。

2. **成本结构不同**：训练是一次性的巨大投入（固定成本），推理是持续的小额支出（变动成本）。你的业务成本模型和传统后端服务不同——流量越大，AI 成本越高，而且是线性增长。

3. **你无法控制模型能力**：既然你只做推理，模型本身的能力边界不是你能改变的。你能做的是**通过 prompt 工程和 Agent 架构设计来最大化模型的有效输出**。这也是这个教程的核心主题。

4. **模型更新的影响**：模型提供商可能随时更新模型版本，这可能导致你的应用行为发生变化。这和前端依赖升级是一个道理——你需要测试和版本锁定策略。

## 1.5 Temperature 与 Top-P：创造力与确定性的控制面板

### 直觉理解

**Temperature 和 Top-P 是两个控制模型"随机性"的旋钮。Temperature 越高，回答越有创造力（也越不可预测）；越低，回答越稳定（也越无聊）。**

> 📌 **适用性说明**：temperature / topP 是绝大多数模型（DeepSeek V4、GPT-4o、Claude 4 及更早版本）的标准参数，本节讲的原理对它们都成立。但最新一代「推理模型」在转向「推理强度」参数（GPT-6 甚至直接移除了 temperature），详见本节末尾的「推理模型时代」小节。

### 前端类比

想象你在写一个**随机颜色生成器**：

- `Temperature = 0`：每次都返回同一个颜色，比如 `#3B82F6`。确定、可预测、但毫无变化。
- `Temperature = 0.7`：在一个合理的颜色范围内随机，可能返回蓝色系的不同色调。有变化，但不会太离谱。
- `Temperature = 1.5`：可能返回任何颜色，包括一些你意想不到的荧光色组合。创造力爆表，但结果可能不是你想要的。

或者想象 `Math.random()`——Temperature 控制的就是这个随机数的"方差"。

### 深入原理

**Temperature 的工作机制**

LLM 在生成每个 token 时，其实是在计算一个概率分布——词汇表里每个 token 被选为"下一个词"的概率。比如在"中国的首都是___"这个位置：

```
"北京": 0.85
"南京": 0.05
"上海": 0.03
"天安门": 0.02
...其他词: 合计 0.05
```

Temperature 做的事情是**在采样前对这个概率分布做缩放**：

- **Temperature < 1**：概率分布变得更"尖锐"。高概率的选项概率更高了，低概率的选项概率更低了。极端情况下（接近 0），几乎总是选最高概率的那个。
- **Temperature = 1**：使用原始概率分布，不做调整。
- **Temperature > 1**：概率分布变得更"平坦"。各选项的概率差距缩小了，低概率的选项也有更多机会被选中。

**Top-P（核采样，Nucleus Sampling）**

Top-P 是另一种控制随机性的方式。它的策略是：**按概率从高到低排列所有可能的 token，累加概率直到达到 P 值，然后只从这些 token 中采样。**

比如 Top-P = 0.9 意味着：从概率最高的 token 开始，一个个累加，直到累积概率达到 90%，然后只在这些 token 中随机选择。这样就排除了那些概率极低（可能是胡说八道）的选项。

**Temperature vs Top-P**

| 维度 | Temperature | Top-P |
|------|-------------|-------|
| 控制方式 | 缩放概率分布 | 截断候选集合 |
| 效果 | 控制整体随机程度 | 控制候选词的多样性 |
| 常用值 | 0-1.0 | 0.1-1.0 |
| 极端值 | 0 = 几乎确定性 | 0.1 = 极少选择 |

**实践建议**

实践中发现，**通常只调一个就够了，同时调两个反而容易产生不可预测的效果**。

- **代码生成、数据提取、格式化输出**：Temperature = 0 ~ 0.2。你希望结果稳定、准确、可预测。
- **通用对话、客服**：Temperature = 0.5 ~ 0.7。要有一定变化，但不能太离谱。
- **创意写作、头脑风暴**：Temperature = 0.8 ~ 1.2。鼓励模型给出不一样的回答。

#### 推理模型时代的「推理强度」参数

先说一个重要区分：**temperature / topP 并没有「消失」，它们仍然是绝大多数模型（DeepSeek V4、GPT-4o、Claude 4 及更早版本）的标准参数。** 变化发生在最新一代「推理模型」上——它们引入了一个新的控制维度，但各家做法和程度不同：

| 厂商（新一代模型） | temperature 现状 | 新的控制参数 |
|------|------|------|
| OpenAI GPT-6 | ❌ 彻底移除，不再支持 | `reasoningEffort`（none~max） |
| Anthropic Claude 5 | ⚠️ 参数仍在，但 thinking 常开、采样意义弱化 | `effort`（low~max）+ `thinking` |
| DeepSeek V4 | ✅ 仍支持，但 thinking 模式下失效 | `reasoning_effort`（none/low/high/max）+ thinking 开关 |

**为什么会有这个转变？**

传统模型「答案对不对」高度依赖 temperature 这种采样策略——温度低就稳定但「笨」，温度高就灵但「飘」。推理模型把这个矛盾**内化**了：它不再靠随机采样去「碰」答案，而是先花 token 做内部的思维链（Chain-of-Thought）推理，想清楚再输出。所以你不再调「随机性」，而是调「思考强度」。

**它控制的是什么？**

temperature 控制「输出 token 的随机性」，而「推理强度」（各家命名不同：OpenAI 叫 `reasoningEffort`、Anthropic 叫 `effort`、DeepSeek 叫 `reasoning_effort`）控制的是「模型在给出最终答案前，先在内部思考多久、想多深」。两者不是一回事：

| 旋钮 | 控制维度 | 典型取值 |
|------|---------|---------|
| temperature / topP | 输出 token 的随机性 / 多样性 | temperature 0~2、topP 0.1~1.0 |
| reasoningEffort / effort | 推理深度（内部思考 token 数） | none / low / medium / high / max |

**取值含义**（以 OpenAI 为例）：

- `none`：不做额外推理，直接回答——最快最便宜，但复杂问题可能翻车
- `low` / `medium`：适度思考，日常任务够用（`medium` 是默认值）
- `high` / `xhigh` / `max`：深度思考，适合难题，但更慢、更贵

**它是如何做到的？**

推理模型在生成最终答案前，会先在内部生成一串**不可见（或只摘要可见）的「思考 token」**——也就是思维链。`reasoningEffort` 本质上是控制这个思考阶段投入多少「预算」：

- effort 越高 → 内部思维链越长 → 模型「想」得越充分 → 但产生的思考 token 越多 → 越慢、越贵
- effort 越低 → 思维链越短 → 直接给答案 → 快而省，但难题可能想不深

用前端的话说，就像你给一个异步任务设「算力预算」：预算给得多，它可以做更多轮内部计算（更充分但更慢）；预算给得少，它就得快速收敛。区别在于这里的「预算」是 token/算力，而不是时间。

**对你（前端开发者）的实际影响：**

1. **调参数前先看模型**：GPT-6 传 temperature 会被忽略或报 warning；Claude 5 要看 `effort`；DeepSeek 在 thinking 模式下 temperature 也失效。写代码时按模型查对应参数，别想当然。
2. 想要「稳定、确定」的输出，在推理模型上对应的是把推理强度设低，而不是把 temperature 设为 0
3. 成本模型变了：推理模型的「思考 token」也算钱，推理强度越高，隐藏成本越高（第 22 章会细讲）

## 1.6 上下文窗口（Context Window）

### 直觉理解

**上下文窗口是模型一次能"看到"的文字总量上限，包括你发给它的内容和它回复的内容。超出这个窗口的内容，模型就完全不知道了——不是忘了，是根本没看到。**

### 前端类比

**上下文窗口就是浏览器的"可用内存"。**

你打开 Chrome，每个标签页都会占用内存。打开 5 个标签页很流畅，打开 50 个开始卡了，打开 500 个直接崩溃。上下文窗口就是这个硬性内存限制——模型能同时处理的信息量是有上限的。

或者更精确地说，上下文窗口像是 **`localStorage` 的容量限制**（通常 5-10MB）。你可以在这个限制内自由存取数据，但一旦超了，要么报错，要么你需要自己管理淘汰策略——决定哪些数据保留、哪些清除。

### 深入原理

**主流模型的上下文窗口对比**

| 模型 | 上下文窗口 | 大约等于 |
|------|-----------|---------|
| GPT-5 / GPT-6 | 200K~400K tokens | 约 150K-300K 英文单词 |
| Claude 4 / 5 | 200K tokens | 约 150K 英文单词 |
| DeepSeek-V4 | 1M tokens | 约 750K 英文单词 |
| Gemini 2.5 / 3 | 1M~2M tokens | 约 750K-1.5M 英文单词 |
| GPT-4o（上一代） | 128K tokens | 约 96K 英文单词 |

> 注：各型号具体窗口值不同且仍在持续变大，上表为撰写时（2026-10）的概览，以各厂商官方文档为准。

**128K 真的比 8K 好吗？长上下文的代价是什么？**

这是一个非常实际的问题，答案是：**不一定，长上下文有三个显著代价。**

**代价一：成本线性增长**

每次 API 调用的费用和输入 token 数量成正比。如果你因为"反正窗口够大"就把所有历史对话都塞进去，成本会迅速失控。

我在实际项目中见过这样的反模式：一个客服 Agent 每次都把完整的 50 轮对话历史发给模型——即使用户只是在问"我的订单到哪了"这种简单问题。结果每次调用消耗 10K+ token，大部分都是浪费的。

**代价二："大海捞针"问题（Lost in the Middle）**

研究表明，LLM 对长上下文中信息的利用是不均匀的。模型对**开头和结尾**的信息关注度最高，中间部分的信息容易被"忽略"。

这就像你读一份 100 页的技术文档——你记得住开头的摘要和结尾的总结，但中间第 47 页的某个细节？大概率忘了。

所以，**信息在上下文中的位置很重要**。重要的信息应该放在开头（system prompt）或者靠近结尾（最近的用户消息）。

**代价三：推理速度下降**

上下文越长，模型处理每个 token 的时间就越长（因为自注意力机制的计算复杂度是 O(n^2)，其中 n 是序列长度）。虽然各种优化技术在努力解决这个问题，但物理限制摆在那里——更长的上下文意味着更慢的响应。

**实际应用中的策略**

1. **滑动窗口**：只保留最近 N 轮对话
2. **摘要压缩**：把旧的对话用 LLM 总结成简短摘要
3. **RAG（检索增强生成）**：不把所有信息塞进上下文，而是根据当前问题检索相关内容
4. **分层上下文**：system prompt（固定） + 关键信息（半固定） + 最近对话（动态）

## 1.7 幻觉（Hallucination）：为什么 AI 会一本正经地胡说八道

### 直觉理解

**幻觉是指 LLM 生成的内容看起来完全合理、自信满满，但实际上是错误的或虚构的。这不是 bug，而是 LLM 架构的固有特性。**

### 前端类比

你有没有遇到过这种情况：你写了一个 React 组件，TypeScript 编译通过了，ESLint 也没报错，页面渲染出来了——但业务逻辑是错的？

LLM 的幻觉就类似这种情况。模型生成的文字在**语法层面**完美无缺（通顺、逻辑自洽、格式正确），但在**事实层面**可能完全错误。就像你的代码在"语法层面"正确（编译通过），但在"语义层面"有 bug。

更精确的类比是 **TypeScript 的类型系统**。TypeScript 能确保类型安全（形式正确），但不能确保运行时逻辑正确。`const result: number = calculatePrice(item)` 类型没问题，但 `calculatePrice` 内部可能算错了价格。LLM 确保了"输出看起来像正确答案"，但不保证"输出的内容确实正确"。

### 深入原理

**为什么幻觉会发生？**

要理解幻觉，你需要回到 LLM 的本质——它是一个**概率模型**，做的是"下一个词预测"。

关键洞见：**LLM 没有"事实数据库"。它不是先查询"北京是中国的首都"这个事实，然后回答你的问题。它做的是：基于训练时学到的统计模式，计算在当前语境下每个 token 的概率，然后采样。**

这意味着：
1. 如果训练数据中某个错误信息出现的频率足够高，模型可能会"学"到这个错误信息
2. 当模型在知识边界上（对某个主题了解不深），它仍然会自信地生成文字——因为它优化的目标是"生成流畅的文字"，而不是"只在确定时才说话"
3. 模型无法判断自己是否真的"知道"答案。它没有元认知（meta-cognition）——不知道自己不知道什么

**幻觉的常见类型**

1. **事实性幻觉**：编造不存在的论文、引用错误的数据
2. **推理幻觉**：逻辑链条中间某一步出错，但前后文衔接得很好
3. **指令幻觉**：你要求 JSON 格式输出，它给了个看起来像 JSON 但不合法的东西
4. **自信幻觉**：对自己的错误答案表现得极其自信

**开发者如何应对幻觉？**

1. **结构化输出**：使用 JSON Schema 约束输出格式，减少格式层面的幻觉
2. **RAG**：让模型基于检索到的真实数据回答，而不是凭记忆
3. **多重验证**：让模型自己检查自己的回答，或用另一个模型交叉验证
4. **明确指令**：在 prompt 中加上"如果你不确定，请说不知道"（虽然效果有限，但聊胜于无）
5. **人工审核**：对于关键决策，永远不要完全信任 LLM 的输出

## 1.8 Embedding：AI 如何"理解"语义

### 直觉理解

**Embedding 就是把一段文字变成一组数字（向量），使得语义相似的文字在数学空间中距离更近。这是 AI 理解"意思"的基础能力。**

### 前端类比

这个类比我觉得特别好：**Embedding 就像把颜色从名字映射到 RGB/HSL 坐标。**

"红色"、"猩红"、"朱红"——这三个词作为字符串完全不同，你用 `===` 比较都是 `false`。但一旦映射到 RGB 空间：

```
红色:   rgb(255, 0, 0)
猩红:   rgb(220, 20, 60)
朱红:   rgb(255, 69, 0)
```

你立刻能看出它们在数学空间中距离很近——因为 R 值都很高，G 和 B 值都很低。你可以用欧氏距离或余弦相似度来量化"这两个颜色有多像"。

Embedding 做的是同样的事情，只不过维度从 3（RGB）变成了 768、1536 甚至更多。在这个高维空间中，"如何退款" 和 "我想退钱" 这两个表面上不同的句子，会被映射到相近的坐标位置。

### 深入原理

**Embedding 的维度**

主流 Embedding 模型的维度：

| 模型 | 维度 | 含义 |
|------|------|------|
| OpenAI text-embedding-3-small | 1536 | 每段文字变成 1536 个数字 |
| OpenAI text-embedding-3-large | 3072 | 更高精度 |
| BGE-large-zh | 1024 | 中文优化 |

这些维度中的每一个数字都不对应一个具体的、人类可理解的含义（不像 RGB 中 R 就是"红色程度"）。它们是模型在训练过程中自动学会的抽象特征。

**为什么 Embedding 如此重要？**

Embedding 是连接"文字世界"和"数学世界"的桥梁。一旦文字变成了向量，你就可以做这些事情：

1. **语义搜索**：不靠关键词匹配，而是靠"意思"匹配。用户搜"头疼怎么办"，能匹配到"缓解偏头痛的方法"——因为它们的向量距离很近。

2. **文本分类**：把文本向量扔给一个简单的分类器，就能判断情感、主题、意图等。

3. **RAG（检索增强生成）**：这是你后面做 Agent 必须掌握的核心技术。先把知识库文档全部转成 Embedding 存起来，用户提问时把问题也转成 Embedding，然后找到最相似的文档片段，喂给 LLM 作为参考。

4. **聚类分析**：把大量文本转成向量后做聚类，自动发现文本中的主题和模式。

**余弦相似度**

衡量两个 Embedding 向量"有多像"，最常用的方法是**余弦相似度**：

- 值域：-1 到 1
- 1 = 完全相同方向（语义非常相似）
- 0 = 正交（语义无关）
- -1 = 完全相反方向（语义相反）

实际应用中，相似度 > 0.8 通常表示语义高度相关，0.5-0.8 表示有一定关联，< 0.5 通常认为不太相关。但这些阈值需要根据具体场景调优。

**Embedding 的局限性**

1. **无法捕捉否定**：有些 Embedding 模型对 "我喜欢这个产品" 和 "我不喜欢这个产品" 算出来的相似度很高——因为它们的用词高度重叠。新一代模型在改进这个问题，但仍需注意。

2. **长文本表现衰减**：当文本超过一定长度，Embedding 的质量会下降。所以实际使用中通常先做文本分块（chunking），再对每个块做 Embedding。

3. **领域偏差**：通用 Embedding 模型在专业领域（医疗、法律、金融）可能表现不佳，需要领域特化的模型。

## 概念辨析

| 易混概念 | 概念 A | 概念 B | 核心区别 |
|---------|--------|--------|---------|
| Token vs 字符 | Token | Character | Token 是分词器切出来的语言片段，一个 token 可能对应多个字符或一个字符的一部分 |
| 训练 vs 推理 | Training | Inference | 训练是"教"模型，天价成本做一次；推理是"用"模型，小额成本做无数次 |
| Temperature vs Top-P | Temperature | Top-P | Temperature 缩放概率分布的形状；Top-P 截断候选词的范围 |
| 上下文 vs 记忆 | Context Window | Memory | 上下文是单次对话的信息容量；"记忆"是跨对话保持信息的机制 |
| 幻觉 vs 错误 | Hallucination | Bug | 幻觉是模型架构固有的；Bug 是代码逻辑问题。幻觉无法彻底消除，只能缓解 |
| 参数量 vs 能力 | Parameters | Capability | 参数量是模型的"容量"；能力还取决于训练数据质量、训练方法等 |
| Embedding vs Encoding | Embedding | One-hot Encoding | Embedding 是稠密的、有语义的向量；One-hot 是稀疏的、无语义的编码 |

## 灵魂拷问

> **Q1: Token 和字符什么关系？中文一个字消耗多少 token？为什么这影响成本？**

> A: Token 和字符不是一一对应的关系。在英文中，一个常见单词（如 "the"、"hello"）通常是 1 个 token，而较长或罕见的单词可能被拆成多个 token（如 "unbelievable" 可能是 3 个 token："un" + "believ" + "able"）。
>
> 在中文里情况更复杂。由于主流 tokenizer 是以英文语料为主训练的，中文汉字并不在高频词汇表中。一个常见汉字通常消耗 1-2 个 token，生僻字可能要 2-3 个 token。平均下来，中文每个字大约消耗 1.5 个 token。
>
> 这对成本的影响是直接的：假设 API 价格是每百万 token 2 美元。一段 1000 字的中文内容大约消耗 1500 个 token，而表达相同意思的 600 个英文单词大约只消耗 800 个 token。中文场景下的 token 成本几乎是英文的两倍。
>
> 对于 Agent 开发来说，这意味着你的 system prompt 如果不面向用户，用英文写可以省下接近一半的 token 成本。这是一个非常实际的优化手段。

> **Q2: Temperature 设为 0 就一定能得到相同结果吗？**

> A: **不一定。** 这是一个常见的误解。Temperature = 0 从数学上说意味着"总是选概率最高的 token"（贪心解码），理论上应该是确定性的。但实际中有几个原因导致结果可能不同：
>
> 1. **GPU 浮点数运算的非确定性**：GPU 并行计算的顺序可能影响浮点数精度，导致概率排名第一和第二的 token 在不同运行中发生微妙的交换。
> 2. **模型服务端的基础设施变化**：API 提供商可能使用不同的服务器实例、不同的 batch 大小，这些都可能导致微小的数值差异。
> 3. **概率相近的 token**：当多个 token 的概率非常接近时（比如 0.301 和 0.300），微小的数值波动就可能改变选择。
>
> 所以正确的理解是：Temperature = 0 使输出**接近确定性**，但不保证**完全确定性**。如果你的业务逻辑严重依赖"相同输入一定得到相同输出"，你需要额外的缓存层来处理，而不能仅靠 Temperature = 0。

> （补充：以上讨论的前提是模型还支持 temperature 参数。对于 GPT-6 这类已移除 temperature 的推理模型，这个问题本身就不成立了——见下方的 Q7。）

> **Q3: 为什么 128K 上下文的模型不一定比 8K 的好？长上下文有什么代价？**

> A: 三个关键代价：
>
> **成本代价**：API 按 token 收费，把 128K token 塞进去比 8K 贵 16 倍。很多场景下你根本不需要这么多上下文。
>
> **注意力衰减（Lost in the Middle）**：多项研究表明，LLM 对长文本中间部分的信息利用率显著下降。128K 的窗口不意味着模型能同等质量地利用每一个 token。就像你给一个 100 页的需求文档，开发者大概率只认真看前几页和最后几页。
>
> **推理延迟**：自注意力机制的计算复杂度是 O(n^2)。上下文从 8K 增长到 128K 是 16 倍，但自注意力的计算量增长了 256 倍（16^2）。虽然有 FlashAttention 等优化技术，但延迟增加仍然显著。
>
> 我的经验是：**与其追求更大的上下文窗口，不如投资在更好的信息管理策略上。** RAG、对话摘要、分层上下文这些技术，在实际效果上往往比单纯增大窗口更有效。

> **Q4: LLM 真的在"理解"语言吗？它和搜索引擎的本质区别是什么？**

> A: 这个问题可以从两个层面回答。
>
> **哲学层面**：目前没有定论。一派认为 LLM 只是"随机鹦鹉"（Stochastic Parrots），在做高级的模式匹配而非真正理解；另一派认为，如果一个系统的行为和"理解"完全一致，那讨论它是否"真的"理解已经没有意义（鸭子测试——如果走起来像鸭子、叫起来像鸭子，那它就是鸭子）。
>
> **实用层面**：LLM 和搜索引擎有本质区别。搜索引擎是**检索**——在已有的网页库中找到匹配的结果。它不创造新内容，不做推理，不理解你的意图（虽然现代搜索引擎加入了一些语义理解）。LLM 是**生成**——基于对语言的深层建模，它可以创造从未存在过的内容，可以推理，可以根据上下文理解模糊的意图。
>
> 一个简单的测试：你问搜索引擎"帮我把这段代码从 React 类组件重构成函数组件"，它只能给你搜到相关教程。你问 LLM 同样的问题并附上代码，它能直接给你重构后的版本。这需要的不只是检索，还需要对代码结构的"理解"和"转换"。

> **Q5: 为什么说 Embedding 是 AI 的"六维空间坐标"？**

> A: 这个说法的核心是：**Embedding 把离散的文字映射到了连续的数学空间，使得"语义"变得可以计算。**
>
> 在人类的三维空间中，我们用 (x, y, z) 三个坐标就能精确定位任何一个点，并且可以计算任意两点之间的距离。Embedding 做了类似的事——只不过维度从 3 变成了 768 或 1536。
>
> 为什么需要这么多维度？因为语义关系远比空间位置复杂得多。两个词之间的关系可能是：同义、反义、上下位（"苹果"和"水果"）、部分整体（"轮胎"和"汽车"）、因果、时序等等。三维空间根本不够表达这么丰富的关系。
>
> 有趣的是，高维 Embedding 空间中存在有意义的"方向"。经典的例子：`vector("国王") - vector("男人") + vector("女人") ≈ vector("女王")`。这说明"性别"这个概念在 Embedding 空间中对应了一个特定的方向。
>
> 但"六维空间"只是一个比喻——实际上是千维级别的空间，人类无法可视化，但数学上完全可以操作。这就是 Embedding 的威力：**让计算机能做"语义算术"。**

> **Q6: 为什么模型的参数量增长速度远快于能力增长速度？**

> A: 这涉及到 Scaling Law（缩放定律）。研究发现，模型性能的提升和参数量的增长不是线性关系，而是对数关系——参数量翻倍，性能可能只提升 10-15%。
>
> 用前端的话说，这就像 Lighthouse 性能分数。从 60 分优化到 80 分可能只需要基本的优化（代码分割、图片压缩），但从 95 分到 98 分可能需要极其精细的调优。每提升一分的边际成本越来越高。
>
> 这也解释了为什么行业趋势在转向：不是一味地增大模型，而是在训练数据质量、训练方法、架构优化上下功夫。DeepSeek 的 MoE（混合专家）架构就是一个好例子——通过让不同的"专家"处理不同类型的问题，在不增加推理计算量的前提下提升了模型的有效参数利用率。

> **Q7: 新模型（如 GPT-6）不支持 temperature 了，那「想要稳定/确定输出」这件事现在怎么做？**

> A: 这是推理模型时代必须更新认知的一点。传统模型靠「temperature = 0」逼近确定性，但即便那样也不保证 100% 确定（见 Q2）。推理模型把稳定性诉求转移到了另一个维度：
>
> 1. **调 reasoningEffort**：把它设低（`none` / `low`），模型少「自由发挥」，输出更贴近直答。注意它不是「随机性」旋钮，而是「思考深度」旋钮，机制不同。
> 2. **结构化输出兜底**：无论什么模型，要求 JSON 就用 JSON Schema / 结构化输出约束（第 5 章会讲），从格式层面保证确定性。
> 3. **应用层缓存**：如果真的需要「相同输入 → 相同输出」，最可靠的办法是自己在应用层做缓存（把结果存下来），而不是依赖模型行为。这和前端里「用 memo 缓存计算结果」是一个道理。
>
> 一句话：**确定性从「调模型参数」转向「工程手段」**——参数层面调 reasoningEffort，格式层面用结构化输出，业务层面做缓存。

## 最佳实践

### DO（推荐做法）

- **DO 理解 token 消耗**：在设计 Agent 时，预估每次调用的 token 消耗，设定预算上限。就像前端要关注 bundle size 一样，token 消耗是你最重要的成本指标。

- **DO 根据任务选择 Temperature**：代码生成用低 Temperature（0-0.2），创意任务用高 Temperature（0.7-1.0）。不要所有场景都用默认值。

- **DO 主动管理上下文**：设计对话记忆策略——滑动窗口、摘要压缩、RAG 检索。不要把所有历史消息无脑塞进去。

- **DO 对 LLM 输出做校验**：永远不要直接信任 LLM 的输出。如果它应该返回 JSON，就用 JSON Schema 验证。如果它应该返回代码，就跑一下看看能不能运行。

- **DO 用英文写 system prompt**：除非面向用户的输出需要中文，否则系统指令用英文写，节省 token。

- **DO 建立基准测试**：在你的具体场景下测试不同模型的表现，而不是只看公开的 benchmark 排名。

### DON'T（避免做法）

- **DON'T 把 LLM 当数据库用**：不要问 LLM "2024 年 GDP 是多少"这类需要精确数据的问题。它不是数据库，它的"知识"有截止日期且可能不准确。

- **DON'T 一上来就用最贵的模型**：先用便宜的模型验证思路，效果不够再升级。从 DeepSeek 开始试，够用就不要换 GPT-5。

- **DON'T 忽略 token 限制**：别以为 128K 的窗口就可以随便塞内容。长上下文有性能代价、成本代价和注意力衰减问题。

- **DON'T 期望 Temperature=0 得到完全确定的输出**：如果你需要确定性，在应用层做缓存，而不是依赖模型行为。

- **DON'T 把幻觉当 bug 来"修"**：幻觉是架构特性，不可能完全消除。你的策略应该是"缓解 + 检测 + 兜底"，而不是"消灭"。

- **DON'T 忽视中英文 token 差异**：做成本估算时要考虑中文的 token 效率更低这一事实。

/**
 * 一个简化的 token 估算器
 * 实际中你会用 tiktoken 等专业库，这里只是帮你建立直觉
 */
function estimateTokenCount(text: string): {
  charCount: number;
  estimatedTokens: number;
  chineseCharCount: number;
  englishWordCount: number;
} {
  const charCount = text.length;

  // 统计中文字符数
  const chineseChars = text.match(/[一-鿿]/g) || [];
  const chineseCharCount = chineseChars.length;

  // 统计英文单词数
  const englishWords = text.match(/[a-zA-Z]+/g) || [];
  const englishWordCount = englishWords.length;

  // 粗略估算：中文每字约 1.5 token，英文每词约 1.3 token
  const estimatedTokens = Math.ceil(
    chineseCharCount * 1.5 + englishWordCount * 1.3
  );

  return { charCount, estimatedTokens, chineseCharCount, englishWordCount };
}

// 对比中英文的 token 效率

    text: "Artificial intelligence is transforming how we build software applications.",

/**
 * 模拟 Temperature 采样
 * 展示不同 Temperature 下，同一概率分布产生的结果差异
 */
function simulateTemperatureSampling(
  probabilities: Record<string, number>,
  temperature: number,
  samples: number = 10
): Record<string, number> {
  // 应用 temperature 缩放
  const entries = Object.entries(probabilities);
  const logits = entries.map(([token, prob]) => [
    token,
    Math.log(prob) / Math.max(temperature, 0.01),
  ] as const);

  // softmax 归一化
  const maxLogit = Math.max(...logits.map(([, l]) => l));
  const expValues = logits.map(
    ([token, l]) => [token, Math.exp(l - maxLogit)] as const
  );
  const sumExp = expValues.reduce((sum, [, e]) => sum + e, 0);
  const scaledProbs = expValues.map(
    ([token, e]) => [token, e / sumExp] as const
  );

  // 采样统计
  const counts: Record<string, number> = {};
  for (let i = 0; i < samples; i++) {
    const rand = Math.random();
    let cumProb = 0;
    for (const [token, prob] of scaledProbs) {
      cumProb += prob;
      if (rand <= cumProb) {
        counts[token] = (counts[token] || 0) + 1;
        break;
      }
    }
  }
  return counts;
}

// 模拟 "中国的首都是___" 的下一个 token 概率分布
const nextTokenProbs = {

  很: 0.01,

console.log('=== Temperature 对采样的影响 ===');

// Part 3: 简易 Embedding 相似度计算
// ============================================

/**
 * 计算余弦相似度
 * 这是衡量两个 Embedding 向量相似程度的标准方法
 */
function cosineSimilarity(a: number[], b: number[]): number {
  if (a.length !== b.length) throw new Error("向量维度不一致");

  let dotProduct = 0;
  let normA = 0;
  let normB = 0;

  for (let i = 0; i < a.length; i++) {
    dotProduct += a[i] * b[i];
    normA += a[i] * a[i];
    normB += b[i] * b[i];
  }

  return dotProduct / (Math.sqrt(normA) * Math.sqrt(normB));
}

// 用简化的手工向量演示语义相似度
// 实际中这些向量由 Embedding 模型生成，维度在 768-3072 之间
// 这里用 5 维向量做演示：[技术, 情感, 食物, 动作, 自然]
const mockEmbeddings: Record<string, number[]> = {

  "我今天很开心":   [0.0, 0.9, 0.0, 0.1, 0.1],
  "今天心情不错":   [0.0, 0.8, 0.0, 0.1, 0.2],
  "红烧肉怎么做":   [0.0, 0.1, 0.9, 0.3, 0.0],
};

console.log("=== Embedding 相似度演示 ===\n");

const texts = Object.keys(mockEmbeddings);
for (let i = 0; i < texts.length; i++) {
  for (let j = i + 1; j < texts.length; j++) {
    const sim = cosineSimilarity(
      mockEmbeddings[texts[i]],
      mockEmbeddings[texts[j]]
    );
    const simBar = "█".repeat(Math.round(sim * 20));
    console.log(
      `"${texts[i]}" vs "${texts[j]}"\n  相似度: ${sim.toFixed(3)} ${simBar}\n`
    );
  }
}

interface ModelPricing {
  name: string;
  inputPricePerMillion: number;  // 美元 / 百万 token
  outputPricePerMillion: number; // 美元 / 百万 token
}

// 注意：模型价格变化极快，下面数值是撰写时（2026-10）的参考值，
// 仅用于演示"成本估算方法"，实际开发请以各厂商官方定价页为准。
// DeepSeek 现在采用峰谷定价（off-peak/peak），这里取 off-peak 价。
const models: ModelPricing[] = [
  { name: "DeepSeek-V4-Pro", inputPricePerMillion: 0.66, outputPricePerMillion: 1.98 },
  { name: "DeepSeek-V4-Flash", inputPricePerMillion: 0.15, outputPricePerMillion: 0.60 },
  { name: "GPT-5.x", inputPricePerMillion: 1.25, outputPricePerMillion: 10.00 },
  { name: "Claude 4.x / 5.x", inputPricePerMillion: 3.00, outputPricePerMillion: 15.00 },
];

function estimateCost(
  model: ModelPricing,
  inputTokens: number,
  outputTokens: number
): number {
  return (
    (inputTokens / 1_000_000) * model.inputPricePerMillion +
    (outputTokens / 1_000_000) * model.outputPricePerMillion
  );
}

console.log("=== 成本估算：每天 1000 次对话 ===");
console.log("假设：每次对话平均输入 500 token，输出 300 token\n");

const dailyCalls = 1000;
const avgInputTokens = 500;
const avgOutputTokens = 300;

for (const model of models) {
  const dailyCost =
    estimateCost(model, avgInputTokens, avgOutputTokens) * dailyCalls;
  const monthlyCost = dailyCost * 30;
  console.log(`${model.name}:`);
  console.log(`  单次: $${estimateCost(model, avgInputTokens, avgOutputTokens).toFixed(6)}`);
  console.log(`  日均: $${dailyCost.toFixed(2)}`);
  console.log(`  月均: $${monthlyCost.toFixed(2)}`);
  console.log();
}

## 本章小结

1. **LLM 的本质是"下一个词预测器"**，但当这件事做到极致，就涌现出了看起来像智能的能力。理解这个本质，你就能预判它能做什么、不能做什么。

2. **Token 是你的成本单位**。它不是字符也不是单词，是 tokenizer 切出来的语言片段。中文的 token 效率比英文低约 50%，这直接影响成本和上下文利用率。

3. **参数量不等于能力**。选模型要看实际效果，不是看参数量排名。从便宜的模型开始，效果不够再升级——这是最务实的策略。

4. **幻觉是特性不是 bug**。永远不要完全信任 LLM 的输出。在你的 Agent 架构中，必须设计验证和兜底机制。

5. **Embedding 是连接文字世界和数学世界的桥梁**。理解它，是后面做 RAG（检索增强生成）的基础。当你的 Agent 需要处理知识库时，Embedding 就是核心技术。
