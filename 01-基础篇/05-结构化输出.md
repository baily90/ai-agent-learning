# 第5章：结构化输出 -- 让 AI 返回可靠的 JSON 数据

## 引言

想象你在开发一个电商后台，调用了一个"商品分析 API"，期待拿到 `{ name, price, category }` 这样的 JSON，结果 API 返回了这么一段话：

> "这个商品是一款高端蓝牙耳机，售价 299 元，属于电子产品类别，性价比很不错哦~"

你能用吗？技术上能 -- 你可以写正则去提取价格，写 NLP 去判断类别。但你愿意吗？你的 React 组件能直接渲染这段话吗？

这就是 AI 开发中最常见的"数据格式鸿沟" -- AI 天生说人话，但你的程序需要结构化数据。

如果你做过前端开发，一定经历过后端返回"不规范数据"的痛苦。想象一下，后端不返回 JSON，而是返回一段自然语言描述，让你自己去提取信息 -- 这简直是噩梦。但 AI 默认就是这么干的。

本章要解决的核心问题就是：**如何让 AI 像一个靠谱的后端 API 一样，稳定地返回你要的数据结构？**

这不是一个"锦上添花"的能力，而是 Agent 开发的基础设施。因为后面所有章节 -- 工具调用、任务规划、多 Agent 协作 -- 都依赖 AI 能可靠地输出结构化数据。

---

## 5.1 为什么需要结构化输出

### 一句话直觉

AI 说的是人话，但你的代码需要的是数据。

### 前端类比

你一定用过 `fetch` 调用 REST API：

```typescript
const res = await fetch('/api/products/123');
const data = await res.json(); // { name: "耳机", price: 299, category: "电子" }
console.log(data.price); // 299，确定的，可用的
```

这是理所当然的 -- 后端返回 JSON，前端解析后直接用。但如果 AI 是你的"后端"，情况就变了：

```typescript
const result = await generateText({
  model: deepseek('deepseek-chat'),
  prompt: '分析这个商品：高端蓝牙耳机AirMax Pro，售价299元'
});

console.log(result.text);
// "这是一款高端蓝牙耳机，名称为AirMax Pro，价格是299元人民币，
//  属于电子产品/音频设备类别。产品定位中高端市场..."
```

你拿到的是一段自然语言。你怎么从里面提取 `price`？用正则 `/(\d+)元/`？那如果 AI 说的是"售价两百九十九元"呢？或者"价格区间在 250-350 之间"呢？

**问题的本质**：自然语言是非结构化的、不确定的、充满歧义的。但程序需要结构化的、确定的、无歧义的数据。

### 深入原理

这个问题在 AI 开发中被称为"最后一公里问题"（Last Mile Problem）。AI 的能力很强，理解力很好，但如果输出格式不可控，这些能力就无法被程序利用。

具体来说，不做结构化输出会面临三个层次的问题：

**第一层：格式不可预测**

AI 每次回答的格式可能不一样。同一个问题问三次，可能得到三种不同的表述方式。你的解析代码不可能覆盖所有变体。

**第二层：类型不安全**

即使你用正则提取出了数据，你怎么确保 `price` 是一个 number 而不是 string？你怎么确保 `category` 是你预定义的枚举值之一？在 TypeScript 的世界里，没有类型保证的数据是危险的。

**第三层：错误难以处理**

如果 AI 的回答里漏掉了某个字段呢？如果某个字段的值不合理呢？在自然语言中，"缺失"和"错误"很难被程序检测到。

### 深层追问

> 你可能会想：那我在 prompt 里详细说明格式不就行了？

确实，很多人的第一反应是这样：

```
请按照以下JSON格式返回：{"name": "商品名", "price": 数字, "category": "类别"}
```

这能工作吗？能。但靠谱吗？不靠谱。原因后面细讲。

## 5.2 三种结构化输出方式对比

在深入具体技术之前，先建立全局认知。获取 AI 结构化输出有三种方式，它们的可靠性递增：

### 方式一：Prompt 约束（不推荐用于生产）

**直觉**：求 AI "请用 JSON 回答" -- 本质上是"口头约定"。

```typescript
const result = await generateText({
  model: deepseek('deepseek-chat'),
  prompt: `分析以下商品信息，以JSON格式返回，包含name、price、category字段。
  
商品：高端蓝牙耳机AirMax Pro，售价299元`
});

// result.text 可能是：
// ```json
// {"name": "AirMax Pro", "price": 299, "category": "电子产品"}
// ```
// 
// 也可能是：
// 当然！以下是分析结果：
// {"name": "AirMax Pro", "price": "299元", "category": "电子"}
//
// 甚至可能是：
// {"name": "AirMax Pro", "price": 299, "category": "电子", "description": "..."}
```

**前端类比**：这就像你跟后端口头说"这个接口返回的 JSON 里要有 name 字段"，但没有写接口文档，也没有做 schema 校验。后端可能返回 `name`，也可能返回 `productName`，甚至可能多返回几个你没预料到的字段。

**问题**：
- AI 可能在 JSON 前后加上解释文字（"好的，以下是结果：..."）
- 字段名可能不一致（`price` vs `price_rmb` vs `售价`）
- 值的类型可能不对（`299` vs `"299元"`）
- 可能多出或少了字段
- 用 Markdown 的代码块包裹 JSON（```json ... ```）

**可靠度**：约 70-85%。在 demo 里够用，在生产环境会让你夜不能寐。

### 方式二：JSON Mode（保证 JSON，不保证结构）

**直觉**：让 AI "只能说 JSON" -- 像是给 API 加了 `Content-Type: application/json` 头。

JSON Mode 是模型提供商提供的一种能力，它从底层保证 AI 的输出一定是一个合法的 JSON。注意这两个字 -- "合法"。它保证的是语法层面的正确性，就像 `JSON.parse()` 不会报错，但不保证里面的结构是你想要的。

```typescript
import { generateText, Output } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';

const result = await generateText({
  model: deepseek('deepseek-chat'),
  prompt: '分析商品：高端蓝牙耳机AirMax Pro，售价299元。返回name、price、category。',
  // AI SDK 7 的 JSON Mode：Output.json() 保证输出是合法 JSON（但不约束结构）
  output: Output.json(),
});

const data = result.output; // 保证是合法 JSON，已解析为对象
// 但 data 的具体结构不确定
```

**前端类比**：这就像后端 API 保证了 `Content-Type: application/json`，你知道 `res.json()` 不会报错，但返回的 JSON 里有哪些字段、字段是什么类型 -- 不确定。

**比方式一好在哪**：
- 输出一定是合法 JSON，不会夹杂自然语言
- `JSON.parse()` 保证成功
- 不会有 Markdown 代码块包裹

**仍然存在的问题**：
- 字段名可能和你期望的不一样
- 值的类型不受控
- 可能多出或少了字段
- 没有运行时类型校验

**可靠度**：约 90-95%。比方式一好很多，但在类型严格的 TypeScript 项目中还不够。

### 方式三：Schema-based 结构化输出（generateText + output）

**直觉**：给 AI 一个严格的"表单" -- 它只能按你定义的结构填写，不能自由发挥。

这是目前最可靠的方式，也是本章的重点。你用 Zod Schema 定义输出结构，AI SDK 会确保 AI 的输出严格符合你定义的类型。

```typescript
import { generateText, Output } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';
import { z } from 'zod';

const { output } = await generateText({
  model: deepseek('deepseek-chat'),
  output: Output.object({
    schema: z.object({
      name: z.string().describe('商品名称'),
      price: z.number().describe('价格，单位：元'),
      category: z.enum(['电子', '服装', '食品', '家居', '其他']).describe('商品类别'),
    }),
  }),
  prompt: '分析商品：高端蓝牙耳机AirMax Pro，售价299元',
});

// output 的类型是 { name: string; price: number; category: "电子" | "服装" | "食品" | "家居" | "其他" }
console.log(output.name);     // "AirMax Pro" -- 一定是 string
console.log(output.price);    // 299 -- 一定是 number
console.log(output.category); // "电子" -- 一定是枚举值之一
```

**前端类比**：这就像你用 TypeScript 的 interface 定义了 API 的响应类型，而且在运行时用 Zod 做了校验 -- 你不仅有编译期的类型安全，还有运行时的数据保证。

**可靠度**：约 99%+。除非模型本身出现严重故障，否则输出一定符合你定义的 schema。

### 三种方式的核心区别

| 维度 | Prompt 约束 | JSON Mode | Schema-based |
|------|-----------|-----------|-------------|
| 保证合法 JSON | 否 | 是 | 是 |
| 保证结构正确 | 否 | 否 | 是 |
| 类型安全 | 否 | 否 | 是（编译期+运行时） |
| 需要后处理 | 大量正则/解析 | JSON.parse | 直接使用 |
| 生产可靠性 | 低 | 中 | 高 |
| 使用门槛 | 最低 | 低 | 需要学 Zod |

**结论**：在生产环境中，Schema-based 结构化输出是唯一推荐的方式。下面我们深入每个关键技术点。

## 5.3 Zod Schema -- 用 TypeScript 的方式定义 AI 输出

### 一句话直觉

Zod 是 TypeScript 世界的 JSON Schema -- 你用代码定义数据结构，它帮你做运行时校验。

### 前端类比

如果你用过 Zod 做表单验证，那你已经会了 80%：

```typescript
// 你熟悉的：验证用户提交的表单
const UserFormSchema = z.object({
  name: z.string().min(2, '名字至少2个字'),
  age: z.number().min(0).max(150),
  email: z.string().email('邮箱格式不对'),
});

// 新的场景：验证 AI 返回的数据
const ProductAnalysisSchema = z.object({
  name: z.string().describe('商品名称'),
  price: z.number().describe('价格，单位：元'),
  category: z.enum(['电子', '服装', '食品', '家居', '其他']),
});
```

看到区别了吗？核心用法完全一样，只是验证的对象从"用户输入"变成了"AI 输出"。而且多了一个关键方法 `.describe()` -- 这是给 AI 看的注释，后面会详细讲。

### 深入原理

Zod 在结构化输出中扮演三个角色：

**角色一：Schema 定义**

你的 Zod Schema 会被 AI SDK 转换成 JSON Schema，然后发送给模型。模型根据这个 JSON Schema 来约束自己的输出。

```typescript
// 你写的 Zod Schema
const schema = z.object({
  sentiment: z.enum(['positive', 'negative', 'neutral']),
  confidence: z.number().min(0).max(1),
  keywords: z.array(z.string()),
});

// AI SDK 内部会转换成类似这样的 JSON Schema 发给模型：
// {
//   "type": "object",
//   "properties": {
//     "sentiment": { "type": "string", "enum": ["positive", "negative", "neutral"] },
//     "confidence": { "type": "number", "minimum": 0, "maximum": 1 },
//     "keywords": { "type": "array", "items": { "type": "string" } }
//   },
//   "required": ["sentiment", "confidence", "keywords"]
// }
```

**角色二：运行时验证**

模型返回数据后，Zod 会对数据做解析和校验。如果数据不符合 schema，会抛出明确的错误。

**角色三：类型推导**

Zod Schema 会自动推导出 TypeScript 类型，你在使用返回数据时能获得完整的类型提示和自动补全。

```typescript
const { output } = await generateText({
  model: deepseek('deepseek-chat'),
  output: Output.object({ schema }),
  prompt,
});
// TypeScript 自动推导出 output 的类型：
// {
//   sentiment: "positive" | "negative" | "neutral";
//   confidence: number;
//   keywords: string[];
// }

output.sentiment  // 自动补全，只能是三个值之一
output.confidence // 类型是 number
output.keywords   // 类型是 string[]
```

这种"定义一次，三处受益"的体验，对 TypeScript 开发者来说简直是天然的。

## 5.4 结构化输出（output 参数）详解

### 一句话直觉

结构化输出就是给 `generateText` 加一个 `output` 参数 -- 同样是调用 AI，但返回的不是自由文本，而是符合指定结构的对象。

### 前端类比

```typescript
// generateText = fetch 拿到 text/plain 响应
const textRes = await fetch('/api/analyze', { headers: { Accept: 'text/plain' } });
const text = await textRes.text(); // 自由文本，格式不确定

// 结构化输出（output）= fetch 拿到结构化 JSON 响应，且经过 Zod 校验
const jsonRes = await fetch('/api/analyze', { headers: { Accept: 'application/json' } });
const data = ProductSchema.parse(await jsonRes.json()); // 结构确定，类型安全
```

### 基本用法

```typescript
import { generateText, Output } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';
import { z } from 'zod';

// 定义输出结构
const RecipeSchema = z.object({
  name: z.string().describe('菜谱名称'),
  ingredients: z.array(
    z.object({
      name: z.string().describe('食材名称'),
      amount: z.string().describe('用量，如"200g"、"2汤匙"'),
    })
  ).describe('食材清单'),
  steps: z.array(z.string()).describe('烹饪步骤'),
  difficulty: z.enum(['简单', '中等', '困难']).describe('难度等级'),
  cookingTime: z.number().describe('烹饪时间，单位：分钟'),
});

// 调用 AI 生成结构化数据
const { output: recipe } = await generateText({
  model: deepseek('deepseek-chat'),
  output: Output.object({ schema: RecipeSchema }),
  prompt: '给我一个番茄炒蛋的菜谱',
});

// 直接使用，完全类型安全
console.log(`菜名：${recipe.name}`);
console.log(`难度：${recipe.difficulty}`);
console.log(`耗时：${recipe.cookingTime}分钟`);
recipe.ingredients.forEach(ing => {
  console.log(`  ${ing.name}: ${ing.amount}`);
});
```

### 与普通文本生成的关系

| 特性 | 普通文本生成 | 结构化输出（output） |
|------|-------------|----------------|
| 返回类型 | `{ text: string }` | `{ output: T }` |
| 输出格式 | 自由文本 | 结构化对象 |
| 类型安全 | 无 | 完整的 TS 类型 |
| 需要 Zod | 否 | 是 |
| 适用场景 | 对话、写作、翻译 | 数据提取、分类、分析 |

**重要理解**：结构化输出不是普通文本生成的"升级版"，它们是同一套 `generateText` API 的两种用法。当你需要 AI 写一篇文章，直接 `generateText`（不带 output）；当你需要 AI 返回结构化数据，加一个 `output` 参数。就像你不会用 `JSON.stringify` 来写文章一样。

### output 模式

`generateText` 支持不同的输出模式，通过 `output` 参数控制：

```typescript
// 对象模式：返回一个对象
const { output } = await generateText({
  model: deepseek('deepseek-chat'),
  output: Output.object({ schema: ProductSchema }),
  prompt: '分析这个商品',
});

// 数组模式：返回对象数组
const { output: products } = await generateText({
  model: deepseek('deepseek-chat'),
  output: Output.array({ element: ProductSchema }),
  prompt: '列出5个推荐的蓝牙耳机',
});
// products 的类型是 Product[]

// 枚举模式：返回枚举值
const { output: category } = await generateText({
  model: deepseek('deepseek-chat'),
  output: Output.choice({ options: ['positive', 'negative', 'neutral'] }),
  prompt: '这条评论的情感倾向是什么？评论：这个产品太棒了！',
});
// category 的类型是 'positive' | 'negative' | 'neutral'
```

`Output.array` 特别实用。想象你需要 AI 批量分析 10 条用户评论，返回每条的情感分析结果 -- 用数组模式一次搞定。

`Output.choice` 则适用于分类场景 -- 你只需要 AI 从预定义的选项中选一个。

## 5.5 Schema 设计最佳实践

### 一句话直觉

Schema 不只是给你的代码看的，更是给 AI 看的 -- 好的 schema 设计能显著提升 AI 输出的质量。

### description 的重要性

这是很多人忽略的关键点：**Zod schema 中的 `.describe()` 不只是给开发者看的注释，它会被发送给模型，直接影响模型的输出质量**。

```typescript
// 差的 schema -- AI 不知道你具体要什么
const BadSchema = z.object({
  a: z.string(),
  b: z.number(),
  c: z.boolean(),
});

// 好的 schema -- AI 能从描述中理解每个字段的含义
const GoodSchema = z.object({
  summary: z.string().describe('文章的一句话摘要，不超过50字'),
  wordCount: z.number().describe('文章的总字数'),
  isOriginal: z.boolean().describe('文章是否为原创内容（非转载/翻译）'),
});
```

**前端类比**：这就像写 JSDoc 注释 vs 不写。代码都能跑，但有注释的代码，无论是人还是工具（TypeScript/IDE）都能更好地理解你的意图。而对于 AI 来说，`.describe()` 就是它理解"你到底想要什么"的关键线索。

### 字段命名的艺术

```typescript
// 差：缩写和模糊命名
const Bad = z.object({
  t: z.string(),        // AI 不知道这是什么
  cnt: z.number(),      // count 的缩写？AI 可能猜不到
  flag: z.boolean(),    // 什么 flag？
});

// 好：语义化命名
const Good = z.object({
  title: z.string().describe('文章标题'),
  commentCount: z.number().describe('评论数量'),
  isPublished: z.boolean().describe('是否已发布'),
});
```

AI 能读懂你的字段名。语义化的字段名本身就是一种"提示"。`sentimentScore` 比 `score` 更能引导 AI 输出情感分析分数，而不是其他类型的分数。

### 枚举值的使用

当字段的取值范围有限时，务必使用枚举：

```typescript
// 差：自由字符串，AI 可能返回任何值
const Bad = z.object({
  priority: z.string().describe('优先级'),
  // AI 可能返回："高"、"High"、"P0"、"紧急"、"很重要"...
});

// 好：用枚举约束
const Good = z.object({
  priority: z.enum(['P0', 'P1', 'P2', 'P3']).describe('优先级，P0最高P3最低'),
  // AI 只能返回这四个值之一
});
```

**这跟前端的 Select 组件逻辑一样** -- 与其给一个 input 让用户随便填，不如给一个 select 让用户从选项中选。枚举就是给 AI 的"下拉选项"。

### 嵌套结构的设计

复杂数据可以通过嵌套对象和数组来表达：

```typescript
const ArticleAnalysisSchema = z.object({
  title: z.string().describe('文章标题'),
  
  author: z.object({
    name: z.string().describe('作者姓名'),
    role: z.string().describe('作者职位/角色'),
  }).describe('作者信息'),
  
  sections: z.array(
    z.object({
      heading: z.string().describe('章节标题'),
      summary: z.string().describe('章节摘要，一句话概括'),
      keyPoints: z.array(z.string()).describe('关键要点，每个不超过20字'),
    })
  ).describe('文章各章节分析'),
  
  metadata: z.object({
    language: z.enum(['zh', 'en', 'ja', 'other']).describe('文章语言'),
    estimatedReadTime: z.number().describe('预计阅读时间，单位：分钟'),
    topics: z.array(z.string()).describe('文章涉及的主题标签'),
  }).describe('文章元数据'),
});
```

**前端类比**：这跟你设计 React 组件的 Props 类型一模一样 -- 复杂的 Props 用嵌套的 interface 表达，每一层都有明确的类型定义。

### 可选字段的处理

有些信息不一定能从输入中提取到，这时用 `.optional()` 或 `.nullable()`：

```typescript
const ContactSchema = z.object({
  name: z.string().describe('联系人姓名'),
  email: z.string().email().describe('邮箱地址'),
  phone: z.string().optional().describe('电话号码，如果文本中提到的话'),
  company: z.string().optional().describe('所在公司，如果文本中提到的话'),
  notes: z.string().optional().describe('其他备注信息'),
});
```

**注意**：不要把所有字段都设为可选。如果你的业务逻辑需要某个字段必须存在，就让它必填。这样如果 AI 实在无法从输入中提取出该信息，会报错而不是悄悄返回 `undefined` -- 显式的错误比隐式的 bug 好处理得多。

## 5.6 Union 类型和条件输出

### 一句话直觉

有时你需要 AI 根据不同情况返回不同结构的数据 -- 就像 TypeScript 的 discriminated union。

### 前端类比

在 TypeScript 中，你经常这样定义 API 响应类型：

```typescript
type ApiResponse = 
  | { status: 'success'; data: Product }
  | { status: 'error'; message: string; code: number }
  | { status: 'loading' };
```

这种模式叫 discriminated union -- 通过一个"判别字段"（这里是 `status`）来确定具体是哪种结构。AI 的输出也需要类似的能力。

### 在结构化输出中使用

```typescript
const ClassificationSchema = z.discriminatedUnion('type', [
  z.object({
    type: z.literal('bug_report'),
    severity: z.enum(['critical', 'major', 'minor']),
    component: z.string().describe('受影响的组件/模块'),
    stepsToReproduce: z.array(z.string()).describe('重现步骤'),
  }),
  z.object({
    type: z.literal('feature_request'),
    priority: z.enum(['high', 'medium', 'low']),
    description: z.string().describe('功能描述'),
    useCase: z.string().describe('使用场景'),
  }),
  z.object({
    type: z.literal('question'),
    topic: z.string().describe('问题主题'),
    relatedDocs: z.array(z.string()).optional().describe('可能相关的文档链接'),
  }),
]);

const { output: ticket } = await generateText({
  model: deepseek('deepseek-chat'),
  output: Output.object({ schema: ClassificationSchema }),
  prompt: `分类以下用户反馈：
  "登录页面点击按钮后一直转圈，刷新也没用，Chrome和Firefox都试过了"`,
});

// TypeScript 知道根据 type 字段，ticket 有不同的结构
if (ticket.type === 'bug_report') {
  console.log(ticket.severity);        // 类型正确
  console.log(ticket.stepsToReproduce); // 类型正确
}
```

**实际应用场景**：客服系统的工单自动分类、内容审核的多类型标注、表单数据的智能路由。

### 注意事项

使用 discriminated union 时要注意，并非所有模型都能很好地处理复杂的 union 类型。如果你发现某个模型在 union 类型上表现不好，可以考虑两种替代策略：

1. **两步法**：先用一次调用确定类型，再用对应的 schema 做第二次调用
2. **扁平化**：把所有字段放在一个对象里，用可选字段代替 union

```typescript
// 替代方案：扁平化 + 可选字段
const FlatTicketSchema = z.object({
  type: z.enum(['bug_report', 'feature_request', 'question']),
  // bug_report 的字段
  severity: z.enum(['critical', 'major', 'minor']).optional(),
  stepsToReproduce: z.array(z.string()).optional(),
  // feature_request 的字段
  priority: z.enum(['high', 'medium', 'low']).optional(),
  useCase: z.string().optional(),
  // 通用字段
  description: z.string(),
});
```

这种方案牺牲了一些类型精确度，但兼容性更好。

## 5.7 错误处理和重试策略

### 一句话直觉

AI 不是数据库查询，它有一定的"不确定性"。你需要为"输出不符合预期"的情况做好准备。

### 前端类比

你写前端时，不会假设每个 API 调用都成功，对吧？

```typescript
// 前端的错误处理
try {
  const res = await fetch('/api/data');
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  const data = schema.parse(await res.json()); // Zod 校验
} catch (error) {
  if (error instanceof z.ZodError) {
    // 数据格式不对
  } else if (error instanceof TypeError) {
    // 网络错误
  }
  // 降级/重试/展示错误
}
```

AI 结构化输出也需要同样的防御性编程。

### 常见的错误类型

**1. Schema 验证失败**

虽然 schema-based 模式很可靠，但在某些边界情况下仍可能出错：

```typescript
import { generateText, Output } from 'ai';

try {
  const { output } = await generateText({
    model,
    output: Output.object({ schema: ProductSchema }),
    prompt: '分析这个商品...',
  });
  // 正常使用 output
} catch (error) {
  if (error.name === 'AI_NoObjectGeneratedError') {
    // AI 无法生成符合 schema 的对象
    console.error('AI 无法按要求的格式输出');
  }
}
```

**2. 语义错误**

Schema 验证通过了，但数据语义上不合理。比如，价格是负数（schema 没限制），类别明显错误等。

```typescript
const schema = z.object({
  price: z.number().min(0).describe('商品价格，单位：元'), // 加上 min(0) 防止负数
  rating: z.number().min(1).max(5).describe('评分，1-5分'),
});
```

**3. 模型能力不足**

某些小模型可能不支持结构化输出，或者支持得不好。

### 重试策略

```typescript
async function generateWithRetry<T>(
  options: Parameters<typeof generateText>[0],
  maxRetries = 3
): Promise<T> {
  let lastError: Error | null = null;
  
  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      const { output } = await generateText(options);
      return output as T;
    } catch (error) {
      lastError = error as Error;
      console.warn(`第 ${attempt} 次尝试失败:`, error.message);
      
      if (attempt < maxRetries) {
        // 可以在重试时稍微调整 prompt，增加约束
        await new Promise(resolve => setTimeout(resolve, 1000 * attempt));
      }
    }
  }
  
  throw new Error(`${maxRetries} 次尝试后仍然失败: ${lastError?.message}`);
}
```

### 降级策略

当结构化输出反复失败时，考虑降级方案：

```typescript
async function analyzeProduct(description: string) {
  try {
    // 首选：结构化输出
    const { output } = await generateText({
      model: deepseek('deepseek-chat'),
      output: Output.object({ schema: ProductSchema }),
      prompt: `分析商品：${description}`,
    });
    return { source: 'structured', data: output };
  } catch {
    try {
      // 降级：用 generateText + JSON.parse
      const { text } = await generateText({
        model: deepseek('deepseek-chat'),
        prompt: `分析商品，以JSON格式返回name/price/category：${description}`,
      });
      const parsed = JSON.parse(text);
      const validated = ProductSchema.parse(parsed);
      return { source: 'text_parsed', data: validated };
    } catch {
      // 最终降级：返回原始文本
      const { text } = await generateText({
        model: deepseek('deepseek-chat'),
        prompt: `分析商品：${description}`,
      });
      return { source: 'raw_text', data: { rawAnalysis: text } };
    }
  }
}
```

**前端类比**：这跟你做图片加载降级一样 -- 先尝试 WebP，不支持就降级到 PNG，再不行就用占位图。关键是保证用户体验不会因为某个环节失败而完全崩溃。

## 5.8 底层原理：AI 如何做到输出符合 Schema？

这一节不影响你使用结构化输出，但理解原理能帮助你在出问题时做出更好的判断。

### Constrained Decoding（受约束解码）

我们在第1章讲过，AI 生成文本是逐个 token 预测的过程。每一步，模型会计算所有可能的下一个 token 的概率分布，然后从中选一个。

**Constrained Decoding** 的原理是：在每一步预测时，根据 schema 的约束，把不合法的 token 的概率设为 0。

举个例子，假设 schema 要求当前位置应该输出一个数字类型的值：

```
正常的概率分布：
  "hello" -> 0.15
  123     -> 0.25
  true    -> 0.10
  "world" -> 0.12
  456     -> 0.20
  ...

约束后的概率分布（只保留数字 token）：
  "hello" -> 0     ← 被屏蔽
  123     -> 0.56  ← 重新归一化
  true    -> 0     ← 被屏蔽
  "world" -> 0     ← 被屏蔽
  456     -> 0.44  ← 重新归一化
  ...
```

**前端类比**：这就像 `<input type="number">` -- 浏览器从键盘层面就阻止了你输入字母。不是"输入后校验"，而是"从源头阻止非法输入"。

### 不同模型的实现差异

需要注意的是，并非所有模型都用 constrained decoding 实现结构化输出：

- **OpenAI（GPT-5 等）**：支持原生的 structured output，通过 constrained decoding 在服务端实现
- **Anthropic（Claude 系列）**：通过 tool use 的机制来实现结构化输出，效果同样可靠
- **一些开源模型**：可能需要在推理框架（如 vLLM、Outlines）层面实现 constrained decoding

对于你作为使用者来说，Vercel AI SDK 屏蔽了这些底层差异 -- 你用同一套 `generateText` API，SDK 会根据不同的 model provider 采用对应的实现方式。这就是用 SDK 而不是直接调原始 API 的价值。

## 概念辨析

### 普通文本生成 vs 结构化输出

- **普通文本生成**（`generateText` 不带 output）：AI 自由发挥，返回自然语言文本。适合对话、写作等场景。
- **结构化输出**（`generateText` + `output`）：AI 按 schema 填写，返回结构化对象。适合数据提取、分类、分析等场景。
- **不是替代关系，是互补关系**。一个 Agent 里通常两个都会用到。

### JSON Mode vs Structured Output

- **JSON Mode**：只保证输出是合法 JSON，不保证结构。是一种"宽约束"。
- **Structured Output（Schema-based）**：保证输出符合指定的 schema。是一种"强约束"。
- JSON Mode 是 Structured Output 的"子集能力" -- Structured Output 包含了 JSON Mode 的保证，还额外保证了结构。

### Schema 的 describe vs Prompt

- **describe**：附加在 schema 字段上的描述，告诉 AI"这个字段应该是什么"。
- **prompt**：对任务的整体描述，告诉 AI"你要做什么"。
- 两者配合使用效果最好。prompt 说任务，describe 说结构细节。
- 常见误区：把所有格式要求都塞进 prompt 里 -- 其实大部分格式要求应该通过 schema 和 describe 来表达。

### 运行时校验 vs 编译期类型

- **编译期（TypeScript 类型）**：`generateText` 返回值自动带类型，IDE 有提示。但这只是"编译期的承诺"。
- **运行时（Zod 校验）**：Zod 在运行时会实际校验数据，确保数据真的符合 schema。
- 两者都需要。只有编译期类型没有运行时校验，等于掩耳盗铃。

## 灵魂拷问

> **Q1：为什么不能直接在 prompt 里说"请返回 JSON"就完事了？这和 JSON Mode 有什么本质区别？**

A：这个问题直击结构化输出的核心矛盾。

在 prompt 里说"请返回 JSON"，本质上是一种"软约束" -- 你是在用自然语言向 AI "请求"它按某种格式输出。但 AI 的本质是概率性的文本生成。它完全有可能：

1. 在 JSON 前面加一句"好的，以下是结果："
2. 用 Markdown 的 ```json 包裹
3. 输出不完整的 JSON（因为 token 限制截断了）
4. 字段名用了不同的写法

而 JSON Mode 是一种"硬约束" -- 它在模型的生成过程中从底层保证了输出一定是合法 JSON。这不是通过 prompt 实现的，而是通过 constrained decoding 或后处理机制实现的。

**打个比方**：prompt 约束像是在公路上立了个"限速100"的牌子，司机可能遵守也可能不遵守。JSON Mode 像是在车上安装了物理限速器，速度不可能超过100。

但即使是 JSON Mode，也只保证"是个合法 JSON"，不保证"是你要的那种 JSON"。这就是为什么需要 Schema-based 的结构化输出 -- 它不仅保证了 JSON 的语法正确，还保证了结构正确。

---

> **Q2：AI 是怎么做到保证输出符合 schema 的？底层原理是什么？**

A：核心技术叫 constrained decoding（受约束解码）。

回顾第1章：AI 生成文本是逐 token 的概率预测。每一步，模型会计算词汇表中每个 token 的概率，然后采样。Constrained decoding 在这个过程中加了一层"过滤器"。

假设 schema 定义了 `{ name: string, age: number }`，当 AI 已经输出了 `{"name": "张三", "age":` 这部分时，下一个 token 只能是数字的开头（0-9），所有非数字 token 的概率被设为 0。

这跟编译器的词法分析很像 -- 根据当前的"状态"（schema 上下文），只接受合法的"输入"（token）。

当然不同提供商的实现方式有差异。OpenAI 使用的是服务端的 constrained decoding，Anthropic 通过 tool use 参数传递来实现类似效果。但对你来说，这些差异被 SDK 屏蔽了。

有一个重要推论：**constrained decoding 可能会略微降低生成质量**。因为模型的概率分布被人为修改了。在绝大多数场景下这个影响可以忽略，但如果你发现某个 schema 下 AI 的输出质量明显变差，可以尝试简化 schema 或拆分成多次调用。

---

> **Q3：Schema 字段的 description 为什么那么重要？AI 真的会读它吗？**

A：真的会。而且不只是会读，它对 AI 的输出质量有决定性的影响。

你的 Zod schema 会被 AI SDK 转换成 JSON Schema，然后作为请求的一部分发送给模型。`description` 字段会被原样保留在 JSON Schema 中。模型在生成每个字段的值时，会参考这个 description 来理解"这个字段应该填什么"。

一个实验：

```typescript
// 没有 description
z.object({ score: z.number() })
// AI 可能输出：{ score: 85 }  -- 什么的分数？满分多少？不清楚

// 有 description
z.object({ score: z.number().describe('英语作文的语法正确率，0-100的百分比') })
// AI 会输出：{ score: 73 }  -- 明确知道是语法正确率的百分比
```

**description 就是给 AI 的"字段级 prompt"**。schema 描述结构，description 描述语义。两者结合，AI 才能既知道"格式是什么"，又知道"内容是什么"。

最佳实践：每个字段都写 description，特别是那些名字可能有歧义的字段。description 应该包含：字段的含义、值的范围或格式、必要的上下文。

---

> **Q4：如果你需要 AI 输出一个 100 行的复杂 JSON，可能会遇到什么问题？**

A：这是一个很实际的问题，涉及几个层面：

**Token 限制**：复杂的 JSON 输出会消耗大量的输出 token。如果输出 token 超过模型的限制，JSON 会被截断，导致解析失败。100 行的 JSON 大约需要 2000-5000 个 token（取决于字段值的长度），对于大多数模型来说没问题，但要注意留够余量。

**生成质量下降**：schema 越复杂，模型要同时"记住"的约束越多。字段之间的逻辑一致性可能下降。比如前面说"共有 5 个步骤"，后面的步骤数组可能只列了 3 个。

**延迟增加**：输出越长，生成时间越长。如果是用户等待的场景，100 行 JSON 可能要等 5-10 秒。

**解决策略**：

1. **拆分**：把一个大 schema 拆成多个小的 generateText 调用，每次提取一部分信息
2. **分层**：先提取顶层结构，再对每个部分做细化提取
3. **流式**：使用 `streamText` 流式输出，让用户能看到生成进度

```typescript
// 不好：一个超大的 schema
const GiantSchema = z.object({ /* 50个字段... */ });

// 好：拆分成多次调用
const BasicInfo = z.object({ name, price, category });
const DetailInfo = z.object({ description, specs, features });
const ReviewSummary = z.object({ avgRating, pros, cons });

const basic = await generateText({ output: Output.object({ schema: BasicInfo }), prompt });
const detail = await generateText({ output: Output.object({ schema: DetailInfo }), prompt });
const reviews = await generateText({ output: Output.object({ schema: ReviewSummary }), prompt });

const fullResult = { ...basic.output, ...detail.output, ...reviews.output };
```

> **Q5：结构化输出 vs 让 AI 输出文本再正则提取，各自的 trade-off 是什么？**

A：这两种方案有本质的哲学差异。

**结构化输出**的思路是：从生成阶段就约束 AI，让它只能输出合规的数据。

优点：
- 可靠性高（约束在生成层面）
- 代码简洁（不需要复杂的后处理）
- 类型安全（Zod 给你完整的 TS 类型）

缺点：
- 可能限制 AI 的表达能力（constrained decoding 会修改概率分布）
- 对模型有要求（不是所有模型都支持）
- Schema 设计本身是一项需要学习的技能

**文本 + 正则提取**的思路是：让 AI 自由表达，然后从输出中提取信息。

优点：
- 不限制 AI 的表达能力
- 不依赖模型的结构化输出能力
- 灵活性高

缺点：
- 正则写起来痛苦且脆弱
- 几乎不可能做到 100% 可靠
- 没有类型安全
- 维护成本高（AI 换个说法你的正则就失效了）

**总结**：在绝大多数场景下，结构化输出都是更好的选择。正则提取只在你处理遗留系统（不支持结构化输出的旧模型）或者需要从长文本中提取片段信息时才考虑。

---

> **Q6：结构化输出返回的数据一定是"正确"的吗？Schema 验证通过 = 数据可靠？**

A：这是一个非常好的追问。答案是否定的。

Schema 验证只保证了"格式正确"，不保证"语义正确"。举个例子：

```typescript
const schema = z.object({
  city: z.string().describe('用户所在城市'),
  temperature: z.number().describe('当前气温，摄氏度'),
});

// AI 返回：{ city: "北京", temperature: 25 }
// Schema 验证通过！但 temperature 可能是编造的 -- AI 并不知道此刻北京的真实气温
```

Schema 验证通过只意味着：
1. 返回了一个对象
2. city 是字符串
3. temperature 是数字

它不保证：
1. 城市名是真实存在的
2. 气温是此刻的实时数据
3. 信息来源可靠

**这就是"幻觉"在结构化输出中的体现** -- AI 可能会编造看起来合理但实际上错误的数据，而且因为格式完美，你更容易信以为真。

应对策略：
- 对关键数据做业务层校验（价格范围、日期合理性等）
- 不要让 AI 输出需要实时信息的字段（除非配合 tool use 获取实时数据）
- 在 Zod 中加上更严格的约束（`.min()`, `.max()`, `.regex()` 等）

> **Q7：流式结构化输出（streamText）和非流式（generateText）什么时候用哪个？**

A：判断标准和 `streamText` vs `generateText` 一样 -- 看用户是否需要等待。

`generateText` 是"一锤子买卖"，等所有内容都生成完了才返回。适合后台任务、数据管道等不需要实时反馈的场景。

`streamText` 是流式返回，每生成一部分就返回一部分（partial object）。适合前端需要展示生成进度的场景。

```typescript
import { streamText } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';

const { partialOutputStream } = streamText({
  model: deepseek('deepseek-chat'),
  output: Output.object({ schema: RecipeSchema }),
  prompt: '给我一个番茄炒蛋的菜谱',
});

for await (const partialObject of partialOutputStream) {
  // partialObject 是逐步构建的
  // 第一次可能是 { name: "番茄炒蛋" }
  // 第二次可能是 { name: "番茄炒蛋", difficulty: "简单" }
  // 第三次可能是 { name: "番茄炒蛋", difficulty: "简单", cookingTime: 15 }
  // ...逐步完整
  console.log(partialObject);
}
```

**前端类比**：`generateText` 就像 `await fetch()` 等完整响应，`streamText` 就像用 `ReadableStream` 流式处理。在用户面对的界面中，流式体验几乎总是更好的选择。

## 最佳实践

### DO

- **DO 给每个字段写 `.describe()`**，尤其是名字可能有歧义的字段。这是提升 AI 输出质量最直接的方式。

- **DO 使用枚举约束有限集合的字段**。`z.enum(['high', 'medium', 'low'])` 比 `z.string()` 可靠 100 倍。

- **DO 在 Zod schema 中加上值域约束**。`z.number().min(0).max(5)` 比裸 `z.number()` 能防住很多离谱的值。

- **DO 对关键数据做业务层二次校验**。Schema 验证通过不等于数据正确，幻觉可以藏在完美的格式里。

- **DO 使用 streamText 做面向用户的输出**。用户不想盯着白屏等 5 秒。

- **DO 设计 schema 时考虑 AI 的能力边界**。不要让 AI 输出它不可能知道的信息（如实时数据、精确计算结果）。

### DON'T

- **DON'T 在生产环境用 prompt 约束来代替结构化输出**。"请用 JSON 格式回答"在 demo 里看着行，上线后会让你加班。

- **DON'T 设计过于庞大的 schema**。超过 15-20 个字段时，考虑拆分成多次调用。复杂度越高，输出质量越低。

- **DON'T 把所有字段都设为 optional**。如果业务上某个字段是必需的，就让它必填。显式的报错比隐式的 undefined 好处理。

- **DON'T 忽略错误处理**。AI 不是数据库，总有小概率的异常情况。没有 try-catch 的 generateText 调用是定时炸弹。

- **DON'T 假设 Schema 验证通过 = 数据正确**。格式正确不等于语义正确，AI 可能会编造合理的假数据。

- **DON'T 在 schema 的 description 中写模棱两可的描述**。"相关信息"不如"用户最近30天内购买的商品数量"。

### 实战1：用户反馈智能分类系统

一个完整的用户反馈分析系统，将自由文本的用户反馈转化为结构化的工单数据：

```typescript
import { generateText, Output } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';
import { z } from 'zod';

// 定义反馈分析的输出结构
const FeedbackAnalysisSchema = z.object({
  // 基本分类
  category: z.enum([
    'bug',           // 功能异常
    'feature',       // 功能建议
    'performance',   // 性能问题
    'ui',            // 界面问题
    'documentation', // 文档问题
    'other',         // 其他
  ]).describe('反馈的类别'),

  // 情感分析
  sentiment: z.object({
    polarity: z.enum(['positive', 'negative', 'neutral']).describe('情感倾向'),
    intensity: z.number().min(1).max(5).describe('情感强度，1最弱5最强'),
  }).describe('用户的情感分析'),

  // 优先级评估
  priority: z.enum(['P0', 'P1', 'P2', 'P3']).describe(
    'P0=紧急（影响核心功能），P1=高（影响使用体验），P2=中（有替代方案），P3=低（锦上添花）'
  ),

  // 关键信息提取
  summary: z.string().describe('一句话概括反馈内容，不超过50字'),
  
  affectedFeature: z.string().describe('受影响的功能模块名称'),
  
  userExpectation: z.string().describe('用户期望的行为是什么'),
  
  currentBehavior: z.string().describe('当前实际的行为是什么'),

  // 标签
  tags: z.array(z.string()).describe('相关标签，如"登录"、"支付"、"移动端"等'),

  // 可操作性
  isActionable: z.boolean().describe('这条反馈是否包含足够信息可以直接采取行动'),
  
  suggestedAction: z.string().optional().describe(
    '如果可操作，建议的下一步行动是什么'
  ),
});

// 类型自动推导
type FeedbackAnalysis = z.infer<typeof FeedbackAnalysisSchema>;

// 分析函数
async function analyzeFeedback(feedbackText: string): Promise<FeedbackAnalysis> {
  const { output } = await generateText({
    model: deepseek('deepseek-chat'),
    output: Output.object({ schema: FeedbackAnalysisSchema }),
    instructions: `你是一位经验丰富的产品经理，擅长分析用户反馈。
请根据用户的反馈内容，准确提取关键信息并分类。
注意区分用户的情感强度——抱怨和愤怒是不同的。
如果反馈信息不够具体，将 isActionable 设为 false。`,
    prompt: `请分析以下用户反馈：\n\n${feedbackText}`,
  });

  return output;
}

// 使用示例
async function main() {
  const feedback = `
    你们的导出功能是不是坏了？？我选了"导出为Excel"，等了5分钟，
    最后下载下来的文件打不开！！！之前都是好的，最近一次更新之后就不行了。
    我急着要报表给老板，能不能赶紧修一下？？？
  `;

  const analysis = await analyzeFeedback(feedback);
  
  console.log('分类:', analysis.category);           // "bug"
  console.log('优先级:', analysis.priority);          // "P1"
  console.log('情感:', analysis.sentiment.polarity);  // "negative"
  console.log('强度:', analysis.sentiment.intensity); // 4 或 5
  console.log('摘要:', analysis.summary);
  console.log('标签:', analysis.tags);                // ["导出", "Excel", "文件损坏"]
  console.log('可操作:', analysis.isActionable);      // true
  console.log('建议:', analysis.suggestedAction);
}

main();
```

### 实战2：内容审核流水线

一个支持多种内容类型的审核系统，使用 discriminated union 处理不同类型的审核结果：

```typescript
import { generateText, Output } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';
import { z } from 'zod';

// 审核结果的 schema -- 使用 discriminated union
const ModerationResultSchema = z.object({
  decision: z.enum(['approved', 'rejected', 'needs_review']).describe(
    'approved=通过，rejected=拒绝，needs_review=需要人工复审'
  ),

  // 各维度的风险评估
  riskAssessment: z.object({
    violence: z.number().min(0).max(1).describe('暴力内容风险，0-1'),
    harassment: z.number().min(0).max(1).describe('骚扰内容风险，0-1'),
    spam: z.number().min(0).max(1).describe('垃圾信息风险，0-1'),
    misinformation: z.number().min(0).max(1).describe('虚假信息风险，0-1'),
    adult: z.number().min(0).max(1).describe('成人内容风险，0-1'),
  }).describe('各维度的风险评分'),

  // 具体问题
  flaggedIssues: z.array(
    z.object({
      type: z.string().describe('问题类型'),
      excerpt: z.string().describe('有问题的原文片段'),
      reason: z.string().describe('标记原因'),
      severity: z.enum(['low', 'medium', 'high']).describe('严重程度'),
    })
  ).describe('标记的具体问题列表，没有问题则为空数组'),

  // 审核理由
  reasoning: z.string().describe('做出该审核决定的详细理由'),
  
  // 置信度
  confidence: z.number().min(0).max(1).describe('对审核决定的置信度'),
});

type ModerationResult = z.infer<typeof ModerationResultSchema>;

async function moderateContent(content: string): Promise<ModerationResult> {
  const { output } = await generateText({
    model: deepseek('deepseek-chat'),
    output: Output.object({ schema: ModerationResultSchema }),
    instructions: `你是一位内容审核专家。请客观评估内容的风险，不要过度审核。
规则：
- 任何维度风险 > 0.7 → rejected
- 任何维度风险在 0.4-0.7 → needs_review
- 所有维度风险 < 0.4 → approved
- 不确定时倾向于 needs_review，让人工复核`,
    prompt: `请审核以下内容：\n\n${content}`,
  });

  return output;
}

// 批量审核
async function moderateBatch(contents: string[]) {
  const results = await Promise.all(
    contents.map(async (content, index) => {
      const result = await moderateContent(content);
      return { index, content: content.slice(0, 50) + '...', ...result };
    })
  );

  // 按审核结果分组
  const approved = results.filter(r => r.decision === 'approved');
  const rejected = results.filter(r => r.decision === 'rejected');
  const needsReview = results.filter(r => r.decision === 'needs_review');

  console.log(`审核完成：${approved.length} 通过，${rejected.length} 拒绝，${needsReview.length} 待复审`);
  
  return { approved, rejected, needsReview };
}
```

### 实战3：streamText 的前端集成

展示如何在 React 组件中使用流式结构化输出：

```typescript
// ---- 后端 API Route (Next.js App Router) ----
// app/api/analyze/route.ts
import { streamText, Output, toTextStream, createTextStreamResponse } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';
import { z } from 'zod';

const AnalysisSchema = z.object({
  title: z.string().describe('分析报告标题'),
  summary: z.string().describe('一段话概括分析结果'),
  keyFindings: z.array(
    z.object({
      finding: z.string().describe('发现'),
      impact: z.enum(['high', 'medium', 'low']).describe('影响程度'),
    })
  ).describe('关键发现'),
  recommendation: z.string().describe('总结建议'),
  score: z.number().min(0).max(100).describe('综合评分'),
});

export async function POST(req: Request) {
  const { text } = await req.json();

  const result = streamText({
    model: deepseek('deepseek-chat'),
    output: Output.object({ schema: AnalysisSchema }),
    prompt: `请分析以下内容：\n\n${text}`,
  });

  return createTextStreamResponse({
    stream: toTextStream({ stream: result.stream }),
  });
}

// ---- 前端组件 ----
// components/AnalysisPanel.tsx
'use client';
import { useObject } from '@ai-sdk/react';
import { z } from 'zod';

// 同一个 Schema 前后端复用
const AnalysisSchema = z.object({
  title: z.string(),
  summary: z.string(),
  keyFindings: z.array(
    z.object({
      finding: z.string(),
      impact: z.enum(['high', 'medium', 'low']),
    })
  ),
  recommendation: z.string(),
  score: z.number().min(0).max(100),
});

export function AnalysisPanel() {
  const { object, submit, isLoading, error } = useObject({
    api: '/api/analyze',
    output: Output.object({ schema: AnalysisSchema }),
  });

  return (
    <div>
      <button
        onClick={() => submit({ text: '要分析的文本内容...' })}
        disabled={isLoading}
      >
        {isLoading ? '分析中...' : '开始分析'}
      </button>

      {error && <div className="error">分析失败: {error.message}</div>}

      {/* 流式渲染 -- 各字段逐步出现 */}
      {object && (
        <div className="analysis-result">
          {object.title && <h2>{object.title}</h2>}
          {object.summary && <p>{object.summary}</p>}
          
          {object.score !== undefined && (
            <div className="score">
              综合评分: <strong>{object.score}</strong>/100
            </div>
          )}

          {object.keyFindings && object.keyFindings.length > 0 && (
            <ul>
              {object.keyFindings.map((finding, i) => (
                <li key={i}>
                  <span className={`impact-${finding?.impact}`}>
                    [{finding?.impact}]
                  </span>
                  {finding?.finding}
                </li>
              ))}
            </ul>
          )}

          {object.recommendation && (
            <div className="recommendation">
              <h3>建议</h3>
              <p>{object.recommendation}</p>
            </div>
          )}
        </div>
      )}
    </div>
  );
}
```

**注意流式渲染中的可选链操作符**（`?.`）：因为对象是逐步构建的，任何字段在某个时刻可能还不存在，所以每个字段访问都要用可选链。

**Step 4：添加错误处理**

实现带重试和降级的日程提取。

**Step 5：前端集成**

## 本章小结

本章解决了一个 Agent 开发的基础问题：**如何让 AI 的输出从"人类可读"变为"程序可用"**。

**核心要点**：

1. **三种方式递进**：Prompt 约束（不可靠）→ JSON Mode（保证 JSON）→ Schema-based（保证结构）。生产环境请直接用第三种。

2. **Zod 是桥梁**：它同时解决了 schema 定义、运行时校验、类型推导三个问题。一次定义，三处受益。

3. **description 是秘密武器**：给 schema 字段写好描述，相当于给 AI 做字段级的 prompt engineering。这是提升输出质量最被低估的技巧。

4. **结构化输出不是万能的**：Schema 验证通过只保证格式正确，不保证语义正确。AI 的幻觉可以穿着完美格式的外衣出现。

5. **工程化思维不能丢**：错误处理、重试机制、降级策略 -- 这些前端工程的最佳实践，在 AI 开发中同样适用，甚至更重要（因为 AI 的不确定性比传统 API 大）。

**一句话总结**：`generateText` + Zod Schema 就是 AI 世界的"强类型 API 契约" -- 让 AI 的输出像后端接口一样可靠、可预测、可直接使用。
