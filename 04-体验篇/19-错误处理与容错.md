# 第19章：错误处理与容错 -- 让你的 Agent 不再脆弱

## 引言

你写过这样的代码吗？

```typescript
const result = await generateText({ model, prompt });
console.log(result.text);
```

两行代码，跑 demo 的时候完美运行。但你知道线上会发生什么吗？

API 限流了——429。模型服务挂了——500。请求超时了——网络错误。模型返回了一堆胡说八道——幻觉。工具调用的参数错了——执行失败。工具调用成功了但返回的数据不对——静悄悄的错误。Agent 完成了所有步骤但结果是错的——业务逻辑错误。

传统 Web 应用的错误处理你很熟——HTTP 状态码告诉你发生了什么，try-catch 兜住异常，该重试重试，该降级降级。但 AI 应用的"错误"有一个根本性的不同：**很多时候它不会报错，它只是"不太对"**。

模型返回了一个看起来合理但实际错误的回答，这算不算错误？技术上不算——没有异常抛出，HTTP 200，JSON 格式正确。但业务上绝对算——用户得到了错误的信息并据此做了决策。

这类"软错误"是 AI 应用中最危险的。因为硬错误会报警、会被监控捕获、会阻止流程继续。但软错误会悄悄溜过所有防线，穿着正确的格式外衣，被用户当成真的。

这一章的目标是建立一套完整的错误处理体系——从 API 层的硬错误到模型层的软错误，从简单的重试到复杂的降级和兜底策略。读完之后，你的 Agent 应该像一个经验丰富的老司机——不是不会遇到问题，而是遇到问题时知道怎么处理，不会翻车。

## 19.1 AI 应用的错误和传统应用不同

### 一句话直觉

传统应用的错误像交通事故——明显、可见、有现场。AI 应用的错误像慢性病——不易察觉，但危害更大。

### 前端类比

你写 React 组件时，错误是确定性的：

```typescript
// 传统错误——确定性的
const user = await fetch('/api/user/123');
if (user.status === 404) {
  // 明确知道：用户不存在
  showError('用户不存在');
}
if (user.status === 500) {
  // 明确知道：服务器出错了
  showError('服务器异常，请稍后重试');
}
```

每个错误都有明确的信号（HTTP 状态码），你知道发生了什么，知道该如何处理。

但 AI 应用是这样的：

```typescript
import { deepseek } from "@ai-sdk/deepseek";

// AI 的"错误"——不确定性的
const result = await generateText({
  model: deepseek('deepseek-chat'),
  prompt: '北京今天的天气怎么样？'
});

console.log(result.text);
// "北京今天晴，气温22°C，适合出行。"
// 
// 这个回答...
// HTTP 200 ✅
// JSON 格式正确 ✅
// 语句通顺 ✅
// 但内容是编造的 ❌（模型不知道实时天气）
// 
// 没有任何技术层面的"错误信号"
```

这就是 AI 应用错误处理的核心难题：**最危险的错误不会触发 catch 块**。

### 详细原理

让我们建立一个 AI 应用的错误分类体系。把错误按"发生在哪一层"来分类，从底层到上层：

**第一层：API/基础设施层错误**

这是最容易处理的——和传统 Web 应用的错误处理完全一样。

| 错误类型 | 状态码 | 含义 | 处理方式 |
|---------|--------|------|---------|
| 限流 | 429 | 请求太频繁 | 退避重试 |
| 服务器错误 | 500/502/503 | 模型服务故障 | 切换备用模型或重试 |
| 认证失败 | 401 | API Key 无效 | 告警，不要重试 |
| 超时 | - | 请求超时 | 重试或降级 |
| 网络错误 | - | 连不上服务器 | 检查网络，重试 |
| 输入过长 | 400 | 超过上下文窗口 | 裁剪输入，不要重试 |

**第二层：模型层错误**

这一层开始变得棘手。模型可能"成功"返回了结果，但结果本身有问题。

- **幻觉**：模型编造了不存在的信息。HTTP 200，格式完美，内容错误。
- **拒绝回答**：模型认为你的请求违反了安全策略，拒绝响应。不是报错，而是返回"我无法回答这个问题"。
- **偏离指令**：你让它返回 JSON，它返回了一段散文。你让它用中文回答，它用英文回答了。
- **格式错误**：你用了 `generateText`，但模型返回的 JSON 不符合 schema（极少见但会发生）。
- **重复和退化**：模型陷入了循环，反复输出同样的内容。

**第三层：工具层错误**

当 Agent 调用工具时，工具本身可能出错。

- **参数错误**：模型生成的工具参数不合法。比如日期格式错误、数值超出范围。
- **执行失败**：工具调用了外部 API 但外部 API 挂了。
- **返回异常**：工具执行成功了但返回的数据不符合预期。比如查询数据库，SQL 没报错，但返回了空结果（可能是查询条件有误）。
- **副作用已发生但后续失败**：工具发出了一封邮件（副作用已发生），但 Agent 后续步骤失败了。邮件收不回来。

**第四层：业务层错误**

这是最高层、最难检测的错误。Agent 成功完成了所有步骤，没有任何技术错误，但最终结果不符合业务预期。

- Agent 帮用户订了机票，但订的是错误的日期
- Agent 分析了数据，但遗漏了一个关键因素
- Agent 写了一份报告，结论正确但论据有误

### 深层追问

**为什么说"软错误"比"硬错误"更危险？**

硬错误（500、超时、异常）有一个天然的优势：**它会被发现**。监控系统会告警，用户会看到错误提示，开发者会去修。

但软错误（幻觉、偏离指令、业务结果不对）默默地通过了所有检查，被当成正确结果交付给了用户。用户可能基于这个错误结果做了决策，直到很久以后才发现问题。这就像食品安全中的慢性中毒——急性食物中毒（硬错误）很快就会被发现和处理，但重金属超标（软错误）可能几年后才发现。

所以 AI 应用的错误处理不能只做"异常捕获"——那只能抓住第一层错误。你还需要"结果校验"来应对第二到四层错误。

## 19.2 重试策略：不只是"再来一次"

### 一句话直觉

重试是错误处理的第一道防线，但粗暴的重试会把问题变得更糟。

### 前端类比

你一定写过网络请求的重试逻辑。最原始的版本：

```typescript
// 菜鸟版重试——立刻重试3次
async function fetchWithRetry(url: string) {
  for (let i = 0; i < 3; i++) {
    try {
      return await fetch(url);
    } catch (e) {
      if (i === 2) throw e;
    }
  }
}
```

这有什么问题？如果服务器因为过载而返回 500，你立刻重试 3 次 = 给已经过载的服务器又加了 3 次压力。如果 1000 个客户端同时这样做，服务器直接被打死。

### 详细原理

**指数退避（Exponential Backoff）**

核心思想：每次重试的间隔翻倍。第一次等 1 秒，第二次等 2 秒，第三次等 4 秒……

为什么？因为如果服务器过载了，它需要时间恢复。你越早重试，服务器越难恢复。逐步增大等待时间，给服务器喘息的空间。

```typescript
async function retryWithExponentialBackoff<T>(
  fn: () => Promise<T>,
  options: {
    maxRetries?: number;
    baseDelay?: number;     // 基础延迟（毫秒）
    maxDelay?: number;      // 最大延迟（毫秒）
  } = {}
): Promise<T> {
  const { maxRetries = 3, baseDelay = 1000, maxDelay = 30000 } = options;

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await fn();
    } catch (error) {
      if (attempt === maxRetries) throw error;

      // 判断是否值得重试
      if (!isRetryableError(error)) throw error;

      // 指数退避：1s, 2s, 4s, 8s...
      const delay = Math.min(baseDelay * Math.pow(2, attempt), maxDelay);
      console.log(`第 ${attempt + 1} 次重试，等待 ${delay}ms...`);
      await sleep(delay);
    }
  }
  throw new Error('不会到达这里');
}

function isRetryableError(error: unknown): boolean {
  if (error instanceof Error) {
    const message = error.message.toLowerCase();
    // 429 限流、500 服务器错误、网络错误——值得重试
    if (message.includes('429') || message.includes('rate limit')) return true;
    if (message.includes('500') || message.includes('502') || message.includes('503')) return true;
    if (message.includes('timeout') || message.includes('network')) return true;
    // 401 认证失败、400 参数错误——重试也没用
    if (message.includes('401') || message.includes('400')) return false;
  }
  return false;
}

function sleep(ms: number): Promise<void> {
  return new Promise(resolve => setTimeout(resolve, ms));
}
```

**带抖动的退避（Jittered Backoff）**

纯指数退避有一个问题：如果 1000 个客户端同时失败，它们会在完全相同的时间点重试（1秒后、2秒后、4秒后……），造成**重试风暴**——周期性的请求洪峰。

解决方案：在延迟中加入随机抖动。

```typescript
// 带抖动的指数退避
function getDelayWithJitter(attempt: number, baseDelay: number, maxDelay: number): number {
  const exponentialDelay = baseDelay * Math.pow(2, attempt);
  const cappedDelay = Math.min(exponentialDelay, maxDelay);
  // 在 [0, cappedDelay] 之间随机选择
  return Math.random() * cappedDelay;
}
```

前端类比：这就像高速公路的匝道信号灯——不是让所有车同时上高速，而是随机间隔放行，避免拥堵。

**重试 Budget（重试预算）**

不是每次请求都应该无限重试。你需要一个全局的"重试预算"——限制在一定时间窗口内的总重试次数。

```typescript
class RetryBudget {
  private retryCount = 0;
  private windowStart = Date.now();

  constructor(
    private maxRetries: number,  // 时间窗口内最大重试次数
    private windowMs: number,     // 时间窗口大小
  ) {}

  canRetry(): boolean {
    const now = Date.now();
    if (now - this.windowStart > this.windowMs) {
      // 新的时间窗口
      this.retryCount = 0;
      this.windowStart = now;
    }
    return this.retryCount < this.maxRetries;
  }

  recordRetry(): void {
    this.retryCount++;
  }
}

// 每分钟最多重试 10 次
const budget = new RetryBudget(10, 60000);
```

为什么需要重试预算？因为在级联故障中，没有预算限制的重试会像滚雪球一样放大问题。上游服务挂了，你的 Agent 疯狂重试 → 中间件被重试请求淹没 → 中间件也挂了 → 更多的重试……这就是分布式系统中经典的"重试风暴"。

**幂等性考量：重试安全吗？**

这是最容易被忽略的问题。重试一个"查询天气"的工具调用是安全的——查两次天气不会有副作用。但重试一个"发送邮件"的工具调用呢？用户可能收到两封一样的邮件。

```typescript
// 危险：重试有副作用的操作
try {
  await toolCall('sendEmail', { to: 'boss@company.com', content: '...' });
} catch (e) {
  // 如果邮件其实已经发出去了，只是确认超时了呢？
  // 重试 = 发两封邮件
  await toolCall('sendEmail', { to: 'boss@company.com', content: '...' });
}
```

解决方案：

1. **幂等键（Idempotency Key）**：每次调用带一个唯一 ID，工具端保证同一 ID 的请求只执行一次

```typescript
import { randomUUID } from 'crypto';

async function safeToolCall(toolName: string, args: Record<string, unknown>) {
  const idempotencyKey = randomUUID();

  return retryWithExponentialBackoff(
    () => executeTool(toolName, { ...args, _idempotencyKey: idempotencyKey })
  );
}
```

2. **分类处理**：只对安全的操作自动重试

```typescript
const SAFE_TO_RETRY: Record<string, boolean> = {
  searchDatabase: true,  // 查询——安全
  getWeather: true,      // 查询——安全
  sendEmail: false,      // 副作用——不安全
  deleteRecord: false,   // 副作用——不安全
  createOrder: false,    // 副作用——不安全
};
```

### 深层追问

**429 限流错误应该怎么重试？**

429 是一个特殊的错误。它不是说"服务挂了"，而是说"你请求太频繁了，歇一会儿"。大多数 API 会在 429 的响应头里返回 `Retry-After`，告诉你应该等多久。

```typescript
async function handleRateLimit(response: Response): Promise<number> {
  const retryAfter = response.headers.get('Retry-After');
  if (retryAfter) {
    // Retry-After 可能是秒数，也可能是日期
    const seconds = parseInt(retryAfter, 10);
    if (!isNaN(seconds)) return seconds * 1000;
    // 如果是日期格式
    const date = new Date(retryAfter);
    return date.getTime() - Date.now();
  }
  // 没有 Retry-After 头，用默认退避
  return 5000;
}
```

另一个常被忽略的点：不同模型提供商的限流策略不同。有些按请求数限流（RPM），有些按 Token 数限流（TPM），有些按并发数限流。你需要了解你使用的 API 的限流维度，然后相应地设计重试策略。

## 19.3 降级策略（Fallback）：当最优方案不可用时

### 一句话直觉

降级不是失败，是一种有计划的退让——放弃最好的，保住能用的。

### 前端类比

你一定做过前端的降级方案：

```typescript
// 图片加载降级
<img 
  src="hero.webp"          // 最优：WebP 格式
  onError={(e) => {
    e.currentTarget.src = "hero.jpg";   // 降级1：JPG 格式
    e.currentTarget.onerror = () => {
      e.currentTarget.src = "placeholder.svg";  // 降级2：占位图
    };
  }}
/>

// API 降级
async function getUserData(id: string) {
  try {
    return await fetch(`/api/v2/users/${id}`);  // 最优：新版 API
  } catch {
    return await fetch(`/api/v1/users/${id}`);  // 降级：旧版 API
  }
}
```

AI 应用的降级逻辑是完全一样的，只不过降级的维度更多。

### 详细原理

AI 应用有三个维度的降级：

**维度一：模型降级**

主模型不可用时，切换到备用模型。

> **注意**：模型降级要「换一个不共命运的服务商」才有意义，所以这里的示例用了 **DeepSeek + Claude 两个 provider** 做容灾，需要同时配置 `DEEPSEEK_API_KEY` 和 `ANTHROPIC_API_KEY`。如果只想要单 key，把 secondary 也换成 DeepSeek 的不同模型即可。

```typescript
import { generateText } from 'ai';
import { deepseek } from "@ai-sdk/deepseek";
import { anthropic } from "@ai-sdk/anthropic";

interface ModelConfig {
  model: Parameters<typeof generateText>[0]['model'];
  name: string;
  tier: 'primary' | 'secondary' | 'fallback';
}

const MODEL_CHAIN: ModelConfig[] = [
  { model: deepseek('deepseek-reasoner'), name: 'DeepSeek Reasoner', tier: 'primary' },
  { model: anthropic('claude-sonnet-5-5'), name: 'Claude Sonnet', tier: 'secondary' },
  { model: deepseek('deepseek-chat'), name: 'DeepSeek Chat', tier: 'fallback' },
];

async function generateWithFallback(
  params: Omit<Parameters<typeof generateText>[0], 'model'>
): Promise<{
  text: string;
  modelUsed: string;
  tier: string;
}> {
  for (const config of MODEL_CHAIN) {
    try {
      const result = await generateText({
        ...params,
        model: config.model,
      });
      return {
        text: result.text,
        modelUsed: config.name,
        tier: config.tier,
      };
    } catch (error) {
      console.warn(`${config.name} 失败:`, error);
      // 如果是最后一个模型也失败了，抛出错误
      if (config === MODEL_CHAIN[MODEL_CHAIN.length - 1]) {
        throw new Error(`所有模型都不可用: ${(error as Error).message}`);
      }
      // 否则尝试下一个模型
    }
  }
  throw new Error('不会到达这里');
}

// 使用
const { text, modelUsed, tier } = await generateWithFallback({
  instructions: 'You are a helpful assistant.',
  prompt: '解释什么是 React Server Components',
});

if (tier !== 'primary') {
  console.warn(`注意：使用了备用模型 ${modelUsed}`);
  // 可以在 UI 上提示用户当前使用的是备用模型
}
```

**模型降级的陷阱**：不同模型对 System Prompt 的响应方式可能不同。你的 Prompt 在 GPT-5 上测试得很好，切到 Claude 可能效果不一样。最佳实践是：降级模型也要经过 Prompt 测试，确保基本质量。

**维度二：功能降级**

Agent 模式失败时，降级为更简单的模式。

```typescript
import { deepseek } from "@ai-sdk/deepseek";

async function handleUserQuery(query: string) {
  try {
    // 最优：完整的 Agent 模式（可以调用工具、多步推理）
    return await runAgent({
      query,
      tools: [searchTool, databaseTool, chartTool],
      stopWhen: isStepCount(10),
    });
  } catch (agentError) {
    console.warn('Agent 模式失败，降级为 RAG 模式');
    try {
      // 降级1：RAG 模式（检索增强，但不调用工具）
      const context = await searchKnowledgeBase(query);
      return await generateText({
        model: deepseek('deepseek-chat'),
        instructions: '基于以下参考资料回答用户问题。如果资料中没有相关信息，请明确说明。',
        prompt: `参考资料：\n${context}\n\n用户问题：${query}`,
      });
    } catch (ragError) {
      console.warn('RAG 模式失败，降级为直接问答');
      try {
        // 降级2：直接问答（没有工具也没有检索）
        return await generateText({
          model: deepseek('deepseek-chat'),
          instructions: '你是一个有帮助的助手。如果你不确定答案，请明确说明。',
          prompt: query,
        });
      } catch (directError) {
        // 降级3：人工兜底
        return {
          text: '抱歉，AI 助手当前不可用。您的问题已记录，我们的人工客服将在 24 小时内回复您。',
          needsHumanFollowup: true,
        };
      }
    }
  }
}
```

功能降级的核心原则：**宁可给用户一个不那么完美的答案，也不要给用户一个错误页面**。

**维度三：人工兜底**

当 AI 完全无法处理时，转人工。

```typescript
interface EscalationConfig {
  maxAutoRetries: number;    // 自动重试次数用完
  confidenceThreshold: number; // AI 置信度低于阈值
  sensitiveTopics: string[];   // 敏感话题直接转人工
}

async function handleWithEscalation(
  query: string,
  config: EscalationConfig
): Promise<{ text: string; escalated: boolean }> {
  // 敏感话题检测
  const isSensitive = config.sensitiveTopics.some(topic =>
    query.toLowerCase().includes(topic)
  );
  if (isSensitive) {
    return {
      text: '这个问题涉及敏感领域，我已为您转接人工客服。',
      escalated: true,
    };
  }

  try {
    const result = await generateWithFallback({
      instructions: '...',
      prompt: query,
    });

    // 这里可以加一个置信度评估
    // 如果回答质量太低，也转人工
    return { text: result.text, escalated: false };
  } catch {
    return {
      text: '抱歉，我暂时无法回答这个问题。已为您转接人工服务。',
      escalated: true,
    };
  }
}
```

### 深层追问

**模型降级可能导致回答质量下降，用户更希望"慢但准"还是"快但可能不太准"？**

这没有标准答案，取决于业务场景。

- **数据分析、法律咨询、医疗建议**：用户希望"慢但准"。宁可等长一点，也不要有错误的分析。这种场景下，降级到弱模型不如直接告诉用户"当前服务不稳定，请稍后重试"。

- **闲聊、内容推荐、翻译**：用户希望"快且有"。降级到弱模型也能给出基本可用的结果，总比什么都没有好。

- **客服场景**：看问题的紧急程度。简单问题降级回答，复杂问题转人工。

最佳实践是：**让用户知道当前的服务状态**。如果降级了，在 UI 上提示"当前使用备用模型，回答质量可能有所下降"——让用户自己判断是接受这个回答还是稍后重试。这和 17 章讲的信任建设是一脉相承的。

## 19.4 幻觉检测与防护

### 一句话直觉

幻觉是 AI 的"自信地胡说八道"——它不知道自己不知道。你需要一套机制来帮它（和用户）意识到这一点。

### 前端类比

想象你调了一个后端 API，它返回了一个 JSON，所有字段都有值，格式完美。但某些字段的值是后端"编的"——不是从数据库查出来的，而是后端程序员偷懒写了个随机生成器。

你作为前端怎么发现？几乎不可能——因为数据格式完全正确，只有值不对。唯一的办法是交叉验证——用另一个数据源来校验。

幻觉检测做的就是这件事——用其他方式来验证 AI 的输出。

### 详细原理

**策略一：基于 RAG 的事实核验**

如果 AI 的回答应该基于你的知识库，你可以检查回答中的关键信息是否有检索文档支撑。

```typescript
import { generateText, Output } from 'ai';
import { deepseek } from "@ai-sdk/deepseek";
import { z } from 'zod';

interface FactCheckResult {
  claim: string;
  supported: boolean;
  source?: string;
  confidence: number;
}

async function factCheckResponse(
  aiResponse: string,
  retrievedDocuments: string[]
): Promise<FactCheckResult[]> {
  // 1. 从 AI 回答中提取关键声明
  const { output: claims } = await generateText({
    model: deepseek('deepseek-chat'),
    output: Output.object({
      schema: z.object({
        claims: z.array(z.object({
          claim: z.string().describe('AI 回答中的一个事实性声明'),
          isFactual: z.boolean().describe('这是事实性声明（可以验证真假）还是观点/推测'),
        })),
      }),
    }),
    prompt: `从以下 AI 回答中提取所有事实性声明（不包括观点和推测）：\n\n${aiResponse}`,
  });

  // 2. 对每个声明检查是否有文档支撑
  const results: FactCheckResult[] = [];
  
  for (const { claim, isFactual } of claims.claims) {
    if (!isFactual) continue;

    const { output: check } = await generateText({
      model: deepseek('deepseek-chat'),
      output: Output.object({
        schema: z.object({
          supported: z.boolean().describe('这个声明是否在参考文档中有支撑'),
          sourceExcerpt: z.string().optional().describe('如果有支撑，引用相关文档原文'),
          confidence: z.number().min(0).max(1).describe('判断的置信度'),
        }),
      }),
      prompt: `判断以下声明是否在参考文档中有支撑：
      
声明："${claim}"

参考文档：
${retrievedDocuments.join('\n---\n')}`,
    });

    results.push({
      claim,
      supported: check.supported,
      source: check.sourceExcerpt,
      confidence: check.confidence,
    });
  }

  return results;
}
```

**策略二：自我一致性检查（Self-Consistency）**

同一个问题让模型回答多次（用较高的 temperature），如果多次回答一致，说明模型比较"确定"；如果回答差异很大，说明模型在"猜"。

```typescript
import { generateText, Output } from 'ai';
import { deepseek } from "@ai-sdk/deepseek";
import { z } from 'zod';

async function selfConsistencyCheck(
  prompt: string,
  runs: number = 3
): Promise<{
  answers: string[];
  isConsistent: boolean;
  consensusAnswer?: string;
}> {
  // 多次生成
  const answers = await Promise.all(
    Array.from({ length: runs }, () =>
      generateText({
        model: deepseek('deepseek-chat'),
        prompt,
        temperature: 0.8,  // 稍高的温度，增加多样性
      }).then(r => r.text)
    )
  );

  // 用模型判断答案是否一致
  const { output: consistency } = await generateText({
    model: deepseek('deepseek-chat'),
    output: Output.object({
      schema: z.object({
        isConsistent: z.boolean().describe('多个回答的核心结论是否一致'),
        consensusAnswer: z.string().optional().describe('如果一致，核心结论是什么'),
        disagreements: z.array(z.string()).describe('如果不一致，分歧点是什么'),
      }),
    }),
    prompt: `以下是同一个问题的 ${runs} 个独立回答。判断它们的核心结论是否一致：

${answers.map((a, i) => `回答 ${i + 1}：${a}`).join('\n\n')}`,
  });

  return {
    answers,
    isConsistent: consistency.isConsistent,
    consensusAnswer: consistency.consensusAnswer,
  };
}
```

**策略三：关键信息的二次确认**

对于高风险场景，让 AI 先给出回答，然后再问一次"你确定吗？"——听起来像开玩笑，但实际上有效。

```typescript
import { generateText, Output } from 'ai';
import { deepseek } from "@ai-sdk/deepseek";
import { z } from 'zod';

async function generateWithDoubleCheck(
  prompt: string
): Promise<{
  answer: string;
  confidence: 'high' | 'medium' | 'low';
  caveats: string[];
}> {
  // 第一次：生成回答
  const firstAnswer = await generateText({
    model: deepseek('deepseek-chat'),
    prompt,
  });

  // 第二次：让模型审视自己的回答
  const { output: review } = await generateText({
    model: deepseek('deepseek-chat'),
    output: Output.object({
      schema: z.object({
        confidence: z.enum(['high', 'medium', 'low']).describe(
          'high=非常确定, medium=基本确定但有一些不确定的点, low=不太确定'
        ),
        potentialIssues: z.array(z.string()).describe('回答中可能有问题的地方'),
        caveats: z.array(z.string()).describe('用户应该注意的事项'),
        shouldRevise: z.boolean().describe('是否需要修正回答'),
        revisedAnswer: z.string().optional().describe('如果需要修正，修正后的回答'),
      }),
    }),
    prompt: `你之前对以下问题给出了一个回答。请审视你的回答，评估其可靠性：

问题：${prompt}

你的回答：${firstAnswer.text}

请诚实评估：这个回答有多可靠？有没有你不确定的地方？有没有可能是错误的？`,
  });

  return {
    answer: review.shouldRevise && review.revisedAnswer
      ? review.revisedAnswer
      : firstAnswer.text,
    confidence: review.confidence,
    caveats: review.caveats,
  };
}
```

### 深层追问

**幻觉检测的准确率只有 80%，是做了检测好还是不做好？过度检测的代价？**

这是一个精彩的工程权衡。

**做检测**的好处：能挡住 80% 的幻觉。假设没检测时有 10% 的回答包含幻觉，加上检测后降到 2%——这是巨大的改进。

**做检测**的代价：
1. **延迟增加**：检测本身需要额外的 API 调用，会增加响应时间
2. **成本增加**：检测用的 API 调用也花钱
3. **误杀**：20% 的检测是错误的——可能把正确的回答标记为"疑似幻觉"

**不做检测**的风险：所有幻觉都会到达用户。在低风险场景（聊天机器人推荐餐厅）可能无所谓，在高风险场景（医疗建议、法律咨询）可能是灾难。

我的建议是**分场景决策**：

| 场景 | 风险 | 检测策略 |
|------|------|---------|
| 闲聊/推荐 | 低 | 不检测，或轻量检测（只看置信度） |
| 信息查询 | 中 | 基于 RAG 的事实核验 |
| 数据分析 | 高 | 完整检测 + 人工复核敏感结论 |
| 医疗/法律/财务 | 极高 | 强制检测 + 专家复核 + 免责声明 |

还有一个折中方案：**不阻断，只标注**。不阻止幻觉到达用户，但在 UI 上标注不确定性等级——让用户自己判断。这在 17 章的错误状态设计中我们已经讲过了。

## 19.5 超时处理：等不起的 AI

### 一句话直觉

超时不是错误，是一种资源保护机制——防止一个请求无限期地占用资源。

### 前端类比

你一定给 `fetch` 设过超时：

```typescript
const controller = new AbortController();
const timeout = setTimeout(() => controller.abort(), 10000); // 10秒超时

try {
  const res = await fetch('/api/data', { signal: controller.signal });
  clearTimeout(timeout);
  return res.json();
} catch (e) {
  if (e instanceof DOMException && e.name === 'AbortError') {
    console.log('请求超时了');
  }
}
```

AI 应用的超时更复杂，因为有两种超时需要处理。

### 详细原理

**API 调用超时 vs Agent 整体超时**

这是两个不同层面的超时：

```
API 调用超时（单次请求）
├─ 每次 generateText / 工具调用 有独立的超时限制
├─ 比如单次 API 调用最多等 30 秒
└─ 超时后可以重试

Agent 整体超时（整个任务）
├─ Agent 可能要执行 10 个步骤
├─ 即使每个步骤没超时，总时间可能太长
├─ 比如整个 Agent 任务最多执行 5 分钟
└─ 超时后需要返回已有结果或转人工
```

```typescript
import { generateText } from 'ai';
import { deepseek } from "@ai-sdk/deepseek";

// 给单次 AI 调用加超时
async function generateTextWithTimeout(
  params: Parameters<typeof generateText>[0],
  timeoutMs: number = 30000
): Promise<Awaited<ReturnType<typeof generateText>>> {
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(), timeoutMs);

  try {
    const result = await generateText({
      ...params,
      abortSignal: controller.signal,
    });
    clearTimeout(timeout);
    return result;
  } catch (error) {
    clearTimeout(timeout);
    if ((error as Error).name === 'AbortError') {
      throw new Error(`AI 调用超时 (${timeoutMs}ms)`);
    }
    throw error;
  }
}

// 给整个 Agent 任务加超时
async function runAgentWithTimeout(
  task: string,
  totalTimeoutMs: number = 300000 // 5分钟
): Promise<{ result: string; completed: boolean; stepsCompleted: number }> {
  const startTime = Date.now();
  const steps: string[] = [];

  for (let step = 0; step < 10; step++) {
    // 检查总时间
    const elapsed = Date.now() - startTime;
    if (elapsed > totalTimeoutMs) {
      return {
        result: `任务未完成。已完成 ${steps.length} 步：\n${steps.join('\n')}`,
        completed: false,
        stepsCompleted: steps.length,
      };
    }

    // 单步执行，剩余时间不能超过总超时
    const remainingTime = totalTimeoutMs - elapsed;
    const stepTimeout = Math.min(30000, remainingTime); // 单步最多 30 秒

    try {
      const result = await generateTextWithTimeout(
        {
          model: deepseek('deepseek-chat'),
          prompt: `任务: ${task}\n已完成步骤:\n${steps.join('\n')}\n请执行下一步。如果任务已完成，回复 [DONE]。`,
        },
        stepTimeout
      );

      if (result.text.includes('[DONE]')) {
        return {
          result: result.text,
          completed: true,
          stepsCompleted: steps.length + 1,
        };
      }

      steps.push(`步骤 ${step + 1}: ${result.text.slice(0, 100)}`);
    } catch (error) {
      console.warn(`步骤 ${step + 1} 失败:`, error);
      // 单步失败不一定要终止整个 Agent
      steps.push(`步骤 ${step + 1}: 失败 - ${(error as Error).message}`);
    }
  }

  return {
    result: steps.join('\n'),
    completed: true,
    stepsCompleted: steps.length,
  };
}
```

**心跳机制**

对于长时间运行的 Agent 任务，需要心跳来让前端知道"Agent 还活着"。

```typescript
// 后端：在 Agent 执行期间发送心跳
function createHeartbeatStream(agentTask: Promise<string>) {
  const encoder = new TextEncoder();
  
  const stream = new ReadableStream({
    async start(controller) {
      // 心跳定时器
      const heartbeatInterval = setInterval(() => {
        controller.enqueue(encoder.encode(`data: {"type":"heartbeat","timestamp":${Date.now()}}\n\n`));
      }, 5000); // 每5秒发一次心跳

      try {
        const result = await agentTask;
        clearInterval(heartbeatInterval);
        controller.enqueue(encoder.encode(`data: {"type":"result","data":${JSON.stringify(result)}}\n\n`));
        controller.close();
      } catch (error) {
        clearInterval(heartbeatInterval);
        controller.enqueue(encoder.encode(`data: {"type":"error","message":"${(error as Error).message}"}\n\n`));
        controller.close();
      }
    },
  });

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
      Connection: 'keep-alive',
    },
  });
}
```

**前端等待超时的 UX 处理怎么做？**

这和 17 章的进度展示（17.5）直接关联。几个要点：

1. **分级提示**：
   - 0-10秒：正常 loading 状态
   - 10-30秒："正在处理，请稍候"
   - 30-60秒："处理时间较长，你可以继续等待或稍后查看结果"
   - 60秒+："是否取消？你也可以在后台运行，完成后通知你"

2. **不要让用户以为卡死了**：只要有心跳，就展示动画或更新时间戳

3. **取消按钮始终可见**：用户应该随时能退出

## 19.6 用户确认机制

### 一句话直觉

不是所有的操作都需要确认，也不是所有的确认都应该一样。关键是分清"什么操作需要人在回路中"。

### 前端类比

想想你做表单的 `beforeunload` 事件——只在用户有未保存的修改时才弹确认。不是每次关闭页面都弹。

```typescript
// 好的确认策略——只在需要时确认
window.addEventListener('beforeunload', (e) => {
  if (hasUnsavedChanges) {
    e.preventDefault();      // 有未保存修改，确认
  }
  // 没有修改就直接关闭，不打扰用户
});
```

### 详细原理

**确认的分类标准**

```typescript
type ConfirmationLevel = 'auto' | 'notify' | 'confirm' | 'require_reason';

interface OperationConfig {
  level: ConfirmationLevel;
  description: string;
}

const OPERATION_CONFIGS: Record<string, OperationConfig> = {
  // 自动执行——只读操作，无副作用
  searchDatabase: { level: 'auto', description: '查询数据库' },
  readFile: { level: 'auto', description: '读取文件' },
  generateSummary: { level: 'auto', description: '生成摘要' },

  // 通知用户——有副作用但可逆
  createDraft: { level: 'notify', description: '创建草稿' },
  addTag: { level: 'notify', description: '添加标签' },

  // 需要确认——有副作用且难以逆转
  sendEmail: { level: 'confirm', description: '发送邮件' },
  updateRecord: { level: 'confirm', description: '更新记录' },
  publishContent: { level: 'confirm', description: '发布内容' },

  // 需要确认+理由——高风险操作
  deleteData: { level: 'require_reason', description: '删除数据' },
  transferMoney: { level: 'require_reason', description: '转账' },
  modifyPermissions: { level: 'require_reason', description: '修改权限' },
};
```

**确认粒度的权衡**

| 粒度 | 安全性 | 效率 | 适用场景 |
|------|--------|------|---------|
| 每步确认 | 最高 | 最低 | 首次使用、高风险操作 |
| 批量确认 | 高 | 中 | 常规 Agent 任务 |
| 异常确认 | 中 | 高 | 成熟用户、低风险场景 |
| 全自动 | 最低 | 最高 | 完全信任的内部工具 |

实际产品中，通常是混合使用：只读操作全自动，写操作批量确认，高危操作逐步确认。

**事后确认**

有些时候，你可以让 Agent 先执行，然后让用户确认是否保留结果——这叫"乐观执行"。

```typescript
// 乐观执行模式
async function optimisticExecution(action: AgentAction) {
  // 先执行
  const result = await executeAction(action);

  // 在可撤销的时间窗口内等待用户确认
  const userDecision = await waitForUserConfirmation(result, {
    timeout: 30000,  // 30秒内可撤销
    default: 'keep', // 超时默认保留
  });

  if (userDecision === 'undo') {
    await rollbackAction(action, result);
    return { status: 'undone' };
  }

  return { status: 'confirmed', result };
}
```

这就像 Gmail 发邮件后的"撤回"功能——邮件已经"发了"（乐观执行），但在 30 秒内你可以撤回（事后确认）。对于用户来说，这比事前确认流畅得多。

### 深层追问

**哪些操作需要用户确认？**

判断标准有三个维度：

1. **可逆性**：操作能否撤回？创建草稿可以删除（可逆），发出的邮件收不回来（不可逆）。不可逆操作需要确认。

2. **影响范围**：操作影响自己还是别人？修改自己的备注无所谓（小范围），给全公司发公告（大范围）需要慎重。影响范围大的需要确认。

3. **成本**：操作有没有直接的财务成本？调用免费 API 无所谓，每次调用花 $10 的 API 需要确认。有成本的需要确认。

把这三个维度组合起来，就是你的确认策略矩阵。

## 19.7 Agent 多步执行的失败处理

### 一句话直觉

Agent 执行 5 步后在第 6 步失败了——你要回答一个难题：前 5 步的结果是保留还是回滚？

### 前端类比

这和数据库的事务（Transaction）是同一个问题：

```typescript
// 数据库事务——全部成功或全部回滚
const transaction = await db.beginTransaction();
try {
  await transaction.execute('UPDATE accounts SET balance = balance - 100 WHERE id = 1');
  await transaction.execute('UPDATE accounts SET balance = balance + 100 WHERE id = 2');
  await transaction.commit(); // 全部成功
} catch {
  await transaction.rollback(); // 全部回滚
}
```

但 Agent 的步骤不像数据库事务——很多步骤是不可逆的（邮件发出去了、文件发布了），你没法"回滚"。

### 详细原理

**三种失败处理策略**

**策略一：部分结果保留 + 告知用户**

最常用的策略。保留已完成的步骤结果，告诉用户执行到哪里失败了，让用户决定下一步。

```typescript
interface AgentExecutionResult {
  status: 'completed' | 'partial' | 'failed';
  completedSteps: StepResult[];
  failedStep?: {
    stepNumber: number;
    description: string;
    error: string;
    retryable: boolean;
  };
  pendingSteps: string[];
}

async function executeAgentPlan(
  plan: AgentPlan
): Promise<AgentExecutionResult> {
  const completedSteps: StepResult[] = [];

  for (let i = 0; i < plan.steps.length; i++) {
    const step = plan.steps[i];
    try {
      const result = await executeStep(step);
      completedSteps.push(result);
    } catch (error) {
      // 失败了，但不丢弃已完成的结果
      return {
        status: 'partial',
        completedSteps,
        failedStep: {
          stepNumber: i + 1,
          description: step.description,
          error: (error as Error).message,
          retryable: isRetryableError(error),
        },
        pendingSteps: plan.steps.slice(i + 1).map(s => s.description),
      };
    }
  }

  return { status: 'completed', completedSteps, pendingSteps: [] };
}
```

**策略二：回滚已完成步骤（只适用于可逆操作）**

如果所有步骤都是可逆的，可以像数据库事务一样回滚。

```typescript
interface ReversibleStep {
  execute: () => Promise<unknown>;
  rollback: () => Promise<void>;
  description: string;
}

async function executeWithRollback(steps: ReversibleStep[]) {
  const executedSteps: ReversibleStep[] = [];

  for (const step of steps) {
    try {
      await step.execute();
      executedSteps.push(step);
    } catch (error) {
      console.error(`步骤 "${step.description}" 失败，开始回滚...`);

      // 逆序回滚已执行的步骤
      for (const executed of executedSteps.reverse()) {
        try {
          await executed.rollback();
          console.log(`已回滚：${executed.description}`);
        } catch (rollbackError) {
          // 回滚也失败了——这是最糟糕的情况
          console.error(`回滚失败！${executed.description}:`, rollbackError);
          // 这种情况必须告警，需要人工介入
        }
      }

      throw error;
    }
  }
}
```

**策略三：补偿操作（Saga 模式）**

借鉴分布式系统的 Saga 模式——每个步骤都有对应的"补偿操作"。失败时不是"回滚"（恢复到原始状态），而是执行补偿（尽量抵消影响）。

```typescript
// Agent 发了邮件（不可回滚），但后续步骤失败了
// 补偿操作：发一封更正邮件
const emailStep = {
  execute: async () => {
    await sendEmail({
      to: 'team@company.com',
      subject: '月度报告',
      body: reportContent,
    });
  },
  compensate: async () => {
    // 无法撤回邮件，但可以发更正
    await sendEmail({
      to: 'team@company.com',
      subject: '【更正】月度报告 - 请忽略上一封',
      body: '由于系统处理中断，请忽略上一封报告。更正版本将稍后发送。',
    });
  },
};
```

### 深层追问

**Agent 执行了 5 步后在第 6 步失败了，前 5 步的结果怎么处理？回滚还是保留？**

这取决于步骤之间的依赖关系和可逆性。把步骤画成一张依赖图：

```
如果是独立的步骤（各自独立，互不依赖）：
  步骤1 ✅   步骤2 ✅   步骤3 ✅   步骤4 ✅   步骤5 ✅   步骤6 ❌
  → 保留 1-5 的结果，让用户决定是否重试 6

如果是链式依赖（后面的步骤依赖前面的结果）：
  步骤1 → 步骤2 → 步骤3 → 步骤4 → 步骤5 → 步骤6 ❌
  → 要看步骤 6 的失败是否影响 1-5 结果的有效性
  → 如果步骤 6 是"生成总结报告"，1-5 是数据收集，保留 1-5
  → 如果步骤 6 是"确认支付"，1-5 是订单创建，需要回滚

如果包含不可逆步骤：
  步骤1 ✅ → 步骤2(发邮件) ✅ → 步骤3 ✅ → 步骤4 ❌
  → 邮件已发出，无法回滚。只能做补偿。
```

实际设计建议：**把不可逆操作尽量放在最后执行**。先做可逆的准备工作（查询数据、生成草稿、预览结果），让用户确认后再执行不可逆操作（发送、删除、支付）。这样即使前面的步骤失败了，也没有产生不可逆的副作用。

## 19.8 优雅降级的用户体验

### 一句话直觉

错误信息不是给程序员看的，是给用户看的。用户不需要知道"connection timeout after 30000ms"，他们需要知道"我可以怎么做"。

### 前端类比

对比两种错误处理：

```typescript
// 差的错误展示
catch (error) {
  alert(error.message);
  // "Error: ECONNREFUSED 127.0.0.1:5432 - Connection refused"
  // 用户：啥？？？
}

// 好的错误展示
catch (error) {
  showToast({
    type: 'warning',
    title: '查询暂时不可用',
    message: '数据服务正在维护中，预计 10 分钟后恢复。你可以稍后重试。',
    actions: [
      { label: '稍后重试', onClick: retry },
      { label: '查看缓存数据', onClick: showCachedData },
    ],
  });
}
```

### 详细原理

**错误信息的三层结构**

每个面向用户的错误信息应该包含三层：

```
1. 发生了什么（What）——用户能理解的语言
2. 为什么发生（Why）——简要的原因说明
3. 怎么解决（How）——用户可以采取的行动
```

```typescript
interface UserFriendlyError {
  title: string;             // 一句话概括
  description: string;       // 简要原因
  actions: UserAction[];     // 可执行的操作
  technicalDetail?: string;  // 技术详情（可选，给开发者）
}

function toUserFriendlyError(error: Error): UserFriendlyError {
  // API 限流
  if (error.message.includes('429') || error.message.includes('rate limit')) {
    return {
      title: 'AI 助手正忙',
      description: '当前使用人数较多，请稍等片刻再试。',
      actions: [
        { label: '30秒后自动重试', type: 'auto-retry', delay: 30000 },
        { label: '取消', type: 'cancel' },
      ],
    };
  }

  // 模型服务不可用
  if (error.message.includes('500') || error.message.includes('503')) {
    return {
      title: 'AI 服务暂时不可用',
      description: '我们的 AI 服务正在恢复中，这通常会在几分钟内解决。',
      actions: [
        { label: '使用备用模型', type: 'fallback' },
        { label: '稍后重试', type: 'retry' },
        { label: '联系客服', type: 'escalate' },
      ],
    };
  }

  // 超时
  if (error.message.includes('timeout')) {
    return {
      title: '处理时间超出预期',
      description: '这个问题可能比较复杂，需要更长时间处理。',
      actions: [
        { label: '继续等待', type: 'wait' },
        { label: '简化问题后重试', type: 'simplify' },
        { label: '获取部分结果', type: 'partial' },
      ],
    };
  }

  // 上下文过长
  if (error.message.includes('context length') || error.message.includes('too long')) {
    return {
      title: '内容过长',
      description: '输入的内容超出了 AI 的处理范围。试试缩短内容或分批处理。',
      actions: [
        { label: '自动精简', type: 'truncate' },
        { label: '分批处理', type: 'split' },
      ],
    };
  }

  // 未知错误
  return {
    title: '出了点问题',
    description: '遇到了一个意料之外的问题。我们已经记录下来了。',
    actions: [
      { label: '重试', type: 'retry' },
      { label: '联系客服', type: 'escalate' },
    ],
    technicalDetail: error.message,
  };
}
```

**关键原则**

1. **不暴露技术细节**：用户不需要看到 `ECONNREFUSED`、`status 502`、`JSON.parse error`。把这些记到日志里，给用户看人话。

2. **始终提供出路**：每个错误状态都要有至少一个用户可以执行的操作。"出错了"是死胡同，"出错了，你可以重试或联系客服"是活路。

3. **区分暂时和永久**：限流是暂时的（等一会就好），API Key 过期是永久的（需要管理员介入）。暂时性错误给"重试"按钮，永久性错误给"联系管理员"按钮。

4. **记录一切**：前端展示友好信息，但后端要把原始错误、堆栈、上下文全部记录下来。这是后续排查的唯一依据。

## 19.9 错误监控和告警

### 一句话直觉

最可怕的不是你知道 Agent 出错了，而是你不知道 Agent 在出错。

### 前端类比

你一定用过 Sentry 或类似的前端监控——不是用户报 bug 了你才知道有问题，而是 Sentry 自动捕获异常并通知你。

AI 应用的监控需要比传统应用更全面，因为"错误"的定义更广。

### 详细原理

**监控三个层面**

**第一层：硬指标（和传统监控一样）**

```typescript
// 这些指标你很熟悉
interface HardMetrics {
  errorRate: number;        // 错误率
  latencyP50: number;       // 延迟中位数
  latencyP99: number;       // 延迟 99 分位
  timeoutRate: number;      // 超时率
  tokenUsage: number;       // Token 消耗
  costPerRequest: number;   // 单次请求成本
}
```

**第二层：AI 特有指标**

```typescript
interface AIMetrics {
  hallucinationRate: number;    // 幻觉检测触发率
  refusalRate: number;          // 模型拒绝回答的比例
  fallbackRate: number;         // 降级到备用模型的比例
  toolCallFailureRate: number;  // 工具调用失败率
  retryRate: number;            // 重试率
  avgStepsPerTask: number;      // Agent 平均步骤数（突然增加可能说明 Agent 在循环）
}
```

**第三层：业务质量指标**

```typescript
interface QualityMetrics {
  userSatisfactionRate: number; // 用户满意度（thumbs up/down）
  regenerationRate: number;     // 用户要求重新生成的比例
  escalationRate: number;       // 转人工的比例
  taskCompletionRate: number;   // 任务完成率
}
```

**告警规则示例**

```typescript
const ALERT_RULES = [
  {
    name: '错误率飙升',
    condition: (metrics: HardMetrics) => metrics.errorRate > 0.05, // 5%
    severity: 'high',
    action: '检查 API 服务状态，是否需要切换备用模型',
  },
  {
    name: '幻觉率偏高',
    condition: (metrics: AIMetrics) => metrics.hallucinationRate > 0.1, // 10%
    severity: 'medium',
    action: '检查最近的 prompt 变更，是否引入了新的幻觉模式',
  },
  {
    name: '用户频繁重新生成',
    condition: (metrics: QualityMetrics) => metrics.regenerationRate > 0.3, // 30%
    severity: 'medium',
    action: '抽查最近的对话记录，分析用户不满意的原因',
  },
  {
    name: 'Agent 步骤异常',
    condition: (metrics: AIMetrics) => metrics.avgStepsPerTask > 15,
    severity: 'high',
    action: 'Agent 可能陷入了循环，检查最近的任务日志',
  },
  {
    name: '成本异常',
    condition: (metrics: HardMetrics) => metrics.costPerRequest > 0.5, // $0.5/请求
    severity: 'high',
    action: '检查是否有 prompt 膨胀或无效的重试',
  },
];
```

**发现"静悄悄的错误"**

前面说过，AI 应用最危险的是"软错误"——没有异常但结果不对。怎么发现？

1. **用户反馈信号**：thumbs down、重新生成、修改后再发送——这些都是"结果不好"的信号
2. **自动抽检**：定期随机抽取一批 AI 回答，用另一个模型或人工来评估质量
3. **异常模式检测**：回答长度突然变短、总是拒绝回答、工具调用模式异常——这些可能是 prompt 或模型出了问题
4. **A/B 测试**：新版本 prompt 或模型上线后，用 A/B 测试对比质量指标，而不是凭感觉

---

## 概念辨析

### 硬错误 vs 软错误

| 维度 | 硬错误 | 软错误 |
|------|--------|--------|
| 表现 | 异常抛出、HTTP 非 200 | 正常返回但内容有问题 |
| 检测 | try-catch 自动捕获 | 需要额外的检测机制 |
| 示例 | 429 限流、500 服务器错误 | 幻觉、偏离指令、遗漏信息 |
| 处理 | 重试、降级、告警 | 事实核验、自我一致性检查 |
| 危险程度 | 可控——会被发现 | 更高——可能长期不被发现 |

### 重试 vs 降级 vs 兜底

| 策略 | 含义 | 适用场景 |
|------|------|---------|
| 重试 | 用相同方式再试一次 | 暂时性错误（限流、网络抖动） |
| 降级 | 换一种次优方式执行 | 主路径不可用但有替代方案 |
| 兜底 | 放弃自动处理，转人工 | 所有自动方式都失败了 |

### API 超时 vs Agent 超时

| 维度 | API 超时 | Agent 超时 |
|------|---------|-----------|
| 粒度 | 单次 API 调用 | 整个 Agent 任务（多个步骤） |
| 典型值 | 10-30 秒 | 1-5 分钟 |
| 处理方式 | 重试单次调用 | 返回部分结果 + 让用户决定 |
| 前端体验 | spinner / skeleton | 步骤进度 + 超时提示 |

## 灵魂拷问

> **Q1：AI 返回了一个看起来合理但其实错误的回答，这算不算"错误"？怎么检测？**

A：这绝对算错误——而且是最危险的一种。

传统错误是"系统告诉你出错了"，这个是"系统告诉你一切正常但其实不正常"。就像一个计算器，你输入 `2 + 2`，它返回 `5`，没有报错，格式正确，但结果是错的。

检测方法从轻到重：

**轻量级**：让模型自己评估置信度。在生成回答后，附加一步让模型评估"你对这个回答有多确定？"。不完美，但能抓住一部分明显的不确定性。

**中量级**：事实核验。如果回答基于知识库，检查关键论断是否有文档支撑。如果回答包含数据，检查数据是否和数据库一致。

**重量级**：自我一致性检查 + 人工抽检。多次生成对比一致性，定期人工抽查回答质量。

关键认知：**你不可能 100% 检测所有幻觉**。目标不是消除幻觉，而是把幻觉控制在可接受的范围内，并在 UI 上传达不确定性，让用户有能力自己判断。

---

> **Q2：重试一个 Tool Call 是安全的吗？如果这个工具是"发送邮件"呢？**

A：关键看工具的**幂等性**。

**幂等操作**（重试安全）：同一个请求执行一次和执行多次，效果完全相同。比如查询数据库、获取天气、读取文件。

**非幂等操作**（重试危险）：同一个请求执行多次会产生不同的效果。比如发送邮件（发两封）、创建订单（建两个）、扣钱（扣两次）。

对于非幂等操作，有三种应对方案：

1. **幂等键**：每次操作带一个唯一 ID，服务端保证同 ID 只执行一次。这是 Stripe 等支付 API 的标准做法。

2. **状态检查后重试**：重试前先检查操作是否已经成功了。比如重试发邮件前，先查一下邮件发送记录。

3. **不重试，转人工**：对于高风险的非幂等操作，失败后不自动重试，而是通知用户手动处理。

在 Agent 系统中，最佳实践是：**给每个工具标记幂等性，只自动重试幂等的工具，非幂等工具失败后让 Agent 或用户决定下一步**。

---

> **Q3：模型降级可能导致回答质量下降，用户更希望"慢但准"还是"快但可能不太准"？**

A：这取决于用户的心理预期和任务的重要程度。

一个好的设计不是替用户做这个选择，而是**让用户自己选**：

```
主模型暂时不可用。你可以：
1. 等待恢复（预计 5 分钟后可用，回答质量更高）
2. 使用备用模型（立即可用，但回答质量可能略有下降）
```

如果必须自动决策（比如你做的是 API 不是面向用户的界面），那么：
- 对准确性敏感的场景（金融、医疗）→ 宁可失败也不降级
- 对可用性敏感的场景（客服、推荐）→ 降级好过不可用

还有一个细节：**降级后一定要在响应中标注**。让下游消费者知道"这个回答来自备用模型，质量可能有所不同"。这和 HTTP 的 `Warning` 头是同一个思路。

---

> **Q4：幻觉检测的准确率只有 80%，是做了检测好还是不做好？过度检测的代价？**

A：做。80% 总比 0% 好。

但你需要理解 80% 准确率意味着什么。假设 100 个回答中有 10 个包含幻觉：

- 不做检测：10 个幻觉全部到达用户
- 做检测（80% 准确率）：捕获 8 个幻觉，漏掉 2 个。但同时误标了约 18 个正确回答为"疑似幻觉"

过度检测的代价：
1. **用户信任下降**：如果 18% 的正确回答被标记为"不确定"，用户会觉得这个 AI 太不自信了
2. **体验变差**：每个回答都附带"仅供参考"标签，等于什么都没说
3. **成本增加**：检测本身需要额外 API 调用

解决方案：**不做二元判断，做概率标注**。不是"这是幻觉/不是幻觉"，而是给出置信度分数。高置信度的直接展示，低置信度的标注"仅供参考"，极低置信度的标注"无法确认准确性"。让 UI 的展示粒度和检测的粒度匹配。

---

> **Q5：Agent 执行了 5 步后在第 6 步失败了，前 5 步的结果怎么处理？回滚还是保留？**

A：大多数情况下应该**保留并告知**，而不是回滚。原因有三：

1. **很多步骤不可逆**：如果第 3 步是发邮件，你没法回滚
2. **前面的结果可能有独立价值**：用户查询数据（步骤1-3）后生成报告（步骤4-5）再发送（步骤6），即使发送失败，查询结果和报告对用户也是有用的
3. **用户可以手动续接**：告诉用户"我做到了第 5 步，第 6 步（发送报告）失败了。你可以点击重试第 6 步，或者手动发送报告。"

但有一个例外：如果步骤之间是**原子性依赖**的（缺一不可），则应该回滚。比如"创建订单 → 锁定库存 → 扣款"三个步骤，扣款失败了，库存锁定和订单创建都应该回滚。

设计建议：**在 Agent 的规划阶段就标记好每个步骤的原子性关系——哪些步骤必须一起成功或一起失败，哪些步骤可以独立保留**。

---

> **Q6：如何区分"AI 不确定所以拒绝回答"和"AI 确定但回答错误"？哪个更危险？**

A：**AI 确定但回答错误更危险**。远远更危险。

"不确定所以拒绝回答"虽然用户体验不好，但至少是安全的——用户知道 AI 没有给出答案，会去寻找其他信息源。这是一种"fail-safe"设计。

"确定但回答错误"是灾难性的——用户会信任这个回答并据此行动。在医疗场景下，这可能导致错误的治疗；在金融场景下，这可能导致错误的投资决策。

区分方法：

1. **看模型的拒绝信号**：大多数模型在拒绝时会使用特定的措辞（"I'm not able to..."、"I don't have enough information..."）。你可以检测这些模式。

2. **置信度评估**：让模型在回答后自评置信度。虽然不完全可靠，但高置信度+错误回答（过度自信）是可以通过自我一致性检查来发现的。

3. **领域约束**：在特定领域中，设定硬性规则。比如医疗场景的 Agent 必须引用具体的医学文献，不能"凭记忆"回答。

产品设计建议：**宁可过度拒绝，也不要过度自信**。在安全敏感的场景中，调整 prompt 让模型更倾向于说"我不确定"，而不是编造一个看似合理的答案。这就是 19.1 中提到的"设定不确定时的行为"。

## 最佳实践

### DO

- **DO 对每个 AI 调用都加 try-catch**。没有错误处理的 AI 调用在生产环境中是定时炸弹。

- **DO 使用指数退避 + 抖动来重试**。不要立即重试，不要固定间隔重试。给服务器恢复的时间。

- **DO 区分可重试和不可重试的错误**。429 可以重试，401 不应该重试。只对暂时性错误重试。

- **DO 给非幂等工具加幂等键或状态检查**。重试发邮件前先确认邮件是否已发出。

- **DO 实现模型降级链**。主模型 → 备用模型 → 兜底文案。不要让一个模型的不可用导致整个系统不可用。

- **DO 在 UI 上展示友好的错误信息**。告诉用户发生了什么、为什么、怎么办——不是技术堆栈。

- **DO 建立 AI 特有的监控指标**。幻觉率、拒绝率、降级率、用户重新生成率——这些是传统监控不覆盖的。

- **DO 把不可逆操作放在 Agent 执行的最后**。先做可逆的准备工作，最后执行不可逆操作。

### DON'T

- **DON'T 无限制地重试**。设定重试次数上限和重试预算，避免重试风暴。

- **DON'T 自动重试有副作用的操作**。发邮件、创建订单、扣款——失败后让用户或 Agent 决策，不要盲目重试。

- **DON'T 对所有场景用同一套检测策略**。闲聊不需要幻觉检测，医疗建议需要最严格的检测。

- **DON'T 把原始错误信息展示给用户**。`ECONNREFUSED`、`JSON.parse error`、`status 502` 对用户没有意义。

- **DON'T 忽略"用户重新生成"信号**。如果 30% 的回答被用户要求重新生成，说明你的 AI 质量有严重问题。

- **DON'T 假设降级是无代价的**。降级后的回答质量可能不达标，必须标注并监控降级后的用户满意度。

- **DON'T 只关注硬错误而忽略软错误**。幻觉和偏离指令不会触发 catch 块，但对用户的伤害可能更大。

### 实战1：完整的 AI 调用容错层

一个可以直接在项目中使用的 AI 调用包装器，集成了重试、降级、超时和错误转换：

```typescript
// lib/resilient-ai.ts
import { generateText } from 'ai';
import type { LanguageModel } from 'ai';
import { deepseek } from "@ai-sdk/deepseek";
import { anthropic } from "@ai-sdk/anthropic";

// ─── 配置 ───

interface ModelConfig {
  model: LanguageModel;
  name: string;
  tier: 'primary' | 'secondary' | 'fallback';
}

const MODEL_CHAIN: ModelConfig[] = [
  { model: deepseek('deepseek-reasoner'), name: 'DeepSeek Reasoner', tier: 'primary' },
  { model: anthropic('claude-sonnet-5-5'), name: 'Claude Sonnet', tier: 'secondary' },
  { model: deepseek('deepseek-chat'), name: 'DeepSeek Chat', tier: 'fallback' },
];

interface RetryConfig {
  maxRetries: number;
  baseDelay: number;
  maxDelay: number;
}

const DEFAULT_RETRY_CONFIG: RetryConfig = {
  maxRetries: 3,
  baseDelay: 1000,
  maxDelay: 15000,
};

// ─── 工具函数 ───

function sleep(ms: number): Promise<void> {
  return new Promise(resolve => setTimeout(resolve, ms));
}

function getDelayWithJitter(attempt: number, baseDelay: number, maxDelay: number): number {
  const exponentialDelay = baseDelay * Math.pow(2, attempt);
  const cappedDelay = Math.min(exponentialDelay, maxDelay);
  return Math.random() * cappedDelay;
}

function isRetryableError(error: unknown): boolean {
  const message = error instanceof Error ? error.message.toLowerCase() : '';
  // 429、500系列、网络错误、超时——可重试
  if (/429|rate.?limit|too.?many/.test(message)) return true;
  if (/5\d{2}|server.?error|internal/.test(message)) return true;
  if (/timeout|network|econnr|fetch.?failed/.test(message)) return true;
  // 401、403、400——不要重试
  if (/401|403|400|invalid|unauthorized/.test(message)) return false;
  // 上下文过长——不要重试
  if (/context.?length|too.?long|token/.test(message)) return false;
  return false;
}

// ─── 用户友好的错误转换 ───

interface UserError {
  title: string;
  description: string;
  retryable: boolean;
  retryDelay?: number;
}

function toUserError(error: unknown): UserError {
  const message = error instanceof Error ? error.message.toLowerCase() : '';

  if (/429|rate.?limit/.test(message)) {
    return {
      title: 'AI 助手正忙',
      description: '当前使用人数较多，请稍后再试。',
      retryable: true,
      retryDelay: 30000,
    };
  }
  if (/5\d{2}|server/.test(message)) {
    return {
      title: 'AI 服务暂时不可用',
      description: '服务正在恢复中，通常几分钟内会解决。',
      retryable: true,
      retryDelay: 60000,
    };
  }
  if (/timeout/.test(message)) {
    return {
      title: '处理超时',
      description: '这个问题比较复杂，处理时间超出了预期。',
      retryable: true,
    };
  }
  if (/context.?length|too.?long/.test(message)) {
    return {
      title: '内容过长',
      description: '输入内容超出了 AI 的处理范围，试试缩短内容。',
      retryable: false,
    };
  }
  return {
    title: '出了点问题',
    description: '遇到了意料之外的问题，请重试。',
    retryable: true,
  };
}

// ─── 核心：带重试的单模型调用 ───

async function callWithRetry(
  params: Parameters<typeof generateText>[0],
  retryConfig: RetryConfig = DEFAULT_RETRY_CONFIG
): Promise<Awaited<ReturnType<typeof generateText>>> {
  const { maxRetries, baseDelay, maxDelay } = retryConfig;

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await generateText(params);
    } catch (error) {
      const isLastAttempt = attempt === maxRetries;

      if (isLastAttempt || !isRetryableError(error)) {
        throw error;
      }

      const delay = getDelayWithJitter(attempt, baseDelay, maxDelay);
      console.warn(
        `[resilient-ai] 第 ${attempt + 1}/${maxRetries} 次重试，等待 ${Math.round(delay)}ms`,
        error instanceof Error ? error.message : error
      );
      await sleep(delay);
    }
  }
  throw new Error('unreachable');
}

// ─── 核心：带降级的多模型调用 ───

export interface ResilientResult {
  text: string;
  modelUsed: string;
  tier: string;
  retryCount: number;
  warnings: string[];
}

export async function resilientGenerate(
  params: Omit<Parameters<typeof generateText>[0], 'model'>,
  options: {
    retryConfig?: RetryConfig;
    timeoutMs?: number;
  } = {}
): Promise<ResilientResult> {
  const { retryConfig = DEFAULT_RETRY_CONFIG, timeoutMs = 30000 } = options;
  const warnings: string[] = [];
  let totalRetries = 0;

  for (const config of MODEL_CHAIN) {
    try {
      // 加超时控制
      const controller = new AbortController();
      const timeout = setTimeout(() => controller.abort(), timeoutMs);

      const result = await callWithRetry(
        { ...params, model: config.model, abortSignal: controller.signal },
        retryConfig
      );

      clearTimeout(timeout);

      if (config.tier !== 'primary') {
        warnings.push(`使用了备用模型 ${config.name}，回答质量可能有所不同`);
      }

      return {
        text: result.text,
        modelUsed: config.name,
        tier: config.tier,
        retryCount: totalRetries,
        warnings,
      };
    } catch (error) {
      totalRetries++;
      console.warn(`[resilient-ai] ${config.name} 不可用:`, error);
      warnings.push(`${config.name} 不可用: ${(error as Error).message}`);

      if (config === MODEL_CHAIN[MODEL_CHAIN.length - 1]) {
        // 所有模型都失败了
        const userError = toUserError(error);
        throw Object.assign(new Error(userError.title), {
          userError,
          warnings,
          retryCount: totalRetries,
        });
      }
    }
  }
  throw new Error('unreachable');
}

// ─── 导出便捷方法 ───

export { toUserError };
```

### 实战2：Agent 错误恢复中间件

在 Agent 的工具调用层添加错误恢复能力：

```typescript
// lib/tool-error-handler.ts
import { tool } from 'ai';
import { z } from 'zod';

// 工具的幂等性和安全性标记
interface ToolSafetyConfig {
  idempotent: boolean;       // 是否幂等（重试安全）
  reversible: boolean;        // 是否可逆（可回滚）
  hasSideEffects: boolean;    // 是否有副作用
  maxRetries: number;         // 该工具的最大重试次数
  requiresConfirmation: boolean; // 是否需要用户确认
}

const TOOL_SAFETY: Record<string, ToolSafetyConfig> = {
  searchDatabase: {
    idempotent: true,
    reversible: true,
    hasSideEffects: false,
    maxRetries: 3,
    requiresConfirmation: false,
  },
  sendEmail: {
    idempotent: false,
    reversible: false,
    hasSideEffects: true,
    maxRetries: 0,          // 不自动重试
    requiresConfirmation: true,
  },
  updateRecord: {
    idempotent: true,       // 相同更新多次执行结果相同
    reversible: true,
    hasSideEffects: true,
    maxRetries: 2,
    requiresConfirmation: true,
  },
  deleteRecord: {
    idempotent: true,       // 删除已删除的记录不会再次删除
    reversible: false,      // 但删除是不可逆的
    hasSideEffects: true,
    maxRetries: 0,
    requiresConfirmation: true,
  },
};

// 包装工具，添加错误处理逻辑
function wrapToolWithErrorHandling<T extends z.ZodType>(
  toolName: string,
  originalTool: {
    description: string;
    inputSchema: T;
    execute: (args: z.infer<T>) => Promise<unknown>;
  }
) {
  const safety = TOOL_SAFETY[toolName] ?? {
    idempotent: false,
    reversible: false,
    hasSideEffects: true,
    maxRetries: 1,
    requiresConfirmation: true,
  };

  return tool({
    description: originalTool.description,
    inputSchema: originalTool.inputSchema,
    execute: async (args: z.infer<T>) => {
      let lastError: Error | null = null;

      for (let attempt = 0; attempt <= safety.maxRetries; attempt++) {
        try {
          const result = await originalTool.execute(args);
          
          // 记录成功的工具调用
          console.log(`[tool] ${toolName} 成功`, {
            attempt: attempt + 1,
            args: JSON.stringify(args).slice(0, 200),
          });

          return result;
        } catch (error) {
          lastError = error as Error;
          
          console.warn(`[tool] ${toolName} 失败 (${attempt + 1}/${safety.maxRetries + 1})`, {
            error: (error as Error).message,
          });

          if (attempt < safety.maxRetries && safety.idempotent) {
            // 幂等工具可以安全重试
            await new Promise(resolve => 
              setTimeout(resolve, 1000 * Math.pow(2, attempt))
            );
          } else {
            break;
          }
        }
      }

      // 所有重试都失败了，返回错误信息给 Agent
      // 注意：不是抛出异常，而是返回一个错误对象
      // 这样 Agent 可以根据错误信息决定下一步
      return {
        error: true,
        toolName,
        message: lastError?.message || '未知错误',
        suggestion: safety.hasSideEffects
          ? '这个操作有副作用，建议通知用户手动处理。'
          : '这个操作是只读的，可以稍后重试。',
        retryable: safety.idempotent,
        retried: safety.maxRetries > 0,
      };
    },
  });
}

// 使用示例
const searchTool = wrapToolWithErrorHandling('searchDatabase', {
  description: '搜索数据库',
  inputSchema: z.object({
    query: z.string().describe('搜索关键词'),
    table: z.string().describe('要搜索的表名'),
  }),
  execute: async ({ query, table }) => {
    // 实际的数据库查询逻辑：db 换成你自己的数据库客户端
    const results = await db.search(table, query);
    return { count: results.length, data: results };
  },
});
```

### 实战3：前端错误边界组件

专为 Agent 设计的 React 错误边界，支持重试、降级和用户友好的错误展示：

```tsx
// components/AgentErrorBoundary.tsx
'use client';
import { Component, type ReactNode } from 'react';

interface UserError {
  title: string;
  description: string;
  retryable: boolean;
  retryDelay?: number;
}

interface Props {
  children: ReactNode;
  onError?: (error: Error) => void;
  fallbackComponent?: ReactNode;
}

interface State {
  hasError: boolean;
  error: Error | null;
  userError: UserError | null;
  retryCount: number;
  isRetrying: boolean;
  retryCountdown: number;
}

export class AgentErrorBoundary extends Component<Props, State> {
  private countdownTimer?: NodeJS.Timeout;

  state: State = {
    hasError: false,
    error: null,
    userError: null,
    retryCount: 0,
    isRetrying: false,
    retryCountdown: 0,
  };

  static getDerivedStateFromError(error: Error): Partial<State> {
    // 尝试从 error 上提取 userError
    const userError = (error as Error & { userError?: UserError }).userError ?? {
      title: '出了点问题',
      description: '遇到了意料之外的问题。',
      retryable: true,
    };

    return { hasError: true, error, userError };
  }

  componentDidCatch(error: Error) {
    this.props.onError?.(error);
    console.error('[AgentErrorBoundary]', error);
  }

  componentWillUnmount() {
    if (this.countdownTimer) clearInterval(this.countdownTimer);
  }

  handleRetry = () => {
    this.setState({
      hasError: false,
      error: null,
      userError: null,
      retryCount: this.state.retryCount + 1,
      isRetrying: false,
    });
  };

  handleAutoRetry = (delay: number) => {
    const seconds = Math.ceil(delay / 1000);
    this.setState({ isRetrying: true, retryCountdown: seconds });

    this.countdownTimer = setInterval(() => {
      this.setState(prev => {
        if (prev.retryCountdown <= 1) {
          if (this.countdownTimer) clearInterval(this.countdownTimer);
          // 自动重试
          setTimeout(this.handleRetry, 0);
          return { ...prev, retryCountdown: 0 };
        }
        return { ...prev, retryCountdown: prev.retryCountdown - 1 };
      });
    }, 1000);
  };

  render() {
    if (!this.state.hasError) return this.props.children;
    if (this.props.fallbackComponent) return this.props.fallbackComponent;

    const { userError, retryCount, isRetrying, retryCountdown } = this.state;

    return (
      <div className="rounded-lg border border-red-200 bg-red-50 p-6 my-4">
        <div className="flex items-start gap-3">
          <span className="text-2xl">⚠️</span>
          <div className="flex-1">
            <h3 className="font-semibold text-red-800 text-lg">
              {userError?.title ?? '出了点问题'}
            </h3>
            <p className="text-red-700 mt-1">
              {userError?.description ?? '遇到了意料之外的问题。'}
            </p>

            {retryCount > 0 && (
              <p className="text-red-500 text-sm mt-2">
                已重试 {retryCount} 次
              </p>
            )}

            <div className="flex gap-2 mt-4">
              {userError?.retryable && !isRetrying && (
                <>
                  <button
                    className="px-4 py-2 bg-red-600 text-white rounded-lg hover:bg-red-700 text-sm font-medium"
                    onClick={this.handleRetry}
                  >
                    立即重试
                  </button>
                  {userError.retryDelay && (
                    <button
                      className="px-4 py-2 bg-white text-red-700 border border-red-300 rounded-lg hover:bg-red-100 text-sm"
                      onClick={() => this.handleAutoRetry(userError.retryDelay!)}
                    >
                      {retryCountdown > 0
                        ? `${retryCountdown}秒后自动重试`
                        : `${Math.ceil(userError.retryDelay / 1000)}秒后自动重试`}
                    </button>
                  )}
                </>
              )}

              {isRetrying && (
                <span className="text-red-600 text-sm flex items-center gap-2">
                  <span className="animate-spin">⏳</span>
                  {retryCountdown}秒后自动重试...
                </span>
              )}
            </div>
          </div>
        </div>
      </div>
    );
  }
}
```

## 实操练习

### 目标

为"AI 智能工作助手"项目添加完善的错误处理和容错机制。让助手不再因为一个工具失败就"死机"，而是能智能地重试、降级和恢复。

### 步骤

**Step 1：实现重试层（30 分钟）**

- 创建 `retryWithExponentialBackoff` 工具函数
- 支持指数退避 + 抖动
- 能区分可重试和不可重试的错误
- 有重试预算限制

**Step 2：实现模型降级链（30 分钟）**

- 配置主模型 → 备用模型 → 兜底模型的降级链
- 降级后在响应中标注使用了哪个模型
- 所有模型都不可用时，返回友好的兜底文案

**Step 3：工具调用错误处理（40 分钟）**

- 为每个工具标记幂等性和安全性
- 幂等工具自动重试，非幂等工具返回错误信息给 Agent
- Agent 收到工具错误后，能自主决定下一步（重试、换工具、告知用户）

**Step 4：前端错误展示（30 分钟）**

- 实现 `AgentErrorBoundary` 错误边界组件
- 实现 `toUserFriendlyError` 错误信息转换
- 不同类型的错误展示不同的 UI 和操作选项

**Step 5：监控指标（30 分钟）**

- 记录每次 AI 调用的延迟、是否成功、使用的模型、重试次数
- 记录每次工具调用的成功/失败
- 实现一个简单的仪表盘展示这些指标

### 验收标准

- [ ] AI 调用有完整的重试机制，使用指数退避 + 抖动
- [ ] 主模型不可用时自动降级到备用模型，UI 有提示
- [ ] 工具调用失败不会导致 Agent 整体崩溃
- [ ] 前端展示的错误信息是用户友好的，不含技术细节
- [ ] 有基本的监控指标记录

### 挑战加分项

- [ ] 实现自我一致性检查：同一个问题用不同温度生成 3 次，对比结果一致性
- [ ] 实现基于 RAG 的事实核验：检查 AI 回答中的关键声明是否有文档支撑
- [ ] 实现幂等键机制：为有副作用的工具调用添加幂等键，防止重复执行
- [ ] 实现 Agent 多步执行的部分结果保留：执行到第 N 步失败时，返回前 N-1 步的结果并让用户决定下一步

## 本章小结

这一章我们建立了一套完整的 AI 应用错误处理体系。从"能跑就行"到"跑不了也不怕"，你的 Agent 从此有了安全气囊。

**核心要点**：

1. **AI 错误的四个层次**：API 层（硬错误，好处理）→ 模型层（幻觉、偏离，需要检测）→ 工具层（调用失败，需要重试和降级）→ 业务层（结果不对，需要校验和监控）。越上层越难检测。

2. **重试不是万能药**。指数退避 + 抖动 + 重试预算是基本操作，但更重要的是区分"可重试"和"不可重试"的错误，以及处理非幂等操作的重试风险。

3. **降级是有计划的退让**。模型降级、功能降级、人工兜底——三道防线确保用户总能得到一个回应，即使不是最优的。

4. **幻觉是 AI 的"自信地胡说八道"**。事实核验、自我一致性检查、二次确认是三种主要的检测手段。不追求完美检测（做不到），追求把风险控制在可接受范围内。

5. **软错误比硬错误更危险**。硬错误会被发现和处理，软错误会悄悄伤害用户。建立 AI 特有的监控指标（幻觉率、拒绝率、重新生成率）来发现这些"静悄悄的错误"。

6. **用户友好的错误处理**：告诉用户"发生了什么、为什么、怎么办"——不是技术堆栈。每个错误状态都应该有出路。

**一句话总结**：没有错误处理的 Agent 就像没有安全带的赛车——晴天跑得飞快，一个坑就翻车。好的错误处理不是让 Agent 永远不犯错，而是让它犯错时能优雅地恢复，让用户始终感到安心和掌控。

下一章，我们进入生产篇的第一个话题——安全与防护。如果说错误处理是防止 Agent "自己出问题"，安全防护就是防止"别人搞你的 Agent"。Prompt 注入、权限穿透、数据泄露——这些都是上线前必须解决的问题。
