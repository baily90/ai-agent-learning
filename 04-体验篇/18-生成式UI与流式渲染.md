# 第18章：生成式 UI（Generative UI）—— 让 AI 输出"界面"而不只是"文字"

## 引言

到目前为止，我们的 AI 助手都是"话痨"——不管用户问什么，它都只会回一段文字，最多再带几个工具调用结果。用户问"北京天气怎么样"，它回"北京今天 22°C，晴"；用户问"帮我查下这个订单"，它回一段文字描述订单状态。

但真实的产品里，用户期待的远不止这些。用户想看的是一个**天气卡片**（带图标、温度曲线、穿衣建议），一个**订单详情面板**（带物流时间轴、操作按钮），一个**可交互的图表**。这些是"界面"，不是"文字"。

这就是**生成式 UI（Generative UI）**要解决的问题：让 AI 不只是"说"，而是能"画"——根据对话内容，动态生成对应的 UI 组件。

这一章，你会看到前端开发者在 AI 时代的真正主场在哪里：**AI 负责理解意图和产出结构化数据，前端负责把这些数据变成漂亮的、可交互的界面。** 这是纯后端转岗的人给不了的。

---

## 18.1 什么是生成式 UI

### 一句话直觉

**生成式 UI = AI 输出结构化数据（工具调用 / JSON）+ 前端用组件渲染这些数据，而不是把 AI 的回复当纯文本显示。**

### 传统聊天 UI vs 生成式 UI

| 维度 | 传统聊天 UI | 生成式 UI |
|------|-----------|----------|
| AI 输出 | 一段自然语言文本 | 结构化数据（工具调用 / 对象） |
| 前端渲染 | 把文本塞进一个 `<div>` | 根据数据类型渲染对应的**组件** |
| 用户体验 | 读文字 | 看卡片、图表、表单，甚至直接操作 |
| 前端工作 | 几乎为 0 | 设计组件库 + 数据到组件的映射 |

举个例子。用户问"帮我看看深圳到北京的航班"：

- **传统聊天 UI**：AI 回一段文字："深圳到北京明天有 3 个航班，最早 7:30 起飞的 CA1234……"——用户要自己在大脑里"解析"这段文字。
- **生成式 UI**：AI 调用 `searchFlights` 工具，返回结构化的航班列表，前端把它渲染成一个**航班卡片列表**，每个卡片有起飞时间、价格、余票，甚至"预订"按钮。

差别一目了然。生成式 UI 的价值，就是**把"读"变成"看"和"点"**。

### 前端类比

生成式 UI 之于聊天应用，就像 **`dangerouslySetInnerHTML` 之于富文本编辑器**——不对，这个类比太吓人了。换个更好的：

**生成式 UI 就像 React 的"服务端组件 + 客户端组件"的流式渲染**。传统的做法是：前端发请求 → 后端返回完整 HTML → 前端一次性渲染。而生成式 UI 是：AI 流式地"吐出"一个个结构化片段，前端边接收边渲染对应的组件，就像打字机效果之于组件。

更贴切的类比：**这是"AI 版的组件驱动开发"**。你不再为每一种情况手写 if-else 判断显示哪个组件，而是让 AI 来决定"这次该渲染什么组件、带什么数据"。

## 18.2 生成式 UI 的三种实现层次

从简单到复杂，生成式 UI 有三个层次。理解这三个层次，你就理解了它的完整光谱。

### 层次一：工具调用驱动的 UI（最基础，必学）

AI 调用工具 → 工具返回结构化数据 → 前端根据工具名渲染对应的组件。

这是生成式 UI 的**地基**。你在第 7 章已经学会了工具调用，其实你离生成式 UI 只差一步：**把工具调用的结果，渲染成组件而不是纯文本。**

```typescript
// 工具返回结构化数据
const searchFlights = tool({
  description: '搜索航班，返回航班列表',
  inputSchema: z.object({
    from: z.string(),
    to: z.string(),
    date: z.string(),
  }),
  execute: async ({ from, to, date }) => {
    return {
      flights: [
        { id: 'CA1234', from, to, departTime: '07:30', price: 1280, seats: 5 },
        { id: 'CZ5678', from, to, departTime: '10:15', price: 980, seats: 12 },
      ],
    };
  },
});
```

前端拿到这个工具调用的结果后，不再 `JSON.stringify` 塞进聊天框，而是渲染成 `<FlightCard>` 组件。

### 层次二：结构化输出的 UI（进阶）

AI 不调用工具，而是用 `output` 参数直接输出一个结构化对象，前端把它渲染成组件。

```typescript
import { generateText, Output } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';
import { z } from 'zod';

const { output } = await generateText({
  model: deepseek('deepseek-chat'),
  output: Output.object({
    schema: z.object({
      type: z.enum(['weather', 'flight', 'order']),  // 组件类型
      data: z.object({}).passthrough(),              // 组件数据
    }),
  }),
  prompt: '帮我查北京今天的天气',
});

// output = { type: 'weather', data: {...} }
// 前端根据 output.type 渲染 <WeatherCard> 或 <FlightCard> 或 <OrderPanel>
```

这里的关键设计：**让 AI 输出一个"组件类型 + 组件数据"的结构**，前端用这个结构做组件路由。

### 层次三：流式生成 UI（高级，2026 年的前沿）

AI 边思考边"吐出"UI 片段，前端边接收边渲染，用户可以**边看 AI 生成边看到界面逐渐成形**。

这是生成式 UI 的完整形态，底层依赖流式协议（第 4 章的 UI Message Stream）承载组件数据。实现复杂度最高，但体验也最好——它是 ChatGPT 高级模式、Cursor 这类产品正在做的事。

## 18.3 核心：数据到组件的映射

不管哪个层次，生成式 UI 的核心机制都是同一个：**一个"数据 → 组件"的映射表。**

```typescript
// 组件注册表：工具名 → 组件
import FlightCard from './components/FlightCard';
import WeatherCard from './components/WeatherCard';
import OrderPanel from './components/OrderPanel';

const toolComponents: Record<string, React.ComponentType<any>> = {
  searchFlights: FlightCard,
  getWeather: WeatherCard,
  getOrder: OrderPanel,
};

// 渲染时：根据工具名查组件，把工具结果作为 props 传入
function ToolRenderer({ toolName, result }) {
  const Component = toolComponents[toolName];
  if (!Component) {
    // 没有注册组件的工具，降级为纯文本 JSON
    return <pre>{JSON.stringify(result, null, 2)}</pre>;
  }
  return <Component {...result} />;
}
```

这个模式极其简单，但它是生成式 UI 的**全部秘密**。剩下的都是工程细节：

1. **组件要"耐造"**：AI 返回的数据可能有缺失、类型漂移、字段名变化，组件要做防御性渲染（给 props 设默认值、做兜底）。
2. **降级路径**：总有没注册组件的工具，或数据不符合预期的场景，要有纯文本降级。
3. **渐进增强**：先让组件"能显示"，再让组件"能交互"（按钮、表单、审批流）。

## 18.4 实战：把天气工具变成天气卡片

让我们把第 7 章的天气工具，升级成一个真正的生成式 UI。

### 后端：流式 + 工具调用

```typescript
// app/api/chat/route.ts
import { streamText, isStepCount, toUIMessageStream, createUIMessageStreamResponse, tool } from 'ai';
import { deepseek } from '@ai-sdk/deepseek';
import { z } from 'zod';

const getWeather = tool({
  description: '获取指定城市的实时天气，返回温度、天气状况、湿度和风速',
  inputSchema: z.object({
    city: z.string().describe('城市名，如：北京'),
  }),
  execute: async ({ city }) => {
    // 实际项目调用真实天气 API，这里用模拟数据
    return {
      city,
      temperature: 22,
      condition: '晴',
      humidity: 45,
      wind: '北风 3 级',
      suggestion: '适合户外活动，建议穿薄外套',
    };
  },
});

export async function POST(req: Request) {
  const { messages } = await req.json();

  const result = streamText({
    model: deepseek('deepseek-chat'),
    instructions: '你是一个天气助手，用户问天气时调用 getWeather 工具。',
    tools: { getWeather },
    stopWhen: isStepCount(3),
    messages,
  });

  return createUIMessageStreamResponse({
    stream: toUIMessageStream({ stream: result.stream }),
  });
}
```

### 前端：天气卡片组件 + 组件映射

```tsx
// app/page.tsx
'use client';

import { useChat } from '@ai-sdk/react';

// 天气卡片组件
function WeatherCard({ city, temperature, condition, humidity, wind, suggestion }: any) {
  return (
    <div className="border rounded-xl p-4 bg-gradient-to-br from-blue-50 to-cyan-50">
      <div className="flex items-center justify-between">
        <h3 className="text-lg font-bold">{city}</h3>
        <span className="text-3xl">{condition === '晴' ? '☀️' : '⛅'}</span>
      </div>
      <div className="text-4xl font-bold my-2">{temperature}°C</div>
      <div className="text-sm text-gray-600 space-y-1">
        <div>湿度 {humidity}% · {wind}</div>
        <div className="text-green-600">💡 {suggestion}</div>
      </div>
    </div>
  );
}

// 组件注册表
const toolComponents: Record<string, React.ComponentType<any>> = {
  getWeather: WeatherCard,
};

export default function Chat() {
  const { messages, input, handleInputChange, handleSubmit, isLoading } = useChat({
    api: '/api/chat',
  });

  return (
    <div className="max-w-2xl mx-auto p-4 flex flex-col h-screen">
      <div className="flex-1 overflow-y-auto space-y-4">
        {messages.map((message) => (
          <div key={message.id}>
            {/* 文本内容 */}
            {message.content && <div className="whitespace-pre-wrap">{message.content}</div>}

            {/* 工具调用 → 渲染组件 */}
            {message.parts?.map((part, i) => {
              if (part.type !== 'tool-invocation') return null;
              const { toolName, state } = part;
              if (state !== 'result') return <div key={i}>执行中...</div>;

              const Component = toolComponents[toolName];
              if (!Component) {
                return <pre key={i}>{JSON.stringify(part.result, null, 2)}</pre>;
              }
              return <Component key={i} {...(part.result as any)} />;
            })}
          </div>
        ))}
      </div>

      <form onSubmit={handleSubmit} className="flex gap-2 pt-4 border-t">
        <input
          value={input}
          onChange={handleInputChange}
          placeholder="问我天气..."
          className="flex-1 border rounded px-3 py-2"
          disabled={isLoading}
        />
        <button type="submit" disabled={isLoading} className="px-4 py-2 bg-blue-500 text-white rounded">
          发送
        </button>
      </form>
    </div>
  );
}
```

### 关键点解析

1. **后端没变多少**：还是 `streamText` + `tool`，只是工具返回的数据更"结构化"了（一个天气对象而不是一句话）。
2. **前端是主场**：`toolComponents` 注册表 + `WeatherCard` 组件，把工具结果渲染成卡片。
3. **降级路径**：没注册组件的工具，`<pre>` 显示原始 JSON，保证不崩溃。

> 注：`message.parts` 里的工具调用结构可能随 AI SDK 版本微调（字段名如 `tool-invocation` / `result` 等）。核心思想不变：**从消息里取工具调用结果 → 查组件表 → 渲染组件**。写代码时以当前版本的 useChat 类型定义为准。

## 18.5 最佳实践

### DO

- **DO 让工具返回"组件友好的数据结构"**：扁平的对象、明确的字段名、可选的字段都设好默认值。组件不应该去猜数据长什么样。
- **DO 给每个工具配一个"降级"渲染**：AI 的输出永远不可 100% 信任，组件渲染失败时要能退回到纯文本。
- **DO 把组件和数据解耦**：组件只负责"展示 + 交互"，数据由 AI 产出。这样 AI 升级了，组件不用改。
- **DO 渐进增强**：先做"能显示的静态卡片"，再逐步加"可交互的按钮/表单"。
- **DO 复用第 17 章的 UI/UX 模式**：审批流、进度展示、确认机制——这些和生成式 UI 是天然搭配。

### DON'T

- **DON'T 把 AI 返回的 HTML 直接 `dangerouslySetInnerHTML`**——这是 XSS 的直通车，也是安全审查（第 20 章）的红线。
- **DON'T 让组件过度依赖 AI 输出的精确性**：AI 可能漏字段、错类型、改字段名，组件要"耐造"。
- **DON'T 一上来就做流式生成 UI（层次三）**：先用层次一（工具调用驱动）跑通，再逐步升级。
- **DON'T 为每个工具都手写一个特殊组件**：先抽象出通用组件（卡片、列表、表格），再针对高频场景做专用组件。

## 实操练习

### 目标

把第 7 章的 AI 工作助手，从"纯文本工具调用"升级为"生成式 UI"。

### 步骤

1. **挑一个工具**：从你已有的工具里挑一个（天气、日程、搜索都行）。
2. **写组件**：为这个工具写一个对应的 React 组件，展示它的结果（卡片、列表、时间轴……）。
3. **建注册表**：创建 `toolComponents` 映射表，把工具名映射到组件。
4. **接入前端**：在 `useChat` 的消息渲染里，检测工具调用，渲染组件而不是纯文本。
5. **加降级**：给一个"没注册组件"的工具，验证它回退到纯文本 JSON 不崩溃。

### 验收标准

- [ ] 工具调用结果渲染成了组件（不是纯文本）
- [ ] 有降级路径，未注册组件的工具不崩溃
- [ ] 组件对缺失字段做了兜底（不报 undefined 错误）
- [ ] 文本内容和组件能同时显示（AI 的文字说明 + 组件卡片）

### 挑战加分项

- 给卡片加交互：天气卡片的"切换城市"、订单面板的"申请退款"按钮
- 实现层次二：用 `Output.object` 让 AI 直接输出"组件类型 + 数据"，前端做组件路由
- 研究 AI SDK 的流式 UI 能力（层次三），尝试流式渲染组件

## 本章小结

1. **生成式 UI 的本质**：AI 输出结构化数据，前端把数据渲染成组件，而不是把 AI 回复当纯文本。这是"把读变成看和点"。

2. **三个层次**：工具调用驱动（基础）→ 结构化输出驱动（进阶）→ 流式生成 UI（前沿）。先跑通第一层，再逐步升级。

3. **核心机制就一个**：数据到组件的映射表。工具名/组件类型 → 组件。剩下的都是工程细节（防御渲染、降级、渐进增强）。

4. **前端的主场**：这是 AI 时代前端开发者最值钱的能力——AI 负责理解和产出数据，前端负责把数据变成漂亮、可交互的界面。纯后端转岗的人给不了这个。

5. **安全和降级是底线**：永远不要信任 AI 的输出直接进 DOM，永远给组件留降级路径。

到这里，你的 AI 助手已经能从"会说话"进化到"会展示"了。下一章，我们将解决另一个生产级问题：**当 AI 出错时怎么办**——错误处理与容错。
