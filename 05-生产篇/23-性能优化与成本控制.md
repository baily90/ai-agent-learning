# 第23章：性能优化与成本控制 — 别让 AI 吃穷你

## 引言

在传统前端开发中，你担心的成本问题是什么？服务器费用？CDN 流量？数据库存储？对于大多数中小应用来说，这些费用加起来每月可能也就几百美元。

现在想象一下：你开发了一个 AI 客服助手，上线第一周运行良好。第二周，运营团队在公众号推了一波，日活从 100 涨到 10000。月底你打开 AI 服务商的账单，发现费用是 $3,200。

你的 CTO 问你："我们的服务器费用才 $50，为什么 AI 的费用是服务器的 64 倍？"

欢迎来到 AI 应用的成本世界。**在传统应用中，成本的大头是基础设施（服务器、数据库、带宽）。在 AI 应用中，成本的大头是 token——每一次 API 调用都在烧钱，而且是按使用量线性增长的。** 传统应用的边际成本趋近于零（多一个用户几乎不增加成本），AI 应用的边际成本是恒定的（每个用户每次对话都消耗 token）。

这不是说 AI 应用"太贵不能用"。而是说，如果你不做优化，它确实会很贵。好消息是，优化空间非常大——一个精心优化过的 Agent 的成本可能只有未优化版本的 1/10 甚至 1/20。

这一章，我们从成本结构分析开始，逐一讲解 token 优化、prompt 缓存、语义缓存、延迟优化、限流策略和成本监控。读完之后，你能让你的 Agent 在保持质量的前提下，花尽可能少的钱。

## 23.1 AI 应用的成本结构

### 一句话直觉解释

传统应用花钱买"房子"（服务器），AI 应用花钱买"水电"（token）——房子买一次就行，水电是用多少花多少。

### 前端类比

想象两种商业模式：

```
传统应用 = 自助餐
  → 你付固定的月租（服务器），用户随便吃（请求）
  → 多来 10 个客人，成本几乎不变
  → 瓶颈是"座位数"（并发上限）

AI 应用 = 按菜收费的餐厅
  → 每道菜（每次 API 调用）都单独收费
  → 多来 10 个客人，成本线性增长
  → 瓶颈是"菜钱"（token 费用）
```

### 详细原理讲解

让我们拆解一个典型 AI 应用的成本组成：

**API 调用费用（通常占 70%-90%）**

这是最大的一块。以 Claude Sonnet 为例（价格以实际为准）：
- Input tokens: $3 / 百万 tokens
- Output tokens: $15 / 百万 tokens

一次典型的 Agent 对话：
- System prompt: ~800 tokens
- 用户消息 + 历史: ~500 tokens
- 模型输出: ~300 tokens
- 如果有工具调用，再加一轮：~800 tokens input, ~200 tokens output

单次对话总计约 2,600 tokens，成本约 $0.01。

听起来不多？算一下规模：
- 每天 10,000 次对话 → $100/天 → $3,000/月
- 如果 Agent 平均需要 3 轮对话才能完成任务 → $9,000/月

**向量数据库费用（5%-15%）**

如果你用 RAG，需要一个向量数据库。托管服务（Pinecone、Weaviate Cloud）按存储量和查询量计费。

**Embedding 费用（2%-5%）**

文本转向量需要调用 Embedding API。好消息是 Embedding 很便宜（约 $0.1/百万 tokens），坏消息是如果你的文档量大、更新频繁，费用也会累积。

**基础设施费用（5%-10%）**

服务器、CDN、数据库——这些和传统应用一样，通常不是瓶颈。

**隐性成本**

还有一些容易忽略的成本：
- 开发和测试阶段的 API 调用（开发者每天可能调用几百次来测试 prompt）
- 评估和监控的 API 调用（自动化评估本身也要调 AI）
- 错误重试（一次失败重试三次，成本翻四倍）

### 深层追问

**为什么 output token 比 input token 贵这么多？**

因为生成 output 需要的计算量远大于处理 input。处理 input 是并行的（所有 token 同时通过注意力层），生成 output 是串行的（一个 token 一个 token 生成，每生成一个都要重新计算注意力）。output 的计算成本大约是 input 的 3-5 倍，定价反映了这个差异。

这意味着一个优化方向：**控制输出长度比压缩输入更有成本效益**。减少 100 个 output token 的节省等于减少 300-500 个 input token。

## 23.2 Token 优化：花更少的 token 做同样的事

### 一句话直觉解释

Token 优化就像代码压缩——去掉不必要的空白和冗余，保留核心功能。

### 前端类比

你做过 JavaScript 打包优化吗？

```
Tree Shaking     → 只导入用到的工具定义，不要全量加载
Code Splitting   → 按需加载上下文，不要一次塞入所有历史消息
Minification     → 精简 Prompt 措辞，用更少的词表达相同的意思
Lazy Loading     → 只在需要时才加载 RAG 检索结果
```

思路完全一样——减少"bundle size"（prompt 长度）。

### 详细原理讲解

**策略一：Prompt 精简**

很多 prompt 写得像散文，充满了冗余的描述。精简不是删掉有用的信息，而是用更紧凑的方式表达。

冗余版本（约 200 tokens）：
```
你是一个非常专业和友好的客服助手。你的工作是帮助用户解决他们
在使用我们产品时遇到的各种各样的问题。当用户提出问题时，你应
该首先表示理解和同情，然后提供清晰、详细、有帮助的回答。如果
你不确定答案，请诚实地告诉用户你不知道，不要编造信息。请始终
保持礼貌和专业的态度。
```

精简版本（约 80 tokens）：
```
角色：产品客服助手
规则：
- 先理解问题，再回答
- 回答要清晰具体
- 不确定时说"我不确定"，不编造
- 保持专业友好
```

效果几乎一样，token 数减少了 60%。每次请求节省 120 tokens，如果每天 10,000 次请求，一个月节省约 3,600 万 tokens——按 $3/百万 tokens 算，节省 $108/月。

**策略二：上下文裁剪**

多轮对话中，每次请求都会把历史消息全部发送给模型。10 轮对话后，历史消息可能有 5,000 tokens，但其中大部分对当前问题不重要。

裁剪策略：

1. **滑动窗口**：只保留最近 N 轮对话
2. **摘要压缩**：用一个便宜的模型（如 Haiku）把旧的对话历史压缩成一段摘要
3. **相关性过滤**：只保留和当前问题相关的历史消息（用 Embedding 相似度判断）

```
优化前：每次发送完整的 20 轮对话历史（~5000 tokens）
优化后：最近 3 轮 + 历史摘要（~1500 tokens）
节省：70% 的 input tokens
```

**策略三：输出长度控制**

通过 `maxOutputTokens` 参数限制模型的输出长度。但更有效的方式是在 prompt 中明确告诉模型输出格式：

```
// 不好：模型可能输出 500 tokens 的长篇回答
"回答用户的问题"

// 好：模型输出大约 100 tokens
"用 2-3 句话简洁回答用户的问题。不需要额外解释。"
```

**策略四：选择性工具加载**

如果你的 Agent 有 20 个工具，每个工具定义约 100 tokens，那每次请求光工具定义就 2,000 tokens。但大多数请求只需要其中 3-5 个工具。

优化方案：
1. 根据用户意图预分类，只加载相关的工具
2. 用一个轻量级的分类模型（甚至规则引擎）先判断需要哪些工具
3. 按使用频率排序，高频工具始终加载，低频工具按需加载

### 实际应用场景

一个真实的案例：某团队的 Agent 每次请求消耗约 4,000 tokens，月费 $4,800。经过以下优化：
- Prompt 精简：4,000 → 2,800 tokens（-30%）
- 上下文裁剪：2,800 → 1,800 tokens（-36%）
- 工具选择性加载：1,800 → 1,400 tokens（-22%）

总计节省 65%，月费从 $4,800 降到 $1,680。质量评估显示回答准确率从 92% 微降到 90%——完全可以接受。

## 23.3 Prompt 缓存：相同前缀不重复计算

### 一句话直觉解释

Prompt 缓存就是"CDN for Prompts"——相同的内容只计算一次，后续请求直接复用。

### 前端类比

你一定理解 HTTP 缓存：

```
第一次请求：
GET /bundle.js → 200 OK (从服务器下载，耗时 500ms)

第二次请求（有缓存）：
GET /bundle.js → 304 Not Modified (从缓存读取，耗时 5ms)
```

Prompt 缓存的原理一模一样：

```
第一次请求：
[system prompt: 800 tokens] + [user message: 200 tokens]
→ 全量计算，input 按原价收费

第二次请求（相同 system prompt）：
[system prompt: 800 tokens ← 缓存命中] + [新 user message: 200 tokens]
→ 缓存部分只收 10% 的价格
```

### 详细原理讲解

**Prompt 缓存的工作原理**

当你发送一个请求给 AI API 时，模型需要处理所有的 input tokens——包括 system prompt、工具定义、历史消息和当前用户输入。这个处理过程叫做"prefill"。

Prompt 缓存的核心思想是：如果多个请求的 prompt 有相同的前缀，那么这个前缀的 prefill 计算结果可以被缓存和复用。

**关键限制：前缀匹配**

缓存是基于**前缀精确匹配**的。这意味着：

```
请求 A: [System Prompt] + [工具定义] + [用户消息 A]
请求 B: [System Prompt] + [工具定义] + [用户消息 B]
                 ↑ 这部分完全相同 → 缓存命中 ✓

请求 C: [不同的 System Prompt] + [工具定义] + [用户消息 C]
                 ↑ 前缀不同 → 缓存未命中 ✗
```

所以 prompt 的结构设计非常重要——你要把不变的部分放在前面，变化的部分放在后面。

**Anthropic 的 Prompt Caching 实现**

Anthropic 提供了显式的 cache control 机制。你可以用 `cache_control` 标记哪些内容块应该被缓存：

```typescript
const response = await client.messages.create({
  model: "claude-sonnet-5-5",
  max_tokens: 1024,
  system: [
    {
      type: "text",
      text: "你是一个专业的产品客服助手...(很长的 system prompt)",
      cache_control: { type: "ephemeral" }  // 标记这个块可以被缓存
    }
  ],
  messages: [
    { role: "user", content: "你好，我想问个问题" }
  ]
});
```

缓存命中时，缓存部分的 input token 价格降为原价的 10%。写入缓存时有 25% 的额外费用，但只要缓存被命中 2 次以上就能回本。

**如何设计 prompt 结构以最大化缓存命中率**

核心原则：**不变的在前，变化的在后**。

```
最佳结构（缓存命中率高）：
┌─────────────────────────┐
│ System Prompt（不变）      │ ← 缓存
├─────────────────────────┤
│ 工具定义（不变）           │ ← 缓存
├─────────────────────────┤
│ Few-shot 示例（不变）      │ ← 缓存
├─────────────────────────┤
│ 用户特定上下文（每用户不同）│ ← 不缓存
├─────────────────────────┤
│ 当前用户消息（每次不同）   │ ← 不缓存
└─────────────────────────┘
```

```
差的结构（缓存命中率低）：
┌─────────────────────────┐
│ System Prompt + 用户名    │ ← 每个用户不同，无法缓存！
├─────────────────────────┤
│ 当前对话历史             │ ← 每次不同
├─────────────────────────┤
│ 工具定义                 │ ← 虽然不变，但前面的变了
└─────────────────────────┘
```

第二种结构中，因为 system prompt 里嵌入了用户名（每个用户不同），导致前缀不同，整个缓存失效。

**修复方案**：把用户特定信息从 system prompt 中分离出来，放到后面的 user message 中。

**成本节省的数学**

假设你的 prompt 总共 2,000 tokens，其中 1,500 tokens 是不变的前缀（system prompt + 工具定义）：

```
不用缓存：
  每次请求 input 成本 = 2,000 × $3/1M = $0.006

用缓存（假设 90% 命中率）：
  缓存命中时：1,500 × $0.3/1M + 500 × $3/1M = $0.00045 + $0.0015 = $0.00195
  缓存未命中时：2,000 × $3/1M + 1,500 × $0.75/1M = $0.006 + $0.001125 = $0.007125
  
  加权平均：0.9 × $0.00195 + 0.1 × $0.007125 = $0.002468

节省：$0.006 → $0.002468，节省约 59%
```

如果每月 100 万次请求，节省 $3,532/月。

### 深层追问

**每个用户的对话历史不同，缓存命中率不会很低吗？**

对话历史确实是每个用户不同的。但关键是把它放在缓存前缀之后。system prompt + 工具定义 + few-shot 示例这些对所有用户都一样的部分放在前面做缓存，用户特定的历史放在后面。这样前缀部分的缓存命中率可以接近 100%。

如果你的 system prompt 有 1,500 tokens，即使对话历史完全不同，1,500 tokens 的缓存也能给每次请求节省可观的成本。

## 23.4 语义缓存：用相似度换精确度

### 一句话直觉解释

语义缓存是"模糊匹配版的缓存"——不要求问题完全一样，只要意思差不多就返回缓存的回答。

### 前端类比

```
精确缓存（HTTP 缓存）：
  URL 完全相同 → 返回缓存    /api/products?id=123 ✓
  URL 有一点不同 → 不命中     /api/products?id=124 ✗

语义缓存：
  问题意思相近 → 返回缓存    "iPhone 15 多少钱？" → 缓存命中
                              "iPhone 15 售价是多少？" → 也命中！
  问题意思不同 → 不命中       "iPhone 15 好用吗？" → 不命中
```

### 详细原理讲解

**实现原理**

1. 用户提问时，先将问题转换为 Embedding 向量
2. 在缓存中搜索语义最相似的历史问题
3. 如果相似度超过阈值（如 0.95），直接返回缓存的回答
4. 如果相似度不够，正常调用 AI API，并将问答对存入缓存

```
用户问题: "北京现在天气怎么样？"
    ↓
转为 Embedding 向量
    ↓
在缓存中搜索相似问题
    ↓
找到: "北京今天天气如何？"（相似度 0.97）
    ↓
返回缓存的回答（跳过 AI API 调用）
```

**适用场景**

语义缓存特别适合：
- FAQ 类场景：用户的问题集中在有限的几个主题上
- 通用知识查询：答案不随时间变化
- 高频重复问题：客服场景中 80% 的问题可能只有 20 种

**不适用场景**

语义缓存不适合：
- 个性化回答：答案依赖用户身份或上下文
- 实时数据查询："今天的股价是多少？"——答案每秒都在变
- 创意生成：用户期望每次得到不同的回答

**风险和缓解**

最大的风险是**语义"相似"不代表答案相同**。

经典案例：
```
缓存问题: "如何取消订单？"
缓存回答: "在订单详情页点击'取消订单'按钮"

新问题: "如何取消订阅？"
相似度: 0.93

如果阈值设为 0.90，缓存命中，但回答是错的——取消订单和取消订阅是完全不同的操作。
```

缓解策略：
1. **阈值设高一点**：0.95 比 0.90 更安全，宁可少命中不要错命中
2. **加入意图分类**：先分类意图，只在同一意图类别内做语义匹配
3. **设置过期时间**：缓存不是永久有效的，特别是涉及实时数据的回答
4. **提供反馈机制**：让用户标记"这不是我要的回答"，命中时自动删除错误缓存
5. **A/B 测试**：对比有缓存和无缓存的用户满意度，确保缓存没有降低质量

### 深层追问

**语义缓存的 ROI 怎么算？**

收益 = 缓存命中次数 × 每次 AI 调用成本
成本 = Embedding 调用次数 × Embedding 单价 + 向量数据库费用

Embedding 非常便宜（约 AI 调用成本的 1/100），所以只要命中率超过 1%，语义缓存就是划算的。在 FAQ 场景中，命中率可以达到 30%-50%，ROI 非常可观。

## 23.5 延迟优化：让用户感觉更快

### 一句话直觉解释

延迟优化分两种：让实际速度更快，和让用户感觉更快。后者在 AI 应用中尤其重要。

### 前端类比

前端性能优化的经典思路完全适用：

```
前端                          AI 应用
骨架屏（Skeleton）     →      流式输出（Streaming）
预加载（Prefetch）     →      预测下一步并预热
懒加载（Lazy Loading）  →     按需加载工具和上下文
CDN（边缘缓存）        →      Edge Runtime 部署
Web Worker（并行）     →      并行 AI 调用
```

### 详细原理讲解

**策略一：流式输出（Streaming）**

这是最重要也是最容易实现的优化。

不用流式输出时，用户要等 AI 生成完所有内容后才能看到回答——可能等 3-5 秒，页面毫无反应，用户以为卡了。

用流式输出时，AI 每生成一个 token 就立刻推送给前端，用户在几百毫秒内就能看到第一个字开始出现，然后文字一个个"流淌"出来。

**注意：流式输出不会减少总延迟。** 模型生成 300 tokens 的总时间是一样的。它减少的是 TTFB（Time to First Byte）——用户看到第一个字的时间从 3 秒降到 300 毫秒。这是感知延迟的巨大改善。

```
非流式：[等待 3 秒...........] [一次性显示全部文字]
流式：  [200ms] 北 [50ms] 京 [50ms] 今 [50ms] 天...（逐字显示）
```

**策略二：并行调用**

当 Agent 需要调用多个独立的工具或数据源时，不要串行调用，要并行。

```typescript
// 串行（慢）：总延迟 = 200ms + 300ms + 150ms = 650ms
const weather = await getWeather("北京");
const news = await getNews("北京");
const traffic = await getTraffic("北京");

// 并行（快）：总延迟 = max(200ms, 300ms, 150ms) = 300ms
const [weather, news, traffic] = await Promise.all([
  getWeather("北京"),
  getNews("北京"),
  getTraffic("北京"),
]);
```

这和前端同时发多个 API 请求的逻辑一模一样。

**策略三：预加载和预计算**

如果你能预测用户的下一步操作，提前做准备：

- **预加载 RAG 结果**：用户输入过程中就开始检索（debounce + 预检索）
- **预热模型连接**：在用户打开对话页面时就建立好到 AI API 的连接
- **预计算 Embedding**：新文档入库时立刻计算 Embedding，不要等到用户查询时才算

**策略四：Edge 部署**

如果你的用户在中国，但 AI API 的服务器在美国，光网络延迟就有 200-300ms。把你的 API 路由部署到边缘节点（如 Vercel Edge Functions、Cloudflare Workers），可以减少你的应用服务器到用户之间的延迟。

但要注意：Edge 节点到 AI API 服务器的延迟不会减少。Edge 部署主要优化的是你的业务逻辑（认证、限流、prompt 构建）部分的延迟，不是 AI API 调用本身的延迟。

**策略五：选择更快的模型**

不是所有场景都需要最强的模型。一个分类任务用 Claude Haiku 可能比 Claude Sonnet 快 3 倍，成本低 10 倍，准确率只低 2%。

```
场景分级策略：
├── 简单分类 / 意图识别 → Haiku（快且便宜）
├── 一般对话 / 问答      → Sonnet（平衡）
└── 复杂推理 / 代码生成  → Opus（强但慢且贵）
```

这就像前端的图片优化——缩略图用 WebP 低质量，大图用 PNG 高质量。

**策略六：减少 Agent 循环次数**

Agent 的总延迟 = 循环次数 × 单次 LLM 调用延迟。如果 Agent 需要 5 轮才能完成任务，总延迟就是 5 × 2 秒 = 10 秒。

减少循环的方法：
- 让 prompt 更明确，减少模型"试错"的次数
- 在一次调用中允许多个工具同时调用（parallel tool use）
- 提供更好的工具描述，让模型一次选对

### 深层追问

**streaming 减少了用户感知延迟但没减少总延迟。有没有办法减少总延迟？**

有几个方向：(1) 使用更小更快的模型——Haiku 的生成速度是 Sonnet 的 2-3 倍；(2) 减少输出 token 数——prompt 中明确要求"简洁回答"；(3) 减少 Agent 循环次数——每少一轮循环就少一次 LLM 调用的完整延迟；(4) 并行化——让独立的工具调用同时执行而不是串行。最根本的方式是减少调用次数和每次调用的 token 数。

## 23.6 限流和排队：保护你的钱包和系统

### 一句话直觉解释

限流是给 AI 应用装个"水表"——不是限制谁能用水，而是防止一个人打开水龙头不关，让全楼停水。

### 前端类比

你一定实现过前端的防抖（debounce）和节流（throttle）。AI 应用的限流是同一个概念在后端的放大版。

```
前端 throttle：用户疯狂点击按钮 → 每 300ms 最多触发一次
后端限流：用户疯狂发消息 → 每分钟最多 10 次 AI 调用
API 限流：你的应用疯狂调 API → 服务商每分钟最多 100 次（429 Too Many Requests）
```

### 详细原理讲解

**客户端限流：保护用户体验**

防止单个用户短时间内大量请求。不只是省钱，还能防止用户因为网络延迟而重复点击。

常见策略：
- 按用户限流：每个用户每分钟最多 N 次请求
- 按 IP 限流：防止未登录用户滥用
- 按功能限流：高成本功能（如长文档分析）限制更严
- 滑动窗口 vs 令牌桶：选择适合你场景的算法

**服务端限流：尊重 API Provider 的 Rate Limit**

AI 服务商都有 rate limit。如果你超了，会收到 429 错误。更糟糕的是，有些服务商会在你持续超限时临时降低你的限额。

应对策略：
1. 在应用层维护一个请求队列，控制并发数不超过服务商限制
2. 收到 429 时，使用指数退避重试（exponential backoff）
3. 监控 rate limit 使用情况，在接近上限时主动降速

**请求队列：高并发时的排队策略**

当并发请求超过你能处理的上限时，需要一个队列来排队等待。

```
设计考虑：
├── 优先级队列：VIP 用户的请求优先处理
├── 超时设置：等待超过 30 秒的请求自动取消并返回友好提示
├── 背压（Backpressure）：队列长度超过阈值时，直接拒绝新请求
└── 公平调度：防止一个大用户占满队列
```

### 实际应用场景

一个社交产品的 AI 功能在上线当天被刷屏——某个 KOL 发了一条引导粉丝体验 AI 的微博，瞬间涌入 5 万用户。没有限流的结果：

1. AI API 的 rate limit 被打满，大量请求返回 429
2. 前端没处理 429，疯狂重试，放大了请求量
3. 重试风暴导致 rate limit 被进一步压低
4. 30 分钟内 AI 功能完全不可用

有限流的正确做法：
1. 客户端限流：每用户每分钟最多 5 次请求，超过后显示"太快了，稍等一下"
2. 服务端队列：最多 200 个并发请求，超过的排队等待，等待超过 15 秒返回"当前使用人数较多"
3. API 调用层：并发数控制在 rate limit 的 80% 以内，留出余量
4. 降级策略：极端情况下，切换到更快更便宜的模型（如 Haiku），保证可用性

## 23.7 成本监控和预警：知道钱花在哪了

### 一句话直觉解释

成本监控就像你手机上的流量监控 App——不是帮你省流量，而是让你知道流量花在哪了，以及在快用完时提醒你。

### 详细原理讲解

**多维度成本统计**

一个有效的成本监控系统需要能从多个维度查看成本：

```
维度拆解：
├── 按时间：小时 / 天 / 周 / 月趋势
├── 按用户：哪些用户消耗最多？（识别异常使用）
├── 按功能：聊天 / 搜索 / 文档分析，哪个最贵？
├── 按模型：Sonnet / Haiku / Opus 各花了多少？
└── 按 token 类型：input vs output 的比例
```

**预算告警设计**

```
告警分级：
├── 信息通知：日花费达到预算的 50%（帮你心里有数）
├── 警告通知：日花费达到预算的 80%（开始关注）
├── 严重告警：日花费达到预算的 100%（需要行动）
└── 自动熔断：日花费达到预算的 150%（自动降级或暂停服务）
```

自动熔断听起来激进，但它是你的最后一道防线。想象一下：某个 bug 导致 Agent 陷入无限循环，每次循环都在烧钱。没有熔断，你可能第二天早上醒来发现账单上多了 $5,000。

**成本归因**

"哪个功能最烧钱？"——这个问题的答案可能会改变你的产品决策。

例如：
- 发现"智能搜索"功能每次调用成本 $0.05，但使用率只有 2% → 考虑降低模型规格或下线
- 发现"文档问答"功能成本占总成本的 60%，但贡献了 80% 的用户满意度 → 值得投入
- 发现某个用户每天调用 500 次 → 可能是在用你的 API 套壳，需要加限制

### 深层追问

**把 system prompt 从 2000 token 精简到 500 token，节省了 75% 的 input 成本。但 Agent 表现下降了 5%。值不值？**

这取决于你的优化目标和业务场景。算一笔账：假设月 API 费用 $4,000，精简后降到 $1,000，省了 $3,000。表现下降 5% 意味着什么？如果是客服场景，5% 可能意味着每天多 50 个不满意的客户需要人工介入，人工成本可能远超 $3,000。如果是内部工具，5% 的表现差异几乎无感，省钱就是赚到了。**没有通用的答案，但你需要量化两边的成本。**

## 概念辨析

| 概念 | Prompt 缓存 | 语义缓存 | 响应缓存 |
|---|---|---|---|
| 匹配方式 | 前缀精确匹配 | Embedding 相似度 | 完整输入精确匹配 |
| 缓存什么 | 模型的中间计算状态 | 最终回答 | 最终回答 |
| 由谁实现 | AI 服务商（API 层面） | 开发者（应用层面） | 开发者（应用层面） |
| 适用场景 | 相同 system prompt 的请求 | FAQ、重复问题 | 确定性查询 |
| 风险 | 几乎没有 | 语义相似但答案不同 | 缓存过期、数据不一致 |
| 成本节省 | 50%-90% input 成本 | 100% API 调用成本（命中时） | 100% API 调用成本（命中时） |

| 概念 | 延迟（Latency） | 吞吐量（Throughput） | 成本（Cost） |
|---|---|---|---|
| 关注点 | 单次请求多快 | 单位时间处理多少请求 | 花了多少钱 |
| 优化手段 | 流式输出、并行调用、小模型 | 队列、并发控制 | Token 优化、缓存 |
| 常见冲突 | 小模型更快但质量可能降低 | 高并发增加基础设施成本 | 缓存减少成本但增加复杂度 |

## 灵魂拷问

> **Q: 你的 Agent 每次调用花费 $0.01，听起来不多。如果每天 10 万次调用呢？**

> A: $0.01 × 100,000 = $1,000/天 = $30,000/月。这已经是一个全职工程师的月薪了。更关键的是，AI 成本是**线性增长**的——用户翻倍，成本翻倍。传统应用有规模效应（多一个用户边际成本几乎为零），AI 应用没有。所以成本优化不是"锦上添花"而是"生死攸关"。如果你的单位经济模型（unit economics）算不过来——每个用户贡献的收入低于 AI 成本——那产品就是在亏钱增长。

> **Q: Prompt 缓存要求前缀完全相同才能命中。如果每个用户的上下文不同，缓存命中率会很低吗？怎么设计？**

> A: 关键是分离"不变层"和"变化层"。把 system prompt、工具定义、few-shot 示例这些所有用户共享的内容放在最前面，标记为可缓存。用户特定的上下文（用户名、偏好、对话历史）放在后面。这样前缀部分对所有用户都一样，缓存命中率可以接近 100%。常见的错误是在 system prompt 里写"你好，{userName}，我是你的专属助手"——这个 userName 让整个 system prompt 变成了每个用户不同，彻底破坏了缓存。把个性化信息移到 user message 中就行了。

> **Q: 语义缓存返回了一个"相似问题"的缓存回答给用户，但答案其实不对。这个风险怎么评估？**

> A: 这本质上是一个精确率（precision）vs 召回率（recall）的权衡。阈值设太低，命中率高但错误多（低精确率）；阈值设太高，错误少但命中率低（低召回率）。评估方法：(1) 从历史请求中抽样 1000 个语义缓存命中的案例；(2) 人工或用 AI 评估这些缓存回答是否正确；(3) 如果错误率 > 5%，要么提高阈值，要么在特定场景下关闭语义缓存。对于错误成本高的场景（医疗、金融），建议不用语义缓存或设置非常高的阈值（0.98+）。

> **Q: 把 system prompt 从 2000 token 精简到 500 token，节省了 75% 的 input 成本。但 Agent 表现下降了 5%。值不值？**

> A: 不能用直觉判断，要用数据决策。第一步：量化"5% 表现下降"的业务影响。在客服场景中，5% 可能意味着每天多几十个需要人工介入的工单，每个工单的人工成本可能 $5-10。第二步：量化成本节省。假设月 API 费用从 $4,000 降到 $1,000，省了 $3,000。第三步：比较。如果人工介入的额外成本是 $1,500/月，那净节省还有 $1,500，值得。如果人工成本是 $5,000/月，那得不偿失。另一个思路是：能不能精简到 1000 tokens，表现只下降 1%？通常存在一个"sweet spot"。

> **Q: streaming 减少了用户感知延迟但没减少总延迟。有没有办法减少总延迟？**

> A: 有，但需要在质量上做取舍。(1) 用更小的模型——Haiku 的生成速度是 Sonnet 的 2-3 倍，适合简单任务；(2) 限制输出长度——prompt 中明确要求"用一句话回答"，模型生成的 token 少了自然快了；(3) 减少 Agent 循环——每少一轮 LLM 调用，总延迟减少 1-2 秒；(4) 并行工具调用——多个独立的工具调用同时发起而不是串行；(5) speculative decoding——部分 API 提供商支持用小模型预测大模型的输出来加速。核心认知是：总延迟 = 循环次数 × 单次调用延迟，两个因子都可以优化。

> **Q: 成本优化和质量之间有没有不冲突的"免费午餐"？**

> A: 有几个优化是纯赢的：(1) Prompt 缓存——不改变任何行为，只是避免重复计算，质量完全不变但成本降低；(2) 消除明确的浪费——比如去掉 prompt 中重复的句子、去掉从未被使用的工具定义、修复导致额外循环的 bug；(3) 对不同复杂度的任务用不同的模型——简单问题用 Haiku 不是"降低质量"，而是"匹配需求"。真正的"免费午餐"来自消除浪费，而不是压缩有效内容。

## 最佳实践

### DO

- **DO** 在项目早期就建立成本监控。不要等到账单吓你一跳再开始关注
- **DO** 分析你的 prompt，找出重复和冗余的部分。大多数 prompt 都可以精简 30% 以上而不影响效果
- **DO** 使用 Prompt 缓存。这是性价比最高的优化——几乎没有副作用，只有收益
- **DO** 设置成本预算告警和自动熔断。一个无限循环的 bug 能一晚上烧掉你一个月的预算
- **DO** 对不同复杂度的任务使用不同的模型。不要用大炮打蚊子
- **DO** 实现流式输出。这是用户体验的最低门槛
- **DO** 在限流提示中给用户友好的反馈。"太快了，请等一下"比 HTTP 429 好得多
- **DO** 定期审查成本报告，找出成本最高的功能和用户

### DON'T

- **DON'T** 忽视 output token 的成本。它比 input 贵 3-5 倍，控制输出长度是高效的优化
- **DON'T** 在 system prompt 中嵌入用户特定信息。这会破坏 prompt 缓存
- **DON'T** 盲目追求语义缓存的高命中率。错误的缓存回答比慢一点但正确的回答更糟糕
- **DON'T** 没有限流就上线。一次流量突增可能一天烧完你一个月的预算
- **DON'T** 在没有数据支撑的情况下做成本 vs 质量的权衡。"感觉差不多"不是决策依据
- **DON'T** 把所有工具定义每次都塞进 prompt。你的 Agent 不需要每次都带着 20 把刀上场
- **DON'T** 忘记算开发和测试阶段的 API 成本。团队 10 个人每天调试可能就花掉 $50

### 项目：构建一个带缓存和成本控制的 AI 请求层

> **项目归属**：下面 5 个文件都在**主线 Next.js 项目**的 `lib/optimization/` 目录下。`semantic-cache.ts`、`cost-controller.ts`、`rate-limiter.ts` 与模型无关，可直接被 DeepSeek + AI SDK 复用；`prompt-cache.ts`、`optimized-agent.ts` 用**原生 Anthropic SDK**（`@anthropic-ai/sdk`）演示 Prompt 缓存（`cache_control` 是 Anthropic 专属特性，DeepSeek 无对应 API），运行前需 `npm i @anthropic-ai/sdk` 并配置 `ANTHROPIC_API_KEY`。换成 DeepSeek 时，把这两个文件里的 `client.messages.create` 换成 AI SDK 的 `generateText`，缓存/成本/限流三个类照常复用。

```typescript
// ============================================
// 文件：lib/optimization/prompt-cache.ts
// 说明：利用 Anthropic Prompt Caching 的最佳实践
// 注意：cache_control 是 Anthropic 专属特性，DeepSeek 没有对应 API
// ============================================

import Anthropic from "@anthropic-ai/sdk";

// Prompt 结构设计：不变部分在前，变化部分在后
interface CacheOptimizedPrompt {
  // 第一层：完全不变的系统指令（缓存）
  systemInstructions: string;
  // 第二层：工具定义（缓存）
  tools: Anthropic.Tool[];
  // 第三层：Few-shot 示例（缓存）
  examples: Array<{ role: "user" | "assistant"; content: string }>;
  // 第四层：用户特定上下文（不缓存）
  userContext?: string;
  // 第五层：当前对话（不缓存）
  messages: Anthropic.MessageParam[];
}

async function callWithPromptCache(
  client: Anthropic,
  prompt: CacheOptimizedPrompt,
  model = "claude-sonnet-5-5"
): Promise<Anthropic.Message> {
  // 构建 system 消息，带 cache_control
  const systemBlocks: Anthropic.TextBlockParam[] = [
    {
      type: "text",
      text: prompt.systemInstructions,
      // @ts-ignore cache_control 是 Anthropic 扩展字段
      cache_control: { type: "ephemeral" },
    },
  ];

  // 如果有用户特定上下文，追加到 system（不缓存）
  if (prompt.userContext) {
    systemBlocks.push({
      type: "text",
      text: `\n\n用户上下文：${prompt.userContext}`,
    });
  }

  // 构建完整的消息列表
  const messages: Anthropic.MessageParam[] = [
    // Few-shot 示例
    ...prompt.examples.map((ex) => ({
      role: ex.role as "user" | "assistant",
      content: ex.content,
    })),
    // 当前对话
    ...prompt.messages,
  ];

  const response = await client.messages.create({
    model,
    max_tokens: 1024,
    system: systemBlocks,
    messages,
    tools: prompt.tools.length > 0 ? prompt.tools : undefined,
  });

  // 记录缓存命中情况（用于监控）
  const usage = response.usage as Record<string, number>;
  console.log(`Cache: read=${usage.cache_read_input_tokens ?? 0}, ` +
    `creation=${usage.cache_creation_input_tokens ?? 0}, ` +
    `normal=${usage.input_tokens}`);

  return response;
}

export { callWithPromptCache, type CacheOptimizedPrompt };
```

```typescript
// ============================================
// 文件：lib/optimization/semantic-cache.ts
// 说明：基于向量相似度的语义缓存
// ============================================

// 缓存条目
interface CacheEntry {
  question: string;
  embedding: number[];
  answer: string;
  createdAt: number;
  hitCount: number;
}

// 计算余弦相似度
function cosineSimilarity(a: number[], b: number[]): number {
  if (a.length !== b.length) return 0;
  let dotProduct = 0;
  let normA = 0;
  let normB = 0;
  for (let i = 0; i < a.length; i++) {
    dotProduct += a[i] * b[i];
    normA += a[i] * a[i];
    normB += b[i] * b[i];
  }
  return dotProduct / (Math.sqrt(normA) * Math.sqrt(normB));
}

class SemanticCache {
  private cache: CacheEntry[] = [];
  private similarityThreshold: number;
  private maxEntries: number;
  private ttlMs: number;
  private getEmbedding: (text: string) => Promise<number[]>;

  constructor(options: {
    similarityThreshold?: number; // 默认 0.95
    maxEntries?: number;          // 默认 1000
    ttlMs?: number;               // 默认 1 小时
    getEmbedding: (text: string) => Promise<number[]>;
  }) {
    this.similarityThreshold = options.similarityThreshold ?? 0.95;
    this.maxEntries = options.maxEntries ?? 1000;
    this.ttlMs = options.ttlMs ?? 60 * 60 * 1000;
    this.getEmbedding = options.getEmbedding;
  }

  // 查找缓存
  async lookup(question: string): Promise<{
    hit: boolean;
    answer?: string;
    similarity?: number;
    cachedQuestion?: string;
  }> {
    const now = Date.now();
    const embedding = await this.getEmbedding(question);

    // 清理过期条目
    this.cache = this.cache.filter(
      (entry) => now - entry.createdAt < this.ttlMs
    );

    // 搜索最相似的条目
    let bestMatch: CacheEntry | null = null;
    let bestSimilarity = 0;

    for (const entry of this.cache) {
      const similarity = cosineSimilarity(embedding, entry.embedding);
      if (similarity > bestSimilarity) {
        bestSimilarity = similarity;
        bestMatch = entry;
      }
    }

    if (bestMatch && bestSimilarity >= this.similarityThreshold) {
      bestMatch.hitCount++;
      return {
        hit: true,
        answer: bestMatch.answer,
        similarity: bestSimilarity,
        cachedQuestion: bestMatch.question,
      };
    }

    return { hit: false, similarity: bestSimilarity };
  }

  // 存入缓存
  async store(question: string, answer: string): Promise<void> {
    const embedding = await this.getEmbedding(question);

    this.cache.push({
      question,
      embedding,
      answer,
      createdAt: Date.now(),
      hitCount: 0,
    });

    // 超过上限时，移除最少命中的条目
    if (this.cache.length > this.maxEntries) {
      this.cache.sort((a, b) => a.hitCount - b.hitCount);
      this.cache = this.cache.slice(this.cache.length - this.maxEntries);
    }
  }

  // 删除错误的缓存（用户反馈"回答不对"时调用）
  async invalidate(question: string): Promise<boolean> {
    const embedding = await this.getEmbedding(question);
    const initialLength = this.cache.length;

    this.cache = this.cache.filter(
      (entry) =>
        cosineSimilarity(embedding, entry.embedding) < this.similarityThreshold
    );

    return this.cache.length < initialLength;
  }

  // 获取缓存统计
  getStats(): {
    size: number;
    totalHits: number;
    avgHits: number;
  } {
    const totalHits = this.cache.reduce((sum, e) => sum + e.hitCount, 0);
    return {
      size: this.cache.length,
      totalHits,
      avgHits: this.cache.length > 0 ? totalHits / this.cache.length : 0,
    };
  }
}

export { SemanticCache };
```

```typescript
interface CostRecord {

  userId: string;

// 预算配置
interface BudgetConfig {
  dailyLimitUsd: number;
  monthlyLimitUsd: number;
  perUserDailyLimitUsd: number;
  alertThresholds: number[]; // 例如 [0.5, 0.8, 1.0, 1.5]
  onAlert: (level: string, message: string) => void;
  onBudgetExceeded: () => void; // 熔断回调
}

// 模型定价表
const MODEL_PRICING: Record<
  string,
  { inputPer1k: number; outputPer1k: number; cachedInputPer1k: number }
> = {
  "claude-sonnet-5-5": {
    inputPer1k: 0.003,
    outputPer1k: 0.015,
    cachedInputPer1k: 0.0003,
  },
  "claude-haiku-5-5": {
    inputPer1k: 0.00025,
    outputPer1k: 0.00125,
    cachedInputPer1k: 0.000025,
  },
  "claude-opus-5-5": {
    inputPer1k: 0.015,
    outputPer1k: 0.075,
    cachedInputPer1k: 0.0015,
  },
};

class CostController {
  private records: CostRecord[] = [];
  private config: BudgetConfig;
  private alertedThresholds: Set<string> = new Set();

  constructor(config: BudgetConfig) {
    this.config = config;
  }

  // 计算一次调用的成本
  calculateCost(
    model: string,
    inputTokens: number,
    outputTokens: number,
    cachedInputTokens = 0
  ): number {
    const pricing = MODEL_PRICING[model];
    if (!pricing) {
      console.warn(`Unknown model pricing: ${model}, using Sonnet pricing`);
      return this.calculateCost(
        "claude-sonnet-5-5",
        inputTokens,
        outputTokens,
        cachedInputTokens
      );
    }

    const regularInputTokens = inputTokens - cachedInputTokens;
    return (
      (regularInputTokens / 1000) * pricing.inputPer1k +
      (cachedInputTokens / 1000) * pricing.cachedInputPer1k +
      (outputTokens / 1000) * pricing.outputPer1k
    );
  }

  // 记录一次调用的成本
  recordCost(record: CostRecord): void {
    this.records.push(record);
    this.checkBudget();
  }

  // 检查是否超预算
  private checkBudget(): void {
    const dailyCost = this.getDailyCost();
    const monthlyCost = this.getMonthlyCost();

    // 检查日预算告警
    for (const threshold of this.config.alertThresholds) {
      const alertKey = `daily-${threshold}-${this.getTodayKey()}`;
      if (
        dailyCost >= this.config.dailyLimitUsd * threshold &&
        !this.alertedThresholds.has(alertKey)
      ) {
        this.alertedThresholds.add(alertKey);
        const level =
          threshold >= 1.5 ? "critical" :
          threshold >= 1.0 ? "error" :
          threshold >= 0.8 ? "warning" : "info";
        this.config.onAlert(
          level,
          `日花费已达预算的 ${(threshold * 100).toFixed(0)}%: ` +
          `$${dailyCost.toFixed(2)} / $${this.config.dailyLimitUsd}`
        );
      }
    }

    // 熔断检查
    if (dailyCost >= this.config.dailyLimitUsd * 1.5) {
      this.config.onBudgetExceeded();
    }

    // 月预算检查
    if (monthlyCost >= this.config.monthlyLimitUsd) {
      this.config.onAlert(
        "critical",
        `月花费已超预算: $${monthlyCost.toFixed(2)} / $${this.config.monthlyLimitUsd}`
      );
    }
  }

  // 检查用户是否超过个人预算
  canUserMakeRequest(userId: string): {
    allowed: boolean;
    reason?: string;
    dailyCost: number;
  } {
    const userDailyCost = this.getUserDailyCost(userId);
    if (userDailyCost >= this.config.perUserDailyLimitUsd) {
      return {
        allowed: false,
        reason: "您今日的 AI 使用量已达上限，请明天再试",
        dailyCost: userDailyCost,
      };
    }
    return { allowed: true, dailyCost: userDailyCost };
  }

  // 获取今日总成本
  getDailyCost(): number {
    const todayStart = this.getTodayStart();
    return this.records
      .filter((r) => r.timestamp >= todayStart)
      .reduce((sum, r) => sum + r.costUsd, 0);
  }

  // 获取本月总成本
  getMonthlyCost(): number {
    const monthStart = this.getMonthStart();
    return this.records
      .filter((r) => r.timestamp >= monthStart)
      .reduce((sum, r) => sum + r.costUsd, 0);
  }

  // 获取用户今日成本
  getUserDailyCost(userId: string): number {
    const todayStart = this.getTodayStart();
    return this.records
      .filter((r) => r.timestamp >= todayStart && r.userId === userId)
      .reduce((sum, r) => sum + r.costUsd, 0);
  }

  // 获取成本分布报告
  getCostReport(): {
    daily: number;
    monthly: number;
    byModel: Record<string, number>;
    byFeature: Record<string, number>;
    topUsers: Array<{ userId: string; cost: number }>;
  } {
    const todayStart = this.getTodayStart();
    const monthStart = this.getMonthStart();
    const todayRecords = this.records.filter((r) => r.timestamp >= todayStart);
    const monthRecords = this.records.filter((r) => r.timestamp >= monthStart);

    // 按模型分组
    const byModel: Record<string, number> = {};
    for (const r of monthRecords) {
      byModel[r.model] = (byModel[r.model] ?? 0) + r.costUsd;
    }

    // 按功能分组
    const byFeature: Record<string, number> = {};
    for (const r of monthRecords) {
      byFeature[r.feature] = (byFeature[r.feature] ?? 0) + r.costUsd;
    }

    // Top 用户
    const userCosts: Record<string, number> = {};
    for (const r of monthRecords) {
      userCosts[r.userId] = (userCosts[r.userId] ?? 0) + r.costUsd;
    }
    const topUsers = Object.entries(userCosts)
      .map(([userId, cost]) => ({ userId, cost }))
      .sort((a, b) => b.cost - a.cost)
      .slice(0, 10);

    return {
      daily: todayRecords.reduce((sum, r) => sum + r.costUsd, 0),
      monthly: monthRecords.reduce((sum, r) => sum + r.costUsd, 0),
      byModel,
      byFeature,
      topUsers,
    };
  }

  private getTodayKey(): string {
    return new Date().toISOString().split("T")[0];
  }

  private getTodayStart(): number {
    const now = new Date();
    return new Date(now.getFullYear(), now.getMonth(), now.getDate()).getTime();
  }

  private getMonthStart(): number {
    const now = new Date();
    return new Date(now.getFullYear(), now.getMonth(), 1).getTime();
  }
}

export { CostController, MODEL_PRICING, type CostRecord, type BudgetConfig };
```

```typescript
// 令牌桶算法
class TokenBucket {
  private tokens: number;
  private lastRefill: number;

  constructor(
    private maxOutputTokens: number,
    private refillRate: number, // 每秒补充多少 token
  ) {
    this.tokens = maxOutputTokens;
    this.lastRefill = Date.now();
  }

  // 尝试消费一个 token
  tryConsume(count = 1): { allowed: boolean; retryAfterMs?: number } {
    this.refill();

    if (this.tokens >= count) {
      this.tokens -= count;
      return { allowed: true };
    }

    // 计算需要等待多久
    const deficit = count - this.tokens;
    const retryAfterMs = (deficit / this.refillRate) * 1000;
    return { allowed: false, retryAfterMs };
  }

  private refill(): void {
    const now = Date.now();
    const elapsed = (now - this.lastRefill) / 1000;
    this.tokens = Math.min(
      this.maxOutputTokens,
      this.tokens + elapsed * this.refillRate
    );
    this.lastRefill = now;
  }
}

// 多层限流器
class RateLimiter {
  // 全局限流
  private globalBucket: TokenBucket;
  // 用户限流
  private userBuckets: Map<string, TokenBucket> = new Map();
  // 功能限流
  private featureBuckets: Map<string, TokenBucket> = new Map();

  constructor(
    private config: {
      globalRps: number;       // 全局每秒请求数
      perUserRpm: number;      // 每用户每分钟请求数
      featureLimits?: Record<string, number>; // 特定功能的每分钟限制
    }
  ) {
    this.globalBucket = new TokenBucket(
      config.globalRps * 2,  // 突发容量为 2 倍
      config.globalRps
    );
  }

  // 检查是否允许请求
  checkLimit(
    userId: string,
    feature?: string
  ): {
    allowed: boolean;
    reason?: string;
    retryAfterMs?: number;
  } {
    // 1. 全局限流
    const globalResult = this.globalBucket.tryConsume();
    if (!globalResult.allowed) {
      return {
        allowed: false,
        reason: "系统繁忙，请稍后再试",
        retryAfterMs: globalResult.retryAfterMs,
      };
    }

    // 2. 用户限流
    if (!this.userBuckets.has(userId)) {
      this.userBuckets.set(
        userId,
        new TokenBucket(
          this.config.perUserRpm,
          this.config.perUserRpm / 60 // 转换为每秒
        )
      );
    }
    const userResult = this.userBuckets.get(userId)!.tryConsume();
    if (!userResult.allowed) {
      return {
        allowed: false,
        reason: "请求太频繁了，请稍等一下再试",
        retryAfterMs: userResult.retryAfterMs,
      };
    }

    // 3. 功能限流
    if (feature && this.config.featureLimits?.[feature]) {
      if (!this.featureBuckets.has(feature)) {
        const limit = this.config.featureLimits[feature];
        this.featureBuckets.set(
          feature,
          new TokenBucket(limit, limit / 60)
        );
      }
      const featureResult = this.featureBuckets.get(feature)!.tryConsume();
      if (!featureResult.allowed) {
        return {
          allowed: false,
          reason: "该功能当前使用人数较多，请稍后再试",
          retryAfterMs: featureResult.retryAfterMs,
        };
      }
    }

    return { allowed: true };
  }

  // 清理不活跃的用户桶（定期调用，防止内存泄漏）
  cleanup(): void {
    // 简单策略：如果用户桶太多，清空全部（桶会按需重建）
    if (this.userBuckets.size > 10000) {
      this.userBuckets.clear();
    }
  }
}

export { RateLimiter, TokenBucket };
```

```typescript
import {

// 整合所有优化的请求处理器
class OptimizedAIRequestHandler {
  private client: Anthropic;
  private semanticCache: SemanticCache;
  private costController: CostController;
  private rateLimiter: RateLimiter;

  constructor(config: {
    semanticCacheThreshold?: number;
    dailyBudgetUsd: number;
    monthlyBudgetUsd: number;
    perUserDailyLimitUsd: number;
    globalRps: number;
    perUserRpm: number;
    getEmbedding: (text: string) => Promise<number[]>;
  }) {
    this.client = new Anthropic();

    this.semanticCache = new SemanticCache({
      similarityThreshold: config.semanticCacheThreshold ?? 0.95,
      getEmbedding: config.getEmbedding,
    });

    this.costController = new CostController({
      dailyLimitUsd: config.dailyBudgetUsd,
      monthlyLimitUsd: config.monthlyBudgetUsd,
      perUserDailyLimitUsd: config.perUserDailyLimitUsd,
      alertThresholds: [0.5, 0.8, 1.0, 1.5],
      onAlert: (level, message) => {
        console.warn(`[COST ${level.toUpperCase()}] ${message}`);
        // 实际环境中：发送到 Slack/PagerDuty/企微
      },
      onBudgetExceeded: () => {
        console.error("[COST CRITICAL] Budget exceeded, enabling degraded mode");
        // 实际环境中：切换到更便宜的模型或暂停服务
      },
    });

    this.rateLimiter = new RateLimiter({
      globalRps: config.globalRps,
      perUserRpm: config.perUserRpm,
      featureLimits: {
        document_analysis: 5,  // 高成本功能限制更严
        chat: 30,
      },
    });
  }

  async handleRequest(params: {
    userId: string;
    userMessage: string;
    feature: string;
    systemPrompt: string;
    tools?: Anthropic.Tool[];
    conversationHistory?: Anthropic.MessageParam[];
    model?: string;
    enableSemanticCache?: boolean;
  }): Promise<{
    response: string;
    cached: boolean;
    cost: number;
    latencyMs: number;
  }> {
    const startTime = Date.now();
    const model = params.model ?? "claude-sonnet-5-5";

    // 第一层：限流检查
    const rateCheck = this.rateLimiter.checkLimit(
      params.userId,
      params.feature
    );
    if (!rateCheck.allowed) {
      return {
        response: rateCheck.reason ?? "请稍后再试",
        cached: false,
        cost: 0,
        latencyMs: Date.now() - startTime,
      };
    }

    // 第二层：用户预算检查
    const budgetCheck = this.costController.canUserMakeRequest(params.userId);
    if (!budgetCheck.allowed) {
      return {
        response: budgetCheck.reason ?? "使用量已达上限",
        cached: false,
        cost: 0,
        latencyMs: Date.now() - startTime,
      };
    }

    // 第三层：语义缓存检查
    if (params.enableSemanticCache !== false) {
      const cacheResult = await this.semanticCache.lookup(params.userMessage);
      if (cacheResult.hit && cacheResult.answer) {
        return {
          response: cacheResult.answer,
          cached: true,
          cost: 0,
          latencyMs: Date.now() - startTime,
        };
      }
    }

    // 第四层：构建缓存优化的 prompt 并调用 AI
    const prompt: CacheOptimizedPrompt = {
      systemInstructions: params.systemPrompt,
      tools: params.tools ?? [],
      examples: [],
      messages: [
        ...(params.conversationHistory ?? []),
        { role: "user", content: params.userMessage },
      ],
    };

    const response = await callWithPromptCache(this.client, prompt, model);

    const responseText = response.content
      .filter((b): b is Anthropic.TextBlock => b.type === "text")
      .map((b) => b.text)
      .join("");

    // 计算成本
    const usage = response.usage as Record<string, number>;
    const cost = this.costController.calculateCost(
      model,
      usage.input_tokens,
      usage.output_tokens,
      usage.cache_read_input_tokens ?? 0
    );

    // 记录成本
    this.costController.recordCost({
      timestamp: Date.now(),
      model,
      feature: params.feature,
      userId: params.userId,
      inputTokens: usage.input_tokens,
      outputTokens: usage.output_tokens,
      costUsd: cost,
      cached: false,
    });

    // 存入语义缓存
    if (params.enableSemanticCache !== false) {
      await this.semanticCache.store(params.userMessage, responseText);
    }

    return {
      response: responseText,
      cached: false,
      cost,
      latencyMs: Date.now() - startTime,
    };
  }

  // 获取成本报告
  getCostReport() {
    return this.costController.getCostReport();
  }

  // 获取缓存统计
  getCacheStats() {
    return this.semanticCache.getStats();
  }
}

export { OptimizedAIRequestHandler };
```

## 本章小结

这一章我们系统地学习了 AI 应用的性能优化和成本控制：

1. **成本结构不同**：AI 应用的成本大头是 token（API 调用费），不是服务器。成本随用户量线性增长，没有传统应用的规模效应。理解这一点是所有优化的前提。

2. **Token 优化是基础**：精简 prompt、裁剪上下文、控制输出长度、选择性加载工具。大多数 Agent 的 token 使用量可以优化 50% 以上。

3. **Prompt 缓存是免费午餐**：相同前缀只计算一次，缓存命中时 input 成本降为 10%。关键是把 prompt 结构设计成"不变部分在前，变化部分在后"。

4. **语义缓存有风险**：命中率和正确率是跷跷板。适合 FAQ 场景，不适合需要精确回答的场景。阈值宁高勿低。

5. **延迟优化借鉴前端**：流式输出、并行调用、预加载、Edge 部署——这些前端性能优化的思路完全适用于 AI 应用。

6. **限流和预算是安全网**：没有限流的 AI 应用就像没有油门限制的汽车——迟早会出事。日预算告警 + 自动熔断是你的最后防线。

下一章，我们把所有东西打包上线——部署架构、CI/CD、AI Gateway，让你的 Agent 正式面对真实用户。
