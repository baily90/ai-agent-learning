# 第22章：可观测性与调试 — Agent 出了问题怎么找

## 引言

作为前端开发者，你一定经历过这样的场景：页面上一个按钮点击没反应，你打开 DevTools，看到一个清晰的红色报错 `TypeError: Cannot read property 'map' of undefined`，三秒钟定位到问题代码行，修复，收工。

现在想象另一个场景：你的 AI 客服助手，昨天还好好的，今天突然开始给客户推荐竞品。没有报错，没有异常日志，API 返回 200，一切"正常"——除了 AI 的回答是错的。

这就是 AI 应用调试的本质困难：**传统应用的 bug 是"程序崩了"，Agent 的 bug 是"程序没崩但结果不对"**。

更可怕的是，"结果不对"还分好几种：可能是 prompt 写得有歧义，可能是模型版本悄悄更新了，可能是 RAG 检索到了过时的文档，可能是某个工具返回了误导性的数据。你面对的不是一个确定性的 bug，而是一个**概率性的、多因素叠加的行为偏差**。

怎么办？答案是可观测性（Observability）。

传统运维讲"监控"（Monitoring）——我预先知道要看什么指标，然后盯着看。可观测性比监控更进一步——**我不知道问题会出在哪，但我有足够的数据去事后分析任何问题**。对于 AI 应用这种"不知道 bug 会以什么形式出现"的系统，可观测性不是锦上添花，而是生存必需品。

这一章，我们从 AI 调试的特殊困难讲起，深入到 Tracing、日志设计、行为回放等核心技术，最后搭建一套完整的可观测性方案。读完之后，你的 Agent 不再是一个"黑盒"——它的每一步决策都清晰可追溯。

## 22.1 AI 应用调试的特殊困难

### 一句话直觉解释

传统应用的 bug 像数学考试做错了——有标准答案可以对照；Agent 的 bug 像作文写跑题了——什么叫"对"本身就很模糊。

### 前端类比

调试 Agent 最像什么？调试 CSS 布局问题。

你看着页面上一个元素的位置不对，你知道结果是错的。但问题出在哪？可能是 `margin` 被继承了，可能是 `flexbox` 的 `align-items` 和 `justify-content` 搞混了，可能是某个父元素的 `overflow: hidden` 截断了内容，可能是媒体查询的断点不对。你打开 DevTools，看到 Computed 面板里一堆层叠的规则，每一条都"正确"地执行了，但组合起来就是不对。

Agent 调试完全是同一种痛苦。每个环节都"正常工作"了——prompt 发出去了、模型回复了、工具调用了、结果返回了——但最终输出就是不对。

### 详细原理讲解

让我们梳理一下 Agent 执行中的每一个可能出错的环节：

```
用户输入 → [1] 输入处理 → [2] Prompt 构建 → [3] 模型调用 → [4] 输出解析 
         → [5] 工具调用 → [6] 结果整合 → [7] 最终输出
```

每个环节都可能是"bug"的来源：

1. **输入处理**：用户意图被误解。用户说"帮我取消"，指的是取消订单还是取消对话？
2. **Prompt 构建**：system prompt 的指令有歧义，few-shot 示例误导了模型
3. **模型调用**：模型版本更新了行为变了，temperature 太高导致输出不稳定
4. **输出解析**：模型返回的 JSON 格式不标准，正则匹配失败
5. **工具调用**：Agent 选错了工具，或者给工具传了错误的参数
6. **结果整合**：RAG 检索到了不相关的文档，工具返回了过时的数据
7. **最终输出**：所有中间步骤都对，但拼接起来的回答逻辑不通

最致命的是：**这些错误经常不会触发任何异常**。HTTP 200，JSON 解析成功，函数没有 throw——一切从代码层面看都"正常"。

传统调试手段在这里基本失效：

| 传统调试手段 | AI 应用中的局限 |
|---|---|
| 断点调试 | 你能在 `fetch` 调用前打断点，但你无法"进入"模型内部看它在想什么 |
| 单元测试 | 相同的输入，模型每次可能给不同的输出（非确定性） |
| 错误堆栈 | 模型"答错了"不会产生 Error 对象 |
| 日志 grep | 你 grep 什么关键词？"回答质量差"不是一个可搜索的字符串 |
| 二分法定位 | 你无法"注释掉一半的 prompt"来看问题是否消失 |

### 深层追问

**Agent 的"bug"和传统代码 bug 有什么本质区别？**

本质区别在于**确定性**。传统代码的 bug 是确定性的——给定相同的输入和环境，你一定能复现它。Agent 的"bug"是概率性的——同样的输入，这次回答正确，下次可能就错了。这不是"bug"在传统意义上的定义，更准确地说，它是**行为偏差**。

这意味着你需要一套全新的调试思维：不是"找到那一行出错的代码"，而是"收集足够多的数据来发现行为模式中的异常"。

### 实际应用场景

一个真实的例子：你的 Agent 突然开始在回答中混入英文，之前一直用纯中文。排查后发现，不是 prompt 变了，不是代码变了，而是 AI 服务商悄悄把底层模型从 GPT-4-0613 切换到了 GPT-4-1106-preview。新模型对中文指令的遵循度略有不同。

如果没有可观测性系统记录每次调用的模型版本，你可能要花几天时间排查这个问题。

## 22.2 Tracing（追踪）：记录 Agent 执行的完整链路

### 一句话直觉解释

Tracing 就是给 Agent 的每次执行录像，让你能回看它走的每一步。

### 前端类比

如果你用过分布式追踪工具（Jaeger、Zipkin），或者至少在 Chrome DevTools 的 Network 面板里看过一个页面加载的完整瀑布图，你就理解 Tracing 的概念了。

```
前端页面加载的瀑布图：
├── HTML 文档 (200ms)
│   ├── CSS 文件 (50ms)
│   ├── JS Bundle (300ms)
│   │   ├── API 请求 /users (150ms)
│   │   └── API 请求 /posts (200ms)
│   └── 图片资源 (100ms)
└── 总耗时: 600ms

Agent 执行的 Trace：
├── 用户请求处理 (5ms)
│   ├── Prompt 构建 (10ms)
│   │   ├── System Prompt 加载 (2ms)
│   │   └── RAG 检索 (200ms)
│   ├── LLM 调用 #1 (2000ms, 500 tokens in, 200 tokens out)
│   │   └── 工具调用: searchDatabase (300ms)
│   ├── LLM 调用 #2 (1500ms, 800 tokens in, 300 tokens out)
│   └── 响应格式化 (5ms)
└── 总耗时: 4022ms, 总 token: 1800, 成本: $0.03
```

两者的结构几乎一模一样：一个树状的、有层级的、带时间标注的执行记录。

### 详细原理讲解

**Trace 和 Span 的关系**

在追踪系统中，两个核心概念是：

- **Trace（追踪）**：一次完整的 Agent 执行过程。从用户发送请求到最终返回结果，整个链路是一个 Trace。
- **Span（跨度）**：Trace 中的一个步骤。每个 Span 记录一个具体操作的开始时间、结束时间、输入、输出和元数据。

它们是父子关系：一个 Trace 包含多个 Span，Span 之间可以嵌套。

```
Trace: "用户问'北京天气如何'"
├── Span: prompt_building
│   ├── Span: load_system_prompt
│   └── Span: format_user_message
├── Span: llm_call_1
│   ├── input: "你是天气助手..."
│   ├── output: "我需要调用天气查询工具"
│   ├── model: "claude-sonnet-5-5"
│   ├── tokens: { input: 150, output: 30 }
│   └── latency: 800ms
├── Span: tool_call (weather_api)
│   ├── input: { city: "北京" }
│   ├── output: { temp: 25, condition: "晴" }
│   └── latency: 200ms
└── Span: llm_call_2
    ├── input: [包含天气数据的上下文]
    ├── output: "北京今天天气晴朗，气温25度..."
    ├── tokens: { input: 250, output: 80 }
    └── latency: 1200ms
```

**每个 Span 应该记录什么？**

对于 AI 应用，一个有用的 Span 至少需要这些信息：

| 字段 | 说明 | 为什么重要 |
|---|---|---|
| span_id | 唯一标识 | 关联和查询 |
| parent_span_id | 父 Span | 构建树状结构 |
| operation_name | 操作名称（如 "llm_call"） | 快速分类 |
| start_time / end_time | 时间戳 | 计算延迟 |
| input | 输入数据 | 复现问题 |
| output | 输出数据 | 分析结果 |
| model | 使用的模型和版本 | 排查模型相关问题 |
| tokens | input/output token 数 | 成本分析 |
| status | 成功/失败 | 快速过滤异常 |
| metadata | 自定义附加信息 | 灵活扩展 |

**为什么不能只看最终输出？**

因为同样的"错误输出"可能有完全不同的原因。比如 Agent 回答了一个错误的产品价格：

- **原因 A**：RAG 检索到了过时的价格文档 → 需要更新向量数据库
- **原因 B**：模型幻觉，无视了检索到的正确价格 → 需要调整 prompt
- **原因 C**：Agent 调用了错误的 API 端点 → 需要修改工具描述

没有 Tracing，你只能猜。有了 Tracing，你打开这次请求的 Trace，一眼看到是哪个 Span 出了问题。

### 深层追问

**Tracing 会不会拖慢 Agent 的响应速度？**

好的 Tracing 实现应该是异步的——Span 数据先写入内存队列，然后批量异步发送到存储后端。就像前端的性能监控 SDK（Sentry、DataDog RUM），它们在收集数据的同时不会阻塞页面渲染。主路径的额外延迟通常在个位数毫秒级别，可以忽略不计。

## 22.3 日志设计：AI 应用应该记录什么

### 一句话直觉解释

日志是 Agent 的"飞行记录仪"——飞机出事后，黑匣子里的数据决定了你能不能找到原因。

### 前端类比

传统应用的日志像 `console.log`——打个消息，记个错误。AI 应用的日志更像是浏览器的 Performance Recording——不只记录发生了什么，还要记录**为什么发生**、**上下文是什么**、**花了多少资源**。

### 详细原理讲解

**AI 应用的日志和传统应用有什么不同？**

传统应用日志核心关注**事件**：请求来了、数据库查询了、响应返回了。
AI 应用日志还需要关注**语义**：prompt 是什么、模型理解了什么、为什么选了这个工具。

一条传统日志：
```
[INFO] 2024-01-15 10:30:00 - POST /api/chat - 200 - 150ms
```

一条 AI 应用日志：
```json
{
  "timestamp": "2024-01-15T10:30:00Z",
  "level": "info",
  "event": "llm_call_complete",
  "trace_id": "abc-123",
  "model": "claude-sonnet-5-5",
  "input_tokens": 500,
  "output_tokens": 200,
  "latency_ms": 2300,
  "tool_calls": ["searchProducts"],
  "user_intent": "查询产品价格",
  "response_summary": "返回了3个产品的价格信息",
  "cost_usd": 0.008
}
```

**结构化日志：JSON 格式是必须的**

AI 应用的日志量大、维度多，纯文本日志根本没法用。你需要 JSON 格式的结构化日志，原因有三：

1. **可查询**：`jq '.[] | select(.cost_usd > 0.05)'` 找出所有高成本请求
2. **可聚合**：按 model、user_id、tool_name 分组统计
3. **可对接**：直接导入 Elasticsearch、Loki、BigQuery 等分析平台

**日志级别设计**

AI 应用的日志级别需要重新定义，因为传统的 ERROR/WARN/INFO/DEBUG 在 AI 场景下含义不同：

| 级别 | 记录什么 | 生产环境 | 开发环境 |
|---|---|---|---|
| **error** | API 调用失败、工具执行报错、解析异常 | 开启 | 开启 |
| **warn** | Agent 循环超过 3 次、token 超出预期 2 倍、工具返回空结果、模型拒绝回答 | 开启 | 开启 |
| **info** | 每次 LLM 调用的摘要（模型、token 数、延迟、成本）、工具调用记录、最终输出摘要 | 开启 | 开启 |
| **debug** | 完整的 prompt 内容、完整的模型输出、中间推理步骤、RAG 检索的具体文档 | 关闭 | 开启 |

注意 **warn** 级别的特殊设计——"Agent 循环超过 3 次"在传统应用里不算警告，但在 AI 应用里这是一个强烈的异常信号，意味着 Agent 可能陷入了循环。

**隐私考量：日志中的用户数据如何脱敏？**

这是一个极其重要但容易被忽略的问题。AI 应用的日志天然包含大量用户数据——因为用户的输入就是 prompt 的一部分。

脱敏策略：

1. **分级存储**：debug 级别的日志（包含完整 prompt）只保留短时间（如 7 天），info 级别的摘要日志保留更久
2. **字段加密**：对日志中的 `input` 和 `output` 字段做可逆加密，只有在调试时才解密
3. **PII 检测**：自动检测并遮盖手机号、邮箱、身份证号等个人信息
4. **访问控制**：包含完整 prompt 的日志只有特定角色能查看

一个现实中的两难：你想在日志里记录完整的 prompt 以便调试，但 prompt 里可能包含用户的隐私信息（医疗咨询、法律问题、个人财务）。**不记录你就没法调试，记录了你就有合规风险**。这需要根据你的业务场景和合规要求来权衡。

### 深层追问

**有哪些日志信息是 AI 应用必须记录、传统应用不需要的？**

最关键的是三个：模型版本（因为模型更新可能改变行为）、token 使用量（因为直接关联成本）、完整的 prompt/response 对（因为这是唯一能复现 AI 行为的方式）。传统应用不需要记录"函数的完整入参"来调试，但 AI 应用必须。

## 22.4 Agent 行为回放

### 一句话直觉解释

行为回放就是把 Agent 的一次执行过程"录像"，然后像看视频一样回放，看它每一步做了什么决策。

### 前端类比

你一定用过（或至少听过）Session Replay 工具，比如 LogRocket、FullStory、Hotjar。它们录制用户在网页上的操作——鼠标移动、点击、滚动、输入——然后让你像看录像一样回放，理解用户遇到了什么问题。

Agent 行为回放和 Session Replay 的思路完全一样。不同的是：

- Session Replay 录制的是用户的 DOM 操作
- Agent 回放录制的是 Agent 的决策链路

### 详细原理讲解

**为什么不能"给相同输入重新跑一遍"？**

新手最常犯的错误是：Agent 出了问题，拿着相同的用户输入重新跑一遍，发现结果正确了，然后结论是"偶发问题，不管了"。

这有三个严重问题：

1. **非确定性**：LLM 的输出是概率性的。temperature > 0 时，相同输入不保证相同输出。就算 temperature = 0，不同的 API 调用批次也可能产生不同结果。
2. **上下文不同**：Agent 的行为不只取决于当前输入，还取决于对话历史、检索到的文档、工具返回的实时数据。重新跑一遍时，这些上下文可能都变了。
3. **环境不同**：模型版本可能已经更新，API 数据可能已经变化，甚至 system prompt 可能被同事改了。

所以，**回放不是"重新执行"，而是"回看当时的执行记录"**。

**回放数据需要存储什么？**

一条完整的回放记录包含：

```
回放记录 = {
  // 执行环境快照
  timestamp: "2024-01-15T10:30:00Z",
  model_version: "claude-sonnet-5-5",
  system_prompt_hash: "abc123",  // 可以通过 hash 回溯到具体的 prompt 版本
  
  // 完整的消息链
  messages: [
    { role: "system", content: "..." },
    { role: "user", content: "..." },
    { role: "assistant", content: "..." },
    // ...所有中间步骤
  ],
  
  // 每次 LLM 调用的详细记录
  llm_calls: [
    {
      input: { messages: [...], tools: [...] },
      output: { content: "...", tool_calls: [...] },
      model: "claude-sonnet-5-5",
      tokens: { input: 500, output: 200 },
      latency_ms: 2300
    }
  ],
  
  // 每次工具调用的详细记录
  tool_calls: [
    {
      tool_name: "searchProducts",
      input: { query: "iPhone 15 价格" },
      output: { results: [...] },
      latency_ms: 150
    }
  ],
  
  // 最终输出
  final_output: "iPhone 15 的价格是..."
}
```

**如何可视化回放数据**

最直观的方式是把它渲染成一个时间线视图：

```
[10:30:00.000] 用户输入: "iPhone 15 多少钱？"
    │
[10:30:00.005] Prompt 构建完成 (500 tokens)
    │
[10:30:00.010] → LLM 调用 #1
[10:30:02.300] ← 返回: 需要调用 searchProducts 工具
    │              思考过程: "用户想知道价格，我需要搜索产品数据库"
    │
[10:30:02.310] → 工具调用: searchProducts({ query: "iPhone 15" })
[10:30:02.460] ← 返回: [{ name: "iPhone 15", price: 5999 }, ...]
    │
[10:30:02.470] → LLM 调用 #2 (包含工具返回结果)
[10:30:03.800] ← 返回: "iPhone 15 的官方起售价是 5999 元..."
    │
[10:30:03.810] 响应发送给用户
```

这种视图让你能快速定位问题：如果回答的价格是错的，你一眼就能看到是工具返回了错误的数据（工具问题）还是模型无视了正确数据（prompt/模型问题）。

### 实际应用场景

一个电商客服 Agent 回复客户说"这个商品已经下架了"，但实际上商品还在卖。回放发现：Agent 调用了 `getProductStatus` 工具，工具返回了 `{ status: "inactive" }`，但这个 `inactive` 其实是指"暂时缺货"而不是"下架"。Agent 根据工具描述把 `inactive` 理解成了"下架"。

修复方案：更新工具返回值的说明，把 `inactive` 改为更明确的 `out_of_stock`，并在工具描述中写清楚每个状态值的含义。

没有行为回放，你可能会以为是模型幻觉，然后去调 prompt，永远修不好这个问题。

## 22.5 常见调试场景

实践中，Agent 的问题大体上可以归为以下几个典型模式。与其每次从零开始排查，不如建立一套"问题特征 → 排查方向"的映射表。

### Agent 选了错误的工具

**现象**：让 Agent 查天气，它却调用了搜索引擎工具。

**排查方向**：
1. 检查 tool description——工具描述是否清晰区分了各工具的用途？
2. 检查工具命名——`search` 和 `weather_search` 在模型眼里可能很像
3. 检查 system prompt——有没有明确指导工具选择的逻辑？
4. 检查示例——few-shot 示例中有没有展示正确的工具选择？

**修复思路**：让工具描述更明确，加入 "Use this tool WHEN..." 和 "Do NOT use this tool WHEN..." 的指导。

### Agent 回答不相关

**现象**：用户问的是 A，Agent 回答的是 B。

**排查方向**：
1. 如果有 RAG → 检查检索结果是否相关。大概率是检索环节出了问题
2. 如果没有 RAG → 检查上下文窗口，是不是之前的对话历史太长，模型"忘记"了最近的问题
3. 检查 system prompt 是否有冲突的指令

### Agent 陷入循环

**现象**：Agent 反复调用同一个工具，或者在几个工具之间来回切换，就是不给出最终回答。

**排查方向**：
1. 检查工具返回值——是不是返回了模糊或不完整的结果，导致 Agent 认为需要继续调用？
2. 检查终止条件——有没有设置最大循环次数？
3. 检查 prompt——有没有明确告诉 Agent 什么时候应该停止并给出回答？

### 回答质量突然下降

**现象**：Agent 之前回答得很好，突然变差了。代码没改。

**排查方向**：
1. **模型版本变更**——AI 服务商是否更新了模型？这是最常见的原因
2. **数据源变化**——RAG 的文档库是否更新了？更新后的文档质量如何？
3. **流量模式变化**——是不是用户开始问之前没有覆盖过的问题类型？
4. **级联故障**——某个依赖的工具 API 是否响应变慢或返回数据格式变了？

建立这样一份排查清单（Runbook），能让你在遇到问题时不至于手足无措。

## 22.6 可观测性工具生态

### 一句话直觉解释

就像前端有 Sentry 监控错误、DataDog 监控性能、LogRocket 回放用户操作，AI 应用也有自己的一套可观测性工具。

### 前端类比

| 前端工具 | AI 对应工具 | 功能 |
|---|---|---|
| Sentry | LangSmith / Braintrust | 追踪和调试 |
| DataDog RUM | Helicone | 请求级别的监控和分析 |
| Chrome DevTools | Agent 回放面板 | 本地调试 |
| Lighthouse | AI 评估工具 | 质量评分 |

### 详细原理讲解

**LangSmith**

LangChain 生态的追踪和评估工具。如果你用 LangChain / LangGraph 构建 Agent，LangSmith 是最自然的选择。

核心功能：
- 自动追踪所有 LLM 调用、工具调用、检索操作
- 可视化 Trace 树
- 支持在线评估和人工标注
- 提供 Playground 修改 prompt 并看效果

局限：和 LangChain 生态绑定较深。如果你不用 LangChain，集成成本较高。

**Braintrust**

评估 + 追踪一体化的平台。它的独特价值在于把"观测"和"评估"连接在一起。

核心功能：
- 追踪 AI 请求（支持任何框架，不绑定 LangChain）
- 内置评估框架——你可以定义评估指标，然后在追踪数据上自动运行评估
- 支持 A/B 测试不同的 prompt 版本
- 数据集管理——从追踪数据中生成评估数据集

**Helicone**

AI 请求代理——它作为你的应用和 AI API 之间的中间层，透明地记录所有请求。

核心功能：
- 零代码集成——只需要改一行 API base URL
- 记录所有请求和响应
- 成本统计和分析
- 缓存、限流、重试
- 用户级别的用量跟踪

优势在于它的集成成本极低。你不需要改任何代码逻辑，只是把 API 请求通过 Helicone 代理一下。

**自建方案：OpenTelemetry + 自定义 Exporter**

如果你对数据安全有严格要求（不希望 prompt 内容发送到第三方平台），可以基于 OpenTelemetry 自建。

思路：
- 用 OpenTelemetry SDK 创建自定义 Span
- 在每个 LLM 调用前后记录数据
- 通过 Exporter 发送到你自己的存储后端（Jaeger、Grafana Tempo、Elasticsearch）
- 用 Grafana 搭建可视化面板

这条路更费力，但数据完全在你的控制之下。对于处理敏感数据的企业级应用，这可能是唯一选择。

## 22.7 Dashboard 设计：看什么、怎么看

### 一句话直觉解释

Dashboard 不是把所有指标堆在一起，而是让你**一眼看出"现在有没有问题"**。

### 详细原理讲解

**关键指标设计**

一个有效的 AI 应用 Dashboard 需要覆盖四个维度：

**性能维度**
- 延迟 P50/P95/P99：中位数延迟和尾部延迟
- TTFB（Time to First Byte）：流式输出场景下用户看到第一个字的时间
- 各环节延迟拆分：LLM 调用占比、工具调用占比、检索占比

**可靠性维度**
- 成功率：API 调用成功率、工具调用成功率
- 重试率：触发重试机制的比例
- 超时率：请求超时的比例
- 错误分类：4xx（客户端问题）vs 5xx（服务端问题）vs AI 特有错误（模型拒绝、格式解析失败）

**成本维度**
- Token 使用量：按 input/output 分别统计
- 每次请求的平均成本
- 日/周/月总成本趋势
- 按功能/模型分维度的成本分布

**质量维度**
- 用户满意度（如果有反馈机制）
- Agent 平均步骤数（步骤越多通常意味着效率越低）
- 工具调用失败率
- 循环检测触发率

**告警规则设计**

不是所有指标异常都需要告警。告警太多等于没有告警——告警疲劳会让团队对真正的问题麻木。

建议的告警分级：

| 优先级 | 条件 | 响应 |
|---|---|---|
| P0 紧急 | API 成功率 < 95%，持续 5 分钟 | 立即响应，可能需要降级或切换模型 |
| P1 高 | P95 延迟 > 10s，持续 10 分钟 | 15 分钟内响应 |
| P2 中 | 日成本超预算 150% | 工作时间内处理 |
| P3 低 | 某个工具调用失败率 > 10% | 下个工作日处理 |

关键原则是：**告警应该是可操作的**。如果你收到告警后不知道该做什么，那这个告警就不应该存在。

| 概念 | 可观测性（Observability） | 监控（Monitoring） | 调试（Debugging） |
|---|---|---|---|
| 关注点 | 系统内部状态是否可理解 | 预定义指标是否正常 | 具体问题的根因 |

| 存储成本 | 高（数据量大） | 中 | 低（预聚合） |

## 灵魂拷问

> **Q: Agent 的"bug"和传统代码的 bug 有什么本质区别？能用 debugger 断点调试 Agent 吗？**

> A: 本质区别在于确定性。传统 bug 是确定性的——给定相同输入，一定能复现，你可以用 debugger 一步步走到出错的那一行。Agent 的"bug"是概率性的——相同输入可能得到不同输出，而且错误不是"程序崩了"而是"回答不好"。你可以对 Agent 的外围代码（API 调用、工具调用、结果解析）打断点，但你无法对模型内部打断点——你无法看到"它为什么选了这个词而不是那个词"。所以 Agent 调试更像数据分析而不是代码调试：你需要收集足够多的数据，然后通过统计和对比来发现问题模式。

> **Q: 记录完整的 prompt 到日志里有什么安全风险？不记录又会导致什么调试困难？**

> A: 安全风险很明确：prompt 里包含用户的原始输入，可能有个人隐私（姓名、电话、医疗信息等），如果日志泄露就是数据安全事故。在 GDPR/个人信息保护法下，这甚至可能违法。但不记录的代价是：当 Agent 行为异常时，你无法复现当时的 prompt，也就无法理解模型为什么给出那样的回答。你只能靠猜。实践中的平衡方案：开发环境记录完整 prompt；生产环境记录 prompt 的 hash 和摘要（如 token 数、关键字段），完整 prompt 做加密存储并设置短期过期（7-14 天），只在调试时按需解密。

> **Q: Agent 行为回放和"给相同输入重新跑一遍"有什么区别？为什么不能简单重跑？**

> A: 区别在于"回放是回看历史录像，重跑是重新拍一遍"。重跑有三个问题：第一，模型是非确定性的，相同输入不保证相同输出；第二，工具返回的数据是实时的，重跑时数据库里的数据可能已经变了；第三，执行环境可能变了——模型版本可能更新了，system prompt 可能被改了。只有回放——使用当时记录下来的完整数据链路——才能准确还原"那次执行到底发生了什么"。这就像交通事故分析要看行车记录仪，而不是让司机"再开一遍"。

> **Q: 如何发现"Agent 在静悄悄地变差"？有哪些先行指标？**

> A: "静悄悄地变差"是 AI 应用最危险的模式，因为没有明显的报错。先行指标包括：(1) Agent 的平均步骤数在增加——说明它需要更多次尝试才能完成任务；(2) 用户追问率在上升——说明第一次回答没有满足用户需求；(3) 特定工具的调用频率异常变化——可能是模型对工具的理解发生了偏移；(4) 输出 token 数在增加——可能是模型开始"啰嗦"了，这是质量下降的早期信号；(5) 用户负面反馈（点踩）率上升。关键是要建立基线——你得知道"正常情况"的数据长什么样，才能发现偏离。

> **Q: 可观测性工具本身也消耗资源和成本，怎么平衡观测粒度和性能开销？**

> A: 采样是核心策略。不需要 100% 的请求都完整记录，尤其在高流量场景下。建议的策略：(1) 所有请求都记录基础 Metrics（token 数、延迟、成本）——这个开销极低；(2) 10%-20% 的请求记录完整 Trace（包括 prompt/response）；(3) 100% 的异常请求记录完整 Trace（自适应采样——出错了就全量记录）；(4) debug 级别日志只在开发环境开启。具体比例根据你的流量和预算调整。记住：可观测性的成本应该是 AI API 成本的 5%-10%，如果超过这个比例，说明你的观测粒度太细了。

> **Q: 如果 AI 服务商的 API 不提供模型版本号，我怎么知道模型是否被更新了？**

> A: 这是一个非常现实的问题。有些服务商用 "latest" 这样的别名，底层模型可能随时更新。应对方法：(1) 尽量使用固定的模型版本号（如 `gpt-4-0613` 而不是 `gpt-4`）；(2) 建立一组"金丝雀测试"——每天自动发送固定的 prompt 并检查输出的一致性，如果输出突然变化，大概率是模型被更新了；(3) 记录每次请求的 response headers，有些服务商会在 header 中返回实际使用的模型版本；(4) 订阅服务商的 changelog 和状态页面。最佳实践是把模型版本当作基础设施的一部分来监控，就像你会监控数据库版本一样。

> **Q: 团队里没有专门的 SRE，前端开发者自己搞可观测性现实吗？**

> A: 完全现实，因为 AI 应用的可观测性不需要传统 SRE 的那套重装备。从最轻量的方案开始：第一步，用 Helicone 做 API 代理（改一行代码就行），立刻获得请求级别的监控和成本统计；第二步，在关键路径加结构化日志，用免费的 Grafana Cloud 做可视化；第三步，在发现具体问题时再按需增加 Tracing。不要一上来就搭建完整的可观测性平台——先把 80% 的价值用 20% 的投入拿到，然后随着问题的出现逐步增强。前端开发者的优势是对浏览器 DevTools 和 Performance API 已经很熟悉，AI 可观测性的思维模型是一样的。

## 最佳实践

### DO

- **DO** 从第一天就加入基础可观测性。至少记录每次 LLM 调用的模型、token 数、延迟和成本
- **DO** 使用结构化日志（JSON 格式），方便后续查询和分析
- **DO** 记录模型版本号。每次请求都记，这是排查"突然变差"的第一线索
- **DO** 对异常请求自动加大记录粒度（自适应采样）
- **DO** 建立基线指标。你必须知道"正常"的数据长什么样，才能发现异常
- **DO** 把 Trace ID 透传到前端，让用户反馈问题时能附带 Trace ID
- **DO** 对生产环境的 prompt 日志做加密和脱敏处理
- **DO** 定期回顾告警规则，删除不再有用的告警（告警疲劳是真实的威胁）

### DON'T

- **DON'T** 只关注错误日志。Agent 最常见的问题是"没报错但回答不对"
- **DON'T** 在生产环境记录完整的 prompt 而不加密。这是数据安全红线
- **DON'T** 设置太多 P0 告警。如果一切都是紧急的，那什么都不是紧急的
- **DON'T** 依赖"重新跑一遍"来复现问题。AI 的输出是非确定性的
- **DON'T** 把可观测性当作"事后补救"。上线前就应该有基础的追踪和日志
- **DON'T** 忽视成本指标。一个 token 泄漏的 bug 可能悄悄烧掉你的预算

## 代码实战

### 项目：为 Agent 添加完整的可观测性

我们会构建一个轻量级但完整的可观测性层，包括 Tracing、结构化日志和简单的 Dashboard 数据收集。

> **项目归属**：下面 5 个文件都在**主线 Next.js 项目**的 `lib/observability/` 目录下。其中 `tracer.ts`、`logger.ts`、`replay.ts`、`metrics.ts` 是**与模型无关**的通用组件，可以直接被你的 DeepSeek + AI SDK Agent 复用；`observable-agent.ts` 是把这些组件接入 Agent 的**演示**，它用**原生 Anthropic SDK**（`@anthropic-ai/sdk`）演示工具调用追踪，运行前需要 `npm i @anthropic-ai/sdk` 并配置 `ANTHROPIC_API_KEY`（`tracer`/`logger`/`replay`/`metrics` 那四个类才是你真正要复用的部分，换成 AI SDK 的 `streamText`/`tool` 一样能把它们接进去）。

```typescript
// ============================================
// 文件：lib/observability/tracer.ts
// 说明：轻量级 Trace 追踪器
// ============================================

import { randomUUID } from "crypto";

// Span 的状态
type SpanStatus = "running" | "completed" | "error";

// 单个 Span 的数据结构
interface SpanData {
  spanId: string;
  parentSpanId: string | null;
  operationName: string;
  startTime: number;
  endTime: number | null;
  status: SpanStatus;
  input?: unknown;
  output?: unknown;
  metadata: Record<string, unknown>;
  error?: string;
}

// 一个完整 Trace 的数据结构
interface TraceData {
  traceId: string;
  startTime: number;
  endTime: number | null;
  spans: SpanData[];
  metadata: Record<string, unknown>;
}

// Span 类：记录一个操作的执行过程
class Span {
  private data: SpanData;

  constructor(operationName: string, parentSpanId: string | null = null) {
    this.data = {
      spanId: randomUUID(),
      parentSpanId,
      operationName,
      startTime: Date.now(),
      endTime: null,
      status: "running",
      metadata: {},
    };
  }

  // 设置输入
  setInput(input: unknown): this {
    this.data.input = input;
    return this;
  }

  // 设置输出
  setOutput(output: unknown): this {
    this.data.output = output;
    return this;
  }

  // 添加元数据
  setMetadata(key: string, value: unknown): this {
    this.data.metadata[key] = value;
    return this;
  }

  // 标记完成
  end(status: "completed" | "error" = "completed", error?: string): void {
    this.data.endTime = Date.now();
    this.data.status = status;
    if (error) this.data.error = error;
  }

  get id(): string {
    return this.data.spanId;
  }

  get duration(): number | null {
    if (!this.data.endTime) return null;
    return this.data.endTime - this.data.startTime;
  }

  toJSON(): SpanData {
    return { ...this.data };
  }
}

// Trace 类：管理一次完整的执行链路
class Trace {
  private data: TraceData;
  private spanStack: Span[] = [];

  constructor(metadata: Record<string, unknown> = {}) {
    this.data = {
      traceId: randomUUID(),
      startTime: Date.now(),
      endTime: null,
      spans: [],
      metadata,
    };
  }

  get traceId(): string {
    return this.data.traceId;
  }

  // 开始一个新的 Span
  startSpan(operationName: string): Span {
    const parentId =
      this.spanStack.length > 0
        ? this.spanStack[this.spanStack.length - 1].id
        : null;

    const span = new Span(operationName, parentId);
    this.spanStack.push(span);
    return span;
  }

  // 结束当前 Span 并记录
  endSpan(status: "completed" | "error" = "completed", error?: string): void {
    const span = this.spanStack.pop();
    if (span) {
      span.end(status, error);
      this.data.spans.push(span.toJSON());
    }
  }

  // 结束整个 Trace
  end(): TraceData {
    // 结束所有未关闭的 Span
    while (this.spanStack.length > 0) {
      this.endSpan("error", "Trace ended before span completed");
    }
    this.data.endTime = Date.now();
    return { ...this.data };
  }

  toJSON(): TraceData {
    return {
      ...this.data,
      spans: [...this.data.spans],
    };
  }
}

export { Trace, Span, type TraceData, type SpanData };
```

```typescript
// ============================================
// 文件：lib/observability/logger.ts
// 说明：AI 应用的结构化日志器
// ============================================

type LogLevel = "debug" | "info" | "warn" | "error";

interface LogEntry {
  timestamp: string;
  level: LogLevel;
  event: string;
  traceId?: string;
  data: Record<string, unknown>;
}

// PII 检测正则（简化版，生产环境需要更完善的实现）
const PII_PATTERNS = [
  { name: "phone", pattern: /1[3-9]\d{9}/g, replacement: "***PHONE***" },
  {
    name: "email",
    pattern: /[\w.-]+@[\w.-]+\.\w+/g,
    replacement: "***EMAIL***",
  },
  { name: "idcard", pattern: /\d{17}[\dXx]/g, replacement: "***IDCARD***" },
];

function sanitizePII(text: string): string {
  let result = text;
  for (const { pattern, replacement } of PII_PATTERNS) {
    result = result.replace(pattern, replacement);
  }
  return result;
}

// 日志级别优先级
const LOG_LEVEL_PRIORITY: Record<LogLevel, number> = {
  debug: 0,
  info: 1,
  warn: 2,
  error: 3,
};

class AILogger {
  private minLevel: LogLevel;
  private enablePIISanitization: boolean;
  private handlers: ((entry: LogEntry) => void)[] = [];

  constructor(options: {
    minLevel?: LogLevel;
    enablePIISanitization?: boolean;
  } = {}) {
    this.minLevel = options.minLevel ?? "info";
    this.enablePIISanitization = options.enablePIISanitization ?? true;
  }

  // 添加日志处理器（控制台、文件、远程服务等）
  addHandler(handler: (entry: LogEntry) => void): void {
    this.handlers.push(handler);
  }

  private shouldLog(level: LogLevel): boolean {
    return LOG_LEVEL_PRIORITY[level] >= LOG_LEVEL_PRIORITY[this.minLevel];
  }

  private sanitize(data: Record<string, unknown>): Record<string, unknown> {
    if (!this.enablePIISanitization) return data;

    const sanitized: Record<string, unknown> = {};
    for (const [key, value] of Object.entries(data)) {
      if (typeof value === "string") {
        sanitized[key] = sanitizePII(value);
      } else {
        sanitized[key] = value;
      }
    }
    return sanitized;
  }

  private log(
    level: LogLevel,
    event: string,
    data: Record<string, unknown>,
    traceId?: string
  ): void {
    if (!this.shouldLog(level)) return;

    const entry: LogEntry = {
      timestamp: new Date().toISOString(),
      level,
      event,
      traceId,
      data: this.sanitize(data),
    };

    // 发送给所有处理器
    for (const handler of this.handlers) {
      try {
        handler(entry);
      } catch {
        // 日志处理器的错误不应该影响主流程
        console.error("Log handler error (swallowed)");
      }
    }
  }

  // 记录 LLM 调用
  logLLMCall(params: {
    traceId?: string;
    model: string;
    inputTokens: number;
    outputTokens: number;
    latencyMs: number;
    costUsd: number;
    toolCalls?: string[];
    success: boolean;
    error?: string;
  }): void {
    const level = params.success ? "info" : "error";
    this.log(level, "llm_call", { ...params }, params.traceId);
  }

  // 记录工具调用
  logToolCall(params: {
    traceId?: string;
    toolName: string;
    input: unknown;
    output: unknown;
    latencyMs: number;
    success: boolean;
    error?: string;
  }): void {
    const level = params.success ? "info" : "warn";
    this.log(level, "tool_call", { ...params }, params.traceId);
  }

  // 记录 Agent 循环
  logAgentLoop(params: {
    traceId?: string;
    stepNumber: number;
    maxSteps: number;
    action: string;
  }): void {
    const level =
      params.stepNumber > params.maxSteps * 0.7 ? "warn" : "info";
    this.log(level, "agent_loop_step", { ...params }, params.traceId);
  }

  // 记录完整的 prompt（仅 debug 级别）
  logPromptDetail(params: {
    traceId?: string;
    systemPrompt: string;
    userMessage: string;
    fullMessages: unknown[];
  }): void {
    this.log("debug", "prompt_detail", { ...params }, params.traceId);
  }

  // 通用日志方法
  debug(event: string, data: Record<string, unknown>, traceId?: string): void {
    this.log("debug", event, data, traceId);
  }

  info(event: string, data: Record<string, unknown>, traceId?: string): void {
    this.log("info", event, data, traceId);
  }

  warn(event: string, data: Record<string, unknown>, traceId?: string): void {
    this.log("warn", event, data, traceId);
  }

  error(event: string, data: Record<string, unknown>, traceId?: string): void {
    this.log("error", event, data, traceId);
  }
}

// 控制台日志处理器
function consoleHandler(entry: LogEntry): void {
  const { timestamp, level, event, traceId, data } = entry;
  const prefix = traceId ? `[${traceId.slice(0, 8)}]` : "";
  console.log(
    JSON.stringify({ timestamp, level, event, prefix, ...data }, null, 2)
  );
}

// 远程日志处理器（发送到日志收集服务）
function createRemoteHandler(endpoint: string) {
  const buffer: LogEntry[] = [];
  const FLUSH_INTERVAL = 5000; // 5秒刷新一次
  const FLUSH_SIZE = 50; // 或积累50条刷新

  async function flush() {
    if (buffer.length === 0) return;
    const batch = buffer.splice(0, buffer.length);
    try {
      await fetch(endpoint, {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ logs: batch }),
      });
    } catch {
      // 远程日志发送失败不应该影响主流程
      console.error("Failed to send logs to remote (swallowed)");
    }
  }

  // 定时刷新
  setInterval(flush, FLUSH_INTERVAL);

  return (entry: LogEntry) => {
    buffer.push(entry);
    if (buffer.length >= FLUSH_SIZE) {
      flush();
    }
  };
}

export { AILogger, consoleHandler, createRemoteHandler };
```

```typescript
interface ReplayRecord {
  replayId: string;
  traceId: string;
  timestamp: string;
  environment: {
    modelVersion: string;
    systemPromptHash: string;
    appVersion: string;
  };
  userInput: string;
  finalOutput: string;
  llmCalls: ReplayLLMCall[];
  toolCalls: ReplayToolCall[];
  totalLatencyMs: number;
  totalTokens: { input: number; output: number };
  totalCostUsd: number;
}

// 回放记录器
class ReplayRecorder {
  private llmCalls: ReplayLLMCall[] = [];
  private toolCalls: ReplayToolCall[] = [];
  private callCounter = 0;
  private startTime: number;

  constructor(
    private replayId: string,
    private traceId: string,
    private environment: ReplayRecord["environment"]
  ) {
    this.startTime = Date.now();
  }

  // 记录一次 LLM 调用
  recordLLMCall(call: Omit<ReplayLLMCall, "callIndex" | "timestamp">): void {
    this.llmCalls.push({
      ...call,
      callIndex: this.callCounter++,
      timestamp: Date.now(),
    });
  }

  // 记录一次工具调用
  recordToolCall(
    call: Omit<ReplayToolCall, "callIndex" | "timestamp">
  ): void {
    this.toolCalls.push({
      ...call,
      callIndex: this.callCounter++,
      timestamp: Date.now(),
    });
  }

  // 生成完整的回放记录
  finalize(userInput: string, finalOutput: string): ReplayRecord {
    const totalTokens = this.llmCalls.reduce(
      (acc, call) => ({
        input: acc.input + call.tokens.input,
        output: acc.output + call.tokens.output,
      }),
      { input: 0, output: 0 }
    );

    return {
      replayId: this.replayId,
      traceId: this.traceId,
      timestamp: new Date().toISOString(),
      environment: this.environment,
      userInput,
      finalOutput,
      llmCalls: this.llmCalls,
      toolCalls: this.toolCalls,
      totalLatencyMs: Date.now() - this.startTime,
      totalTokens,
      totalCostUsd: this.calculateCost(totalTokens),
    };
  }

  private calculateCost(tokens: { input: number; output: number }): number {
    // 简化的成本计算，实际应根据模型定价
    const INPUT_COST_PER_1K = 0.003;
    const OUTPUT_COST_PER_1K = 0.015;
    return (
      (tokens.input / 1000) * INPUT_COST_PER_1K +
      (tokens.output / 1000) * OUTPUT_COST_PER_1K
    );
  }
}
```

```typescript
interface MetricPoint {
  name: string;
  value: number;
  timestamp: number;
  tags: Record<string, string>;

// 延迟百分位计算器
class LatencyTracker {
  private values: number[] = [];
  private maxSize: number;

  constructor(maxSize = 1000) {
    this.maxSize = maxSize;
  }

  record(value: number): void {
    this.values.push(value);
    // 超过上限时移除最旧的数据
    if (this.values.length > this.maxSize) {
      this.values.shift();
    }
  }

  percentile(p: number): number {
    if (this.values.length === 0) return 0;
    const sorted = [...this.values].sort((a, b) => a - b);
    const index = Math.ceil((p / 100) * sorted.length) - 1;
    return sorted[Math.max(0, index)];
  }

  get p50(): number { return this.percentile(50); }
  get p95(): number { return this.percentile(95); }
  get p99(): number { return this.percentile(99); }
  get count(): number { return this.values.length; }
  get average(): number {
    if (this.values.length === 0) return 0;
    return this.values.reduce((a, b) => a + b, 0) / this.values.length;
  }
}

// 指标收集器
class MetricsCollector {
  private points: MetricPoint[] = [];
  private latencyTrackers: Map<string, LatencyTracker> = new Map();
  private counters: Map<string, number> = new Map();
  private flushHandlers: ((points: MetricPoint[]) => void)[] = [];

  // 记录一个计数器
  increment(name: string, tags: Record<string, string> = {}, delta = 1): void {
    const key = `${name}:${JSON.stringify(tags)}`;
    this.counters.set(key, (this.counters.get(key) ?? 0) + delta);
    this.points.push({
      name,
      value: delta,
      timestamp: Date.now(),
      tags,
    });
  }

  // 记录延迟
  recordLatency(
    name: string,
    valueMs: number,
    tags: Record<string, string> = {}
  ): void {
    const key = `${name}:${JSON.stringify(tags)}`;
    if (!this.latencyTrackers.has(key)) {
      this.latencyTrackers.set(key, new LatencyTracker());
    }
    this.latencyTrackers.get(key)!.record(valueMs);
    this.points.push({
      name: `${name}_ms`,
      value: valueMs,
      timestamp: Date.now(),
      tags,
    });
  }

  // 记录成本
  recordCost(costUsd: number, tags: Record<string, string> = {}): void {
    this.points.push({
      name: "cost_usd",
      value: costUsd,
      timestamp: Date.now(),
      tags,
    });
  }

  // 获取延迟百分位
  getLatencyPercentiles(name: string, tags: Record<string, string> = {}) {
    const key = `${name}:${JSON.stringify(tags)}`;
    const tracker = this.latencyTrackers.get(key);
    if (!tracker) return null;
    return {
      p50: tracker.p50,
      p95: tracker.p95,
      p99: tracker.p99,
      count: tracker.count,
      average: tracker.average,
    };
  }

  // 获取 Dashboard 摘要
  getDashboardSummary(): Record<string, unknown> {
    const llmLatency = this.getLatencyPercentiles("llm_call");
    const toolLatency = this.getLatencyPercentiles("tool_call");

    return {
      llmLatency,
      toolLatency,
      totalRequests: this.counters.get('requests:{}') ?? 0,
      recentMetricPoints: this.points.length,
    };
  }

  // 注册刷新处理器
  onFlush(handler: (points: MetricPoint[]) => void): void {
    this.flushHandlers.push(handler);
  }

  // 定时刷新指标到外部系统
  flush(): void {
    if (this.points.length === 0) return;
    const batch = this.points.splice(0, this.points.length);
    for (const handler of this.flushHandlers) {
      handler(batch);
    }
  }
}

export { MetricsCollector, LatencyTracker };
```

```typescript
import { Trace } from "./tracer";
import { AILogger, consoleHandler } from "./logger";
import { ReplayRecorder } from "./replay";
import { MetricsCollector } from "./metrics";
import { randomUUID } from "crypto";
import Anthropic from "@anthropic-ai/sdk"; // 示例用 Anthropic 原生 SDK 演示工具调用追踪（provider 专属，与主线 AI SDK 无关）

// 初始化可观测性组件
const logger = new AILogger({
  minLevel: process.env.NODE_ENV === "production" ? "info" : "debug",
  enablePIISanitization: process.env.NODE_ENV === "production",
});
logger.addHandler(consoleHandler);

const metrics = new MetricsCollector();

// Agent 工具定义
interface Tool {
  name: string;
  description: string;
  execute: (input: unknown) => Promise<unknown>;
}

// 带完整可观测性的 Agent 执行函数
async function runObservableAgent(params: {
  userMessage: string;
  systemPrompt: string;
  tools: Tool[];
  model?: string;
  maxSteps?: number;
}): Promise<{
  response: string;
  traceId: string;
}> {
  const {
    userMessage,
    systemPrompt,
    tools,
    model = "claude-sonnet-5-5",
    maxSteps = 10,
  } = params;

  // 1. 创建 Trace
  const trace = new Trace({ userId: "anonymous", feature: "chat" });
  const traceId = trace.traceId;

  // 2. 创建回放记录器
  const replayRecorder = new ReplayRecorder(randomUUID(), traceId, {
    modelVersion: model,
    systemPromptHash: simpleHash(systemPrompt),
    appVersion: process.env.APP_VERSION ?? "unknown",
  });

  // 3. 记录请求开始
  metrics.increment("requests", { model });
  logger.info("agent_request_start", { userMessage: userMessage.slice(0, 100) }, traceId);

  const client = new Anthropic();
  const messages: Anthropic.MessageParam[] = [
    { role: "user", content: userMessage },
  ];

  let finalResponse = "";
  let step = 0;

  try {
    while (step < maxSteps) {
      step++;
      logger.logAgentLoop({ traceId, stepNumber: step, maxSteps, action: "llm_call" });

      // 4. LLM 调用 Span
      const llmSpan = trace.startSpan("llm_call");
      llmSpan.setMetadata("model", model);
      llmSpan.setMetadata("step", step);

      const llmStart = Date.now();

      // 构建工具定义
      const toolDefinitions: Anthropic.Tool[] = tools.map((t) => ({
        name: t.name,
        description: t.description,
        input_schema: { type: "object" as const, properties: {} },
      }));

      // 调用 LLM
      const response = await client.messages.create({
        model,
        max_tokens: 1024,
        system: systemPrompt,
        messages,
        tools: toolDefinitions.length > 0 ? toolDefinitions : undefined,
      });

      const llmLatency = Date.now() - llmStart;

      // 5. 记录 LLM 调用指标
      const inputTokens = response.usage.input_tokens;
      const outputTokens = response.usage.output_tokens;

      llmSpan.setMetadata("inputTokens", inputTokens);
      llmSpan.setMetadata("outputTokens", outputTokens);
      llmSpan.setMetadata("latencyMs", llmLatency);
      trace.endSpan("completed");

      logger.logLLMCall({
        traceId,
        model,
        inputTokens,
        outputTokens,
        latencyMs: llmLatency,
        costUsd: calculateCost(model, inputTokens, outputTokens),
        success: true,
      });

      metrics.recordLatency("llm_call", llmLatency, { model });
      metrics.recordCost(calculateCost(model, inputTokens, outputTokens), { model });

      // 记录回放数据
      replayRecorder.recordLLMCall({
        model,
        input: {
          messages: messages.map((m) => ({
            role: m.role,
            content: typeof m.content === "string" ? m.content : "[complex]",
          })),
          tools: toolDefinitions,
        },
        output: {
          content: response.content
            .filter((b): b is Anthropic.TextBlock => b.type === "text")
            .map((b) => b.text)
            .join(""),
          toolCalls: response.content
            .filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use")
            .map((b) => ({ toolName: b.name, arguments: b.input })),
        },
        tokens: { input: inputTokens, output: outputTokens },
        latencyMs: llmLatency,
      });

      // 6. 处理响应
      if (response.stop_reason === "end_turn") {
        // Agent 完成了，提取文本回答
        finalResponse = response.content
          .filter((b): b is Anthropic.TextBlock => b.type === "text")
          .map((b) => b.text)
          .join("");
        break;
      }

      // 7. 处理工具调用
      const toolUseBlocks = response.content.filter(
        (b): b is Anthropic.ToolUseBlock => b.type === "tool_use"
      );

      if (toolUseBlocks.length === 0) {
        finalResponse = response.content
          .filter((b): b is Anthropic.TextBlock => b.type === "text")
          .map((b) => b.text)
          .join("");
        break;
      }

      // 把 assistant 的回复加入消息列表
      messages.push({ role: "assistant", content: response.content });

      // 执行每个工具调用
      const toolResults: Anthropic.ToolResultBlockParam[] = [];

      for (const toolUse of toolUseBlocks) {
        const toolSpan = trace.startSpan("tool_call");
        toolSpan.setInput(toolUse.input);
        toolSpan.setMetadata("toolName", toolUse.name);

        const toolStart = Date.now();
        const tool = tools.find((t) => t.name === toolUse.name);

        if (!tool) {
          const errorMsg = `Tool not found: ${toolUse.name}`;
          toolSpan.end("error", errorMsg);
          trace.endSpan("error", errorMsg);
          logger.logToolCall({
            traceId,
            toolName: toolUse.name,
            input: toolUse.input,
            output: null,
            latencyMs: 0,
            success: false,
            error: errorMsg,
          });
          toolResults.push({
            type: "tool_result",
            tool_use_id: toolUse.id,
            content: errorMsg,
            is_error: true,
          });
          continue;
        }

        try {
          const toolOutput = await tool.execute(toolUse.input);
          const toolLatency = Date.now() - toolStart;

          toolSpan.setOutput(toolOutput);
          trace.endSpan("completed");

          logger.logToolCall({
            traceId,
            toolName: toolUse.name,
            input: toolUse.input,
            output: toolOutput,
            latencyMs: toolLatency,
            success: true,
          });

          metrics.recordLatency("tool_call", toolLatency, { tool: toolUse.name });

          replayRecorder.recordToolCall({
            toolName: toolUse.name,
            input: toolUse.input,
            output: toolOutput,
            latencyMs: toolLatency,
            success: true,
          });

          toolResults.push({
            type: "tool_result",
            tool_use_id: toolUse.id,
            content: JSON.stringify(toolOutput),
          });
        } catch (err) {
          const toolLatency = Date.now() - toolStart;
          const errorMsg = err instanceof Error ? err.message : String(err);

          trace.endSpan("error", errorMsg);

          logger.logToolCall({
            traceId,
            toolName: toolUse.name,
            input: toolUse.input,
            output: null,
            latencyMs: toolLatency,
            success: false,
            error: errorMsg,
          });

          metrics.increment("tool_errors", { tool: toolUse.name });

          toolResults.push({
            type: "tool_result",
            tool_use_id: toolUse.id,
            content: `Tool error: ${errorMsg}`,
            is_error: true,
          });
        }
      }

      // 将工具结果添加到消息列表
      messages.push({ role: "user", content: toolResults });
    }

    // 8. 检查是否超过最大步骤数
    if (step >= maxSteps) {
      logger.warn("agent_max_steps_reached", { maxSteps, step }, traceId);
      metrics.increment("max_steps_reached");
    }

    // 9. 完成 Trace 和回放记录
    const traceData = trace.end();
    const replayData = replayRecorder.finalize(userMessage, finalResponse);

    logger.info(
      "agent_request_complete",
      {
        totalSteps: step,
        totalLatencyMs: traceData.endTime! - traceData.startTime,
        responseLength: finalResponse.length,
      },
      traceId
    );

    // 异步存储 Trace 和回放数据（不阻塞响应）
    storeTraceAsync(traceData);
    storeReplayAsync(replayData);

    return { response: finalResponse, traceId };
  } catch (err) {
    const errorMsg = err instanceof Error ? err.message : String(err);
    trace.end();
    logger.error("agent_request_error", { error: errorMsg }, traceId);
    metrics.increment("request_errors");
    throw err;
  }
}

// 辅助函数
function simpleHash(str: string): string {
  let hash = 0;
  for (let i = 0; i < str.length; i++) {
    const char = str.charCodeAt(i);
    hash = (hash << 5) - hash + char;
    hash |= 0;
  }
  return Math.abs(hash).toString(36);
}

    (inputTokens / 1000) * price.input +

  );
```

## 实操练习

### 目标
为你的 Agent 项目添加完整的可观测性，能够追踪、记录和回放 Agent 的每一次执行。

### 步骤

1. **集成 Trace 追踪器**
   - 将 `Trace` 类集成到你的 Agent 执行流程中
   - 为每次 LLM 调用和工具调用创建对应的 Span
   - 确保 Trace ID 贯穿整个请求链路

2. **添加结构化日志**
   - 用 `AILogger` 替换你现有的 `console.log`
   - 为不同环境配置不同的日志级别
   - 在生产环境开启 PII 脱敏

3. **实现行为回放**
   - 用 `ReplayRecorder` 记录每次执行的完整数据
   - 将回放数据存储到本地文件（开发阶段）
   - 写一个简单的脚本读取回放数据并格式化打印

4. **搭建简易 Dashboard**
   - 用 `MetricsCollector` 收集关键指标
   - 创建一个 API 端点 `/api/metrics` 返回 Dashboard 摘要
   - （可选）用 React 搭建一个简单的指标展示页面

5. **模拟调试场景**
   - 故意让一个工具返回错误数据，然后通过 Trace 和日志定位问题
   - 修改 system prompt 导致行为变化，然后通过对比回放记录发现变更

### 验收标准
- [ ] 每次 Agent 请求都生成完整的 Trace，包含所有 Span

## 本章小结

这一章我们系统地学习了 AI 应用的可观测性：

1. **AI 调试的特殊性**：Agent 的"bug"是概率性的行为偏差，不是确定性的代码错误。传统的断点调试和单元测试手段不够用，你需要基于数据的分析方法。

2. **Tracing 是基石**：用 Trace 和 Span 记录 Agent 执行的完整链路，让你能看到每一步做了什么、花了多少时间和 token。这就像给 Agent 装了行车记录仪。

3. **日志要结构化**：JSON 格式的结构化日志是 AI 应用的标配。记住特殊的日志级别设计——"Agent 循环太多次"是 warn 而不是 info。隐私脱敏不是可选的，而是必须的。

4. **回放比重跑更可靠**：Agent 的行为是非确定性的，"给相同输入重新跑一遍"无法复现问题。你需要记录完整的执行数据用于回放分析。

5. **工具选择务实**：从轻量级方案（Helicone 代理 + 结构化日志）开始，随着问题复杂度增加再逐步引入完整方案。不要一上来就过度设计。

6. **Dashboard 聚焦可操作指标**：延迟、成本、成功率、质量。每个告警都应该对应一个明确的响应动作。

下一章我们聊钱——AI 应用的性能优化和成本控制。你会发现，可观测性数据是优化的前提，因为你必须先知道钱花在哪了，才能开始省钱。
