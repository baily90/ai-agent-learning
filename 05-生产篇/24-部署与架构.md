# 第23章：部署与架构 — 让你的 Agent 上线

## 引言

你已经有了一个能跑的 Agent——它能理解用户意图、调用工具、检索知识库、给出高质量的回答。在本地开发环境里，一切完美。

现在，是时候让它面对真实用户了。

如果你之前部署过 React 应用，流程大概是：`npm run build` → 把产出物扔到 Vercel/Netlify → 搞定。整个过程可能不到 5 分钟。

AI 应用的部署……不是这样的。

**AI 应用的部署比传统前端复杂得多**，原因在于它不只是"静态文件 + API"。你需要管理：

- **API 密钥**：AI 服务商的密钥需要安全存储和轮转
- **模型版本**：你依赖的外部模型可能随时更新，你需要锁定版本或及时适配
- **向量数据库**：如果用了 RAG，你的知识库需要持续维护和更新
- **长时间运行的任务**：Agent 可能需要 30 秒甚至几分钟才能完成，这和典型的 HTTP 请求模型不匹配
- **成本控制**：部署上线意味着开始真金白银地花钱，你需要监控和限制
- **质量保障**：代码没有 bug 不代表 AI 的回答正确，你需要在部署流程中加入质量评估

这一章，我们从部署架构选型开始，讲到 Next.js 全栈方案、AI Gateway、向量数据库运维、CI/CD，最后搭建完整的监控体系。读完之后，你的 Agent 不再是一个本地 demo，而是一个可以服务真实用户的生产级应用。

---

## 23.1 部署架构选型

### 一句话直觉解释

部署架构就像选房子——独栋别墅（物理服务器）、公寓楼（容器化）、酒店（Serverless）各有优劣，关键是匹配你的需求和预算。

### 前端类比

前端开发者对部署平台其实很熟悉：

```
前端部署               AI 应用部署
Vercel/Netlify    →    Serverless（简单但有限制）
Docker + VPS      →    容器化（灵活但要运维）
CDN 边缘缓存     →    Edge Runtime（快但功能受限）
前端 CDN + 后端 K8s → 混合架构（组合各自优势）
```

### 详细原理讲解

**方案一：Serverless（Vercel / Netlify / AWS Lambda）**

**适合场景**：中小规模，团队没有专职运维，想快速上线。

优势：
- 零运维：不用管服务器、扩缩容、负载均衡
- 按量计费：没有请求时不花钱
- 部署简单：git push 就上线
- 自动扩缩：流量突增时自动扩容

限制：
- **超时限制**：这是最大的痛点。Vercel 的 Hobby 计划函数超时 10 秒，Pro 计划 60 秒，Enterprise 300 秒。而一个复杂 Agent 可能需要 30 秒以上。
- **冷启动**：函数长时间不调用后会被回收，下次调用需要重新初始化（1-3 秒延迟）
- **无状态**：每次调用都是独立的，不能在内存中保持状态（如连接池）
- **包大小限制**：部分平台限制函数的 bundle 大小

**超时问题的解法**：
1. 使用流式响应——Vercel 的流式函数可以运行更长时间（因为在持续发送数据）
2. 拆分长任务——把一次 Agent 执行拆成多次 API 调用，前端轮询或用 WebSocket
3. 使用后台任务——如 Vercel 的 Background Functions 或 Inngest

**方案二：容器化（Docker + Kubernetes）**

**适合场景**：大规模、有运维团队、需要精细控制。

优势：
- 无超时限制：你的函数想跑多久跑多久
- 持久连接：可以维护连接池、缓存池
- 资源控制：精确分配 CPU/内存
- 环境一致性：开发/测试/生产完全相同的运行环境

限制：
- 运维复杂度高：K8s 本身就是一个需要专门学习的系统
- 固定成本：即使没有请求也要付服务器费用
- 扩缩容不如 Serverless 灵活

**什么时候从 Serverless 迁移到容器化？**

一般来说，当你遇到以下任何一个问题时：
- Serverless 超时限制频繁触发
- 冷启动延迟影响用户体验
- 需要 WebSocket 长连接
- 需要 GPU 做本地模型推理
- 月费用超过同等配置的容器方案

**方案三：Edge Runtime**

**适合场景**：对延迟敏感的轻量级 AI 功能。

Edge Runtime（如 Vercel Edge Functions、Cloudflare Workers）把你的代码部署到全球数百个边缘节点，用户的请求被路由到最近的节点。

优势：
- 超低延迟：代码在用户附近执行
- 全球覆盖：自动多区域部署
- 快速冷启动：通常 < 50ms

限制：
- 功能受限：不支持所有 Node.js API（没有 fs、部分 crypto 不可用）
- 执行时间短：通常限制在 30 秒以内
- 包大小限制：通常 < 1MB

**Edge Runtime 适合做什么？**
- AI 请求的路由和认证
- 简单的 AI 请求转发（不需要复杂逻辑）
- 语义缓存的查找层
- 用户请求的预处理和限流

**不适合做什么？**
- 复杂的 Agent 执行逻辑
- 需要大量依赖的处理
- 长时间运行的任务

**方案四：混合架构（推荐）**

**最佳实践是混合使用**：

```
┌────────────────────────────────────────────────┐
│                    用户浏览器                     │
└───────────────┬────────────────────────────────┘
                │
┌───────────────▼────────────────────────────────┐
│          Edge Runtime（Vercel Edge）              │
│  · 认证和限流                                     │
│  · 语义缓存查找                                   │
│  · 简单请求的快速响应                              │
└───────────────┬────────────────────────────────┘
                │ 复杂请求转发
┌───────────────▼────────────────────────────────┐
│         Serverless Functions（Vercel）            │
│  · API Routes 处理 AI 请求                        │
│  · 流式响应                                      │
│  · 大部分 Agent 逻辑                              │
└───────────────┬────────────────────────────────┘
                │ 超长任务 / 后台处理
┌───────────────▼────────────────────────────────┐
│         Container Service（Railway/Fly.io）       │
│  · 长时间运行的 Agent 任务                         │
│  · WebSocket 连接                                 │
│  · 向量数据库维护                                  │
└────────────────────────────────────────────────┘
```

这种架构让每一层做自己最擅长的事：Edge 做轻活快活，Serverless 做中等复杂度的活，Container 做重活。

### 深层追问

**小团队没有运维经验，怎么选？**

从 Serverless 开始。Vercel + Next.js 是对前端开发者最友好的方案。当你真的遇到 Serverless 解决不了的问题时，再考虑引入容器。不要预先过度架构——先用最简单的方案上线，根据真实问题迭代。

## 23.2 Next.js 全栈部署方案

### 一句话直觉解释

Next.js 就是 AI 应用的"全家桶"——前端渲染、后端 API、中间件认证、部署上线，一个框架全搞定。

### 前端类比

如果你用过 Create React App，你知道它只管前端。要加后端就得自己搞 Express。Next.js 不一样——它从诞生就是"全栈的"。对于 AI 应用来说，这意味着你不需要维护两个项目（前端 + 后端 API），一个 Next.js 项目就够了。

### 详细原理讲解

**API Routes 处理 AI 请求**

Next.js 的 API Routes 是处理 AI 请求的天然选择：

```
app/
├── api/
│   ├── chat/
│   │   └── route.ts      ← AI 对话接口
│   ├── search/
│   │   └── route.ts      ← RAG 搜索接口
│   └── feedback/
│       └── route.ts      ← 用户反馈接口
├── page.tsx               ← 前端页面
└── layout.tsx
```

API Route 的优势在于：
- 和前端同一个项目，共享类型定义
- 自动部署，不需要单独管理后端服务
- 支持流式响应（对 AI 应用至关重要）
- 支持 Edge Runtime 和 Node.js Runtime 两种模式

**Server Actions 简化前后端交互**

Next.js 的 Server Actions 让前后端交互更简洁。对于简单的 AI 操作（如提交反馈、触发后台任务），不需要写完整的 API Route：

```typescript
// app/actions.ts
"use server";

export async function submitFeedback(traceId: string, rating: "good" | "bad") {
  // 直接在服务端执行，不需要写 API Route
  await db.feedback.create({
    data: { traceId, rating, createdAt: new Date() },
  });
}
```

前端直接调用，就像调用一个本地函数一样：

```typescript
// 组件中
import { submitFeedback } from "./actions";

<button onClick={() => submitFeedback(traceId, "good")}>👍</button>
```

**Middleware 做认证和限流**

Next.js Middleware 运行在 Edge Runtime，在请求到达 API Route 之前执行。非常适合做：

- 认证检查：验证 JWT token
- 限流：检查请求频率
- 路由：根据条件转发到不同的后端
- 日志：记录请求信息

```typescript
// middleware.ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  // 只对 AI 相关的 API 路由应用中间件
  if (request.nextUrl.pathname.startsWith("/api/chat")) {
    // 1. 认证检查
    const token = request.headers.get("authorization");
    if (!token) {
      return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
    }

    // 2. 限流检查（简化版，生产环境用 Redis）
    const clientIp = request.headers.get("x-forwarded-for") ?? "unknown";
    // ... 检查请求频率

    // 3. 添加追踪头
    const requestHeaders = new Headers(request.headers);
    requestHeaders.set("x-trace-id", crypto.randomUUID());

    return NextResponse.next({ request: { headers: requestHeaders } });
  }

  return NextResponse.next();
}

export const config = {
  matcher: "/api/:path*",
};
```

**部署到 Vercel 的完整流程**

```
1. 代码准备
   ├── 确保 .env.local 中的密钥不会提交到 Git
   ├── 在 Vercel 项目设置中添加环境变量
   │   ├── ANTHROPIC_API_KEY
   │   ├── DATABASE_URL
   │   └── VECTOR_DB_URL
   └── 配置 vercel.json（如果需要自定义超时等）

2. 部署配置
   ├── 连接 Git 仓库
   ├── 设置构建命令：next build
   ├── 配置函数超时（Pro 计划最长 60 秒）
   └── 配置区域（选择离你的 AI API 服务器近的区域）

3. 上线后
   ├── 检查 Functions 日志
   ├── 监控冷启动频率
   ├── 检查流式响应是否正常
   └── 验证环境变量是否正确加载
```

### 深层追问

**Vercel 的免费计划能跑 AI 应用吗？**

能，但有很多限制。最大的限制是函数超时 10 秒——大多数 Agent 都无法在 10 秒内完成。Pro 计划（$20/月）把超时延长到 60 秒，对于大多数场景够用。如果你的 Agent 需要更长时间，考虑用流式响应（streaming）来延长可用时间，或者把长任务拆分到后台服务。

## 23.3 AI Gateway：AI 调用的统一管理层

### 一句话直觉解释

AI Gateway 就是 AI 版的 Nginx——你不直接访问 AI API，而是通过一个代理层，这个代理层帮你做路由、限流、日志、缓存、容错。

### 前端类比

如果你做过微服务架构，你一定知道 API Gateway（如 Kong、Traefik）。它在你的前端和一堆微服务之间充当统一入口，提供认证、限流、路由、日志等功能。

```
没有 API Gateway：
前端 → 用户服务
前端 → 订单服务
前端 → 支付服务
（每个服务都要自己处理认证、限流、日志）

有 API Gateway：
前端 → API Gateway → 用户服务
                   → 订单服务
                   → 支付服务
（认证、限流、日志在 Gateway 统一处理）
```

AI Gateway 是完全相同的概念：

```
没有 AI Gateway：
你的应用 → Anthropic API
你的应用 → OpenAI API
你的应用 → 本地模型
（每个调用都要自己处理限流、日志、容错）

有 AI Gateway：
你的应用 → AI Gateway → Anthropic API
                      → OpenAI API
                      → 本地模型
（限流、日志、缓存、fallback 在 Gateway 统一处理）
```

### 详细原理讲解

**AI Gateway 的核心功能**

1. **统一路由**：一个接口对接多个 AI 服务商。你的业务代码不需要关心底层用的是 Claude 还是 GPT，Gateway 负责路由。

2. **负载均衡**：当你有多个 AI API key 或多个服务商时，Gateway 可以分配请求。

3. **限流和配额管理**：在 Gateway 层统一管理 rate limit，比在业务代码中各处分散实现更可靠。

4. **日志和追踪**：所有 AI 请求自动记录，包括 prompt、response、token 数、延迟、成本。

5. **缓存**：相同的请求自动返回缓存结果。

6. **Fallback（降级）**：主模型 API 不可用时，自动切换到备用模型。

7. **重试**：遇到临时错误（如 429、500）时自动重试。

**现成方案**

**Portkey**
- 功能最全的 AI Gateway
- 支持 100+ AI 模型
- 内置缓存、限流、日志、评估
- 有免费计划
- 可以自托管

**LiteLLM**
- 开源的 AI API 代理
- 统一了不同服务商的 API 格式（都转成 OpenAI 格式）
- 可以自托管，数据不出你的网络
- Python 为主，但提供 HTTP API

**自建 Gateway**

如果你的需求简单或者对数据安全有严格要求，可以自建一个轻量级 Gateway：

核心就是一个 HTTP 代理，在转发请求的前后做一些额外操作：

```
请求进入 → 认证 → 限流检查 → 缓存查找 → [缓存未命中] → 转发到 AI API
                                         → [缓存命中]  → 返回缓存
                                         
AI API 返回 → 记录日志 → 存入缓存 → 返回给调用方
```

**什么时候需要 AI Gateway？**

坦率地说，不是所有应用都需要。如果你的 Agent 只调一个模型、流量不大、不需要容错，直接调 API 就行。

需要 Gateway 的信号：
- 你同时用多个 AI 服务商
- 你需要在不改代码的情况下切换模型
- 你的流量大到需要精细的限流和负载均衡
- 你需要统一的 AI 调用日志和成本统计
- 你需要自动 fallback（主模型挂了自动切换）

### 深层追问

**AI Gateway 又多了一层，增加了复杂度和延迟。值不值？**

延迟方面，一个好的 Gateway 增加的延迟通常在 5-20ms，相对于 AI API 本身 1-5 秒的延迟来说可以忽略不计。复杂度方面，Gateway 确实增加了一个需要维护的组件。但它也减少了业务代码的复杂度——限流、日志、缓存、容错这些逻辑不用散布在各处。对于生产级应用，这个权衡通常是值得的。对于 MVP 或小规模应用，先不用。

## 23.4 向量数据库的运维

### 一句话直觉解释

向量数据库就像你应用的"知识仓库"。仓库需要定期整理——进新货（更新数据）、清旧货（删除过时数据）、优化布局（索引维护）。

### 前端类比

如果你管理过搜索引擎的索引（比如 Algolia、Elasticsearch），向量数据库的运维思路是类似的——只不过你索引的不是关键词，而是语义向量。

### 详细原理讲解

**数据更新策略**

你的知识库不是一成不变的。产品文档会更新、政策会变化、价格会调整。向量数据库的数据需要和源数据保持同步。

两种更新策略：

**增量更新**（推荐大多数场景）
- 只处理有变化的文档
- 实现方式：监控源数据的变更（如文档的修改时间），只对变更的部分重新生成 Embedding 并更新
- 优势：快速，资源消耗少
- 劣势：需要维护变更追踪逻辑，可能出现不一致

**全量重建**（推荐定期执行）
- 删除旧数据，从源数据重新生成所有 Embedding
- 实现方式：定期（如每周）执行完整的重建流程
- 优势：简单可靠，不会有不一致
- 劣势：耗时长，期间可能影响查询

**推荐方案**：日常增量更新 + 每周全量重建。就像数据库的日常写入 + 定期 vacuum。

**索引维护和性能调优**

向量数据库使用近似最近邻（ANN）算法来加速查询。这些算法依赖索引结构，索引质量直接影响查询速度和准确性。

关注的指标：
- **查询延迟**：P95 应该在 100ms 以内（大多数托管服务能做到 50ms 以下）
- **召回率**：查询结果中包含真正相关文档的比例。ANN 是"近似"的，可能漏掉一些相关文档
- **索引大小**：数据量增长时，索引是否需要更多内存

调优方向：
- 调整 ANN 算法参数（如 HNSW 的 ef_construction 和 M）
- 选择合适的距离函数（余弦相似度 vs 欧几里得距离）
- 数据分区：按类别将文档分到不同的 collection/namespace，查询时只搜索相关分区

**备份和恢复**

向量数据库不像传统数据库那样有成熟的备份生态。但你需要有恢复方案：

1. **源数据是真正的"备份"**：只要源文档还在，你随时可以重建向量数据库
2. **导出快照**：定期导出向量数据库的快照
3. **记录 Embedding 参数**：确保你知道用的是哪个 Embedding 模型和版本。换了模型，所有 Embedding 都要重新生成

### 深层追问

**向量数据库的数据更新了但索引还是旧的，用户搜到的是过时信息。怎么保证一致性？**

这和前端的缓存一致性问题本质相同。策略：(1) 更新文档时同步更新对应的向量（而不是等到下次全量重建）；(2) 给每个向量标记源文档的版本号，查询时过滤掉旧版本；(3) 关键文档的更新走"先写入新版本、再删除旧版本"的流程，避免中间状态。(4) 对于极度时效敏感的信息（如实时库存），不要放在向量数据库里，而是在 Agent 调用实时 API 查询。

## 23.5 环境管理

### 一句话直觉解释

开发环境用"草稿纸"（便宜的模型，宽松的限制），生产环境用"正式文件"（最好的模型，严格的控制）。

### 前端类比

前端开发者对环境管理不陌生：

```
前端                              AI 应用
.env.development               .env.development
  API_URL=http://localhost:3000    AI_MODEL=claude-haiku（便宜的）
                                   AI_LOG_LEVEL=debug（记录一切）
                                   AI_RATE_LIMIT=1000（宽松）

.env.production                .env.production
  API_URL=https://api.prod.com     AI_MODEL=claude-sonnet（好的）
                                   AI_LOG_LEVEL=info（只记摘要）
                                   AI_RATE_LIMIT=100（严格）
```

### 详细原理讲解

**不同环境的配置差异**

| 配置项 | 开发环境 | 测试环境 | 生产环境 |
|---|---|---|---|
| AI 模型 | Haiku（便宜快速） | Sonnet（和生产一致） | Sonnet（最佳效果） |
| 日志级别 | debug（记录完整 prompt） | info | info（敏感数据脱敏） |
| 限流 | 几乎不限 | 模拟生产限流 | 严格限流 |
| 成本预算 | $10/天 | $50/天 | 根据业务设定 |
| API Key | 开发专用 key | 测试专用 key | 生产专用 key |
| 向量数据库 | 本地/开发实例 | 独立测试实例 | 生产集群 |
| 缓存 | 关闭（方便调试） | 开启（测试缓存逻辑） | 开启 |
| 评估 | 手动 | 自动化评估 | 自动化 + 人工抽检 |

**为什么不同环境用不同模型？**

开发阶段你可能每天调用 AI 几百次来调试 prompt。如果每次都用 Sonnet，一个月下来光开发测试的费用就可能上千美元。用 Haiku 做开发，成本只有 Sonnet 的 1/10 左右。

但要注意：最终的验收测试必须用和生产一样的模型。不同模型的行为可能有差异，用 Haiku 调好的 prompt 在 Sonnet 上可能表现不同。

**Feature Flag 控制 AI 功能的灰度发布**

新的 AI 功能不应该一次性对所有用户开放。用 Feature Flag 做灰度：

```typescript
// 灰度策略
const aiFeatureFlags = {
  // 新的 RAG 搜索功能：先开放给 10% 的用户
  newRAGSearch: {
    enabled: true,
    rolloutPercentage: 10,
    allowedUserIds: ["beta-tester-1", "beta-tester-2"], // 白名单
  },
  
  // 新的模型版本：先内部测试
  useClaudeSonnet4: {
    enabled: true,
    rolloutPercentage: 0, // 暂不面向普通用户
    allowedUserIds: ["internal-*"], // 只对内部用户开放
  },
};

function isFeatureEnabled(
  featureName: string,
  userId: string
): boolean {
  const flag = aiFeatureFlags[featureName as keyof typeof aiFeatureFlags];
  if (!flag || !flag.enabled) return false;
  
  // 检查白名单
  if (flag.allowedUserIds.some((pattern) => {
    if (pattern.endsWith("*")) {
      return userId.startsWith(pattern.slice(0, -1));
    }
    return userId === pattern;
  })) {
    return true;
  }
  
  // 按比例灰度
  const hash = simpleHash(userId + featureName);
  return (hash % 100) < flag.rolloutPercentage;
}

function simpleHash(str: string): number {
  let hash = 0;
  for (let i = 0; i < str.length; i++) {
    hash = (hash << 5) - hash + str.charCodeAt(i);
    hash |= 0;
  }
  return Math.abs(hash);
}
```

为什么 AI 功能特别需要灰度？因为 AI 功能的质量在上线前很难 100% 确认。你的评估测试可能覆盖了 95% 的场景，但剩下的 5% 只有真实用户才能暴露。灰度发布让你能在小范围内验证，发现问题及时回滚。

## 23.6 CI/CD for AI

### 一句话直觉解释

传统 CI/CD 检查"代码能不能编译、测试能不能过"。AI 应用的 CI/CD 还要检查"AI 的回答质量有没有下降"。

### 前端类比

你的前端 CI 可能是这样的：

```
代码提交 → 代码检查（ESLint） → 单元测试 → 构建 → 部署
```

AI 应用的 CI 多了几步：

```
代码提交 → 代码检查 → 单元测试 → AI 评估测试 → Prompt 回归测试 → 构建 → 部署
```

### 详细原理讲解

**部署前自动运行评估测试**

在 CI 流程中，自动对一组预定义的测试用例运行 AI Agent，检查输出质量。

```
评估流程：
1. 准备测试数据集（50-100 个代表性问题 + 预期回答）
2. 用当前代码运行 Agent，获得实际回答
3. 用评估指标（准确率、相关性、安全性）打分
4. 对比基线分数（上一次部署的分数）
5. 如果分数下降超过阈值，阻止部署
```

这里有一个成本问题：每次 CI 都跑 100 个测试用例，每个用例调一次 AI API。如果一天合 10 次 PR，就是 1,000 次 AI 调用。用 Haiku 跑评估可以大幅降低成本。

**Prompt 变更的版本管理和回滚**

Prompt 应该像代码一样做版本管理。但有一个关键区别：**prompt 的变更不像代码变更那样可以通过 diff 预测影响**。改了一个词，可能导致 Agent 的行为完全不同。

版本管理策略：

```
prompts/
├── system-prompt.v1.md
├── system-prompt.v2.md      ← 当前生产版本
├── system-prompt.v3.md      ← 开发中的新版本
└── prompt-config.json
    {
      "production": "v2",
      "staging": "v3",
      "rollback": "v1"       ← 回滚目标
    }
```

回滚策略：如果新版本上线后质量下降，快速回滚到上一个版本。这比回滚代码简单——你只需要改一个配置，把 prompt 版本指向旧版本就行。但前提是你保留了所有历史版本的 prompt。

**模型切换的蓝绿部署**

当你需要切换底层模型（比如从 Claude Sonnet 3.5 升级到 Sonnet 4）时，不要一次性切换。用蓝绿部署的方式：

```
阶段一：准备（绿色环境）
  └── 在新模型上运行完整的评估测试套件
  └── 对比新旧模型在相同测试集上的表现

阶段二：灰度（蓝绿并行）
  └── 10% 的流量走新模型，90% 走旧模型
  └── 监控新模型的各项指标（质量、延迟、成本）
  └── 逐步提高比例：10% → 30% → 50% → 100%

阶段三：完全切换
  └── 所有流量走新模型
  └── 保留旧模型配置，随时可以回滚

阶段四：清理
  └── 确认新模型稳定运行 1-2 周
  └── 移除旧模型配置
```

### 深层追问

**CI 中的评估测试失败了（AI 回答质量下降），但产品经理催着上线。怎么决策？**

这取决于质量下降的原因和程度。如果是因为 prompt 变更导致的（可以回滚 prompt 而不回滚代码），那就回滚 prompt 后部署。如果是代码变更无意间影响了 AI 行为，需要先定位问题。关键原则是：**质量下降是有成本的**——错误的 AI 回答会导致客户不满、工单增加、品牌受损。把这个成本和延迟上线的成本做比较。大多数情况下，花一天时间修复质量问题比带着质量问题上线更划算。如果必须紧急上线（比如修复了一个安全漏洞），可以先上线但加一个 Feature Flag 把有质量问题的 AI 功能暂时关闭。

## 23.7 监控和告警

### 一句话直觉解释

监控是你的 Agent 上线后的"体检报告"——不是等用户投诉了才知道有问题，而是问题刚出现就能发现。

### 前端类比

你大概率用过 Sentry 监控前端错误、用过 Google Analytics 监控用户行为。AI 应用的监控是这两者的结合——既要监控技术指标（错误、延迟），也要监控业务指标（回答质量、用户满意度）。

### 详细原理讲解

**健康检查：AI API 是否可用**

最基础的监控——你依赖的 AI API 是不是还活着？

```typescript
// 定期健康检查（每 1 分钟）
async function healthCheck(): Promise<{
  status: "healthy" | "degraded" | "down";
  latencyMs: number;
  details: Record<string, unknown>;
}> {
  const start = Date.now();
  
  try {
    // 发一个最小的请求来检测 API 是否可用
    const response = await client.messages.create({
      model: "claude-haiku-5", // 用最便宜的模型做健康检查
      max_tokens: 10,
      messages: [{ role: "user", content: "ping" }],
    });
    
    const latency = Date.now() - start;
    
    return {
      status: latency > 5000 ? "degraded" : "healthy",
      latencyMs: latency,
      details: {
        model: "claude-haiku-5",
        responseId: response.id,
      },
    };
  } catch (error) {
    return {
      status: "down",
      latencyMs: Date.now() - start,
      details: {
        error: error instanceof Error ? error.message : String(error),
      },
    };
  }
}
```

注意用最便宜的模型做健康检查——你不想每分钟为了一个 "ping" 花 Sonnet 的钱。

**四维监控体系**

一个完整的 AI 应用监控应该覆盖四个维度：

**1. 可用性监控**
- AI API 是否可用（健康检查）
- 请求成功率（目标 > 99%）
- 错误类型分布（429 限流 vs 500 服务器错误 vs 超时）

**2. 性能监控**
- 端到端延迟 P50/P95/P99
- TTFB（流式输出的首字节时间）
- 各环节延迟拆分（prompt 构建、LLM 调用、工具调用、后处理）
- 吞吐量（QPS）

**3. 成本监控**
- 实时费用跟踪（小时/日/月）
- 按模型/功能/用户的成本分布
- 与预算的对比
- 成本趋势（是否在增长？增长速度如何？）

**4. 质量监控**
- 用户反馈（点赞/点踩比例）
- Agent 平均步骤数（是否在增加？）
- 工具调用失败率
- 循环检测触发率
- 输出长度分布（突然变长或变短可能说明行为异常）
- 自动化质量抽检（定期从生产流量中抽样评估）

**告警设计**

告警的核心原则：**每个告警都应该有对应的行动方案**。如果收到告警后不知道该做什么，那这个告警就不应该存在。

```
告警层级设计：

P0 - 立即响应（自动通知 on-call + 电话）
  · AI API 完全不可用（健康检查连续 3 次失败）
  · 请求成功率 < 90%
  · 自动熔断触发（日成本超预算 150%）
  → 行动：检查 AI 服务商状态页面，启动降级方案

P1 - 15 分钟内响应（通知 on-call）
  · P95 延迟 > 15 秒，持续 10 分钟
  · 请求成功率 < 95%
  · 特定工具调用失败率 > 30%
  → 行动：检查日志，定位瓶颈

P2 - 工作时间内处理（发消息通知）
  · 日成本超预算
  · 用户负反馈率突增
  · Agent 平均步骤数比基线高 50%
  → 行动：分析趋势，制定优化计划

P3 - 下个迭代处理（记录 ticket）
  · 某个功能的延迟趋势在缓慢增长
  · 缓存命中率下降
  · 特定类型的问题回答质量下降
  → 行动：纳入技术债务处理
```

## 灵魂拷问

> **Q: Serverless 函数有 10 秒超时限制，但 Agent 可能需要 30 秒才能完成。怎么办？**

> A: 几种方案：(1) 使用流式响应——大多数 Serverless 平台对流式函数的超时更宽容，因为在持续发送数据说明函数还在工作；(2) 升级付费计划——Vercel Pro 是 60 秒，Enterprise 是 300 秒；(3) 任务拆分——把一次 Agent 执行拆成多次短请求，前端轮询或用 Server-Sent Events；(4) 后台任务——把长时间运行的 Agent 逻辑放到后台任务队列（如 Inngest、BullMQ），前端异步等待结果；(5) 混合架构——轻量级请求走 Serverless，重量级请求走容器化服务。最实用的是方案 (1) + (2)：开启流式输出 + 升级到 Pro 计划，能覆盖绝大多数场景。

> **Q: AI Gateway 听起来又多了一层，增加了复杂度。什么规模的应用需要它？**

> A: 简单标准：如果你只用一个 AI 服务商、日请求量 < 10,000、不需要自动 fallback，你不需要 AI Gateway。直接调 API 就行，把限流和日志写在自己的代码里。当你遇到以下任何一个问题时再考虑：(1) 需要同时用多个服务商（成本优化或容灾）；(2) 需要不改代码就能切换模型（运维灵活性）；(3) 需要统一的成本和用量报表（管理需求）；(4) 需要生产级的限流、缓存、重试机制（可靠性需求）。一个粗略的分界线：当 AI API 月费超过 $1,000 或日请求量超过 10,000 时，Gateway 的管理价值开始显现。

> **Q: 向量数据库的数据更新了但索引还是旧的，用户搜到的是过时信息。怎么保证一致性？**

> A: 首先要区分"最终一致性"和"强一致性"。大多数场景下最终一致性就够了——文档更新后几分钟内向量数据库也更新完成。实现方式：(1) 在文档更新的 webhook/事件中触发向量的同步更新；(2) 给每个向量关联源文档的版本号，查询时可以验证是否最新；(3) 对于必须实时准确的信息（价格、库存），不要放在向量数据库里——让 Agent 在需要时调用实时 API 查询。关键认知：**向量数据库适合存储"知识"（变化慢），不适合存储"数据"（变化快）**。

> **Q: 你的 AI 应用部署在中国但调用的是 OpenAI API（服务器在美国），延迟问题怎么解决？**

> A: 这是一个非常现实的问题。几种方案：(1) 换用国内可访问的 AI 服务——如 Anthropic 的 API（通过 AWS Bedrock 的亚太区域端点）、国产大模型（通义千问、智谱、百川等）；(2) 使用 AI Gateway 的就近接入功能——部分 Gateway 在全球有多个节点；(3) 如果必须用 OpenAI，通过 Azure OpenAI Service 的亚洲区域部署——Azure 在日本、新加坡等地有数据中心，延迟比直连美国好很多；(4) 应用层面：用流式输出减少用户感知延迟，用缓存减少实际调用次数。最根本的解法是选择在你的用户附近有服务器的 AI 提供商。

> **Q: CI/CD 中的评估测试失败了（AI 回答质量下降），但产品经理催着上线。怎么决策？**

> A: 这个问题的答案取决于三个因素：(1) 质量下降的程度——是从 95% 降到 93%（可接受）还是从 95% 降到 80%（不可接受）？(2) 质量下降的原因——是这次代码变更导致的（应该修复），还是底层模型变化导致的（需要适配）？(3) 上线的紧迫性——是修复安全漏洞（必须上线）还是新功能（可以等）？我的建议：如果是代码变更导致且可以分离——回滚 prompt/AI 相关变更，只上线非 AI 部分。如果必须全部一起上线——用 Feature Flag 把有问题的 AI 功能暂时关闭，上线后再修复。绝对不要做的是：忽略评估测试结果直接上线。评估测试存在的意义就是防止质量回退，如果可以随意忽略，那就不该浪费时间做评估。

> **Q: 如果模型提供商突然涨价 50%，你的应用怎么办？**

> A: 这不是假设——AI 行业的定价变化很频繁。防御策略：(1) 架构上不要和单一供应商强绑定。使用 AI Gateway 或统一接口层，让切换供应商成为改配置而不是改代码。(2) 持续评估多个模型在你的任务上的表现，保持"候选名单"。(3) 把成本控制做好——如果你已经做了 prompt 缓存、语义缓存、token 优化，涨价 50% 的实际影响可能只有 20%（因为大部分调用被缓存了）。(4) 合同谈判——大客户可以和服务商谈固定价格或批量折扣。核心思想是：**把你的 AI 应用设计成"模型无关"的，模型只是一个可配置的参数。**

## 最佳实践

### DO

- **DO** 从 Serverless 开始，遇到瓶颈再迁移。不要预先过度架构
- **DO** 使用流式响应。这是 AI 应用用户体验的最低标准
- **DO** 把 API 密钥存在环境变量中，永远不要提交到代码仓库
- **DO** 不同环境用不同的 API Key 和模型。开发用便宜的，生产用好的
- **DO** 在 CI 中加入 AI 评估测试。Prompt 变更也需要"测试"
- **DO** 用 Feature Flag 做 AI 功能的灰度发布。AI 行为在上线前不可能 100% 预测
- **DO** 保留所有 prompt 的历史版本。你需要随时能回滚
- **DO** 监控不只是可用性，还要监控质量。"API 没报错"不代表"用户满意"
- **DO** 制定 AI API 不可用时的降级方案。"服务暂时不可用，请稍后再试"比崩溃好

### DON'T

- **DON'T** 把完整的 Agent 逻辑放在 Edge Runtime 里。Edge 适合做轻量级的路由和缓存
- **DON'T** 一次性把新模型切换到 100% 流量。用灰度方式逐步迁移
- **DON'T** 忽略 CI 中的评估测试失败。"这次应该没问题"是最危险的假设
- **DON'T** 让向量数据库的数据永远不更新。过时的知识比没有知识更危险
- **DON'T** 在生产环境用 "latest" 或不带版本号的模型标识。你需要知道确切的模型版本
- **DON'T** 没有健康检查就上线。你需要知道 AI API 什么时候挂了
- **DON'T** 所有告警都设为 P0。告警疲劳会让团队对真正的问题麻木

## 代码实战

### 项目：完整的 AI 应用部署方案

我们将构建一个可部署到 Vercel 的 Next.js AI 应用，包含 API Route、Middleware、健康检查和部署配置。

```typescript
// ============================================
// 文件：app/api/chat/route.ts
// 说明：AI 对话的 API Route（支持流式输出）
// ============================================

import Anthropic from "@anthropic-ai/sdk";
import { NextRequest } from "next/server";

// 环境配置
const MODEL = process.env.AI_MODEL ?? "claude-sonnet-5";
const MAX_TOKENS = parseInt(process.env.AI_MAX_TOKENS ?? "1024", 10);

// 初始化客户端（在模块级别初始化，利用函数实例的连接复用）
const client = new Anthropic();

// System prompt 版本管理
const SYSTEM_PROMPTS: Record<string, string> = {
  v1: "你是一个有帮助的助手。",
  v2: `你是一个专业的产品客服助手。
规则：
- 基于提供的产品知识回答问题
- 不确定时说"我需要确认一下"
- 保持简洁专业`,
};

export async function POST(request: NextRequest) {

    // 从 Middleware 获取 trace ID
    const traceId = request.headers.get("x-trace-id") ?? "unknown";
    
    // 解析请求
    const body = await request.json();
    const { messages, userId } = body as {
      messages: Array<{ role: "user" | "assistant"; content: string }>;
      userId?: string;
    };

    if (!messages || messages.length === 0) {
      return Response.json(
        { error: "messages is required" },
        { status: 400 }
      );
    }

    // 获取当前版本的 system prompt
    const systemPrompt = SYSTEM_PROMPTS[ACTIVE_PROMPT_VERSION];
    if (!systemPrompt) {
      console.error(`Unknown prompt version: ${ACTIVE_PROMPT_VERSION}`);
      return Response.json(
        { error: "Internal configuration error" },
        { status: 500 }
      );
    }

    // 调用 AI（流式）
    const stream = await client.messages.stream({
      model: MODEL,
      max_tokens: MAX_TOKENS,
      system: [
        {
          type: "text",
          text: systemPrompt,
          // @ts-expect-error cache_control 是 Anthropic 扩展字段
          cache_control: { type: "ephemeral" },
        },
      ],
      messages: messages.map((m) => ({
        role: m.role,
        content: m.content,
      })),
    });

    // 转换为 Web 标准的 ReadableStream
    const encoder = new TextEncoder();
    const readableStream = new ReadableStream({
      async start(controller) {
        try {
          for await (const event of stream) {
            if (
              event.type === "content_block_delta" &&
              event.delta.type === "text_delta"
            ) {
              // 发送 Server-Sent Events 格式
              const data = JSON.stringify({ text: event.delta.text });
              controller.enqueue(encoder.encode(`data: ${data}\n\n`));
            }
          }

          // 发送完成标记和使用统计
          const finalMessage = await stream.finalMessage();
          const usage = finalMessage.usage;
          const doneData = JSON.stringify({
            done: true,
            usage: {
              inputTokens: usage.input_tokens,
              outputTokens: usage.output_tokens,
            },
            traceId,
          });
          controller.enqueue(encoder.encode(`data: ${doneData}\n\n`));
          controller.close();
        } catch (error) {
          const errorMsg = error instanceof Error ? error.message : "Unknown error";
          const errorData = JSON.stringify({ error: errorMsg });
          controller.enqueue(encoder.encode(`data: ${errorData}\n\n`));
          controller.close();
        }
      },
    });

    return new Response(readableStream, {
      headers: {
        "Content-Type": "text/event-stream",
        "Cache-Control": "no-cache",
        Connection: "keep-alive",
        "X-Trace-Id": traceId,
      },
    });
  } catch (error) {
    console.error("Chat API error:", error);
    
    // 区分不同类型的错误
    if (error instanceof Anthropic.RateLimitError) {
      return Response.json(
        { error: "服务繁忙，请稍后再试" },
        { status: 429 }
      );
    }
    
    return Response.json(
      { error: "内部错误，请稍后再试" },
      { status: 500 }
    );
  }
}
```

```typescript
// 说明：全局中间件 — 认证、限流、追踪
// ============================================

import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

// 简易内存限流器（生产环境应使用 Redis）
const rateLimitMap = new Map<string, { count: number; resetAt: number }>();

function checkRateLimit(
  key: string,
  limit: number,
  windowMs: number
): { allowed: boolean; remaining: number; retryAfterMs?: number } {
  const now = Date.now();
  const record = rateLimitMap.get(key);

  if (!record || now > record.resetAt) {
    rateLimitMap.set(key, { count: 1, resetAt: now + windowMs });
    return { allowed: true, remaining: limit - 1 };
  }

  if (record.count >= limit) {
    return {
      allowed: false,
      remaining: 0,
      retryAfterMs: record.resetAt - now,
    };
  }

  record.count++;
  return { allowed: true, remaining: limit - record.count };
}

export function middleware(request: NextRequest) {
  // 只对 API 路由应用中间件
  if (!request.nextUrl.pathname.startsWith("/api/")) {
    return NextResponse.next();
  }

  // 1. 生成追踪 ID
  const traceId = crypto.randomUUID();

  // 2. 健康检查端点不需要认证
  if (request.nextUrl.pathname === "/api/health") {
    const response = NextResponse.next();
    response.headers.set("x-trace-id", traceId);
    return response;
  }

  // 3. 认证检查
  const authHeader = request.headers.get("authorization");
  if (!authHeader?.startsWith("Bearer ")) {
    return NextResponse.json(
      { error: "Authentication required" },
      { status: 401 }
    );
  }

  // 简化的 token 验证（生产环境用 JWT 验证库）
  const token = authHeader.slice(7);
  // TODO: 验证 JWT token
  const userId = `user_${token.slice(0, 8)}`; // 简化

  // 4. 限流检查
  const rateResult = checkRateLimit(
    `user:${userId}`,
    30,        // 每用户每分钟 30 次
    60 * 1000  // 1 分钟窗口
  );

  if (!rateResult.allowed) {
    return NextResponse.json(
      {
        error: "请求太频繁，请稍后再试",
        retryAfterMs: rateResult.retryAfterMs,
      },
      {
        status: 429,
        headers: {
          "Retry-After": String(
            Math.ceil((rateResult.retryAfterMs ?? 60000) / 1000)
          ),
        },
      }
    );
  }

  // 5. 传递追踪信息到下游
  const requestHeaders = new Headers(request.headers);
  requestHeaders.set("x-trace-id", traceId);
  requestHeaders.set("x-user-id", userId);
  requestHeaders.set(
    "x-rate-limit-remaining",
    String(rateResult.remaining)
  );

  const response = NextResponse.next({
    request: { headers: requestHeaders },
  });

  // 6. 添加响应头
  response.headers.set("x-trace-id", traceId);
  response.headers.set(
    "x-rate-limit-remaining",
    String(rateResult.remaining)
  );

  return response;
}
```

```typescript
// 说明：轻量级 AI Gateway 实现
// ============================================

import Anthropic from "@anthropic-ai/sdk";

// AI 提供商配置
interface ProviderConfig {
  name: string;
  client: Anthropic;
  models: string[];
  priority: number; // 越小优先级越高
  healthy: boolean;
  lastHealthCheck: number;
}

// Gateway 配置
interface GatewayConfig {
  providers: ProviderConfig[];
  defaultModel: string;
  fallbackModel: string;
  retryAttempts: number;
  retryDelayMs: number;
  healthCheckIntervalMs: number;
}

class AIGateway {
  private config: GatewayConfig;
  private requestLog: Array<{
    timestamp: number;
    provider: string;
    model: string;
    success: boolean;
    latencyMs: number;
    tokens: { input: number; output: number };
  }> = [];

  constructor(config: GatewayConfig) {
    this.config = config;
  }

  // 选择最佳提供商
  private selectProvider(model: string): ProviderConfig | null {
    const candidates = this.config.providers
      .filter((p) => p.healthy && p.models.includes(model))
      .sort((a, b) => a.priority - b.priority);

    return candidates.length > 0 ? candidates[0] : null;
  }

  // 带重试和 fallback 的请求
  async createMessage(params: {
    model?: string;
    maxOutputTokens: number;
    system?: string;
    messages: Anthropic.MessageParam[];
  }): Promise<{
    response: Anthropic.Message;
    provider: string;
    latencyMs: number;
  }> {
    const model = params.model ?? this.config.defaultModel;
    let lastError: Error | null = null;

    // 尝试主模型
    for (let attempt = 0; attempt < this.config.retryAttempts; attempt++) {
      const provider = this.selectProvider(model);
      if (!provider) break;

      try {
        const start = Date.now();
        const response = await provider.client.messages.create({
          model,
          max_tokens: params.maxOutputTokens,
          system: params.system,
          messages: params.messages,
        });
        const latencyMs = Date.now() - start;

        // 记录成功请求
        this.requestLog.push({
          timestamp: Date.now(),
          provider: provider.name,
          model,
          success: true,
          latencyMs,
          tokens: {
            input: response.usage.input_tokens,
            output: response.usage.output_tokens,
          },
        });

        return { response, provider: provider.name, latencyMs };
      } catch (error) {
        lastError = error instanceof Error ? error : new Error(String(error));

        // 记录失败请求
        this.requestLog.push({
          timestamp: Date.now(),
          provider: provider.name,
          model,
          success: false,
          latencyMs: 0,
          tokens: { input: 0, output: 0 },
        });

        // 如果是 rate limit 错误，标记提供商为不健康
        if (error instanceof Anthropic.RateLimitError) {
          provider.healthy = false;
          // 30 秒后恢复
          setTimeout(() => {
            provider.healthy = true;
          }, 30000);
        }

        // 重试延迟（指数退避）
        if (attempt < this.config.retryAttempts - 1) {
          await new Promise((resolve) =>
            setTimeout(resolve, this.config.retryDelayMs * (attempt + 1))
          );
        }
      }
    }

    // 主模型失败，尝试 fallback 模型
    if (model !== this.config.fallbackModel) {
      console.warn(
        `Primary model ${model} failed, falling back to ${this.config.fallbackModel}`
      );
      return this.createMessage({
        ...params,
        model: this.config.fallbackModel,
      });
    }

    throw lastError ?? new Error("All providers failed");
  }

  // 获取请求统计
  getStats(): {
    totalRequests: number;
    successRate: number;
    avgLatencyMs: number;
    byProvider: Record<string, { requests: number; successRate: number }>;
  } {
    const total = this.requestLog.length;
    if (total === 0) {
      return {
        totalRequests: 0,
        successRate: 1,
        avgLatencyMs: 0,
        byProvider: {},
      };
    }

    const successes = this.requestLog.filter((r) => r.success).length;
    const totalLatency = this.requestLog
      .filter((r) => r.success)
      .reduce((sum, r) => sum + r.latencyMs, 0);

    const byProvider: Record<
      string,
      { requests: number; successRate: number }
    > = {};
    for (const record of this.requestLog) {
      if (!byProvider[record.provider]) {
        byProvider[record.provider] = { requests: 0, successRate: 0 };
      }
      byProvider[record.provider].requests++;
    }
    for (const [provider, stats] of Object.entries(byProvider)) {
      const providerSuccesses = this.requestLog.filter(
        (r) => r.provider === provider && r.success
      ).length;
      stats.successRate =
        stats.requests > 0 ? providerSuccesses / stats.requests : 0;
    }

    return {
      totalRequests: total,
      successRate: successes / total,
      avgLatencyMs: successes > 0 ? totalLatency / successes : 0,
      byProvider,
    };
  }
}

export { AIGateway, type GatewayConfig, type ProviderConfig };
```

```typescript
import Anthropic from "@anthropic-ai/sdk";

// 测试用例
interface EvalTestCase {
  id: string;
  input: string;                // 用户输入
  expectedOutput?: string;       // 期望输出（可选，用于精确匹配）
  criteria: string[];            // 评估标准（如 "回答包含价格信息"）
  category: string;              // 分类（如 "faq", "product", "complaint"）
}

// 评估结果
interface EvalResult {
  testCase: EvalTestCase;
  actualOutput: string;
  scores: Record<string, number>; // 每个 criteria 的得分 (0-1)
  overallScore: number;
  latencyMs: number;
  tokens: { input: number; output: number };
  passed: boolean;
}

// 评估报告
interface EvalReport {
  timestamp: string;
  model: string;
  promptVersion: string;
  totalTests: number;
  passedTests: number;
  passRate: number;
  averageScore: number;
  averageLatencyMs: number;
  totalCost: number;
  results: EvalResult[];
  byCategory: Record<
    string,
    { total: number; passed: number; avgScore: number }
  >;
}

class CIEvaluator {
  private client: Anthropic;
  private passThreshold: number;

  constructor(passThreshold = 0.8) {
    this.client = new Anthropic();
    this.passThreshold = passThreshold;
  }

  // 评估单个测试用例
  async evaluateTestCase(
    testCase: EvalTestCase,
    agentRunner: (input: string) => Promise<{
      output: string;
      latencyMs: number;
      tokens: { input: number; output: number };
    }>
  ): Promise<EvalResult> {
    // 1. 运行 Agent
    const { output, latencyMs, tokens } = await agentRunner(testCase.input);

    // 2. 用 AI 评估输出质量
    const scores: Record<string, number> = {};

    for (const criterion of testCase.criteria) {
      const evalResponse = await this.client.messages.create({
        model: "claude-haiku-5", // 用便宜的模型做评估
        max_tokens: 100,
        messages: [
          {
            role: "user",
            content: `评估以下 AI 回答是否满足标准。
            
标准：${criterion}

用户问题：${testCase.input}

AI 回答：${output}

${testCase.expectedOutput ? `参考答案：${testCase.expectedOutput}` : ""}

请只回答一个 0 到 1 之间的数字，表示满足程度。1 表示完全满足，0 表示完全不满足。只输出数字，不要其他文字。`,
          },
        ],
      });

      const scoreText = evalResponse.content
        .filter((b): b is Anthropic.TextBlock => b.type === "text")
        .map((b) => b.text)
        .join("")
        .trim();

      const score = parseFloat(scoreText);
      scores[criterion] = isNaN(score) ? 0 : Math.max(0, Math.min(1, score));
    }

    // 3. 计算总分
    const scoreValues = Object.values(scores);
    const overallScore =
      scoreValues.length > 0
        ? scoreValues.reduce((a, b) => a + b, 0) / scoreValues.length
        : 0;

    return {
      testCase,
      actualOutput: output,
      scores,
      overallScore,
      latencyMs,
      tokens,
      passed: overallScore >= this.passThreshold,
    };
  }

  // 运行完整的评估套件
  async runEvaluation(
    testCases: EvalTestCase[],
    agentRunner: (input: string) => Promise<{
      output: string;
      latencyMs: number;
      tokens: { input: number; output: number };
    }>,
    config: {
      model: string;
      promptVersion: string;
    }
  ): Promise<EvalReport> {
    console.log(`Running ${testCases.length} evaluation tests...`);

    const results: EvalResult[] = [];

    for (const testCase of testCases) {
      try {
        const result = await this.evaluateTestCase(testCase, agentRunner);
        results.push(result);
        const status = result.passed ? "PASS" : "FAIL";
        console.log(
          `[${status}] ${testCase.id}: score=${result.overallScore.toFixed(2)}`
        );
      } catch (error) {
        console.error(`[ERROR] ${testCase.id}: ${error}`);
        results.push({
          testCase,
          actualOutput: "ERROR",
          scores: {},
          overallScore: 0,
          latencyMs: 0,
          tokens: { input: 0, output: 0 },
          passed: false,
        });
      }
    }

    // 汇总报告
    const passedTests = results.filter((r) => r.passed).length;
    const averageScore =
      results.length > 0
        ? results.reduce((sum, r) => sum + r.overallScore, 0) / results.length
        : 0;
    const averageLatency =
      results.length > 0
        ? results.reduce((sum, r) => sum + r.latencyMs, 0) / results.length
        : 0;

    // 按分类统计
    const byCategory: Record<
      string,
      { total: number; passed: number; avgScore: number }
    > = {};
    for (const result of results) {
      const cat = result.testCase.category;
      if (!byCategory[cat]) {
        byCategory[cat] = { total: 0, passed: 0, avgScore: 0 };
      }
      byCategory[cat].total++;
      if (result.passed) byCategory[cat].passed++;
      byCategory[cat].avgScore += result.overallScore;
    }
    for (const stats of Object.values(byCategory)) {
      stats.avgScore =
        stats.total > 0 ? stats.avgScore / stats.total : 0;
    }

    const report: EvalReport = {
      timestamp: new Date().toISOString(),
      model: config.model,
      promptVersion: config.promptVersion,
      totalTests: results.length,
      passedTests,
      passRate: results.length > 0 ? passedTests / results.length : 0,
      averageScore,
      averageLatencyMs: averageLatency,
      totalCost: 0, // 简化：实际应计算
      results,
      byCategory,
    };

    // 打印摘要
    console.log("\n========== Evaluation Report ==========");
    console.log(`Model: ${config.model}`);
    console.log(`Prompt Version: ${config.promptVersion}`);
    console.log(`Pass Rate: ${(report.passRate * 100).toFixed(1)}%`);
    console.log(`Average Score: ${report.averageScore.toFixed(3)}`);
    console.log(`Average Latency: ${report.averageLatencyMs.toFixed(0)}ms`);
    console.log("\nBy Category:");
    for (const [cat, stats] of Object.entries(report.byCategory)) {
      console.log(
        `  ${cat}: ${stats.passed}/${stats.total} passed, avg score ${stats.avgScore.toFixed(3)}`
      );
    }
    console.log("==========================================\n");

    return report;
  }

  // 与基线对比
  compareWithBaseline(
    current: EvalReport,
    baseline: EvalReport
  ): {
    improved: boolean;
    degraded: boolean;
    scoreDiff: number;
    passRateDiff: number;
    summary: string;
  } {
    const scoreDiff = current.averageScore - baseline.averageScore;
    const passRateDiff = current.passRate - baseline.passRate;

    const degraded = scoreDiff < -0.05 || passRateDiff < -0.05;
    const improved = scoreDiff > 0.05 || passRateDiff > 0.05;

    let summary: string;
    if (degraded) {
      summary = `DEGRADATION DETECTED: score ${scoreDiff > 0 ? "+" : ""}${(scoreDiff * 100).toFixed(1)}%, pass rate ${passRateDiff > 0 ? "+" : ""}${(passRateDiff * 100).toFixed(1)}%`;
    } else if (improved) {
      summary = `IMPROVEMENT: score +${(scoreDiff * 100).toFixed(1)}%, pass rate +${(passRateDiff * 100).toFixed(1)}%`;
    } else {
      summary = `STABLE: score ${scoreDiff > 0 ? "+" : ""}${(scoreDiff * 100).toFixed(1)}%, pass rate ${passRateDiff > 0 ? "+" : ""}${(passRateDiff * 100).toFixed(1)}%`;
    }

    return { improved, degraded, scoreDiff, passRateDiff, summary };
  }
}
```

## 本章小结

这一章我们完成了 Agent 从开发到上线的最后一步：

1. **架构选型务实**：从 Serverless 开始是最佳策略。Vercel + Next.js 对前端开发者最友好。超时限制可以用流式响应和后台任务解决。遇到真正的瓶颈再考虑容器化。

2. **Next.js 是 AI 全栈的理想框架**：API Routes 处理 AI 请求、Server Actions 简化交互、Middleware 做认证限流、部署一步到位。一个项目搞定前后端。

3. **AI Gateway 是生产级应用的标配**：统一路由、限流、日志、缓存、fallback。不需要一开始就用，但规模上来后必须有。

4. **向量数据库需要持续维护**：增量更新 + 定期全量重建。知识库过时是 RAG 质量下降的最常见原因。

5. **环境管理和灰度发布至关重要**：不同环境用不同模型和配置。AI 功能必须灰度上线——你无法在上线前 100% 预测 AI 的行为。

6. **CI/CD 必须包含质量评估**：prompt 变更和模型切换不是"代码变更"，但它们对输出质量的影响可能比任何代码变更都大。自动化评估是质量的最后防线。

7. **监控四维覆盖**：可用性、性能、成本、质量。"API 没报错"不等于"用户满意"。质量监控是传统运维中没有的，但在 AI 应用中不可或缺。

到这里，你的 Agent 助手已经正式上线了——有完整的 CI/CD 保证质量、有监控和告警保证稳定、有成本控制保证不超预算、有灰度发布保证安全迭代。这不再是一个 demo，而是一个可以服务真实用户的生产级 AI 应用。
